# [논문 소개] VerifierBench: 에이전트가 직접 쓴 검증기는 왜 정답을 떨어뜨리는가

- **논문:** *VerifierBench: Benchmarking the Generation of Executable Verifiers for LLM Agents*
- **저자:** Jianing Yin, Ziyi Chen, Hao Wang 외 (총 7명), University of Pennsylvania, UIUC, UC Berkeley, New York University, University of Rochester (논문 본문 표기 기준)
- **공개:** 2026년 10월 19일 v1, 10월 30일 v2, arXiv:2610.28679 (cs.SE, cs.AI). 이 글은 v2 HTML 본문 기준이며, 표와 그림 번호는 HTML 판의 캡션 번호를 따릅니다.
- **링크:** [arXiv](https://arxiv.org/abs/2610.28679) · [HTML](https://arxiv.org/html/2610.28679) · [PDF](https://arxiv.org/pdf/2610.28679) · [코드](https://github.com/DwanZhang-AI/verifier-suite) · [데이터셋](https://huggingface.co/datasets/Catherine1213/VerifierBench) · [프로젝트 페이지](https://verifierbench.github.io/)
- **현황 (2026-11-20 기준):** 코드 저장소는 Apache-2.0, GitHub 스타 6개, 포크 1개, 보관(archived) 아님. 커밋은 2026-10-22의 "Initial release" 1개이고 릴리스 태그는 없습니다. 데이터셋은 Hugging Face에 과제 222행, 후보 4,993행으로 공개되어 있습니다.

## 한 줄 요약

**에이전트에게 과제를 푸는 대신 "풀이를 채점하는 실행 가능한 검증기"를 쓰게 했더니, 19개 모델 모두 오답을 거부하는 것보다 정답을 받아들이는 데 훨씬 서툴렀다는 논문입니다.** 공통 하네스에서 가장 좋은 모델의 점수도 100점 만점에 62.1점이었고(36개 구성 전체 최고는 66.2점), 분석한 기록에서 정답을 떨어뜨린 판정의 대부분은 그 과제의 모든 풀이를 거부해 버리는 검증기에서 나왔습니다.

## 왜 이 연구가 필요한가

에이전트가 스스로 학습 데이터를 만드는 흐름에서는 과제와 풀이뿐 아니라 **검증기**(verifier, 풀이가 과제를 만족하는지 PASS 또는 FAIL로 판정하는 프로그램)까지 에이전트가 씁니다. 논문은 이를 데이터 중심 재귀적 자기개선(RSI, recursive self-improvement)이라 부르고, 검증기가 어떤 풀이에 보상을 줄지, 어떤 풀이가 학습 데이터에 들어갈지를 정한다고 설명합니다. 검증기가 틀리면 위반을 반복해서 보상하거나, 올바른 풀이를 반복해서 버리게 됩니다.

저자들이 짚는 핵심은 풀기와 채점하기가 다른 능력이라는 점입니다. 푸는 쪽은 올바른 풀이 하나만 찾으면 되지만, 검증기는 **올바른 풀이를 모두 받아들이면서** 틀린 풀이는 거부해야 합니다. 그러려면 과제가 실제로 요구하는 조건과, 풀이마다 달라도 되는 선택을 구분해야 합니다.

기존 연구는 테스트 단언문 생성(TOGA), 단위 테스트 생성(TestGenEval), 이슈 재현 테스트(SWT-Bench), 실행 가능한 명세 생성(nl2postcond, CodeSpecBench)을 평가해 왔습니다. 이 논문은 같은 계열의 평가를 에이전트 과제로 넓힙니다. 정답 여부가 도구 호출, 실행 뒤의 환경 상태, 코드 변경에 달린 과제에서 검증기를 통째로 쓰게 하는 것입니다.

## 제안 방법

### 과제 정의: 푸는 사람이 받는 것만 주고 검증기를 쓰게 한다

에이전트는 과제를 풀 때와 똑같은 지시문과 환경, 그리고 검증기의 입출력 규약만 받습니다. 기준 검증기와 숨은 테스트 케이스는 주어지지 않습니다. 에이전트는 **하네스**(harness, 모델 호출과 도구 사용, 생성 루프를 관리하는 에이전트 프레임워크) 안에서 실행 가능한 검증기 하나를 써서 제출합니다.

생성 도중 에이전트는 **자기 테스트**(self-test)를 할 수 있습니다. 풀이 후보를 직접 지어내고, 초안 검증기가 의도한 정답에는 PASS, 의도한 오답에는 FAIL을 내는지 확인하는 것입니다. 숨은 케이스를 볼 수 없으므로 자기 테스트가 검증기의 동작에 대해 에이전트가 가진 유일한 증거입니다. 상태 과제와 코드 과제에서는 `run_public`이라는 공개 인터페이스로 과제 환경에서 코드를 실행할 수 있습니다(예: 후보의 행동을 재생하거나 저장소 테스트를 실행).

제출된 검증기는 고정된 뒤 그 과제의 모든 숨은 케이스에 대해 실행됩니다.

### 과제 출처와 테스트 케이스 (표 1, 표 6, 표 10)

과제는 실행 가능한 채점 절차가 있는 공개 에이전트 벤치마크 6개에서 가져왔습니다.

| 유형 | 출처 벤치마크 | 과제 | PASS | FAIL |
|---|---|---|---|---|
| 도구 호출 | BFCL v4(45), ACEBench(50) | 95 | 734 | 2,214 |
| 상태 | τ²-bench(32), AppWorld(28), AgentDojo(20) | 80 | 642 | 769 |
| 코드 | SWE-bench Verified(47) | 47 | 190 | 444 |
| 합계 | | 222 | 1,566 | 3,427 |

도구 호출 검증기는 호출 원문과 파싱된 함수 이름·인자를, 상태 검증기는 후보의 상호작용 기록(AppWorld는 풀이 코드)을, 코드 검증기는 패치와 저장소 체크아웃을 입력으로 받습니다.

숨은 테스트 케이스 4,993개는 네 묶음입니다.

| 묶음 | 라벨 | 개수 | 내용 |
|---|---|---|---|
| 기준 풀이 | PASS | 222 | 지정된 정답(gold) |
| 유효 변형 | PASS | 1,344 | 표현만 바꾼 것 840개, 다른 구현이나 실행 경로 504개 |
| 일반 오류 | FAIL | 2,629 | 초기 상태, 부분 풀이, 아슬아슬한 오답, 회귀 |
| 공격 | FAIL | 798 | 검사 누락 악용, 성공 신호 위조, 검증 방해 |

**유효 변형이 이 벤치마크의 핵심 장치입니다.** 정답 하나만 통과시키는 검증기와, 과제가 허용하는 다른 정답까지 통과시키는 검증기를 구분하기 위한 케이스이기 때문입니다.

### V4V: 채점 기준 자체를 먼저 검증한다

원 벤치마크의 검증기도, 저자들이 만든 테스트 케이스도 틀릴 수 있습니다. 그래서 Verifier4Verifier(V4V)라는 여섯 가지 검사로 둘을 함께 걸렀습니다.

1. **재생(Replay):** 원 검증기를 모든 케이스에 돌려 구성 시점에 붙인 라벨과 비교
2. **반복성(Repeatability):** 같은 초기 상태에서 다시 돌려도 판정이 같아야 함
3. **출처 추적(Provenance):** 기록된 판정마다 케이스 내용과 검증기 버전을 연결
4. **입력-라벨 일관성:** 검증기에 같은 정보를 주는 케이스가 반대 라벨을 가지면 안 됨
5. **자명한 기준선:** 항상 수용, 항상 거부, 기준 풀이만 수용하는 검증기가 각각 오답 케이스, 정답 케이스, 유효 변형에 의해 드러나야 함
6. **변이 테스트(mutation testing):** 원 검증기의 검사 하나를 고쳤을 때 판정이 달라지는 케이스가 있어야 함 (과제-연산자 조합 1,410개, 표 9)

이 과정에서 처음 모은 267개 과제 중 45개가 원 자료의 결함으로 빠졌습니다(부록 B.1). Terminal-Bench는 37개가 전부 제외됐는데, 그중 35개는 테스트 출력 파서가 건너뛴 테스트(SKIPPED/XFAIL)를 통과로 세는 문제였습니다. BFCL 5개는 기본 인자 규칙과 정답 키가 충돌했고, SWE-bench Verified 3개는 파싱 오류와 빈 리포트에 만점을 주는 문제가 있었습니다. 남은 222개 과제의 원 검증기가 기준 검증기가 됩니다.

### 지표: 정규화 균형 정확도

검증기 실행 결과는 유효한 PASS, 유효한 FAIL, 유효한 판정 없음(검증기 누락, 시간 초과, 크래시, 형식 오류) 셋 중 하나입니다.

- **TPR**(참양성률): 과제별로 정답 케이스 중 PASS를 받은 비율을 구해 과제 평균. 이 글에서는 "정답 수용률"로 부릅니다.
- **TNR**(참음성률): 과제별로 오답 케이스 중 FAIL을 받은 비율의 과제 평균. "오답 거부율"입니다.
- **BA_norm**(정규화 균형 정확도): `TPR + TNR − 100`. 항상 PASS나 항상 FAIL만 내는 검증기는 0점, 기준 검증기와 완전히 일치하면 100점입니다. 판정을 하나도 내지 못하면 −100점입니다.
- **FPR_h**(공격 수용률): 공격 케이스 중 PASS를 받은 비율의 과제 평균. 낮을수록 좋습니다.

과제마다 같은 가중치를, 한 과제 안에서는 두 부류에 같은 가중치를 줍니다. 판정을 내지 못한 케이스는 점수 없이 분모에 남습니다.

| 항목 | 내용 |
|---|---|
| 주 비교 | 19개 모델을 공통 하네스 Pi(0.84.2)에서 실행 |
| 추가 구성 | 17개. 계열별 전용 하네스(Claude Code, Codex, Gemini CLI)와 제3자 하네스(OpenClaw, mini-swe-agent), 계열을 넘는 조합(예: GPT-6-astra + Claude Code). 합계 36개 구성 |

## 주요 결과

### 1. 최고 점수가 62.1점, 공통 약점은 정답 수용 (표 2)

Pi 하네스에서 BA_norm은 10.6에서 62.1 사이였습니다. 아래는 표 2의 일부입니다.

| 모델 | BA_norm | TPR | TNR | FPR_h |
|---|---|---|---|---|
| GPT-6-astra | 62.1 | 67.4 | 94.6 | 7.4 |
| Claude Opus 4.8 | 54.0 | 67.7 | 86.3 | 13.5 |
| Kimi K3 | 53.4 | 70.2 | 83.2 | 13.4 |
| GPT-5.6-sol | 52.9 | 56.8 | 96.0 | 0.8 |
| GPT-5.6-terra | 52.9 | 56.5 | 96.3 | 3.6 |
| GLM-5.2 | 48.8 | 68.1 | 80.8 | 12.1 |
| DeepSeek V4 Pro | 44.8 | 65.5 | 79.2 | 10.1 |
| Gemini 2.5 Pro | 14.2 | 31.7 | 82.5 | 4.0 |
| Doubao Seed 2.0 Mini | 10.6 | 21.1 | 89.5 | 3.7 |

**19개 모델 전부 TPR이 TNR보다 낮았습니다.** TPR은 21.1~70.2%, TNR은 79.2~96.3%입니다. 그리고 정답을 받아들이지 못한 경우의 대부분은 "판정 실패"가 아니라 명시적인 FAIL이었습니다. 수용되지 못한 정답 케이스 중 명시적 FAIL의 비중은 모델별로 57.1~100%입니다(표 21). 검증기가 고장 나서가 아니라, 멀쩡히 실행되어 정답을 틀렸다고 판정한 것입니다.

### 2. 상태 과제에서는 어떤 모델도 정답의 절반을 받아들이지 못했다 (표 16~18)

유형별로 나누면 차이가 큽니다. 19개 모델 평균 TPR은 도구 호출 79.2%, 상태 27.7%, 코드 40.2%이고, 평균 TNR은 각각 85.8%, 85.2%, 90.6%입니다. 상태 과제의 TPR은 모든 모델이 50% 미만이었습니다(가장 높은 값이 Qwen3.7 Plus의 49.0%). 반대로 도구 호출 과제에서는 8개 모델의 TPR이 TNR보다 높아, 전체 평균의 비대칭이 모든 유형에 똑같이 나타나는 것은 아닙니다.

유형별 1위도 다릅니다. 도구 호출은 GPT-5.6-sol(85.2), 상태는 Claude Opus 4.8(34.6), 코드는 Kimi K3(76.9)입니다. Kimi K2.6은 도구 호출 3위지만 상태 17위였습니다.

논문이 강조하는 해석상 주의점이 하나 있습니다. **공격 수용률이 낮다고 믿을 만한 검증기는 아닙니다.** 상태 과제에서 GPT-5.6-sol의 FPR_h는 0.0%지만 정답 수용률은 23.0%뿐이라 BA_norm이 16.1입니다. 코드 과제에서는 17개 모델의 FPR_h가 0.0%인데 BA_norm은 −25.9에서 76.9까지 흩어져 있습니다. 거의 다 거부하는 검증기는 공격도 당연히 거부합니다.

### 3. 하네스를 바꾸면 점수가 양쪽으로 크게 움직인다 (표 3, 표 11, 표 12)

같은 모델을 전용 하네스로 옮겼을 때의 BA_norm 변화입니다.

| 모델 | 전용 하네스 | Pi | 전용 | 차이 |
|---|---|---|---|---|
| Claude Opus 4.8 | Claude Code | 54.0 | 66.2 | +12.2 |
| Gemini 3.5 Flash | Gemini CLI | 35.7 | 50.7 | +15.0 |
| GPT-6-astra | Codex | 62.1 | 58.0 | −4.1 |
| Gemini 2.5 Pro | Gemini CLI | 14.2 | 5.0 | −9.2 |
| GPT-5.5 | Codex | 46.6 | 30.3 | −16.4 |
| GPT-5.6-terra | Codex | 52.9 | 31.0 | −21.8 |
| GPT-5.6-sol | Codex | 52.9 | 26.2 | −26.6 |

Claude Opus 4.8 + Claude Code의 66.2점이 36개 구성 전체의 최고점입니다. 이 조합은 TPR(67.7 → 75.8)과 TNR(86.3 → 90.4)이 함께 올랐습니다. 반면 Qwen3.7 Plus를 Codex에 올리면 TNR은 82.6 → 92.1로 오르지만 TPR이 57.6 → 34.0으로 떨어져 BA_norm이 40.2 → 26.1이 됩니다. 저자들은 그래서 하네스 효과를 "수용과 거부 사이의 고정된 맞교환"으로 볼 수 없다고 말합니다. 모든 모델을 개선한 하네스는 없었습니다.

다만 이 비교에는 설정 차이가 섞여 있습니다. 보존된 Opus + Claude Code 궤적은 높은 추론 노력에 사고(thinking)가 켜진 상태였고, 사고 설정이 드러나는 과거 Pi 궤적에서는 사고가 꺼져 있었다고 부록 E에 적혀 있습니다.

### 4. 추론 노력을 올려도 총점은 거의 그대로, 대신 실행 예산이 바닥났다 (표 13~15)

GPT-6-astra의 추론 노력을 LOW에서 HIGH로 올렸을 때 BA_norm은 Pi에서 59.0 → 59.5(+0.5), Claude Code에서 60.5 → 59.2(−1.3)로 거의 변하지 않았습니다. 유형별로는 방향이 엇갈렸습니다. 코드 과제는 두 하네스 모두 올랐고(+3.8, +1.4), 상태 과제는 두 하네스 모두 내렸습니다(−5.4, −3.6).

수용이 늘었다고 변별력이 좋아진 것도 아닙니다. Pi의 도구 호출 과제에서 HIGH는 정답 케이스 63개를 추가로 받아들였지만, 동시에 거짓 수용 128개를 새로 만들었고 3개만 바로잡았습니다.

가장 뚜렷한 변화는 생성 중 실행 예산이었습니다. 과제당 `run_public` 실행은 20회로 제한되고, 탐색과 자기 테스트가 이 예산을 함께 씁니다.

| 하네스 | 노력 | 예산 초과(상태·코드 127개) | 검증기 첫 작성 전 소진(τ²-bench 32개) |
|---|---|---|---|
| Pi | LOW | 4 | 0 |
| Pi | HIGH | 77 | 30 |
| Claude Code | LOW | 21 | 7 |
| Claude Code | HIGH | 98 | 20 |

더 많이 "생각"한 에이전트는 환경 탐색에 예산을 쓰고, 정작 완성한 검증기를 시험할 실행 횟수를 남기지 못했습니다.

### 5. 거짓 거부의 대부분은 "전부 거부" 검증기에서 나온다 (그림 5, 표 22, 표 23)

저자들은 한 과제의 모든 케이스(정답이든 오답이든)에 유효한 FAIL을 내는 검증기를 **전부 거부**(all-reject) 검증기라고 부릅니다. 이런 검증기는 그 과제에서 TPR 0, TNR 100이므로 BA_norm 기여가 0입니다.

보관 기록이 있는 9개 모델에서, 정답에 내려진 FAIL 판정의 87.9~96.0%가 전부 거부 검증기에서 나왔습니다. Astra 추적 배치에서도 같았습니다. 네 조건 각각 222개 검증기 중 68~75개가 전부 거부였고, 이들이 거짓 거부의 93.3~95.5%를 차지했습니다.

표 23을 보면 양상이 더 분명합니다. Astra 네 조건에서 정답 케이스를 전부 받아들인 과제가 123~135개, 하나도 받아들이지 못한 과제가 69~76개였고, 일부만 받아들인 과제는 16~23개에 그쳤습니다. 필자가 보기에 이것은 검증기가 "조금씩 엄격한" 것이 아니라 **과제 단위로 통째로 작동하거나 통째로 막히는** 쪽에 가깝다는 뜻입니다.

### 6. 원인: 과제가 요구하지 않은 검사와, 그 검사를 건드리지 않는 자기 테스트 (표 4, 그림 2, 그림 6~8)

저자들은 Astra 추적 배치에서 생성된 코드와 생성 궤적을 직접 읽고, 거부당한 정답의 속성이 공개된 과제 요구사항에서 허용되는 경우에만 그 검사를 **근거 없는 검사**(unjustified check)로 분류했습니다. 그렇게 확인한 것이 12개 과제의 검증기 16개, 정답 FAIL 판정 119건(서로 다른 케이스 90개)입니다.

| 근거 없는 검사 | 과제 | 검증기 | 정답 FAIL | 자기 테스트 상태 |
|---|---|---|---|---|
| 소스 파일 보호가 과도함 | 2 | 3 | 12 | 검사가 허용하는 풀이만 시험 |
| 허용된 표현 형식을 거부 | 3 | 5 | 35 | 검사가 허용하는 풀이만 시험 |
| 권한 있는 사용자 측 도구 호출을 거부 | 3 | 3 | 27 | 정답 자기 테스트가 한 번도 통과 못함 |
| 허용된 읽기 전용 도구를 누락 | 2 | 2 | 18 | 정답 자기 테스트가 한 번도 통과 못함 |
| 범주 어휘 목록이 불완전 | 2 | 3 | 27 | 정답 자기 테스트가 한 번도 통과 못함 |

구체적인 사례 세 가지입니다. 아래 코드 조각은 논문 그림 6과 그림 7에서 옮긴 발췌이며, 필자가 직접 실행하지 않았습니다.

**사례 A: 테스트 파일을 보호하려다 일반 소스 파일까지 막음 (Django-11734, 그림 6).** Pi 하네스의 검증기는 다음 조건에 걸리는 패치를 거부했습니다.

```python
path.endswith((
    'conftest.py', 'sitecustomize.py',
    '__init__.py'))
```

숨은 정답 케이스 4개는 모두 `django/db/models/fields/__init__.py`라는 평범한 소스 모듈을 고칩니다. 결과는 정답 0/4 수용, 오답 10/10 거부였습니다. 에이전트의 자기 테스트는 `query.py`를 고치는 패치였고, 실행 환경 문제를 여러 번 고친 끝에 "정답 PASS, 오답 FAIL"을 얻었습니다. 하지만 `__init__.py`를 고치는 자기 테스트는 없었습니다. 같은 모델을 Claude Code에서 돌린 검증기는 테스트 파일만 보호하고 동작을 검사해 정답 4/4, 오답 10/10을 맞혔습니다. 정당한 소스 변경을 허용해도 오답 거부가 약해지지 않았다는 점이 중요합니다.

**사례 B: 문서에 적힌 기본값을 무시 (BFCL의 DNA 분석 과제, 그림 7).** 도구 정의는 `mutation_type`이 선택 인자이고 기본값이 `insertion`이라고 명시합니다. Qwen3.7 Plus가 쓴 검증기는 인자를 이렇게 읽었습니다.

```python
for key, val in expected_args.items():
    actual_val = actual_args.get(key, "")
```

인자를 생략하면 기본값 대신 빈 문자열이 되어 `"insertion"`과 다르다고 판정됩니다. 자기 테스트의 정답은 모두 이 인자를 명시적으로 넣었기 때문에 전부 통과했습니다. 숨은 정답 케이스 9개 중 4개가 거부됐습니다.

**사례 C: 허용된 조회 도구를 허용 목록에서 빠뜨림 (τ²-bench banking 044, 그림 2).** GPT-6-astra + Claude Code의 검증기는 관련 없는 변경을 막으려고 도구 허용 목록을 만들었는데, 공개 도구 목록에 있는 읽기 전용 조회 `get_user_dispute_history_7291`을 빠뜨렸습니다. 이 조회를 포함한 정답 9개가 환경 실행 없이 전부 거부됐습니다. 에이전트의 정답 자기 테스트는 실행 예산이 소진되어 재생이 불가능해지면서 FAIL로 끝났고, 에이전트는 최종 응답에서 정답 검증이 끝나지 않았음을 스스로 인정했습니다.

논문은 자기 테스트가 실패하는 방식을 둘로 정리합니다.

- **확인만 하고 도전하지 않는 자기 테스트(4.2절).** 검증기가 이미 허용하는 풀이로만 시험합니다. 같은 위치를 고치는 테스트를 더 늘려도 제한은 드러나지 않습니다. 오답 자기 테스트도 도움이 되지 않습니다. 오답 패치는 진짜 요구사항과 근거 없는 검사를 동시에 어길 수 있어서, 그것을 올바르게 거부했다고 그 검사가 정당해지지 않기 때문입니다.
- **수용을 한 번도 확인하지 못한 자기 테스트(4.3절).** 표 4 아래쪽 8개 검증기는 생성 중 정답 자기 테스트가 한 번도 완전히 통과하지 못한 채 제출됐고, 평가에서 정답 판정 72건을 환경 실행 없이 전부 거부했습니다.

### 저자들의 제안 (5절)

- 모든 수용 조건을 지시문, 도구 정의, 환경 규칙 중 하나로 거슬러 올라가 근거를 찾는다.
- 자기 테스트를 두 종류로 만든다. 하나는 과제를 만족한 채 **허용된 속성 하나를 바꾼** 풀이(다른 파일을 고친 패치, 기본값 인자를 생략한 호출, 권한 있는 사용자 측 호출), 다른 하나는 필수 조건 하나를 어긴 풀이.
- 최종 검증기를 시험할 실행 예산을 남겨 두고, 실행 실패와 요구사항 위반을 구분한다. 막힌 테스트는 그 검사를 "미해결"로 남길 뿐입니다.

저자들은 이 방향들의 효과를 실험으로 평가하지는 않았다고 분명히 적었습니다.

## 한계

**저자가 밝힌 한계**

- 점수는 저자들이 구성한 유한한 테스트 스위트에서 기준 검증기와 얼마나 일치하는지를 잰 값입니다. V4V가 결함 있는 45개 과제를 뺐지만, 구성 라벨과 기준 판정이 일치한다고 모든 라벨이 의미상 옳다는 보증은 아닙니다.
- 36개 구성은 프롬프트, 도구, 추론 설정이 서로 달라 하네스의 어떤 요소가 차이를 만들었는지 분리하지 못합니다. 순위는 반복 생성이나 유의성 검정이 없는 점 추정치입니다.
- 거짓 거부 집중 분석은 19개 모델 전체의 최종 기록이 아니라, 9개 모델의 보관 기록과 한 모델(GPT-6-astra)의 추적 배치를 썼습니다.
- 코드·궤적 분석은 실패를 설명하려고 고른 검증기(대부분 GPT-6-astra)를 대상으로 했고, 개입 실험이 아니라 소스 읽기로 원인을 돌렸습니다. 그래서 메커니즘을 보여 줄 뿐 그것이 얼마나 흔한지는 말해 주지 않습니다.
- 프로젝트 페이지는 제안한 개선책, 학습에 미치는 하류 효과, 여러 라운드의 자기개선을 평가하지 않았다고 덧붙입니다.

**읽으면서 발견한 한계 (필자 판단)**

- **동기와 실험 사이에 간격이 있습니다.** 논문은 학습 데이터 선별을 동기로 들지만, 과도하게 엄격한 검증기로 거른 데이터가 실제 학습 결과를 얼마나 나쁘게 만드는지는 측정하지 않았습니다.
- **테스트 케이스를 누가 어떻게 만들었는지가 본문에 자세히 나오지 않습니다.** 변이 연산자는 "수작업으로 정의했다"고 적혀 있지만, 유효 변형 1,344개와 공격 798개를 사람이 썼는지 모델이 생성했는지는 필자가 본문에서 확인하지 못했습니다. 유효 변형 1,344개 중 840개(필자 계산으로 62.5%)가 표현만 바꾼 것이라는 점도 TPR 해석에 영향을 줍니다.
- **생성 환경의 제약이 결과에 섞여 있습니다.** `run_public` 20회 제한과, 일부 궤적에서 `unshare`를 쓸 수 없어 로컬 실행이 막힌 사례가 보고됩니다. 저자들도 이런 제약이 숨은 거부의 직접 원인은 아니라고 하면서도 검사를 미해결 상태로 남길 수 있다고 인정합니다. 예산이 넉넉한 실제 환경에서는 수치가 달라질 수 있습니다.
- **같은 모델·하네스의 점수가 배치에 따라 몇 점씩 다릅니다.** GPT-6-astra + Pi는 주 결과에서 62.1이고 별도로 생성한 Astra 배치에서는 59.0(LOW), 59.5(HIGH)입니다. 설정이 같다고 단정할 수는 없지만, 순위표에서 몇 점 차이 나는 모델들의 우열은 조심해서 읽는 편이 안전해 보입니다.

## 인사이트

**왜 지금 중요한가: 걱정의 방향이 반대였습니다.** 에이전트가 쓴 채점기를 두고 흔히 하는 걱정은 "허술해서 꼼수 풀이를 통과시키지 않을까"입니다. 이 논문의 데이터는 반대쪽 실패가 더 크다고 말합니다. TNR은 가장 낮은 모델도 79.2%인데 TPR은 가장 높은 모델이 70.2%입니다. 필자가 보기에 더 중요한 것은 실패의 모양입니다. 정답에 대한 거짓 거부의 87.9~96.0%가 전부 거부 검증기에서 나왔다는 것은, 문제가 "판정 기준이 조금 빡빡하다"가 아니라 적지 않은 검증기가 아무 풀이도 통과시키지 못하는 상태로 제출된다는 뜻입니다. GPT-6-astra의 Astra 배치에서는 222개 중 68~75개, 대략 셋 중 하나꼴이었습니다. 이런 검증기는 오답 거부율 100%라는 그럴듯한 숫자 뒤에 숨습니다.

**블로그의 기존 글과의 연결: 같은 가정을 공유한 증거는 독립 증거가 아닙니다.** [Harness² 글](/papers/2026/10/24/harness-squared.html)은 정답 검증기 없이 하네스를 고치는 방법을 다뤘고, 그 실패 분석의 한 유형이 "잘못된 전제가 여러 후보에 함께 퍼진 경우"였습니다. VerifierBench는 반대편에서 같은 지점에 도착합니다. 검증기를 직접 쓰게 해도, 그 검증기를 시험하는 자기 테스트가 같은 에이전트의 같은 가정에서 나오면 오류가 드러나지 않습니다. 검증기가 없어서 생기는 문제와 검증기를 스스로 만들어서 생기는 문제의 뿌리가 같은 셈입니다. 또 [SWE-bench 글](/papers/2026/10/24/swe-bench.html)에서 정리했듯, SWE-bench Verified는 이슈 설명 부족과 함께, 사람이 쓴 테스트가 올바른 해법을 걸러 내는 문제를 바로잡으려고 만들어졌습니다. 이번 논문의 V4V는 그 Verified에서도 3개 과제를 채점 결함으로 제외했고, Terminal-Bench 37개는 전부 제외했습니다. 사람이 만든 채점기도 267개 중 45개가 결함으로 빠졌다는 사실은 "채점기를 채점하는" 절차가 벤치마크 제작의 기본 단계가 되어야 함을 보여 줍니다. [LLM 평가 실무 글](/tech/2026/10/24/llm-evals.html)에서 공식 가이드들이 코드 기반 채점을 가장 신뢰할 수 있는 방법으로 권한다고 썼는데, 여기에 단서를 하나 붙여야 합니다. 코드 채점기의 신뢰성은 그 코드가 "허용된 다른 정답"으로 시험됐을 때만 성립합니다.

**실무에 주는 의미: 검증기로 합성 데이터를 거르는 팀의 점검 항목.** 논문 5절과 사례를 바탕으로 필자가 정리한 목록입니다. 저자들이 효과를 실험으로 확인한 것은 아니라는 점을 감안해 읽어 주세요.

1. **과제별 통과율 0%를 먼저 찾습니다.** 필터를 통과한 풀이가 하나도 없는 과제는 "어려운 과제"가 아니라 전부 거부 검증기일 가능성을 먼저 의심합니다. 전체 통과율 평균만 보면 이 문제가 보이지 않습니다.
2. **거부 조건마다 근거 문장을 답니다.** 검증기의 각 거부 조건이 지시문, 도구 정의, 환경 규칙의 어느 문장에서 나왔는지 적게 합니다. 근거를 댈 수 없는 조건(파일 이름 금지, 도구 허용 목록, 특정 직렬화 형식 요구)은 삭제 후보입니다.
3. **정답 변형으로 시험합니다.** 검증기를 쓴 에이전트의 풀이 하나로 끝내지 말고, 허용된 속성 하나를 바꾼 정답을 따로 만듭니다. 다른 파일을 고친 패치, 기본값 인자를 생략한 호출, 허용된 읽기 전용 조회를 추가한 실행, 다른 표기 형식이 논문에 나온 예입니다. 가능하면 풀이 작성자와 검증기 작성자를 다른 모델이나 다른 프롬프트로 분리하는 것이 필자의 판단으로는 가장 싼 대책입니다.
4. **"판정 불가"를 FAIL과 분리합니다.** 실행 실패, 예산 초과, 파싱 실패를 FAIL로 뭉개면 원인을 추적할 수 없습니다. 논문의 지표와 Gavel README가 모두 세 번째 상태를 따로 둡니다.
5. **최종 검증기를 돌릴 실행 예산을 남깁니다.** 추론 노력을 올렸더니 탐색에 예산을 다 쓰고 검증기를 시험하지 못한 결과(표 15)는, 예산을 "탐색용"과 "최종 시험용"으로 나눠 두어야 한다는 근거입니다.
6. **공격 수용률만으로 합격시키지 않습니다.** 거의 다 거부하는 검증기는 공격도 다 거부합니다. 정답 수용률과 함께 봅니다.
7. **하네스나 추론 설정을 바꾸면 다시 잽니다.** 같은 모델이 하네스에 따라 26.6점까지 움직였습니다. 검증기 품질은 모델의 속성이 아니라 구성의 속성입니다.

**한계와 반론: 엄격함은 정말 나쁜가.** 학습 데이터 필터라면 정밀도를 우선하는 것이 합리적이라는 반론이 가능합니다. 틀린 풀이가 섞이면 데이터가 오염되지만, 맞는 풀이를 버리는 것은 비용일 뿐이라는 논리입니다. BA_norm은 두 오류에 같은 가중치를 주므로 이 관점에서는 점수가 문제를 과장한다고 볼 수도 있습니다. 필자는 이 반론이 절반만 맞다고 봅니다. 전부 거부 검증기는 아무것도 통과시키지 않으므로 정밀도 이득조차 없고, 그 과제를 데이터에서 통째로 지웁니다. 일부만 받아들이는 검증기는 더 조용한 문제를 만듭니다. 논문 결론이 경고하듯 특정 풀이 방식(특정 파일, 특정 호출 순서, 특정 표기)만 반복해서 살아남아 데이터의 다양성이 줄어듭니다. 한편 Gavel의 자체 발표 수치는 반대 방향의 대가를 보여 줍니다. 정답 수용률을 84.1%까지 올리자 공격 수용률이 18.2%가 됐습니다. 보상 신호로 쓸 검증기라면 이 수치는 가볍지 않습니다. 결국 용도에 따라 두 오류의 가중치를 직접 정해야 하고, 단일 점수 하나로 검증기를 고르기는 어렵습니다.

**앞으로 지켜볼 점.** (1) 5절의 제안(허용 속성 변형 테스트, 예산 분리)을 실제로 적용했을 때 TPR이 얼마나 오르고 TNR이 얼마나 유지되는지에 대한 통제 실험. (2) 구성별 반복 생성과 유의성 검정이 붙은 순위. (3) 과도하게 엄격한 검증기로 거른 데이터로 학습했을 때의 하류 효과 측정. (4) Gavel 수치의 제3자 재현과 논문 반영 여부. 특히 (3)이 나와야 "검증기의 거짓 거부가 자기개선 루프를 얼마나 망가뜨리는가"라는 이 논문의 출발 질문에 답할 수 있습니다.
