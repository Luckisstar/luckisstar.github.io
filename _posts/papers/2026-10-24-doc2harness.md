# [논문 소개] Doc2Harness: 문서만 보고 코딩 에이전트 하네스를 처음부터 짓게 하는 벤치마크

- **논문:** *Doc2Harness: Benchmarking LLMs on Long-Horizon Harness Engineering of Coding Agents*
- **저자:** Yuyao Ge, Shenghua Liu 외 (총 11명), 중국과학원 계산기술연구소(ICT, CAS), 칭화대, 베이징대, 동남대 (논문 본문 표기 기준)
- **공개:** 2026년 10월 14일, arXiv:2610.20344 (cs.SE, cs.AI)
- **링크:** [arXiv](https://arxiv.org/abs/2610.20344) · [HTML](https://arxiv.org/html/2610.20344) · [코드](https://github.com/YuyaoGe/doc2harness) · [프로젝트 페이지](https://geyuyao.com/doc2harness/)
- **현황 (2026-10-24 기준):** 코드 저장소 GitHub 스타 113개, README와 LICENSE 파일 기준 Apache 2.0. Hugging Face Papers 업보트 62개.
- **주의: 테스트 케이스는 일부만 공개됐습니다.** README에 따르면 논문의 전체 328개 케이스 중 저장소에는 94개 시나리오(채점 대상 53개 + 이를 받치는 양성 대조 41개)만 공개됐고 나머지는 비공개입니다. README는 리더보드 수치를 공개 부분만으로는 재현할 수 없다고 명시합니다.

## 한 줄 요약

**모델에게 "코딩 에이전트 하네스를 명세서대로 처음부터 지어 보라"고 시킨 뒤, 지은 하네스를 대본대로 움직이는 가짜 모델(mock model)로 돌려 채점했더니 가장 좋은 모델도 절반 가까이 실패했고, 점수는 기능을 여러 모듈에 얼마나 잘게 쪼갰는지와 반대로 움직였다는 논문입니다.**

## 왜 이 연구가 필요한가

에이전트의 성능이 모델만큼이나 하네스(대화 루프, 도구 실행, 컨텍스트, 권한, 세션 상태, 실패 복구를 맡는 바깥 소프트웨어)에 달려 있다는 인식은 이제 널리 퍼졌습니다. 그런데 기존 벤치마크는 대부분 하네스를 **고정한 채** 하류 작업의 성공률을 잽니다. 하네스를 만드는 능력 자체는 따로 측정되지 않았습니다.

저자들은 하네스 구축이 일반 소프트웨어 공학 과제와 다른 점을 두 가지로 듭니다.

1. **학습 데이터 오염이 덜합니다.** SWE 벤치마크가 쓰는 오픈소스 저장소는 대부분 오래된 성숙 프로젝트라 학습 데이터에 여러 번 들어갔을 수 있습니다. 하네스는 최근 몇 년 사이 등장했고 매우 자주 바뀌므로 일반화 능력을 더 많이 봅니다.
2. **기존 단위 테스트 방식이 그대로 통하지 않습니다.** 하나의 기능을 하네스 안에서 구현하는 방법은 여러 가지라 고정된 인터페이스로 관찰하는 단위 테스트가 맞지 않고, 하네스는 혼자 작업을 끝내지 못하므로 모델을 붙여 움직여 봐야 정확성을 알 수 있습니다.

저자들은 이 능력이 결국 에이전트가 자기 하네스를 고치는 재귀적 자기개선의 바탕이 된다고 동기를 설명합니다.

## 제안 방법

Doc2Harness는 두 단계로 이뤄집니다(그림 2).

### 1단계: 구축 (Construction)

평가 대상 모델(build model)은 **고정된 빌더 하네스 OpenCode 1.17.0** 안에서 일합니다. Claude Code나 Codex CLI가 아니라 OpenCode를 쓴 이유는 그 둘이 각 모델 회사가 자기 모델과 함께 개발한 하네스라 Claude와 GPT 계열에 유리할 수 있기 때문이라고 밝힙니다.

모델이 받는 입력은 두 가지입니다.

- **개발 문서:** Claude Code, Kimi Code, Gemini CLI, Qwen Code, OpenCode, OpenClaw, Codex CLI, Aider, OpenHands, Cline, Crush, Cursor, 이렇게 **12개 프런티어 하네스의 사용자 문서**에서 기능을 수집해 하나의 조항(clause) 집합으로 다시 쓴 문서입니다. 도구, 명령과 하위 명령, 다섯 가지 권한 모드와 다섯 가지 역할 모드, 전역 플래그, 세션 내 명령, 영속 메모리, 규약 파일, 교차 일관성 규칙, 종료 코드 등을 다룹니다(표 1). 이름이 겹치는 기능은 합치고(Claude Code의 `/compact`와 Cursor의 `/summarize`를 `/compact`로), 같은 이름의 다른 개념은 나눴습니다(Claude Code의 `plan`은 권한 모드이고 Aider의 architect/editor는 역할이라, 권한과 역할을 별도 조항으로).
- **계약 골격(contract skeleton):** mini-swe-agent를 깎아 만든, 인터페이스만 있고 구현은 없는 Python 파일 5개(약 70줄)입니다. CLI, 헤드리스 진입점, 자동 평가용 API 세 가지가 바꿀 수 없는 외부 계약입니다.

대표적인 후보 하네스는 Python 파일 약 30개, 약 16,000줄이며 그중 약 99.6%를 모델이 직접 씁니다. 구축은 외부 네트워크가 막힌 빈 컨테이너에서 이뤄지고, 시간 제한 2시간, 제출 최대 3회, 최대 24턴입니다. 제출 시 계약 검사는 설치·컴파일, 필수 명령 존재, 남은 스텁 여부만 보고 테스트는 돌리지 않습니다.

### 2단계: 평가 (Evaluation)

얼린 후보 하네스를 테스트 케이스마다 별도 컨테이너로 옮기고, **미리 짠 대본대로 응답하는 mock 모델**이 하네스를 처음부터 끝까지 움직입니다. 실제 LLM을 쓰지 않으므로 평가가 결정적입니다. 결과는 네 가지 관찰 채널로 읽습니다.

1. 모델에게 보낸 요청
2. 디스크의 파일
3. 프로세스 종료 코드
4. 명령 출력

### 핵심 장치: 양성 대조(positive control)

이 논문에서 가장 배울 점이 많은 부분입니다. "작업 공간 밖을 가리키는 심볼릭 링크를 read 도구로 읽으면, 그 파일 내용이 모델 요청에 나타나면 안 된다"는 테스트를 생각해 봅시다. 내용이 나타나지 않았다면 구현이 경계 밖 읽기를 막았을 수도 있지만, **read 도구가 아예 아무 파일도 못 읽어서**일 수도 있습니다. 저자들은 이런 경우를 공허한 통과(vacuous pass)라 부르고, 세 종류의 양성 대조로 막습니다.

| 대조 종류 | 배제하는 원인 | 경로 탈출 예시 |
|---|---|---|
| 채널 | 도구 결과가 관찰 채널에 아예 안 실림 | 평범한 파일을 read로 읽어 내용이 요청에 실리는지 확인 |
| 같은 형태 | 제약과 무관하게 원래 실패하는 경우 | 같은 심볼릭 링크를 bash로 접근해 실제로 밖의 파일이 읽히는지 확인 |
| 역방향 | 해당 형태의 입력을 무조건 거부하는 경우 | 작업 공간 안을 가리키는 심볼릭 링크는 정상적으로 읽히는지 확인 |

양성 대조가 실패하면 그 그룹의 테스트는 자체 결과와 상관없이 FAIL로 기록되며, 대조 자체는 점수에 들어가지 않습니다. 328개 케이스 중 130개가 하나 이상의 대조로 묶여 있습니다(그림 4b).

### 테스트 케이스는 어떻게 만들었나

세 방법을 번갈아 썼습니다(그림 3).

- **공개 이슈 채굴:** Claude Code(9,868), OpenCode(5,438), Gemini CLI(4,831), Kimi Code(946) 저장소의 이슈 총 21,083개를 개발 문서와의 관련도로 정렬해 사람이 검토하고, 같은 현상을 묶어 후보로 만듭니다. "성숙한 하네스가 수년간 드러낸 결함과, 사람이 쓴 코드로 학습한 모델이 만드는 실수가 겹칠 것"이라는 가정입니다.
- **하네스 간 비교:** 후보 하네스와 Kimi Code, Qwen Code 같은 성숙한 구현을 같은 기능 경계로 나눠 차이를 열거하고, 개발 문서 조항으로 거슬러 올라가는 차이만 테스트로 만듭니다.
- **단일 변수 확장:** 이미 변별력이 확인된 케이스에서 도구, 입력 형태(파일 심볼릭 링크, 디렉터리 링크, 다단계 링크 등), 잘못된 파라미터(0을 "없음"으로 취급하는 실수 등), 결과가 나오는 위치(stdout, stderr, 오류 문구) 중 하나만 바꿔 새 케이스를 만듭니다.

## 주요 결과

### 1. 1위도 절반 가까이 실패한다 (표 2, 그림 1)

| 순위 | 모델 | 전체 통과율 |
|---|---|---|
| 1 | GPT-6 Astra | 53.05% ± 0.25 |
| 2 | Opus 5 | 46.65% ± 1.80 |
| 3 | Qwen3.8 Max | 45.83% ± 0.14 |
| 4 | GPT-5.6-sol | 43.80% ± 2.44 |
| 5 | Grok 4.7 | 43.50% ± 2.49 |
| ... | ... | ... |
| 19 | Hy3 | 27.44% ± 0.43 |

19개 모델 평균은 38.30%이고 1위와 19위의 차이는 약 26%p입니다. 저자들은 이 차이를 근거로 테스트 모음이 포화되지도, 변별력이 없지도 않다고 주장합니다. 흥미롭게도 상위 두 모델의 차이는 경계 상황에 몰려 있었습니다. 일반 시나리오에서는 Opus 5가 80.68% 대 72.46%로 앞섰지만, 경계 시나리오에서는 GPT-6 Astra가 48.97% 대 37.02%로 앞섰습니다.

### 2. 범주마다 변별력이 크게 다르다 (표 3)

| 범주 | 케이스 | 평균 통과율 | 최강-최약 차이 | 아무도 못 푼 케이스 |
|---|---|---|---|---|
| 세션 상태 | 84 | 29.9 | 28.6 | 14 |
| 파일 작업 | 75 | 39.6 | 20.9 | 3 |
| 권한 | 61 | 43.7 | 50.8 | 10 |
| 헤드리스 | 40 | 26.4 | 41.7 | 9 |
| 직접 구동 | 33 | 18.8 | 29.3 | 17 |
| 대화형 터미널 | 20 | 79.9 | 33.3 | 0 |

**권한 범주가 모델을 가장 잘 갈랐습니다.** 최강과 최약의 차이가 50.8점이고 61개 중 51개가 변별 케이스였습니다. 대화형 터미널은 평균 79.9%로 포화에 가깝습니다. 전체 56개 케이스는 57개 하네스 모두가 실패했는데, 직접 구동, 세션 상태, 권한, 헤드리스에 몰려 있습니다.

### 3. 범주별 순위는 16계단까지 흔들린다

케이스가 20개 이상인 6개 주요 범주 사이에서 한 모델의 순위가 최대 16계단 바뀌었습니다. Grok 4.7은 파일 작업 1위지만 세션 상태 11위, Opus 4.6은 직접 구동 3위지만 권한 19위입니다. 그러면서도 범주 간 상관 15쌍이 모두 양수(평균 +0.521)이고 KR-20 신뢰도 계수가 0.913이라, 저자들은 이 테스트가 대체로 **하나의 능력 축**을 잰다고 해석합니다.

### 4. 코드 규모는 모델이 정하고, 많이 쓸수록 점수가 높다 (표 4, 그림 5)

모델별 평균 코드량은 1,271줄(GPT-5.5)부터 16,681줄(Qwen3.8 Max)까지 퍼져 있습니다. 코드 줄 수 분산의 95.9%가 모델 간 차이였고, 같은 모델의 세 빌드 사이 변동계수는 평균 12.7%에 불과했습니다. 즉 **얼마나 크게 짓는지는 모델의 습관**에 가깝습니다. 코드 줄 수와 통과율의 상관은 빌드 기준 0.614입니다.

### 5. 같은 양이면 모듈이 많을수록 점수가 낮다 (4.3절)

이 논문의 결론부 핵심 주장입니다. 코드 줄 수를 통제했을 때 **모듈 수와 통과율의 편상관은 -0.423**이고, 모델 하나씩 빼고 다시 계산해도 -0.484에서 -0.309 사이에 머물렀습니다. 모듈당 줄 수의 편상관은 +0.504였습니다. 표 4에서 1위 GPT-6 Astra는 평균 12.3개 모듈에 7,964줄(모듈당 646줄), 2위 Opus 5는 33.3개 모듈에 13,845줄(모듈당 415줄)이었습니다. 저자들은 권한처럼 여러 도구에 걸치는 **횡단 관심사**(cross-cutting concern)를 여러 모듈에 나눠 구현할수록 실패가 늘어난다고 해석하고, "쪼개기는 공짜가 아니다"라고 요약합니다.

## 한계

**저자가 밝힌 한계 (6절)**

- 한 번의 구축만 측정합니다. 제출 3회는 있지만 "빌드, 평가, 수정"을 반복하는 루프가 아니고, 계약 검사는 형태만 보므로 일찍 제출한 모델의 점수는 상한이 아니라 하한입니다.
- 하나의 결함이 여러 케이스를 함께 실패시킬 수 있습니다. 단일 변수 확장으로 만든 변형들은 거리 검사를 거쳐도 서로 상관돼 있습니다.

**읽으면서 발견한 한계 (필자 판단)**

- **"실패가 모듈 분할에 몰린다"는 결론은 상관관계입니다.** 초록과 결론은 실패가 횡단 기능의 모듈 분할 방식에 "몰린다(cluster)"고 쓰지만, 본문이 제시한 근거는 모듈 수와 통과율의 편상관(-0.423)입니다. 개별 실패 케이스를 코드 위치로 추적해 "권한 검사가 이 모듈에는 있고 저 모듈에는 없어서 실패했다"고 귀속한 분석은 본문에 없습니다. 모듈을 잘게 나누는 습관과 다른 품질 요인(예: 테스트 습관)이 함께 움직였을 가능성도 배제되지 않았습니다. 또 GPT-5.5는 평균 2.7개 모듈, 가장 큰 모듈이 코드의 78%인데도 34.65%로 중하위였으므로, "적게 나눌수록 좋다"가 단조로운 규칙은 아닙니다.
- **빌더 하네스 하나에 묶인 결과입니다.** OpenCode를 고른 이유는 타당하지만, 모델마다 익숙한 작업 방식이 달라 OpenCode에서의 순위가 각 모델의 "하네스 구축 능력"을 대표한다고 보기는 어렵습니다.
- **mock 모델은 실제 모델의 엉뚱한 출력까지 재현하지 않습니다.** 결정성을 얻은 대가로, 실제 모델이 잘못된 형식의 도구 호출을 보내거나 중간에 멈추는 상황에서의 견고성은 대본에 있는 만큼만 측정됩니다.
- **공개 부분으로 재현할 수 없습니다.** 전체 328개 중 53개 채점 케이스만 공개돼, 외부에서 리더보드를 검증하거나 새 모델을 같은 기준으로 비교하기 어렵습니다.

## 인사이트

**실무에 주는 의미: 권한은 "도구마다"가 아니라 "한 곳에서" 검사해야 합니다.** 공개된 시나리오 중 `deny_blocks_monitor_spawned_cmd`를 보면 이 논문이 무엇을 재는지 분명해집니다. `Bash(touch*)`를 거부 규칙으로 걸어 둔 뒤, bash 도구가 아니라 **monitor 도구가 띄운 명령**으로 `touch`를 시도하게 합니다. 권한 검사를 bash 도구 안에 넣어 둔 구현은 이 경로를 놓칩니다. 이것이 바로 횡단 관심사가 모듈에 흩어질 때 생기는 결함이고, 권한 범주가 최강-최약 차이 50.8점으로 가장 변별력이 컸던 이유로 보입니다. 사내 에이전트나 도구 서버를 직접 만드는 팀이라면 이 논문의 교훈은 명확합니다. 권한, 경로 경계, 세션 상태처럼 모든 도구에 걸치는 규칙은 각 도구 구현에 복사하지 말고, 모든 도구 호출이 반드시 지나가는 한 지점(디스패처나 미들웨어)에서 강제하는 편이 안전합니다. [Harness² 논문](/papers/2026/10/24/harness-squared.html)이 "프롬프트 문장은 건너뛸 수 있지만 도구 루프 안의 플러그인은 건너뛸 수 없다"며 반드시 지켜야 할 규칙을 플러그인으로 옮기라고 권하는 것과 같은 결론입니다.

**양성 대조는 에이전트 안전 테스트 전반에 가져다 쓸 만한 기법입니다.** "금지된 일이 일어나지 않았다"는 테스트는 기능이 아예 동작하지 않아도 통과합니다. 샌드박스, 비밀값 마스킹, 네트워크 차단처럼 "부정형" 요구사항을 테스트할 때, 같은 경로의 허용된 버전이 실제로 동작하는지(같은 형태), 결과가 관찰 채널에 실리는지(채널), 정상 입력까지 막고 있지 않은지(역방향)를 함께 확인하는 습관은 이 벤치마크와 무관하게 바로 쓸 수 있습니다.

**블로그의 기존 글과의 연결.** [SWE-bench 소개](/papers/2026/10/24/swe-bench.html)가 "고정된 하네스에서 모델이 패치를 얼마나 잘 쓰나"를 쟀다면, Doc2Harness는 그 하네스 자체를 모델에게 짓게 합니다. 같은 날 소개하는 Harness²와 함께 읽으면 흐름이 보입니다. Harness²는 이미 있는 하네스를 배포 중에 고치는 능력을, Doc2Harness는 명세에서 처음부터 짓는 능력을 잽니다. 두 논문 모두 하네스의 품질이 모델 점수를 크게 바꾼다는 전제에 서 있고, 둘 다 "실행해서 관찰한 행동"을 근거로 삼습니다.

**한계와 반론: 이 벤치마크가 재는 것은 "명세 준수"입니다.** 개발 문서는 12개 하네스의 기능을 합친 것이라, 실제로 좋은 하네스가 갖춰야 할 성질(모델 성능을 잘 끌어내는 프롬프트 구성, 컨텍스트 압축 품질 등)보다는 **명세를 얼마나 빠짐없이 정확하게 구현했는지**를 봅니다. mock 모델로 구동하니 "이 하네스를 쓰면 실제 모델이 일을 더 잘하나"는 측정 대상이 아닙니다. 필자의 판단으로는, 53%라는 수치를 "모델이 하네스를 절반밖에 못 만든다"로 읽기보다 "12개 하네스의 기능을 합친 명세를 2시간, 24턴 안에 약 16,000줄 규모로 한 번에 구현하면 경계 조건의 절반 가까이를 놓친다"로 읽는 편이 정확합니다. 이는 사람 개발자에게도 쉬운 일이 아닙니다.

**앞으로 지켜볼 점.** (1) 저자들이 한계로 든 "빌드, 평가, 수정" 반복 루프 버전이 나오면, 테스트 피드백을 받은 모델이 횡단 관심사 결함을 스스로 고치는지 볼 수 있습니다. (2) 실패 케이스를 코드 위치에 귀속하는 분석이 추가되면 모듈 분할 가설이 인과로 강해질지 판단할 수 있습니다. (3) 비공개 케이스가 리더보드 서비스 형태로라도 열리는지에 따라 이 벤치마크가 업계 표준 지표가 될 수 있을지가 갈릴 것입니다.
