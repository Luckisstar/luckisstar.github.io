# [논문 소개] TokenRouter: 토큰마다 모델을 바꾸는 라우팅을 실제로 서빙하는 법

- **논문:** *TokenRouter: Efficient Serving System for Token-Level LLM Routing*
- **저자:** Tianyu Fu, Tengxuan Liu, Ruoxi Wang, Yixin Dong, Yi Ge, Yichen You, Yu Wang (총 7명), 칭화대학교(Yixin Dong은 카네기멜런대학교). 교신저자 Yu Wang
- **공개:** 2026년 10월 8일, arXiv:2610.12242 (cs.CL). arXiv 코멘트와 저장소 README에 NeurIPS 2026 채택으로 표기
- **링크:** [arXiv](https://arxiv.org/abs/2610.12242) · [PDF](https://arxiv.org/pdf/2610.12242) · [HTML](https://arxiv.org/html/2610.12242v1) · [코드](https://github.com/thu-nics/TokenRouter) · [프로젝트 페이지](https://fuvty.github.io/thinking_yard_project_page/projects/tokenrouter/)
- **주의 (2026-10-24 기준):** 코드 저장소에 LICENSE 파일이 없고 GitHub API의 라이선스 항목도 비어 있습니다. 라이선스가 명시되지 않은 코드는 원칙적으로 재사용 권리가 정해지지 않은 상태이므로, 업무에 가져다 쓰기 전에 저자에게 확인하는 편이 안전합니다. (저장소 스타 64개)

## 한 줄 요약

**토큰 단위 라우팅(한 응답 안에서 토큰마다 작은 모델과 큰 모델을 오가는 방식)은 알고리즘으로는 효과가 입증됐지만, 단일 모델을 전제로 만든 서빙 엔진 위에서는 느렸습니다. TokenRouter는 "요청 중심으로 프로그래밍하고, 모델 중심으로 실행한다"는 설계로 이 간극을 메워 기존 구현 대비 2.01~64.15배의 디코딩 처리량을 보고합니다.**

## 왜 이 연구가 필요한가

모델 라우팅(model routing)은 쉬운 일은 작은 모델에, 어려운 일은 큰 모델에 맡겨 비용과 품질의 균형을 맞추는 방식입니다. 논문은 ChatGPT와 Cursor 같은 상용 시스템이 질의(query) 단위로 백엔드 모델을 고르고, RouteLLM 같은 연구도 질의 단위 라우팅을 다룬다고 소개합니다. 이 방식에서는 한 번 라우팅된 요청은 그 라운드가 끝날 때까지 한 모델이 끝까지 생성합니다.

반면 토큰 단위 라우팅은 같은 답변 안에서도 어려운 토큰만 큰 모델에 넘깁니다. 논문이 인용한 예로, R2R은 32B 모델 품질을 맞추는 데 **토큰의 5%만** 32B에 보내고 나머지는 1.5B 모델이 디코딩했습니다. 질의 단위로 같은 품질을 내려면 약 40%의 질의를 32B로 보내야 했다고 합니다.

문제는 SGLang, vLLM 같은 서빙 엔진이 "모든 활성 요청이 같은 모델에서 같은 디코딩 단계를 밟는다"는 가정 위에 서 있다는 점입니다. 토큰마다 대상 모델이 바뀌면 이 가정이 깨지고, 논문은 세 가지 문제를 꼽습니다.

| 문제 | 무엇이 일어나나 |
|---|---|
| **단계 비동기화** (step desynchronization) | 모델마다 한 단계 지연이 크게 다른데, 배치를 동기화하면 매 단계가 가장 느린 모델을 기다리고 빠른 모델은 놉니다 |
| **배치 진입 지연** (batch admission delay) | 라우팅된 요청이 도착했을 때 대상 모델이 이전 배치를 처리 중이면 다음 배치까지 기다려야 해 거품(bubble)과 배치 조각화가 생깁니다 |
| **구현 복잡도** | 기존 엔진에는 단계별 라우팅 결정을 위한 인터페이스가 없어, 연속 배칭이나 접두사 캐시 같은 기능과 맞물린 큰 코드베이스를 직접 고쳐야 합니다 |

실제로 논문이 비교한 공식 구현 중 CITER와 R2R은 연속 배칭(continuous batching, 끝난 요청 자리에 새 요청을 바로 끼워 넣는 기법)이 없는 추론 엔진이고, R-Stitch는 코드가 공개되지 않았습니다. 알고리즘 논문은 많은데 그것을 "서비스처럼" 돌릴 기반이 없었다는 것이 출발점입니다.

## 제안 방법

### 1. 프로그래밍 인터페이스: route, send, receive 세 함수

저자들은 토큰 단위 라우팅 알고리즘들이 정책은 달라도 같은 생애 주기를 공유한다는 데 주목합니다. 요청이 한 모델에서 디코딩되고, 라우터가 계속할지 넘길지 정하고, 넘긴다면 필요한 상태를 상대 모델에 보내고, 상대 모델이 받아 이어서 디코딩합니다.

- `route(result)`: 매 디코딩 단계 뒤에 호출되어 배치의 요청마다 목적지를 정합니다. 은닉 상태, 다음 토큰 로짓, 샘플링된 토큰을 근거로 쓸 수 있고, 0이면 그대로 계속, 0이 아니면 해당 상대 모델로 보냅니다.
- `send(req)`: 상대 모델이 아직 보지 못한 토큰 접미사, 요청 ID, 종료 여부, 알고리즘별 필드를 담은 `PeerReq` 메시지를 만듭니다.
- `receive(peer_req)`: 받은 메시지를 로컬 요청 형식으로 바꿉니다. 기본값은 "넘어온 토큰을 모두 받아들인다"이며 대부분 알고리즘은 이것으로 충분하다고 합니다.

논문 그림 3은 R-Stitch(엔트로피가 높은 토큰을 큰 모델로 넘기는 방법)의 작은 모델 쪽 구현을 보여 줍니다. 핵심만 옮기면 다음과 같습니다(논문 그림 3 코드 발췌, 직접 실행하지 않음).

```python
class RStitchSLM(BaseRouter):
    def route(self, result):
        # 엔트로피가 높은 토큰은 큰 모델로, 나머지는 로컬에서 계속
        probs = result.logits_output.next_token_logits.softmax(dim=-1)
        entropy = -(probs * probs.log()).sum(-1) / math.log(probs.shape[-1])
        destination = torch.zeros_like(entropy, dtype=torch.long)
        destination[entropy > self.tau] = self.peer_idx
        return destination.cpu()

    def send(self, req) -> PeerReq:
        # 방금 뽑은 불확실한 토큰은 빼고, 큰 모델이 아직 못 본 부분만 전송
        token_ids = req.origin_input_ids + req.output_ids[:-1]
        peer_anchor = req.peer_locs[self.peer_idx] or 0
        return PeerReq(rid=req.rid, token_ids=token_ids[peer_anchor:],
                       loc=len(token_ids), finished=req.finished(), ...)
```

개발자는 "요청 하나가 모델 사이를 어떻게 오가는가"만 기술하고, 배칭과 스케줄링은 런타임이 맡습니다. 논문이 평가한 다섯 알고리즘(CITER, R2R, R-Stitch, Co-LLM, ME)이 모두 이 틀로 표현됩니다(표 1). 저장소 README 기준으로는 GlimpRouter와 질의 단위 라우팅 스케줄러도 들어 있습니다.

### 2. 실행 구조: 모델마다 독립 서브서버와 세 개의 루프

런타임은 모델 하나당 서브서버(subserver) 하나를 띄웁니다. 각 서브서버는 자기 스케줄러, 자기 KV 캐시 풀, 위 세 함수를 가지고 독립적으로 진행합니다. 바깥에는 단일 엔드포인트만 노출하므로 클라이언트 입장에서는 vLLM이나 SGLang 같은 일반 단일 모델 서버와 프로토콜이 같습니다.

일반 서빙 엔진은 클라이언트-서버 루프(요청 접수와 스트리밍)와 디코딩 루프(스케줄링과 모델 실행) 두 개를 비동기로 돌립니다. TokenRouter는 여기에 **모델 간 루프**(inter-model loop)를 하나 더 둡니다. 라우팅된 요청은 로컬 배치에서 빠져나가 상대 모델로 가고, 남은 요청들은 자기 속도로 계속 디코딩합니다(그림 2, 그림 4).

여기에 **핸드오프-재개**(handoff-resume) 장치가 붙습니다. 단순하게 구현하면 상대 모델에서 돌아온 요청을 새 요청처럼 처리해 접두사 매칭과 KV 캐시 할당을 다시 하게 됩니다. TokenRouter는 running과 finished 사이에 **pending** 상태를 추가해, 넘겨진 요청의 서빙 상태를 보존한 채 스케줄러가 건너뛰게 합니다. 돌아오면 새 토큰을 붙이고 "떠난 적 없는 것처럼" 배치에 다시 넣습니다. 논문 표현으로는 모델 전환이 "토큰 추가 정도의 비용"이 됩니다.

### 3. 스케줄링: 지연 배칭과 처리량 최적 임계값

비동기 실행만으로는 배치 진입 지연이 남습니다. 요청이 하나라도 오면 바로 단계를 시작하는 방식(논문의 Eager-Async)에서는, 모델이 배치를 처리하는 동안 도착한 요청이 그 단계가 끝날 때까지 기다립니다.

**지연 배칭**(delayed batching)은 대기열에 요청이 임계값 B개 모일 때까지 일부러 기다렸다가 배치를 시작합니다. 먼저 온 요청은 조금 더 기다리지만, 뒤에 온 요청들이 덜 기다려 평균 진입 지연이 줄어듭니다. B가 너무 작으면 진입 지연이 커지고, 너무 크면 요청이 대기열에 갇혀 작은 모델이 할 일이 없어집니다.

저자들은 B를 감으로 정하지 않고 시스템을 **이산 시간 마르코프 연쇄**(DTMC)로 모델링합니다(부록 D). 상태는 모델별 대기 요청 수, 실행 중인 배치 크기, 남은 실행 시간이고, 라우팅 확률 행렬 P, 모델별 단계 지연 L, 동시 요청 수 N을 넣으면 정상 상태 처리량을 B의 함수로 계산해 최댓값을 찾습니다. R2R(Qwen3-0.6B와 Qwen3-32B)에서 측정값은 큰 모델로 넘어갈 확률 p=0.35, 작은 모델 단계 지연 6.0ms, 큰 모델 27.9ms였고, 그림 10에서 **평가한 모든 동시성 수준에서 모델이 예측한 최적 임계값이 실측 최적값과 일치**했다고 보고합니다. 저장소에는 이 계산 스크립트(`evaluation/calculate_delayed_batching.py`)가 들어 있습니다.

### 4. 단일 모델 가정을 깨는 자잘한 최적화들

부록 B는 토큰 라우팅이 깨뜨리는 단일 모델 가정과 그 대응을 정리합니다.

- **KV 메모리 공동 할당:** 한 GPU에 여러 모델을 올리면 각자 "GPU 전체가 내 KV 예산"이라고 가정해 메모리가 부족해지거나 남습니다. 모델별 가중치 크기와 토큰당 KV 크기로 공통 KV 토큰 용량을 계산해 나눠 줍니다.
- **extend 모드 CUDA 그래프:** 보통은 모양이 안정적인 decode 배치만 CUDA 그래프로 캡처하지만, 라우팅에서는 상대 모델에서 돌아온 요청이 모두 extend 배치로 들어오므로 extend 경로가 주류가 됩니다. 일정 범위의 extend 배치를 캡처합니다.
- **프로세스 내 라우터:** 라우터가 요청당 한 번이 아니라 토큰마다 돌기 때문에 프로세스 간 통신을 두면 토큰마다 왕복이 생깁니다. 라우터를 스케줄러와 같은 프로세스, 같은 GPU에 둡니다.

구현은 SGLang 0.5.1 위에 있고, 서브서버 간 메시지는 로컬 ZeroMQ IPC로 오갑니다(부록 C).

## 주요 결과

### 1. 15개 조합 모두에서 처리량 2.01~64.15배

다섯 알고리즘과 세 워크로드의 15개 조합(동시성 4)에서, TokenRouter는 공식 코드와 표준 서빙 중 **더 강한 쪽** 대비 처리량을 2.01~64.15배 높였고, 표준 서빙 대비 종단 지연을 2.03~63.64배 줄였습니다(그림 5, 6). 출력 길이를 2,048에서 8,192로 늘렸을 때 TokenRouter의 처리량은 유지된 반면 표준 서빙은 처리량의 58.1~85.2%를 잃었습니다.

### 2. 표준 서빙이 느린 이유: 디코딩이 아니라 장부 정리

표준 서빙이 왜 이렇게 느린지는 표 10이 잘 보여 줍니다. 2,048 토큰 생성의 마지막 128 단계에서 작은 모델 쪽 단계 시간을 쪼갠 결과입니다.

| 작업 | 지연(ms) | 비율 |
|---|---|---|
| 접두사 매칭 | 7.78 | 20.94% |
| 캐시 노드 잠금 | 6.49 | 17.47% |
| **작은 모델 추론** | **1.56** | **4.20%** |
| 잠금 해제 | 5.13 | 13.81% |
| radix 캐시 갱신 | 12.12 | 32.62% |
| 기타 | 4.08 | 10.98% |

정작 모델 계산은 4.2%이고, 나머지 대부분은 돌아온 토큰을 "새 요청"으로 처리하며 생기는 접두사 매칭과 radix 캐시 관리입니다. 핸드오프-재개가 겨냥한 지점이 바로 이것입니다.

### 3. 원래 논문 설정에서도 공식 구현보다 빠르다

각 알고리즘의 원 논문 설정(표 4: R2R은 DeepSeek-R1-Distill-Qwen 1.5B/32B, CITER는 Qwen2 1.5B/72B, Co-LLM은 LLaMA2 7B/70B, R-Stitch는 L1-1.5B-Short/QwQ-32B)에서 동시성 4일 때, 공식 구현 대비 지연은 2.78~21.61배 줄고 처리량은 2.73~21.97배 늘었습니다(표 2). 다만 표 2에는 **큰 모델 하나만 쓰는 경우(LLM-only)**도 함께 있어 함께 볼 필요가 있습니다.

| 알고리즘 | LLM-only 처리량 | 공식 코드 | TokenRouter | TokenRouter 지연(s) / LLM-only 지연(s) |
|---|---|---|---|---|
| R2R | 145.30 | 89.62 | **244.56** | 270.19 / 411.98 |
| CITER | 123.72 | 17.16 | **149.31** | 0.48 / 2.68 |
| Co-LLM | **134.79** | 3.46 | 76.02 | 11.46 / 13.39 |
| R-Stitch | **150.41** | 공개 코드 없음 | 140.58 | 151.30 / 360.76 |

(처리량 단위 token/s, 동시성 4, 표 2)

R2R과 CITER는 큰 모델 단독보다 처리량이 높지만, **Co-LLM과 R-Stitch는 처리량만 보면 큰 모델 단독보다 낮습니다.** 그런데도 요청당 지연은 TokenRouter 쪽이 짧은데, 알고리즘마다 생성 길이가 달라지기 때문으로 보입니다(논문은 이 차이를 따로 설명하지 않습니다).

### 4. 동시성을 높여도 사용자당 속도를 덜 잃는다

동시성을 1에서 16으로 올렸을 때 TokenRouter의 처리량은 8.61배 늘면서 단일 사용자 속도의 51.7%를 유지했습니다. 공식 R2R은 5.14배, 31.3%였습니다. 동시성 16의 TokenRouter는 동시성 1의 공식 R2R보다 처리량이 18.58배 높으면서 사용자당 속도도 1.13배 빨랐습니다(그림 1(b)).

### 5. 이득은 어디서 오나: 엔지니어링 1.71배, 설계 1.6배

동시성 8에서 이득을 분해하면(그림 1(a), 표 6) 다음과 같습니다.

| 단계 | 처리량(token/s) |
|---|---|
| 공식 R2R 코드 | 134.89 |
| 기본 구현(CUDA 그래프 없음, 약 R2R 수준) | 132.78 |
| + 작은 모델 CUDA 그래프 | 164.08 |
| + 큰 모델 CUDA 그래프 | 228.10 |
| + 라우터 CUDA 그래프 | 230.79 |
| + 비동기 실행 | 296.86 |
| + 지연 배칭 (TokenRouter) | **372.48** |

전체 2.76배 중 1.71배는 CUDA 그래프 같은 엔지니어링에서, 나머지는 비동기 실행과 지연 배칭에서 나옵니다. 동시성 1에서는 비동기 실행과 지연 배칭의 효과가 0입니다(73.02로 동일). 모델 조합을 바꿔도(0.6B/8B, 0.6B/32B, 1.7B/8B, 4B/8B) 공식 R2R 대비 1.99~3.21배였습니다(표 3).

### 6. 노드를 나눠도 성능이 비슷하다

작은 모델과 큰 모델을 서로 다른 노드(RoCE 3.7GB/s 연결)에 두어도 단일 노드와 비슷한 처리량을 냈고, 각 공식 구현 대비 1.93~32.81배였습니다(표 9). GPU를 공유하지 않고 따로 배치하면 처리량이 평균 6.43% 더 올랐습니다(표 8). 모델 사이에 오가는 것이 토큰 ID 몇 개뿐이라 네트워크 부담이 작기 때문으로 보입니다.

## 한계

**저자가 밝힌 한계**

- 처리량 모델은 두 번의 전송 사이 토큰 수가 기하분포를 따른다고 가정합니다. 대부분 알고리즘에는 맞지만, 이 가정을 벗어나는 경우는 후속 과제로 남겼습니다.

**읽으면서 발견한 한계**

- **"64.15배"의 분모가 약합니다.** 비교 대상인 공식 코드 상당수가 연속 배칭이 없는 연구용 구현이고, 표준 서빙도 저자들이 만든 기준선입니다. 실무 관점에서 더 중요한 질문은 "큰 모델 하나를 잘 서빙하는 것보다 나은가"인데, 표 2에서 이 답은 알고리즘마다 갈립니다.
- **동시성이 낮습니다.** 실험 동시성은 1~16입니다. 대형 서비스의 배치 크기에서 지연 배칭과 모델 공존(같은 GPU에 두 모델)이 어떻게 동작할지는 보여 주지 않습니다.
- **품질은 서빙 실험의 주제가 아닙니다.** 정확도와 처리량을 함께 본 것은 AMC23 한 벤치마크의 그림 7(파레토 곡선)뿐이고, 본문에 수치 표는 없습니다. 라우팅 알고리즘 자체의 품질은 각 원 논문을 믿는 구조입니다.
- **같은 연구실의 알고리즘이 많습니다.** R2R과 Think-at-Hard 등 인용된 토큰 라우팅 연구 일부가 같은 저자군의 작업이며, 주 비교 대상(R2R)도 그렇습니다. 결과를 부정할 이유는 아니지만 독립 재현이 나오면 더 단단해질 것입니다.

## 인사이트

**왜 지금 중요한가: 라우팅 단위가 내려가면 서빙 엔진의 기본 가정이 깨진다.** 지금까지 라우팅은 서빙 엔진 "바깥"의 문제였습니다. 게이트웨이가 질의를 보고 모델을 고르면, 각 모델 서버는 평소처럼 연속 배칭과 접두사 캐시를 돌리면 됐습니다. 토큰 단위로 내려오는 순간 라우팅이 디코딩 루프 "안"으로 들어오고, 표 10처럼 모델 계산보다 캐시 장부 관리가 더 비싸지는 일이 생깁니다. 필자가 보기에 이 논문의 가장 큰 기여는 2~64배라는 숫자보다 "어떤 가정이 어디서 깨지는지"를 체계적으로 목록화한 부록 B입니다. KV 예산 독점, decode 위주 CUDA 그래프, 요청당 한 번 도는 라우터라는 세 가정은 앞으로 다른 다중 모델 추론 방식에도 똑같이 문제가 될 것입니다.

**블로그의 기존 글과의 연결.** [KV 캐시와 추측 디코딩](/tech/2026/10/24/kv-cache-speculative-decoding.html) 글에서 다룬 추측 디코딩도 작은 모델과 큰 모델을 함께 씁니다. 차이는 패턴의 규칙성입니다. 추측 디코딩은 "초안 k개 생성, 검증 1회"가 주기적으로 반복되므로 서빙 엔진이 두 모델을 한 몸처럼 묶어 스케줄링할 수 있습니다. 토큰 라우팅은 데이터에 따라 아무 때나 전환이 일어나므로, 논문 그림 4(b)처럼 추측 디코딩 방식으로 묶으면 오히려 유휴 시간이 커집니다. 또 [MoE(전문가 혼합)](/tech/2026/10/24/mixture-of-experts.html)가 모델 "내부"에서 토큰마다 전문가를 고르는 것이라면, 토큰 라우팅은 같은 일을 모델 "사이"에서 하는 셈입니다. MoE가 전문가 병렬과 토큰 재배치 같은 서빙 기술이 따라온 뒤에야 실용화됐듯, 토큰 라우팅도 TokenRouter 같은 런타임이 있어야 알고리즘 논문 밖으로 나올 수 있습니다. 같은 연구실의 [캐시 엔지니어링(AKV)](/papers/2026/10/24/cache-engineering-agents.html) 논문도 "토큰 접두사가 캐시 상태를 결정한다"는 SGLang의 가정을 깨는 문제를 다루는데, 두 논문을 나란히 보면 SGLang 같은 엔진이 앞으로 무엇을 일반화해야 하는지가 보입니다.

**실무에 주는 의미.** 지금 토큰 단위 라우팅을 프로덕션에 넣을 팀은 많지 않을 것입니다. 그래도 두 가지는 바로 쓸 만합니다. 첫째, 자체 라우팅이나 다중 모델 파이프라인을 만든다면 "넘겨받은 요청을 새 요청으로 처리하지 말 것"이라는 교훈입니다. 표 10의 숫자는 이 비용이 모델 계산의 몇 배가 될 수 있음을 보여 줍니다. 둘째, 배치 임계값 같은 스케줄링 파라미터를 측정한 라우팅 확률과 단계 지연으로 계산해 정할 수 있다는 점입니다. 부하 테스트로 하나씩 찾는 대신 모델로 후보를 좁히는 접근은 다른 서빙 튜닝에도 응용할 수 있습니다. 도입을 검토한다면 표 2의 LLM-only 열과 비교해, 쓰려는 알고리즘이 "큰 모델 단독"보다 실제로 나은지부터 확인해야 합니다.

**앞으로 지켜볼 점.** (1) SGLang이나 vLLM 본체가 이런 다중 모델 런타임을 흡수하는지. 지금은 SGLang 0.5.1 포크라 업스트림 기능을 따라가기 어렵습니다. (2) 동시성 수십~수백 수준과 서로 다른 GPU 종류를 섞은 배치에서의 결과. (3) 저장소의 라이선스 명시 여부. 이 세 가지가 채워지면 토큰 라우팅은 "논문 속 기법"에서 "서빙 옵션"으로 넘어갈 수 있다고 봅니다.
