# [논문 소개] Cache Engineering for Agents: 텍스트 대신 KV 캐시를 직접 지우는 에이전트 컨텍스트 관리

- **논문:** *Cache Engineering for Agents*
- **저자:** Tianyu Fu, Ruoxi Wang, Zihan Min, Zhongqi Ren, Zhihao Li, Tengxuan Liu, Shengxu Mu, Hanling Zhang, Yu Wang (총 9명), 칭화대학교(Hanling Zhang은 홍콩중문대학교). 교신저자 Yu Wang
- **공개:** 2026년 10월 20일, arXiv:2610.28577 (cs.CL)
- **링크:** [arXiv](https://arxiv.org/abs/2610.28577) · [PDF](https://arxiv.org/pdf/2610.28577) · [HTML](https://arxiv.org/html/2610.28577v1) · [코드](https://github.com/thu-nics/AKV) · [프로젝트 페이지](https://fuvty.github.io/thinking_yard_project_page/projects/akv/)
- **현황 (2026-10-24 기준):** 코드 저장소 Apache-2.0 라이선스, GitHub 스타 50개. AKV 서버(SGLang 기반)를 직접 띄워야 쓸 수 있는 방식이며, 논문은 상용 API에서의 적용을 다루지 않습니다.

## 한 줄 요약

**에이전트 대화 기록(텍스트)을 요약하거나 잘라내면 그 뒤의 KV 캐시가 모두 무효화되어 다시 계산해야 합니다. 이 논문은 텍스트는 그대로 두고 KV 캐시 일부만 "주의(attention) 대상에서 빼는" 캐시 엔지니어링을 제안하고, 이 방식이 깨뜨리는 접두사 캐시 재사용을 고친 서빙 엔진 AKV를 함께 내놓았습니다.** 요약 기반 방식 대비 평균 점수 +1.7점, 비용 -27.7%를 보고합니다.

## 왜 이 연구가 필요한가

에이전트는 추론, 도구 호출, 도구 응답을 수백 라운드 반복합니다. 궤적이 길어지면 두 가지가 문제입니다.

- **비용:** 쌓인 KV 캐시를 매 라운드 다시 읽어야 합니다. 논문 서론은 KV 캐시 읽기가 전체 API 비용의 82.4%를 차지한 사례를 제시합니다.
- **정확도:** 주의를 기울이는 KV 수나 위치 범위가 모델이 안정적으로 다루는 범위를 넘으면 성능이 크게 떨어집니다.

지금까지의 대응은 컨텍스트 엔지니어링(context engineering)입니다. 오래된 메시지를 자르거나(trim) 요약(summarize)합니다. 문제는 **앞부분 텍스트를 고치는 순간 그 뒤의 KV 상태가 모두 무효가 되어 남긴 부분을 다시 프리필(re-prefill)해야 한다**는 점입니다. 앞쪽을 고칠수록 다시 계산할 양이 많아집니다. 그래서 흔한 하네스는 컨텍스트가 임계값에 닿을 때까지 기다렸다가 한 번에 대부분을 요약하고 최근 몇 라운드만 남깁니다. 이렇게 하면 다시 계산할 양은 줄지만 중간 라운드의 유용한 정보를 잃습니다. 논문은 이것을 "재프리필 비용과 정확도 사이의 딜레마"라고 부릅니다.

그림 3의 예비 실험(GPT-OSS-120B, BrowseComp-Plus 100문제)이 이 딜레마를 보여 줍니다. 최근 12라운드의 도구 응답만 남기는 잘라내기 방식은 전체 컨텍스트 기준선보다 비용이 **1.85배**였고, 48K 임계값 요약은 비용을 약 7% 줄였지만 정확도가 5%p 떨어졌습니다. 반면 오래된 도구 응답의 KV만 지우고 나머지를 재사용하면 정확도와 비용이 동시에 좋아졌습니다.

## 제안 방법

### 1. 캐시 연산 세 가지: append, drop, repos

캐시 엔지니어링은 논리적 토큰 순서(대화 기록)는 바꾸지 않고, "앞으로의 주의에 참여하는 KV"인 **활성 캐시**(active cache)만 조작합니다.

| 연산 | 하는 일 | 바꾸지 않는 것 |
|---|---|---|
| `append(x)` | 새 토큰의 KV를 계산해 붙임(일반 추론과 동일) | |
| `drop(P)` | 선택한 위치의 KV를 이후 주의 대상에서 제외 | 남은 KV, 위치 인코딩, 텍스트 기록 |
| `repos` | 남은 키의 위치 인코딩을 0부터 다시 매기고 다음 토큰 위치도 재설정 | 값(V), 텍스트 기록 |

`repos`가 필요한 이유는 `drop`만 하면 위치 번호가 계속 커지기 때문입니다. 캐시를 아무리 작게 유지해도 위치 인덱스가 모델 한계에 닿으면 실행이 멈춥니다. RoPE(회전 위치 임베딩)에서는 키 K를 위치 p에서 q로 옮기는 회전 `K ← R(q)R(p)⁻¹K`로 재계산 없이 처리합니다.

중요한 성질은 **남긴 KV가 지운 기록의 정보를 일부 품고 있다**는 점입니다. 도구 응답 A를 보고 쓴 추론 B의 KV는 A를 참조해 계산됐으므로, A를 지워도 B 안에 A의 흔적이 남습니다(그림 1). 요약은 이 정보를 텍스트로 다시 써야 하지만, 캐시 엔지니어링은 그대로 들고 갑니다.

### 2. 진짜 난제: 같은 토큰, 다른 캐시

일반 KV 캐싱에서는 토큰 접두사가 캐시 상태를 완전히 결정합니다. vLLM의 PagedAttention과 SGLang의 RadixAttention 같은 접두사 캐시가 이 성질에 기대고 있습니다. 캐시 엔지니어링에서는 이 성질이 깨집니다. 논문 그림 5의 예입니다.

- ① A, B 다음에 C를 붙이고 나서 A를 지움
- ② A를 먼저 지우고 C를 붙임
- ③ B에서 시작해 C를 붙임

세 경우 모두 남은 것은 B와 C이지만, C의 KV는 ①에서는 A를 보고 계산됐고 ②와 ③에서는 A를 보지 못했습니다. ②와 ③도 B의 KV가 다릅니다(②의 B는 A를 보고 계산됨). **토큰 순서와 남은 위치가 같아도 연산 이력에 따라 캐시 상태가 달라지는** 이력 의존성(history dependence) 때문에, 접두사 매칭만으로는 캐시를 올바르게 재사용할 수 없습니다. 잘못 재사용하면 오류 없이 다른 출력이 나옵니다.

### 3. AKV 서빙 엔진: 무상태 인터페이스, 상태 있는 서빙

AKV의 원칙은 "stateless interface, stateful serving"입니다.

**인터페이스.** 클라이언트는 평소처럼 전체 메시지 기록을 보내고, 어떤 메시지 뒤에 무엇을 지우고 언제 위치를 재정렬할지를 추가 필드로 적습니다. 서버에 무엇이 남아 있는지 클라이언트가 추적할 필요가 없고, 서버가 메모리 압박으로 캐시를 버렸더라도 요청 하나만으로 상태를 완전히 복원할 수 있습니다. 저장소 README의 예시를 옮기면 다음과 같습니다(README 기반, 직접 실행하지 않음).

```python
from akv.agent import CachePolicy
from akv.agent.policies import TurnTrigger, TurnSelection, TurnReposition

policy = CachePolicy(
    trigger=TurnTrigger(),          # 언제 지울지: 턴 단위
    selector=TurnSelection(1),      # 무엇을 남길지: 최근 1턴의 도구 결과
    reposition=TurnReposition(after=2, every=2),
)
akv_payload, history = policy.process(payload, api_style="sglang")
# payload에 다음 필드가 추가됨:
#   "drop_message": {"4": [2]}   # 메시지 4를 처리한 뒤 메시지 2의 KV를 제외
#   "reposition": [4]            # 메시지 4 뒤에 위치 재정렬
```

메시지 2는 요청에서 지우지 않고 그대로 보냅니다. README는 "메시지 2를 직접 제거하지 말라"고 강조합니다. (논문 그림 6은 같은 개념을 `cache` 필드 아래 `drop`, `reposition`으로 표기하므로, 실제 필드 이름은 저장소 기준으로 확인해야 합니다.)

**캐시 관리.** 서버 쪽은 세 장치로 일반 서빙 엔진의 성질(동등할 때만 재사용, 요청 격리를 해치지 않는 회수, 한 번의 프리필로 복원)을 지킵니다.

| 과제 | AKV의 해법 |
|---|---|
| 접두사만으로 캐시 상태가 정해지지 않음 | **확장 radix 트리:** 토큰 노드 사이에 drop 노드와 reposition 노드를 끼워 넣어, 토큰과 연산 이력이 모두 같을 때만 재사용 |
| 한 요청이 지운 KV를 다른 요청이 쓸 수 있음 | **drop 인지 회수:** 진행 중인 계산이나 복원이 필요로 하지 않을 때만 회수. 완료된 요청의 캐시보다 지워진 캐시를 먼저 회수 |
| 일반 인과 프리필로는 drop과 repos 결과를 재현할 수 없음 | **세그먼트 배치 주의:** 쿼리를 연산 지점마다 세그먼트로 나눠 각자 볼 수 있는 KV만 주의하게 하고, FFN은 전체를 한 배치로 처리해 한 번의 순전파로 복원 |

위치 재정렬은 은닉 상태를 다시 계산하지 않고 K를 회전해 복사본을 만드는 방식으로 처리하며, 위치 버전마다 따로 회수합니다(부록 A.1.2).

## 주요 결과

### 1. 세 모델 모두 평균 점수 최고, 평균 비용 최저

표 1의 평균(4개 벤치마크)만 옮기면 다음과 같습니다. 점수는 통과율(%), 비용은 과제당 센트입니다.

| 모델 | Standard | Text Engineering | AKV |
|---|---|---|---|
| MiniMax-M2.7 | 52.4점 / 5.0¢ | 52.8점 / 5.7¢ | **53.7점 / 4.4¢** |
| GPT-OSS-120B | 51.0점 / 11.2¢ | 48.3점 / 10.2¢ | **53.1점 / 7.3¢** |
| MiroThinker-1.7-Mini | 44.1점 / 20.4¢ | 37.1점 / 18.1¢ | **45.8점 / 14.8¢** |

평균 점수는 Standard 대비 1.3~2.1점, Text Engineering 대비 0.9~8.7점 높았고, 비용은 모델과 벤치마크 전체 평균으로 Standard 대비 27.7%, Text Engineering 대비 21.9% 낮았습니다. 다만 개별 칸에서는 AKV가 지는 경우도 있습니다. 예를 들어 MiniMax-M2.7의 SWE-Verified(74.4 vs Standard 75.2), GPT-OSS-120B의 xbench-DS(37.5 vs 38.5)가 그렇습니다.

### 2. 정확도 차이는 요약 임계값 근처에서 난다

GPT-OSS-120B로 BCP 100문제를 논리 토큰 길이별로 나눠 보면, 48K 이하에서는 세 방식의 정확도가 비슷했습니다. Text Engineering은 48~96K 구간에서, Standard는 96K 이상에서 가장 낮았습니다(그림 7). 각자의 요약 임계값을 넘는 지점에서 정보를 한꺼번에 잃는다는 해석과 맞아떨어집니다. 롤링 드롭은 오래된 도구 응답을 조금씩 지우므로 이런 급락이 없습니다.

### 3. 서빙 성능: P95 지연 1.51배 개선

GPT-OSS-120B로 SWE-bench Verified에서 컨텍스트가 가장 긴 80개 과제의 궤적을 재생한 결과입니다(표 2). 각 방식이 최대 처리량을 낸 동시성(AKV는 14, Standard는 12)끼리 비교하면 평균 요청 지연 1.36배, P95 요청 지연 1.51배(28.49초 vs 43.16초) 빨랐고, 출력 처리량은 1.18배(369 vs 313 token/s)였습니다. 동시성 16에서는 Standard의 P95 지연이 229.90초까지 치솟는 반면 AKV는 30.63초였습니다. KV 캐시 압박으로 Standard가 재프리필을 반복하기 때문이라고 설명합니다.

속도 이득의 출처는 디코딩의 주의 계산입니다. 같은 배치 크기에서 full-attention 시간은 59.8%, 디코딩 단계 전체 시간은 16.0% 줄었습니다(그림 12). 비용 쪽에서는 Standard 대비 캐시 읽기 비용이 약 17%, Text Engineering 대비 캐시 미스 입력 비용이 약 48% 줄었습니다(부록 A.4.2).

### 4. 무엇을 지울지가 중요하다: 추론은 남기고 도구 응답을 지워라

표 3(GPT-OSS-120B, 각 벤치마크 첫 100문제)의 결과입니다.

| 전략 | repos | BCP 점수 / 비용 | SWE 점수 / 비용 |
|---|---|---|---|
| Standard | 없음 | 56.0 / 13.5 | 41.0 / 19.1 |
| 도구 응답 드롭 | 없음 | 55.0 / 7.1 | 41.0 / 9.4 |
| 추론 드롭 | 있음 | 56.5 / 8.2 | 36.5 / 14.2 |
| 둘 다 드롭 | 있음 | 56.5 / 8.7 | 34.5 / 7.8 |
| **도구 응답 드롭** | **있음** | **62.0** / 10.9 | **41.0** / 9.5 |

repos를 더하면 BCP 통과율이 55%에서 62%로 오릅니다. 위치 한계에 막혀 멈추던 탐색을 계속할 수 있기 때문입니다. 추론 KV를 지우면 SWE에서 점수가 떨어졌습니다. 주의 분석(그림 2, 그림 15)에서도 오래된 도구 응답은 비슷한 위치의 추론 메시지보다 주의를 덜 받았습니다.

### 5. 정책을 에이전트에게 맡기거나, 스스로 개선하게 하기

- **캐시 관리를 도구로:** 에이전트가 `drop_context` 같은 도구를 직접 호출해 무엇을 지울지 정하게 하면, BCP 100문제에서 GPT-OSS-120B 61.0%, MiniMax-M2.7 64.0%로 가장 높은 통과율을 냈습니다(표 4). 비용은 GPT-OSS-120B가 13.4¢에서 12.1¢로 줄었지만, MiniMax-M2.7은 턴을 더 많이 돌아 5.4¢에서 5.9¢로 늘었습니다.
- **재귀적 자기 개선(RSI):** MiniMax-M2.7이 BCP 20문제로 캐시 정책을 다듬고 별도 100문제로 평가했을 때, 3회차와 6회차 정책이 Standard 대비 과제당 비용을 15.6%, 17.8% 줄이면서 Standard 정확도를 유지했습니다(그림 4). 초록은 이것을 "전문가 설계 대비 7.1% 추가 절감"으로 요약합니다.

## 한계

**저자가 밝힌 한계**

- 더 다양한 캐시 정책 탐색, 이 방식에 맞춘 에이전트 학습, 선형 주의(linear attention) 모델로의 서빙 지원 확장이 남은 과제입니다.

**읽으면서 발견한 한계**

- **모델은 이런 캐시를 보고 학습한 적이 없습니다.** drop 이후의 활성 캐시는 어떤 텍스트 접두사와도 대응하지 않는 상태입니다. 학습 분포 밖의 상태라는 점에서, 모델이나 작업에 따라 조용히 성능이 떨어질 수 있습니다. 부록의 GPT-OSS-20B 결과(표 7)에서 AKV가 일부 지표에서 밀리자 저자들이 "작은 모델은 캐시 수정에 더 민감하다"고 해석한 것도 같은 맥락으로 보입니다.
- **비용은 환산값입니다.** 실제 청구서가 아니라 고정 단가표에 토큰 수를 곱한 값입니다. 논문은 상용 API에서 drop 같은 연산을 쓰는 방법을 다루지 않으므로, 이 이득을 얻으려면 모델을 직접 서빙해야 합니다.
- **판정자 의존.** 질의응답 3종의 채점은 LLM 판정자(GLM-5.2)에 의존합니다. SWE-bench Verified만 테스트 기반입니다.
- **서빙 실험은 재생 방식입니다.** 도구를 다시 실행하지 않고 기록된 응답을 재생하며, 고동시성 Standard 두 실행은 1시간 창에서 잘라 미완료 요청이 남은 상태로 보고했습니다(부록 A.1.4).
- **본문의 그림·표 번호가 일부 어긋납니다.** 예를 들어 주의 분석과 drop 대상 비교를 본문은 각각 "그림 4", "표 4"로 가리키지만 실제로는 그림 2와 표 3입니다. 결과 해석에는 영향이 없지만, 원문을 대조할 때 주의가 필요합니다.

## 인사이트

**왜 지금 중요한가: 에이전트 비용의 중심이 "출력"에서 "다시 읽기"로 옮겨 갔다.** 수백 라운드를 도는 에이전트에서는 같은 기록을 매 라운드 다시 읽는 비용이 지배적입니다. [프롬프트 캐싱](/tech/2026/10/24/prompt-caching.html) 글에서 다룬 것처럼 공급자들은 접두사가 같으면 싸게 받는 방식으로 이 비용을 낮춰 왔고, 그래서 "앞쪽을 건드리지 말라"가 에이전트 하네스의 철칙이 됐습니다. [컨텍스트 엔지니어링](/tech/2026/10/24/context-engineering.html)은 반대로 "필요 없는 것은 빼라"고 말합니다. 이 논문은 두 원칙이 충돌하는 지점을 정확히 짚습니다. 텍스트를 빼면 캐시가 깨지고, 캐시를 지키면 텍스트를 뺄 수 없습니다. 캐시 엔지니어링은 "빼는 단위"를 텍스트에서 KV로 옮겨 이 충돌을 피하는 발상입니다.

**블로그의 기존 글과의 연결.** [KV 캐시와 추측 디코딩](/tech/2026/10/24/kv-cache-speculative-decoding.html) 글의 기본 전제는 "KV 캐시는 접두사의 함수"였습니다. 이 논문은 그 전제를 깨는 순간 서빙 엔진의 무엇이 무너지는지 보여 줍니다. 같은 칭화대 연구실의 [TokenRouter](/papers/2026/10/24/tokenrouter.html)도 "요청 하나는 한 모델의 접두사 캐시 위에서 산다"는 단일 모델 가정을 깨는 문제를 다뤘습니다. 두 논문 모두 SGLang을 고쳐 해결했고, 둘 다 radix 트리를 확장하거나 우회하는 쪽으로 갔습니다. 필자의 판단으로는 다음 세대 서빙 엔진의 캐시 키는 "토큰 접두사"가 아니라 "토큰과 연산 이력"이 될 가능성이 큽니다.

**실무에 주는 의미.** 상용 API를 쓰는 팀은 당장 AKV를 쓸 수 없지만, 결과 두 가지는 지금의 컨텍스트 관리에도 적용할 수 있습니다. 첫째, 무엇을 버릴지 고를 때 **오래된 도구 응답이 1순위, 추론은 마지막**이라는 점입니다(표 3). 텍스트 기반 잘라내기에서도 같은 우선순위를 쓰는 편이 안전해 보입니다. 둘째, 요약 임계값 바로 위 구간에서 정확도가 꺾인다는 그림 7의 관찰은, 큰 요약을 드물게 하는 것보다 작은 정리를 자주 하는 편이 나을 수 있음을 시사합니다. 단, 텍스트 방식에서는 이것이 캐시 무효화 비용과 맞바꿔야 하는 선택이라는 점이 바로 이 논문의 출발점입니다. 오픈 웨이트 모델을 직접 서빙하는 팀이라면 AKV를 시험해 볼 만하며, 그때는 자기 모델과 작업에서 표 7 같은 "작은 모델 민감도"를 먼저 확인해야 합니다.

**앞으로 지켜볼 점.** (1) 공급자 API가 "이 메시지의 캐시는 이후 주의에서 빼 달라" 같은 연산을 노출하는지. 그렇게 되면 이 논문의 이득이 자체 서빙 밖으로 나옵니다. (2) drop된 캐시 상태를 학습 단계에서 보여 주는 연구. 저자들이 한계로 꼽은 "이 방식에 맞춘 학습"이 나오면 작은 모델의 민감도 문제가 줄어들 수 있습니다. (3) 부록 A.5가 소개한 AgentKV, SideQuest 등 동시기 연구와의 직접 비교. 지금은 서로 다른 설정의 수치라 우열을 말하기 어렵습니다.
