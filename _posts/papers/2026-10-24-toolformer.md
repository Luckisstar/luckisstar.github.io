# [논문 소개] Toolformer: 언어 모델이 도구 쓰는 법을 스스로 학습 데이터로 만들다

- **논문:** *Toolformer: Language Models Can Teach Themselves to Use Tools*
- **저자:** Timo Schick 외 (총 8명), Meta AI Research, Universitat Pompeu Fabra
- **공개:** 2023년 2월 9일, arXiv:2302.04761 (cs.CL). NeurIPS 2023 학회 논문(Advances in Neural Information Processing Systems 36)입니다.
- **링크:** [arXiv](https://arxiv.org/abs/2302.04761) · [PDF](https://arxiv.org/pdf/2302.04761) · [NeurIPS 2023 논문집](https://proceedings.neurips.cc/paper_files/paper/2023/hash/d842425e4bf79ba039352da0f658a906-Abstract-Conference.html)
- **참고:** 이 글의 수치는 arXiv v1(2023-02-09) 기준입니다. 논문에는 공식 코드 저장소 링크가 없습니다.

## 한 줄 요약

**도구마다 사람이 쓴 예시 몇 개만 주면, 언어 모델이 대량의 텍스트에 API 호출 후보를 스스로 끼워 넣고, "이 호출 결과가 다음 단어 예측에 도움이 됐는가"로 걸러 낸 데이터로 자기 자신을 미세조정해 도구 사용법을 익힌다는 논문입니다.** 67억(6.7B) 파라미터 GPT-J가 이렇게 학습한 뒤 여러 제로샷 과제에서 1,750억(175B) 파라미터 GPT-3를 앞섰습니다.

## 왜 이 연구가 필요한가

저자들은 LLM의 역설에서 출발합니다. 몇 개 예시만으로 새 과제를 풀 만큼 강력한데도, 훨씬 작고 단순한 프로그램이 잘하는 산술이나 사실 조회는 서툽니다. 논문이 꼽는 한계는 최신 정보에 접근하지 못하는 것, 사실을 환각하는 경향, 저자원 언어 이해의 어려움, 정확한 계산 능력 부족, 시간의 흐름을 모르는 것입니다.

해법은 검색 엔진, 계산기, 달력 같은 외부 도구입니다. 그런데 기존 접근은 두 가지 문제가 있었다고 저자들은 지적합니다.

- **사람 주석에 크게 의존**합니다. 비용도 문제지만, 사람이 유용하다고 보는 호출과 모델에게 실제로 유용한 호출이 다를 수 있습니다.
- **특정 과제에 묶여** 있습니다. 어떤 도구를 어떻게 쓸지 과제별 예시를 프롬프트로 미리 보여 줘야 해서, 모델이 스스로 언제 어떤 도구를 쓸지 정하지 못합니다.

그래서 목표를 두 가지로 둡니다. 도구 사용을 **대량의 사람 주석 없이 자기지도(self-supervised) 방식으로** 배울 것, 그리고 언어 모델의 **일반성을 잃지 않으면서** 언제, 어떻게, 어떤 도구를 쓸지 모델 스스로 정할 것.

## 제안 방법

### 1. API 호출을 텍스트로 표현하기

모든 도구는 입력과 출력이 텍스트여야 한다는 제약만 둡니다. API 호출 c는 이름과 입력의 쌍이고, 텍스트 안에서는 특수 토큰으로 감싸 표현합니다.

```text
e(c)    = <API> 이름(입력) </API>
e(c, r) = <API> 이름(입력) → 결과 </API>
```

실제로는 `<API>`, `</API>`, `→`를 새 토큰으로 추가하지 않고 기존 토큰열 `" ["`, `"]"`, `"->"`로 대신했습니다. 어휘(vocabulary)를 바꾸지 않아도 되게 하려는 선택입니다. 그림 1의 예시가 결과물의 모습을 잘 보여 줍니다.

```text
Out of 1400 participants, 400 (or [Calculator(400 / 1400) → 0.29] 29%) passed the test.
The name derives from "la tortuga", the Spanish word for [MT("tortuga") → turtle] turtle.
```

### 2. 데이터 생성 3단계: 샘플링, 실행, 필터링 (그림 2)

핵심은 일반 텍스트 데이터셋 C를 API 호출이 끼워진 데이터셋 C*로 바꾸는 과정입니다.

**① API 호출 샘플링.** 도구마다 "이 텍스트에 질의응답 API 호출을 추가하라"는 지시와 사람이 쓴 예시 몇 개로 이뤄진 프롬프트 P(x)를 씁니다(그림 3). 텍스트의 각 위치 i에서 모델이 `<API>`를 시작할 확률 pᵢ를 계산하고, 그 확률이 임계값 τs를 넘는 위치 중 상위 k개만 남깁니다. 남은 위치마다 모델에게 호출 후보를 최대 m개 생성하게 합니다.

**② API 실행.** 생성된 호출을 실제로 실행해 결과 rᵢ를 얻습니다. 도구에 따라 다른 신경망을 부르거나, 파이썬 스크립트를 돌리거나, 검색 시스템을 씁니다.

**③ API 호출 필터링.** 이 논문의 가장 독창적인 부분입니다. 위치 i 이후 토큰들에 대한 가중 교차 엔트로피 손실을 세 가지 조건에서 비교합니다.

| 기호 | 모델에 앞부분(prefix)으로 주는 것 | 의미 |
|---|---|---|
| L⁺ | 호출과 결과 `e(c, r)` | 도구를 쓰고 결과까지 본 경우 |
| L⁻ | 아무것도 주지 않은 경우와, 호출만 주고 결과는 주지 않은 경우 중 더 작은 손실 | 도구를 안 쓰거나, 써도 결과를 못 본 경우 |

**L⁻ − L⁺ ≥ τf**일 때만 그 호출을 남깁니다. 즉 "호출의 입력과 결과를 함께 줬을 때 다음 단어를 맞히기가 일정 이상 쉬워진 호출만 유용하다"고 판단합니다. 결과 없이 호출만으로도 손실이 줄어드는 경우(호출 입력 자체가 힌트가 되는 경우)를 L⁻에 포함해 걸러 낸 점이 세심합니다. 가중치는 w̃ₜ = max(0, 1 − 0.2·t)로, 호출 직후 몇 토큰에만 무게를 둬 정보가 실제로 쓰이는 위치 가까이에 호출이 놓이게 합니다.

**④ 미세조정.** 남은 호출을 원래 텍스트에 끼워 넣어 C*를 만들고, 표준 언어 모델링 목표로 모델 자신을 미세조정합니다. 저자들이 강조하는 점은 **C*가 끼워 넣은 호출을 빼면 원래 C와 완전히 같은 텍스트**라는 것입니다. 그래서 사전학습에 쓴 데이터셋에 그대로 적용해도 모델의 일반성과 언어 모델링 능력을 해치지 않을 수 있습니다.

### 3. 추론 시: `→`가 나오면 멈추고 도구를 부른다

학습한 모델로 텍스트를 생성하다가 `→` 토큰이 나오면 디코딩을 멈추고, 해당 API를 호출해 결과를 받은 뒤, 결과와 `</API>`를 붙여 디코딩을 이어 갑니다.

### 4. 도구 5종 (표 1)

| 도구 | 구현 | 입력 예 → 출력 예 (표 1) |
|---|---|---|
| 질의응답 | Atlas(Natural Questions로 미세조정한 검색 증강 LM). 데이터 생성에는 Atlas-large, 추론에는 Atlas-xxl | Where was the Knights of Columbus founded? → New Haven, Connecticut |
| 위키백과 검색 | KILT 위키백과 덤프를 색인한 BM25 검색기. 짧은 문단을 반환 | Fishing Reel Types → 낚시 릴 종류에 대한 문단 |
| 계산기 | 사칙연산만 지원하는 파이썬 스크립트, 결과는 소수 둘째 자리 반올림 | 27 + 4 * 2 → 35 |
| 달력 | 입력 없이 현재 날짜를 반환 | ε → Today is Monday, January 30, 2023. |
| 기계 번역 | NLLB 600M(200개 언어), 원문 언어는 fastText로 감지, 목표 언어는 항상 영어 | sûreté nucléaire → nuclear safety |

### 5. 비용을 줄이는 휴리스틱과 하이퍼파라미터

모든 텍스트에 모든 도구를 시도하면 비용이 크므로, 도구가 유용할 법한 텍스트만 고르는 휴리스틱을 둡니다. 예를 들어 계산기는 숫자가 3개 이상 있는 텍스트에만 시도합니다. 기본값은 τs = 0.05(`<API>` 확률 5% 이상인 위치), τf = 1.0, k = 5, m = 5입니다. 휴리스틱 때문에 후보가 적은 계산기와 번역기는 τs = 0.0, k = 20, m = 10, τf = 0.5로 완화했습니다(부록 A).

필터링 임계값에 따라 남는 예시 수(표 2)를 보면, τf = 1.0에서 위키백과 검색 60,974개, 달력 20,587개, 질의응답 18,526개가 남은 반면 계산기는 994개, 번역은 1,034개뿐이었습니다. 미세조정은 API당 최대 2.5만 개 예시, 최대 시퀀스 길이 1,024, 유효 배치 128, 학습률 1·10⁻⁵로 했고, NVIDIA A100 40GB 8장에서 최대 2천 스텝을 돌렸습니다(부록 B).

## 실험 설정

- **데이터와 모델:** CCNet 부분집합을 C로, GPT-J(6.7B)를 M으로 씁니다.
- **비교 모델:** GPT-J, GPT-J + CC(API 호출 없이 같은 CCNet으로 미세조정), Toolformer, Toolformer(disabled, 디코딩 때 `<API>` 확률을 0으로 막아 도구를 못 쓰게 한 같은 모델), 그리고 약 10배, 25배 큰 OPT(66B)와 GPT-3(175B, 지시 학습 전 원본 davinci)
- **평가 방식:** 모든 과제를 **제로샷**(과제별 예시 없이 자연어 지시만)으로 평가합니다. 어떤 도구를 어떻게 쓸지 사용자가 미리 알려 주지 않는 상황에서도 동작하는지 보려는 설정입니다.
- **디코딩 수정:** `<API>`가 가장 확률 높은 토큰일 때만이 아니라 상위 k = 10개 안에 들면 호출을 시작하게 해 도구 사용 성향을 높였습니다. 또 입력당 API 호출은 최대 1번으로 제한해, 출력은 안 내고 호출만 반복하는 루프를 막았습니다.

## 주요 결과

### 1. 사실 완성(LAMA): 질의응답 도구로 GPT-3를 넘다 (표 3)

| 모델 | SQuAD | Google-RE | T-REx |
|---|---|---|---|
| GPT-J | 17.8 | 4.9 | 31.9 |
| GPT-J + CC | 19.2 | 5.6 | 33.2 |
| Toolformer (disabled) | 22.1 | 6.3 | 34.9 |
| Toolformer | **33.8** | **11.5** | **53.5** |
| OPT (66B) | 21.6 | 2.9 | 30.1 |
| GPT-3 (175B) | 26.8 | 7.0 | 39.8 |

빈칸 하나가 있는 문장을 완성하는 과제입니다. LAMA는 위키백과 문장에서 만들어졌기 때문에 공정성을 위해 위키백과 검색 도구는 막았습니다. Toolformer는 같은 크기 최고 기준선보다 각각 11.7, 5.2, 18.6점 높았고 GPT-3도 넘었습니다. 모델은 98.1%의 경우 스스로 질의응답 도구를 골랐고, 0.7%는 다른 도구, 1.2%는 도구를 쓰지 않았습니다.

### 2. 수학 문장제: 계산기로 성능이 두 배 이상 (표 4)

| 모델 | ASDiv | SVAMP | MAWPS |
|---|---|---|---|
| GPT-J | 7.5 | 5.2 | 9.9 |
| Toolformer (disabled) | 14.8 | 6.3 | 15.0 |
| Toolformer | **40.4** | **29.4** | **44.0** |
| OPT (66B) | 6.0 | 4.9 | 7.9 |
| GPT-3 (175B) | 14.0 | 10.0 | 19.8 |

도구를 막아도 GPT-J보다 나은데, 저자들은 API 호출과 결과가 담긴 예시로 학습하면서 모델 자체의 수학 능력이 좋아진 것으로 추정합니다. 도구를 허용하면 모든 과제에서 성능이 두 배 이상이 됐고, 전체 예시의 97.9%에서 계산기를 호출했습니다.

### 3. 질의응답: 같은 크기는 이기지만 GPT-3에는 못 미친다 (표 5)

| 모델 | WebQS | NQ | TriviaQA |
|---|---|---|---|
| GPT-J | 18.5 | 12.8 | 43.9 |
| Toolformer | 26.3 | 17.7 | 48.8 |
| GPT-3 (175B) | **29.0** | **22.6** | **65.9** |

질의응답 도구는 Natural Questions로 학습돼 있어 과제가 너무 쉬워지므로 막았고, 모델은 99.3%의 경우 위키백과 검색을 썼습니다. 그래도 GPT-3에는 졌습니다. 저자들은 원인을 두 가지로 봅니다. 검색 엔진이 단순해 엉뚱한 결과를 자주 돌려주고, Toolformer는 결과가 나쁠 때 **검색어를 고치거나 여러 결과를 둘러보는 상호작용을 하지 못합니다.** 이 한계는 뒤에서 ReAct와 비교할 때 다시 나옵니다.

### 4. 시간이 필요한 질문: 달력이 결정적 (표 7)

| 모델 | TempLAMA | Dateset |
|---|---|---|
| GPT-J | 13.7 | 3.9 |
| Toolformer | **16.3** | **27.3** |
| GPT-3 (175B) | 15.5 | 0.8 |

"30일 전은 무슨 요일이었나" 같은 질문으로 저자들이 만든 Dateset에서는 개선이 전부 달력 도구 덕분이었고, 54.8%의 예시에서 달력을 불렀습니다. 반면 TempLAMA의 개선은 달력(0.2%만 사용)이 아니라 위키백과 검색과 질의응답 도구에서 왔습니다. 최선의 전략은 "달력으로 오늘 날짜를 얻은 뒤 그 날짜로 질의응답 도구에 묻기"인데, 호출을 1번으로 제한했고 학습 데이터의 호출이 서로 독립적으로 샘플링돼 이런 연쇄를 배우기 어렵다고 저자들은 설명합니다.

### 5. 언어 모델링 능력은 그대로, 도구 활용은 약 7.75억 파라미터부터 (표 8, 그림 4)

도구를 막은 상태의 퍼플렉시티(perplexity, 낮을수록 좋음)는 WikiText 10.3, CCNet 10.5로 GPT-J + CC와 같았습니다. API 호출 데이터로 학습해도 기본 언어 모델링 능력은 손해를 보지 않았다는 뜻입니다. GPT-2 계열 124M, 355M, 775M, 1.6B 모델에 같은 방법을 적용한 결과, **도구를 잘 쓰는 능력은 약 775M 파라미터부터 나타났고** 그보다 작은 모델은 도구가 있든 없든 성능이 비슷했습니다. 모델이 커져도 도구 유무에 따른 격차는 줄지 않았습니다.

### 6. 엇갈린 결과: 다국어 질의응답 (표 6)

MLQA(질문이 아랍어, 독일어, 스페인어, 힌디어, 베트남어, 중국어이고 문단은 영어)에서는 번역 도구가 모든 언어에서 도움이 됐고 언어에 따라 63.8~94.9%의 예시에서 쓰였습니다(힌디어만 7.3%). 하지만 CCNet 미세조정 자체가 일부 언어 성능을 떨어뜨려, Toolformer가 원본 GPT-J를 일관되게 이기지는 못했습니다.

### 7. 분석: 호출 문턱 k와 데이터 품질 (표 9, 표 10)

호출 시작 기준을 넓힐수록(k = 1 → 10) 도구를 쓰는 예시 비율이 T-REx 40.3% → 98.1%, WebQS 8.5% → 100%로 늘었습니다. 흥미롭게도 k = 1(일반 탐욕적 디코딩)에서는 모델이 어느 정도 **보정(calibrated)**돼 있었습니다. 도구 없이는 특히 못 풀 예시에서 골라서 도구를 불렀다는 뜻인데, k를 키우면 이 보정은 사라졌습니다. 표 10은 L⁻ − L⁺ 값이 높을수록 직관적으로 유용한 호출이라는 것을 보여 주지만, 예외도 있습니다. 관련 없는 위키백과 결과가 퍼플렉시티만 낮춘 경우가 남았고, 저자들은 이런 잡음이 오히려 모델이 호출 결과를 맹목적으로 따르지 않게 만드는 데 쓸모 있을 수 있다고 봅니다.

## 한계

**저자가 밝힌 한계 (7절)**

- **도구를 연쇄로 쓰지 못합니다.** 한 도구의 출력을 다른 도구의 입력으로 쓰는 예시가 학습 데이터에 없기 때문입니다. 도구별 호출을 독립적으로 생성한 데이터 구조의 결과입니다.
- **도구를 상호작용하며 쓰지 못합니다.** 검색 결과를 둘러보거나 검색어를 고치는 일이 불가능합니다.
- **입력 문구에 민감합니다.** API를 부를지 말지가 입력의 정확한 표현에 따라 달라졌습니다.
- **표본 효율이 낮습니다.** 계산기의 경우 문서 100만 개 이상을 처리해도 유용한 호출 예시는 수천 개에 그쳤습니다.
- **호출 비용을 고려하지 않습니다.** 도구마다 다른 계산 비용을 판단에 넣지 않습니다.

**읽으면서 발견한 한계 (필자의 판단)**

- 평가 기준이 관대합니다. LAMA는 정답이 처음 5단어 안에, QA는 처음 20단어 안에 있으면 정답으로 쳤고, 수학은 첫 번째 숫자를 답으로 봤습니다. 제로샷 설정을 고려한 선택이지만 절대 수치를 다른 논문과 비교할 때는 주의가 필요합니다.
- 비교 대상 GPT-3는 지시 학습 전의 원본 davinci입니다. 지시를 따르도록 학습한 모델과 비교했다면 격차가 달랐을 수 있습니다.
- "입력당 호출 1번" 제한은 루프를 막는 실용적 장치이지만, 동시에 다단계 문제(예: 달력 → 질의응답)를 원천적으로 막습니다. 결과 표의 일부는 방법의 한계라기보다 이 실험 설계의 한계로 보입니다.
- 공식 코드와 학습된 가중치가 논문에 링크돼 있지 않아, 같은 데이터 파이프라인을 그대로 재현하기 어렵습니다.

## 인사이트

**ReAct와의 대비: 프롬프트로 가르치기 대 학습으로 심기.** 같은 시기에 나온 [ReAct 소개](/papers/2026/10/24/react.html)와 나란히 놓으면 두 논문의 성격이 선명해집니다.

| 구분 | ReAct (2022-10) | Toolformer (2023-02) |
|---|---|---|
| 도구 사용을 가르치는 방법 | 퓨샷 프롬프트(사람이 쓴 궤적 1~6개) | 자기지도로 만든 데이터로 미세조정 |
| 모델 | 동결된 PaLM-540B | GPT-J 6.7B를 학습 |
| 호출 횟수 | 여러 단계에 걸쳐 반복 | 입력당 최대 1번 |
| 상호작용 | 관찰을 보고 검색어를 고치며 다시 시도 | 불가(저자가 한계로 명시) |
| 생각(추론) | 명시적인 Thought 텍스트 | 없음. 호출은 텍스트 중간에 바로 삽입 |
| 호출 여부 판단 | 프롬프트 예시를 흉내 냄 | "다음 단어 예측에 도움이 되는가"라는 손실 기준을 학습 |

흥미로운 점은 **각 논문의 약점이 서로의 강점**이라는 것입니다. Toolformer가 한계로 꼽은 "검색어를 고치거나 결과를 둘러보지 못함"은 ReAct가 HotpotQA에서 보여 준 바로 그 행동이고, ReAct가 "작은 모델은 프롬프트만으로 추론과 행동을 못 배운다"며 미세조정을 대안으로 제시한 것은 Toolformer가 택한 길입니다. 필자의 판단으로는, 오늘날의 도구 사용 모델은 이 둘을 합친 모습에 가깝습니다. 여러 단계에 걸쳐 관찰을 보며 도구를 고르는 ReAct의 루프를, 프롬프트가 아닌 학습으로 모델에 심은 형태입니다.

**왜 지금 중요한가: 도구 사용이 학습 단계로 들어갔다.** 2026년 10월의 공식 문서는 도구 사용이 더 이상 프롬프트 기법만이 아님을 보여 줍니다. OpenAI 함수 호출 가이드는 함수 정의가 "모델이 학습한 문법으로" 시스템 메시지에 주입된다고 설명하고, 함수가 많거나 어려운 과제에는 미세조정을 고려하라고 권합니다. Anthropic 문서는 bash, text_editor 같은 Anthropic 스키마 도구가 "학습으로 내장(trained-in)"돼 있으며 수천 개의 성공 궤적으로 최적화됐기 때문에 직접 만든 같은 기능의 도구보다 더 안정적으로 호출된다고 적습니다. 연구 쪽에서도 같은 흐름이 이어졌습니다. Gorilla(2023-05)는 LLaMA를 미세조정해 API 호출 작성에서 GPT-4를 넘었다고 보고했고, ToolLLM(2023-07)은 RapidAPI의 실제 API 16,464개로 ChatGPT를 이용해 지시와 풀이 경로를 자동 생성한 ToolBench로 LLaMA를 학습했습니다. 사람 주석 대신 모델이 만든 데이터로 도구 사용을 가르친다는 Toolformer의 발상이, 데이터를 만드는 쪽이 더 강한 모델로 바뀌는 형태로 이어진 셈입니다.

**실무에 주는 의미.** 대부분의 개발자는 Toolformer처럼 모델을 직접 학습시키지 않지만, 이 논문의 필터링 기준은 그대로 빌려 쓸 수 있습니다. **"이 도구 호출이 결과를 실제로 좋게 만들었는가"를 측정하는 습관**입니다. Toolformer는 결과 없이 호출만 줘도 좋아지는 경우를 따로 걸러 냈는데, 에이전트 평가에서도 도구를 켰을 때의 개선이 도구 결과 덕분인지, 프롬프트가 길어진 덕분인지 나눠 보는 것이 같은 발상입니다. 또 하나는 표 9의 교훈입니다. 호출 문턱을 낮추면 도구 사용률은 쉽게 100%에 가까워지지만, 모델이 "필요할 때만" 부르던 보정은 사라졌습니다. 지금의 `tool_choice`를 `"required"`나 강제 호출로 두는 것이 늘 이득은 아니라는 점과 통합니다. 작은 모델을 직접 미세조정해 도구를 붙이려는 팀이라면, 도구 활용이 약 775M 파라미터부터 나타났다는 그림 4 결과와 계산기처럼 데이터가 희소한 도구는 표본 효율이 크게 떨어졌다는 한계를 출발점으로 삼을 만합니다.

**한계와 반론.** Toolformer가 "스스로 가르친다"는 제목은 과장된 면이 있습니다. 도구별 프롬프트 예시는 사람이 썼고, 어떤 텍스트에 어떤 도구를 시도할지 고르는 휴리스틱(숫자 3개 이상 등)과 도구별 임계값도 사람이 정했습니다. 손실 감소라는 기준도 "다음 단어를 더 잘 맞히게 하는 정보"를 고를 뿐 "사실로 올바른 정보"를 보장하지 않습니다. 표 10의 무관한 검색 결과 사례가 그 증거입니다. 그리고 이 방식은 출력이 텍스트 중간에 끼는 형태라, 결제나 파일 삭제처럼 부작용이 있는 도구에는 그대로 맞지 않습니다. 지금의 함수 호출이 호출을 별도의 구조화된 블록으로 분리하고 실행 여부를 애플리케이션이 쥐게 한 것은, 이런 도구를 안전하게 다루기 위한 설계 변화로 보입니다.

**앞으로 지켜볼 점.** (1) 도구 사용 학습 데이터를 무엇이 만드느냐. Toolformer는 모델 자신, ToolLLM은 더 강한 모델이었는데, 실제 사용 궤적을 학습에 쓰는 방식이 공개 연구로 얼마나 나오는지. (2) Toolformer가 무시한 "호출 비용"을 모델이 판단에 넣게 되는지. 지금 문서들은 도구 정의가 입력 토큰으로 과금된다고 명시하므로, 비용을 아는 도구 선택은 실무에서 점점 중요해질 것으로 보입니다. (3) 도구 사용이 학습으로 내장될수록 공급자가 학습한 형식(Anthropic 스키마 도구 등)과 사용자가 정의한 도구 사이의 신뢰성 격차가 커지는지.
