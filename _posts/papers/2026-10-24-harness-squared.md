# [논문 소개] Harness²: 정답 검증기 없이 에이전트 하네스를 스스로 고치는 2단 재귀

- **논문:** *Harness^2: Recursive Agent Harnessing for an Open World*
- **저자:** Ruiyao Xu, Yanfei Chen 외 (총 9명), Google Cloud AI Research, Northwestern University (논문 본문 표기 기준)
- **공개:** 2026년 10월 9일, arXiv:2610.14224 (cs.AI, cs.CL, cs.LG)
- **링크:** [arXiv](https://arxiv.org/abs/2610.14224) · [HTML](https://arxiv.org/html/2610.14224) · [코드](https://github.com/google-research/harness2) · [프로젝트 페이지](https://harness2.github.io)
- **현황 (2026-10-24 기준):** 코드 저장소 Apache-2.0, GitHub 스타 약 1.8만 개. Hugging Face Papers 업보트 117개. README에 "공식 지원되는 Google 제품이 아니다"라는 고지가 있습니다.
- **주의:** 하네스를 고치는 편집기(editor)는 실험 대부분에서 Claude Opus 4.8입니다. 실행 모델보다 강한 모델이 하네스를 고친 결과가 주 결과이고, 같은 모델로 고친 결과는 별도 실험(그림 8)으로 보고됩니다. 또한 README는 실행기의 네트워크 접근이 기본적으로 제한되지 않아 공개 벤치마크 채점 기준에 접근할 수 있으니 평가 전에 네트워크를 막으라고 안내합니다.

## 한 줄 요약

**정답도 채점기도 없는 새 작업에서, 하네스를 고친 후보를 같은 작업에 실제로 돌려 보고 "행동이 어떻게 달라졌는지"를 근거로 하네스를 조립하면 꾸준히 점수가 오른다는 논문입니다.** 여기에 "어떻게 고쳤는지"의 경험을 라이브러리로 쌓아 다음 작업의 하네스 개선을 돕는 두 번째 재귀를 더했습니다.

## 왜 이 연구가 필요한가

논문은 에이전트의 성능이 모델뿐 아니라 **하네스**(harness, 모델을 감싸는 프롬프트, 메모리, 스킬, 도구, 오케스트레이션 전체)에 달려 있다는 전제에서 출발합니다. 저자들은 이를 `Agent = Model + Harness`로 표기하고, 모델 가중치를 고정한 채 이 바깥층을 최적화하는 과정을 **하네싱**(harnessing)이라 부릅니다.

하네스를 자동으로 개선하려는 재귀적 자기개선(RSI, recursive self-improvement) 연구는 이미 많습니다. 논문의 비교표(표 4)에 27개 방법이 정리되어 있을 정도입니다. 그런데 저자들은 실제 배포 환경("열린 세계", open world)에 두 가지 걸림돌이 있다고 지적합니다.

1. **정답 검증기가 없습니다.** 배포 중 들어오는 작업은 하네스를 설계할 때 본 적이 없는 새 작업이라, 단위 테스트나 정답 라벨로 "이 수정이 맞았는지"를 확인할 수 없습니다. 기존 온라인 방법은 대리 신호, 가정한 정답, 출력 쌍 비교 판정 등에 기대 왔습니다.
2. **한 작업에서 고친 것이 다음 작업으로 잘 넘어가지 않습니다.** 특정 작업에 맞춘 하네스를 그대로 물려받으면, 작업 분포가 바뀔 때 오히려 잡음이 됩니다.

저자들의 관찰은 두 번째 문제에 대한 것입니다. 고친 결과물(하네스)은 재사용이 어렵지만, **고치는 과정**(약점을 어떻게 진단했고, 무엇을 시험했고, 실행이 무엇을 보여 줬는지)은 재사용 가치가 높다는 것입니다.

## 제안 방법

### 하네스를 파일 8개로 나누기

먼저 하네스를 편집 가능한 파일 단위 구성요소 8개로 정의합니다(표 5). 기존 연구 AHE의 분해를 따르고 하나를 더했습니다.

| 그룹 | 구성요소 | 언제 모델에 닿나 |
|---|---|---|
| 컨텍스트 구성 | 시스템 프롬프트, 가드레일, 메모리 | 매 호출 |
| 컨텍스트 구성 | 스킬 | 스킬 도구로 불렀을 때만 |
| 도구 인터페이스 | 도구 사용 지침 | 매 호출 |
| 도구 인터페이스 | 스크립트 | bash로 실행할 때 |
| 오케스트레이션 | 서브에이전트 | task 도구로 불렀을 때 (별도 컨텍스트) |
| 미들웨어 | 플러그인 | 도구 루프 안에서 항상 |

모든 구성요소가 파일이라 수정은 곧 diff입니다. OpenCode에서는 이 파일 트리가, Codex에서는 항상 켜지는 텍스트가 `AGENTS.md`에 들어가는 식으로 같은 구조를 씁니다(부록 D.1).

### 1단: 작업 수준 재귀(Task-level recursion)

현재 작업의 실행 하네스를 고치는 단계이며, 핵심은 **대조 개선 단계 Propose-Probe-Compose**입니다.

- **Propose(제안):** 먼저 현재 하네스로 작업을 한 번 돌려 기준 실행(reference)을 얻습니다. 논문은 이 기준 실행이 "결과물이 맞는지가 아니라 하네스가 어떻게 행동하는지"를 보여 줄 뿐이라고 강조합니다. 이를 보고 후보 하네스 두 개를 만듭니다. 하나는 계획, 도구 사용, 컨텍스트 관리처럼 **분야와 무관하게 반복되는 결함**을 겨냥한 불변(invariant) 후보, 다른 하나는 **이 분야의 지식, 절차, 제약**을 겨냥한 분야(domain) 후보입니다.
- **Probe(탐침):** 각 후보를 같은 작업, 같은 모델, 같은 환경에서 실행하고 기준 실행과 비교합니다. 이 비교를 **행동 대조**(behavioral contrast)라고 부릅니다. 수정이 겨냥한 결함을 줄였는지, 아무 변화가 없는지, 회귀를 일으켰는지를 보는 증거입니다. 저자들은 이것이 정답 검증이 아니라 조립 단계의 근거일 뿐이며, 실행의 무작위성과 모델 공통 편향 때문에 신뢰도에 한계가 있다고 명시합니다.
- **Compose(조립):** 기준 실행, 후보 하네스와 그 diff, 모든 실행 증거를 읽고 후속 하네스를 만듭니다. 근거가 있는 변경만 합치거나, 충돌하는 수정을 고치거나, 후보 하나를 통째로 채택하거나, 기존 하네스를 그대로 둘 수 있습니다. 모든 결정은 "예상 점수 상승"이 아니라 구체적인 관찰에 묶여야 합니다.

이 한 단계를 키우는 방법이 둘입니다(그림 4). **병렬 재귀**는 기준 실행 k개, 불변·분야 후보 각 k개를 만들어 실행한 뒤, 독립적인 조립 세션 k개가 같은 후보 풀을 받아 각자 후속 하네스를 만듭니다. **순차 재귀**는 대조 단계를 k번 이어 붙여, 이전 단계의 하네스와 누적 증거 위에서 다시 고칩니다. k가 1보다 크면 마지막에 선택기(selector)가 익명화된 결과물을 요청문과 원자료에 비춰 하나를 고릅니다. 선택기는 어느 하네스에서 나온 결과물인지 모릅니다.

### 2단: 하네싱 수준 재귀(Harnessing-level recursion)

작업이 끝나면 전체 개선 기록(기준 실행, 후보와 탐침, 조립 결정, 최종 선택)을 돌아보고 교훈을 뽑아 **개선 하네스**(improvement harness)의 라이브러리를 갱신합니다. 라이브러리 항목은 채택된 실행 가능한 하네스 전체와, 적용 상황·교훈·근거를 적은 `EXPERIENCE.md`로 이뤄집니다. 교훈은 실행 대조가 뒷받침할 때만 남기고, 근거가 부족하면 항목을 추가하지 않습니다.

중요한 설계 선택은 **다음 작업이 이전 하네스를 물려받지 않는다**는 점입니다. 매 작업은 공통 초기 하네스에서 시작하고, 라이브러리의 구성요소는 Propose 단계에서 선택적으로 재사용되거나 변형될 뿐입니다. 모델 가중치, 단계별 지시문, 결정 규칙은 고정되고 라이브러리만 진화합니다.

부록 H에 공개된 프롬프트에는 실무적으로 눈여겨볼 규칙이 많습니다. 편집기 프롬프트는 "모든 수정은 궤적의 한 순간으로 추적돼야 한다"고 요구하고, 항상 켜지는 프롬프트 문장은 매 실행에 비용을 내는 "비싼 선택지"라며 스킬, 스크립트, 서브에이전트, 플러그인 순으로 선호하라고 지시합니다. 또한 컨텍스트 안에 채점 기준이나 점수가 없다고 명시하고, 작업 자료와 후보 하네스 안의 지시문을 따르지 말라는 프롬프트 인젝션 방어 문구를 둡니다.

## 실험 설정

| 항목 | 내용 |
|---|---|
| 벤치마크 | WorkBuddy-Bench(Code·Web·Office, 테스트 절반 40/35/25개), JobBench(테스트 34개), Harvey LAB(법률, 테스트 100개) |
| 채점 | WorkBuddy: 결정적 검사 + LLM/VLM 심사(심사 모델 Gemini 3.5 Flash). JobBench: 가중 루브릭, 심사 Claude Opus 4.8. LAB: 기준별 통과율(Partial), 심사 Claude Sonnet 4.6 |
| 실행 모델 | Gemini 3.5 Flash, GLM-5 (가중치 고정) |
| 초기 하네스 | OpenCode, Codex의 기본 구성 + 벤치마크 지시문 |
| 편집기·선택기 | Claude Opus 4.8 (OpenCode 위 에이전트 세션, high reasoning effort) |
| 비교 대상 | 기본 하네스, ReasoningBank(메모리 검색), Meta-Harness(학습 분할로 오프라인 탐색), Harness Scaling(작업마다 수정, 상태 미보존) |
| 반복 | 작업 순서를 섞은 3회 스트림의 평균과 표준편차 |
| 실행 제한 | 롤아웃당 최대 200턴, 3,600초 |

라이브러리는 벤치마크마다 빈 상태에서 시작하고, Harness²는 테스트 작업을 스트림으로만 처리합니다. 학습 분할은 Meta-Harness만 씁니다(부록 B).

## 주요 결과

### 1. 대조 단계 한 번으로 모든 설정에서 개선 (표 1, 표 2)

k=1, 즉 Propose-Probe-Compose를 한 번만 수행해도 4개 실행 모델·하네스 조합 모두에서 세 벤치마크 점수가 올랐습니다. 초록의 "최대" 수치는 각각 다음 칸에서 나왔습니다.

| 벤치마크 | 조합 | 기본 하네스 | Harness² (k=1) | 차이 |
|---|---|---|---|---|
| WorkBuddy-Bench 평균 | GLM-5 + OpenCode | 64.2 | 75.7 | +11.5 |
| JobBench | Gemini 3.5 Flash + OpenCode | 31.5 | 36.0 | +4.5 |
| LAB Partial | GLM-5 + OpenCode | 59.6 | 71.4 | +11.8%p |

비교 대상은 들쭉날쭉했습니다. ReasoningBank는 코딩 작업에서 기본 하네스보다 최대 6.6점 낮았고(GLM-5 + Codex의 Code 56.8 → 50.2), Harness Scaling은 12개 벤치마크·설정 쌍 중 7개에서 기본보다 낮았습니다. Harness²는 WorkBuddy 평균과 JobBench에서 네 설정 모두 비교 대상을 앞섰지만, **LAB의 Gemini 3.5 Flash + Codex 설정에서는 Meta-Harness(76.5)가 Harness²(75.6)보다 높았습니다.**

### 2. 약한 모델 + 좋은 하네스가 강한 모델 + 기본 하네스를 넘는다 (표 1)

WorkBuddy-Bench에서 GLM-5는 한 단계 개선만으로 OpenCode 75.7, Codex 75.3에 도달해, 같은 하네스에서 기본 상태인 Gemini 3.5 Flash(72.4, 74.5)를 넘었습니다. 논문은 이를 "개선된 하네스를 쓴 약한 모델이 원래 하네스를 쓴 강한 모델을 이길 수 있다"고 요약합니다. 다만 JobBench에서는 반대로 Gemini의 개선 폭(OpenCode +4.5, Codex +1.4)이 GLM-5(+3.6, +1.2)보다 컸습니다.

### 3. 탐색 예산을 늘리면 더 오르고, 단순히 더 돌리는 것보다 낫다 (그림 5, 그림 6)

병렬 재귀를 k=5로 늘리면 k=1 대비 WorkBuddy 2.9~3.9점, JobBench 3.0~4.2점, LAB 2.6~6.7%p가 추가로 올랐습니다. WB-code에서는 76.5 → 80.8, WB-office에서는 79.5 → 83.4로 k가 1에서 5로 늘수록 단조 증가했습니다. 반면 같은 예산을 준 Harness Scaling은 k=2에서 3으로 갈 때 두 분야 모두 하락했고, ReasoningBank는 오르내렸습니다. 논문은 이를 근거로 "테스트 시점 탐색을 늘리는 것만으로는 성능 향상이 보장되지 않는다"고 결론짓습니다. 실행 비용과 개선 비용을 모두 합친 토큰 대비 성능에서도 Harness² 두 설정이 경험적 파레토 경계 위에 있었다고 보고합니다(그림 6).

### 4. 라이브러리가 다음 작업의 개선을 돕는다 (표 3, 그림 7)

절제 실험(Gemini 3.5 Flash + OpenCode, k=1)에서 라이브러리를 빼면 WorkBuddy 77.5 → 74.4, JobBench 36.0 → 34.2로 떨어졌습니다. 불변/분야로 역할을 나누지 않으면 74.6, 32.3, 조립 없이 둘 중 하나만 고르면 75.9, 34.1이었습니다.

더 흥미로운 결과는 그림 7입니다. 기준 실행, 후보 탐침, 라이브러리 없이 기본 하네스를 바로 고치면 Code가 73.4 → 63.2, Web이 69.9 → 65.0으로 **오히려 나빠졌습니다.** k=1에서 쌓은 라이브러리를 주면 기본 수준이 회복되고, k=5에서 쌓은 라이브러리를 주면 추가 탐침 없이도 Code·Web·Office에서 0.9, 4.4, 5.1점 올랐습니다. JobBench에서 쌓은 라이브러리를 WorkBuddy에 옮겨도 0.6, 0.5, 2.9점 개선이 있었습니다.

### 5. 같은 모델이 편집기여도 개선된다 (그림 8)

"더 강한 편집기 덕분 아니냐"는 질문에 답하기 위해, 실행기와 편집기를 같은 모델로 두고 OpenCode, k=2로 실험했습니다. GLM-5부터 Claude Opus 5까지 5개 모델 모두 세 벤치마크에서 올랐다고 합니다. Opus 5는 WorkBuddy, JobBench, LAB에서 3.3, 5.5, 3.0점, GLM-5는 LAB에서 13.7점 올랐습니다.

### 6. 무엇이 실제로 바뀌었나 (표 6, 표 7, 그림 9)

개선된 하네스에서 구성요소를 빼 보면 스킬이 가장 중요했습니다(3분야 평균 80.8 → 75.5). 스크립트를 빼면 77.1, 프롬프트 계열을 빼면 79.3이었습니다. 편집의 약 절반이 스킬과 스크립트에 몰렸습니다(부록 E.2). 도구 오류율은 세 벤치마크 모두에서 줄었는데, JobBench에서는 14.4% → 9.1%였습니다. 호출 수는 WorkBuddy에서는 줄고 JobBench와 LAB에서는 늘어, "덜 부르는 것"이 아니라 "더 정확하게 부르는 것"이 개선의 정체였습니다.

사례 연구(그림 9)에서 JobBench 과제 하나의 점수가 43.1에서 77.8로 올랐습니다. 기준 실행의 문제는 지식 부족이 아니라 절차였습니다. 여러 원본 파일의 데이터를 맞춰 보지 않았고, 파일을 쓴 뒤 다시 열어 확인하지 않았습니다. 불변 후보는 입력 목록화, 수치의 출처 추적, 산출물을 다시 여는 검증 스크립트를 넣었고, 분야 후보는 일정·장소·인건비·예산 파일을 맞추는 스킬을 넣었습니다.

## 한계

**저자가 밝힌 한계 (부록 F, E.6)**

- 재귀 개선은 추가 실행과 편집 세션이 필요해 추론 비용이 늘어납니다. 실험은 제한된 예산 범위만 다뤘고 최적 배분을 제시하지 않습니다.
- 정답 감독이 없으므로 행동 대조와 모델 판단에 기대며, 이 신호는 실행 변동성과 모델 공통 편향에 민감합니다. 채택된 변경이 다른 작업으로 옮겨진다는 보장도 없습니다.
- 실패 분석에서 9개 회귀 사례를 세 유형으로 나눴습니다. 선택기가 약한 후보를 고른 경우(WB-code에서 95점짜리 대신 55점짜리 선택), 잘못된 전제가 여러 후보에 함께 퍼진 경우(2~11점 손실), 결과 변동과 심사 누락 등으로 원인을 가리기 어려운 경우입니다.

**읽으면서 발견한 한계 (필자 판단)**

- **편집기와 심사자가 같은 모델 계열입니다.** JobBench의 편집기·선택기와 루브릭 심사자가 모두 Claude Opus 4.8입니다. 루브릭은 편집기에 노출되지 않는다고 하지만, 같은 모델이 "좋은 결과물"을 보는 눈이 편집 방향과 채점에 함께 작용했을 가능성은 남습니다. WorkBuddy의 LLM 심사자도 실행 모델 중 하나인 Gemini 3.5 Flash입니다.
- **표준편차 대비 차이가 작은 칸이 있습니다.** 예를 들어 Gemini 3.5 Flash + Codex의 LAB에서 Harness²는 75.6(±4.5), 기본은 71.6(±1.3)입니다. 3회 평균이라 일부 칸의 개선은 통계적으로 확신하기 어렵습니다.
- **절대 비용 수치가 본문에 없습니다.** 파레토 경계 그림은 있지만, 작업당 토큰이나 금액이 본문 표로 제시되지 않아 실무 도입 판단에 필요한 비용을 직접 계산하기 어렵습니다.
- **"검증기 없음"은 실행 중 채점이 없다는 뜻이지 평가 수단이 없다는 뜻은 아닙니다.** 세 벤치마크 모두 결과물이 명확한 업무형 과제이고, 개선의 근거가 된 것은 "파일을 다시 열지 않았다" 같은 궤적에서 보이는 결함이었습니다. 궤적만으로 결함이 드러나지 않는 과제(예: 판단의 질이 핵심인 과제)에서 같은 효과가 나는지는 이 논문이 보여 주지 않습니다.

## 인사이트

**왜 지금 중요한가: "모델보다 하네스"의 다음 질문.** 2026년 들어 하네스 자동 최적화 논문이 쏟아졌고(표 4에 27개), 같은 날 소개하는 [Doc2Harness](/papers/2026/10/24/doc2harness.html)도 "하네스를 만드는 능력"을 따로 측정합니다. 두 논문은 하네스를 1급 공학 대상으로 본다는 점에서 같은 흐름에 있지만 질문이 다릅니다. Doc2Harness가 "모델이 명세대로 하네스를 처음부터 지을 수 있나"를 묻는다면, Harness²는 "이미 있는 하네스를 정답 없이 배포 중에 고칠 수 있나"를 묻습니다. 필자가 보기에 Harness²의 가장 중요한 결과는 +11.5점이라는 최대 수치보다 그림 7의 하락입니다. **증거 없이 하네스를 고치면 기본보다 나빠진다**(Code 73.4 → 63.2)는 결과는, "에이전트에게 자기 설정을 고치게 하면 알아서 좋아진다"는 기대에 대한 반증입니다. 개선을 만든 것은 자기 반성 자체가 아니라, 같은 작업에 후보를 실제로 돌려 본 대조 증거와 그것이 쌓인 라이브러리였습니다.

**실무에 주는 의미: 사람이 하는 하네스 개선에도 그대로 쓸 수 있는 절차.** 이 논문의 Propose-Probe-Compose는 자동화하지 않아도 유용한 작업 방식입니다. `AGENTS.md`나 스킬을 고칠 때 (1) 같은 작업으로 기준 실행을 남기고, (2) "작업 방식" 수정과 "분야 지식" 수정을 따로 만들어, (3) 각각 같은 조건에서 돌려 궤적을 비교한 뒤, (4) 근거가 있는 것만 합치는 것입니다. 부록 H의 편집기 프롬프트 규칙들(모든 수정은 궤적의 특정 순간으로 추적할 것, 항상 켜지는 문장은 비싸니 스킬이나 스크립트를 먼저 고려할 것, 실패가 한 번뿐이면 잡음으로 볼 것)은 [AGENTS.md 글](/tech/2026/10/24/agents-md.html)에서 다룬 안내문 작성 원칙이나 [컨텍스트 엔지니어링 글](/tech/2026/10/24/context-engineering.html)의 "항상 로드되는 컨텍스트 비용" 논의와 정확히 맞닿아 있습니다. 표 6에서 스킬과 스크립트를 뺐을 때 손실이 가장 컸다는 점도, 안내 문장을 늘리기보다 필요할 때만 불러오는 구성요소로 옮기라는 같은 방향을 가리킵니다.

**한계와 반론: 검증기 없는 자기개선이 어디까지 믿을 만한가.** 저자들도 인정하듯 행동 대조는 정답 검증이 아닙니다. 실패 분석의 두 번째 유형, 즉 잘못된 전제가 여러 후보에 함께 퍼지는 현상은 이 방법의 구조적 약점으로 보입니다. 후보들이 같은 증거와 같은 편집 모델에서 나오므로, 그 모델이 틀린 가정을 하면 "후보 간 합의"가 오류를 강화합니다. 조립 프롬프트가 "합의는 독립적 증거가 아니다"라고 굳이 적어 둔 것도 이 위험을 의식한 것입니다. 또 하나의 의문은 라이브러리의 수명입니다. 라이브러리 항목에는 "이 작업 공간에서는 A 파일의 X가 B 파일의 Y에 대응한다" 같은 작업별 사실이 들어가도록 권장되는데, 라이브러리가 커질 때 오래된 사실과 교훈을 어떻게 정리할지는 향후 과제(부록 G)로 남아 있습니다. 실무에서 이런 시스템을 운영한다면, 라이브러리 자체가 프롬프트 인젝션이나 잘못된 교훈이 누적되는 새 공격면이자 오류 저장소가 될 수 있습니다.

**앞으로 지켜볼 점.** (1) 편집기를 실행기와 같은 모델로 둔 그림 8의 결과가 다른 심사자(편집기와 다른 계열)로도 재현되는지. (2) 작업당 비용을 절대 수치로 공개하고, 사람이 하네스를 직접 다듬는 비용과 비교한 연구가 나오는지. (3) 저자들이 향후 과제로 든 적응형 재귀, 즉 새 증거가 더 나오지 않으면 탐침을 멈추는 방식이 비용 문제를 얼마나 줄이는지. 이 세 가지가 확인되면 "하네스 자동 개선"은 연구 데모에서 운영 도구로 넘어갈 수 있을 것입니다.
