## 한 줄 요약

**대화 기록을 요약·추출·그래프화해 따로 저장하는 메모리 시스템 11종을 같은 조건에서 돌려 보니, 원본 기록을 잘라 그대로 검색하는 RAG(검색 증강 생성, Retrieval-Augmented Generation)보다 낮은 경우가 대부분이었다는 논문입니다.** 표 1의 99개 설정(11개 시스템 × 벤치마크 3종 × 모델 3종) 가운데 RAG 2회 검색보다 점수가 높은 칸은 9개입니다(필자가 표 1에서 센 값). 저자들은 메모리의 순가치를 RAG가 틀린 질문을 맞히는 "메모리 이득"과 RAG가 맞힌 질문을 틀리는 "메모리 세금"으로 나누고, 세금이 어디서 생기는지 추적합니다.

## 왜 이 연구가 필요한가

긴 작업을 하는 에이전트에는 메모리가 붙는 것이 당연해졌습니다. 지난 대화에서 사실을 뽑아 저장하거나, 계층으로 정리하거나, 지식 그래프로 엮는 시스템이 계속 나오고 있습니다. 이런 처리는 모두 원본 기록 위에 추가 계산을 얹습니다.

저자들이 문제 삼는 것은 비교 대상입니다. 메모리 논문은 주로 다른 메모리 시스템과 비교하고, 가장 단순한 대안인 "원본 기록에서 바로 검색하기"는 빠지는 일이 많습니다. 부록 B.2에서 저자들은 평가한 기준선 논문 전체와 Mem0, Zep, MemGPT 등 영향력 있는 메모리 논문 5편을 다시 읽었는데, RAG 결과를 보고한 것은 LightMem, PlugMem, Mem-T 세 편뿐이었다고 적습니다(원래 RAG 시스템인 HippoRAG2 제외). 그 세 편도 임베딩 단독 검색에 top-5나 top-10 정도였고, 청크 방식이나 검색 예산을 밝히지 않은 경우가 있었습니다.

검색 기준선이 없으면 메모리의 가치와 "증거를 잘 찾아오는 것 자체"의 가치가 섞입니다. 그래서 논문의 질문은 하나입니다. **단순 RAG 대비 메모리의 순가치는 얼마인가.**

## 제안 방법

이 논문은 새 메모리 구조를 제안하지 않습니다. 제안하는 것은 메모리를 평가하는 분석 틀입니다.

### 순가치 = 메모리 이득 − 메모리 세금

메모리 시스템은 상호작용 기록을 가공해 메모리 저장소를 만들고(구축), 질문이 오면 관련 메모리 단위를 꺼내(검색) 답을 생성합니다. 단순 RAG는 같은 식에서 구축을 거의 하지 않는 경우입니다. 원본을 청크로 자르기만 하고 그대로 검색합니다. 같은 원본을 최소한의 가공으로 쓰기 때문에 기준점으로 삼기 좋습니다.

저자들은 질문 하나하나에 대해 메모리 시스템과 RAG의 정오를 비교합니다.

- **메모리 이득(memory benefit):** RAG는 틀렸는데 메모리는 맞힌 질문
- **메모리 세금(memory tax):** RAG는 맞혔는데 메모리는 틀린 질문

두 값의 차이가 순가치이고, 세금이 이득보다 크면 전체 점수가 RAG 아래로 내려갑니다. 저자들은 이 둘이 같은 원인에서 나온다고 봅니다. 메모리 처리는 원본 기록에서 벗어나는 변형(deviation)을 반드시 만들고, 흩어진 사실을 모으거나 선호를 뽑아내는 변형은 이득이 되지만 같은 변형이 증거를 지우거나 흐리면 세금이 됩니다. 이 값들은 기준점에 따라 달라지며, 논문 전체에서 단순 RAG를 기준으로 정의됩니다.

### 세금이 생기는 세 곳

| 차원 | 질문 | 측정 방법 |
|---|---|---|
| 충실도 | 정보가 구축을 거치고도 남아 있는가 | 정답 근거가 든 원본 턴만 줬을 때와, 그에 대응하는 메모리 단위만 줬을 때의 정답률 비교. 원본 턴 500개를 뽑아 사람이 손실 정도를 표시 |
| 접근성 | 남아 있는 정보를 쉽게 꺼낼 수 있는가 | 이미 꺼낸 것을 빼고 검색을 반복해 근거가 모두 나올 때까지 몇 라운드가 걸리는지 측정. 질문과 원본 턴, 질문과 메모리 단위의 유사도 비교 |
| 견고성 | 모델을 바꿔도 버티는가 | 메모리를 세 모델로 각각 구축하고, 답변 모델을 바꿔 가며 점수 변동을 RAG와 비교 |

여기에 평가 쪽 요인이 하나 더 있습니다. 벤치마크 자체가 검색만으로 잘 풀리면 메모리가 더 얻을 여지(headroom)가 작아서 작은 손실도 점수에 그대로 드러난다는 것입니다.

### 공정한 비교를 위한 장치

메모리 단위의 크기는 시스템마다 다릅니다. 턴 하나일 수도, 세션 요약 하나일 수도 있어서 같은 top-k(상위 k개 검색)라도 모델이 보는 양이 수백 토큰에서 수만 토큰까지 달라집니다. 저자들은 검색 범위(Retrieval Scope, RS)라는 지표를 둡니다. 검색부터 답변까지 LLM이 본 메모리 단위의 토큰 수를 검색 가능한 저장소 전체 토큰 수로 나눈 비율입니다. 각 시스템의 top-k를 조정해 RS가 RAG 1회 검색보다 낮지 않게 맞췄고, 대부분 기본값보다 k를 늘렸다고 밝힙니다(부록 A.4, B.3).

## 실험 설정

| 항목 | 내용 |
|---|---|
| 벤치마크 | LongMemEval-s(500문항 전체, GPT-5.6 Luna만 100문항), PersonaMem-v2(20%: 40개 코퍼스, 934문항), MINT-Eval(10%: 60개 코퍼스, 1,557문항). 부분집합은 질문 유형별 층화 추출 (PDF 표 5) |
| 메모리 | 평면 저장: A-Mem, SimpleMem, MemOS / 계층·수명주기: MemoryOS, LightMem, OpenViking / 그래프: HippoRAG2, PlugMem, MAGMA / 학습된 정책: Mem-T, Memory-R2 |
| 검색 기준선 | RAG 1회 검색(1rd), RAG 2회 검색(2rd) |
| 참고 기준선 | No Context(질문만), Full Context(원본 전체), Gold Context(정답 근거 턴만) |
| 모델 | Qwen3.5-4B, Qwen3.6-27B, GPT-5.6 Luna(reasoning effort low). 임베딩은 Qwen3-Embedding-0.6B로 통일 |
| 채점 | Qwen3.6-27B 기반 LLM 판정(LLM-as-Judge). PersonaMem-v2는 4지선다라 선택지 일치로 채점 |
| 비용 지표 | 토큰 수, 단일 동시성으로 환산한 소요 시간, LLM 호출 수, 메모리 저장소 크기 |

"단순 RAG"의 실제 구성은 다음과 같습니다(부록 A.2). 대화 턴 단위로 자르되 세션 경계를 넘지 않고, 짧은 턴은 약 1,024자까지 묶으며, 각 청크 앞에 세션 날짜·시각 머리말을 붙입니다. 질문이 오면 BM25(단어 일치 기반 검색)와 임베딩 검색이 각각 상위 k개를 가져오고, 합친 후보를 Qwen3-Reranker-0.6B(재순위화 모델)로 다시 정렬해 상위 k개를 모델에 넘깁니다. 2회 검색 변형은 모델이 1차 결과가 충분한지 판단하고, 부족하면 후속 질의를 한 번 더 던집니다.

LLM 판정의 신뢰도는 사람 판정과의 일치율로 보고됩니다. LongMemEval-s 95.1%, PersonaMem-v2 100.0%, MINT-Eval 97.3%입니다(PDF 표 6).

## 주요 결과

### 1. 99개 설정 중 9개만 RAG 2회 검색을 넘었다 (표 1)

아래는 표 1에서 Qwen3.6-27B 열만 옮긴 것입니다. 점수는 판정 정답률(%)입니다.

| 방법 | LongMemEval-s | PersonaMem-v2 | MINT-Eval |
|---|---|---|---|
| Full Context | 68.4 | 45.4 | 28.7 |
| RAG (1rd) | 77.6 | 46.8 | 28.6 |
| RAG (2rd) | 81.4 | 48.7 | 33.1 |
| A-Mem | 79.4 | 48.4 | 24.4 |
| MemOS | 76.6 | 50.2 | 19.7 |
| SimpleMem | 73.6 | 46.7 | 19.9 |
| MemoryOS | 73.4 | 48.2 | 26.3 |
| LightMem | 78.8 | 47.0 | 23.0 |
| OpenViking | 58.8 | 38.7 | 18.6 |
| HippoRAG2 | 78.2 | 46.5 | 23.5 |
| MAGMA | 68.2 | 40.5 | 27.0 |
| PlugMem | 75.8 | 45.2 | 33.3 |
| Mem-T | 75.0 | 42.1 | 30.4 |
| Memory-R2 | 73.0 | 48.4 | 21.5 |

세 모델 전체로 보면(필자가 표 1에서 센 값) RAG 2회 검색보다 높은 칸은 99개 중 9개입니다. LongMemEval-s에서는 어떤 모델에서도 RAG 2회 검색을 넘은 시스템이 없었습니다. 넘은 9칸은 PersonaMem-v2의 5칸(MemOS 2칸, MemoryOS, LightMem, Memory-R2)과 MINT-Eval의 4칸(PlugMem 2칸, Mem-T 2칸)이며, 차이는 +0.1~+3.9점입니다. 반대쪽 끝에서는 OpenViking이 LongMemEval-s Qwen3.5-4B에서 31.8점으로 RAG 2회 검색(72.2)보다 40.4점 낮았습니다.

기준을 LLM 호출이 한 번 적은 RAG 1회 검색으로 바꾸면 메모리가 높은 칸이 22개, 같은 칸이 2개로 늘어납니다(역시 필자가 센 값). 그래도 4분의 3은 RAG 아래입니다.

### 2. 메모리는 일방적으로 못한 것이 아니라, 얻은 만큼 잃는다 (그림 2)

LongMemEval-s 500문항, Qwen3.6-27B에서 RAG 1회 검색과 질문별로 비교한 결과입니다.

| 시스템 | 이득 | 세금 | 순가치 |
|---|---|---|---|
| A-Mem | 40 | 31 | +9 |
| PlugMem | 63 | 72 | −9 |
| Mem-T | 41 | 54 | −13 |
| SimpleMem | 40 | 60 | −20 |
| OpenViking | 46 | 140 | −94 |

단위는 문항 수입니다. PlugMem은 RAG가 틀린 63문항을 맞혔지만 RAG가 맞힌 72문항을 틀렸습니다. 최종 점수만 보면 "RAG보다 1.8점 낮다"로 끝나지만, 실제로는 135문항에서 결과가 뒤바뀐 것입니다.

부록 D.1은 메모리가 이기는 유형 여섯 가지를 사례로 보여 줍니다. 사실을 짧은 단위로 뽑아 여러 개가 컨텍스트에 함께 들어가는 경우, 여러 세션의 사실을 이어 붙이는 경우, 지나가듯 말한 취향을 명시적 항목으로 만든 경우, "3주 전" 같은 상대 시간을 절대 날짜로 고정한 경우, "잊어 달라"는 요청을 저장 상태에 반영한 경우, 코드 diff 같은 비대화 입력을 자연어로 풀어 둔 경우입니다.

부록 D.4는 **같은 기법이 한 질문에서는 이득, 다른 질문에서는 세금이 되는 쌍**을 보여 줍니다. Memory-R2는 턴을 한 줄짜리 사실로 쪼갠 덕분에 "집을 몇 채 봤나"를 맞혔지만, 같은 쪼개기 과정에서 "500포인트면 5달러 할인"의 금액이 빠져 할인액 질문을 틀렸습니다. PlugMem의 추론 노트는 세 세션에 흩어진 나이를 모아 평균을 계산해 냈지만, 다른 질문에서는 "3주 + 3주 = 6주"라는 잘못된 결론만 답변 모델에 전달했습니다(정답은 3주).

### 3. 세금의 첫 번째 출처: 구축 단계에서 정보가 사라진다 (표 2, 그림 3)

원본 턴 500개를 뽑아 대응하는 메모리 단위와 사람이 비교한 결과입니다(표 2, 단위 %).

| 시스템 | 손실 없음 | 일부 손실 | 큰 손실 | 대응 단위 없음 |
|---|---|---|---|---|
| MemoryOS | 98.4 | 0.0 | 0.0 | 1.6 |
| MAGMA | 93.6 | 6.2 | 0.2 | 0.0 |
| MemOS | 85.8 | 9.0 | 2.4 | 2.8 |
| PlugMem | 79.6 | 10.8 | 5.2 | 4.4 |
| LightMem | 76.2 | 13.6 | 0.6 | 9.6 |
| Memory-R2 | 72.6 | 14.8 | 6.0 | 6.6 |
| SimpleMem | 65.6 | 27.6 | 2.2 | 4.6 |
| OpenViking | 39.4 | 9.6 | 13.0 | 38.0 |

부록 D.2의 사례가 손실의 모습을 구체적으로 보여 줍니다. "공항에서 호텔까지 택시가 60달러쯤"이라는 발화가 OpenViking에서는 "비용 효율적인 교통수단을 선호함"으로 일반화되어 60달러가 사라졌습니다. "가방이 1/20에 도착했다"는 SimpleMem에서 "2023-01-20부터 가방을 쓰기 시작했다"로 바뀌었습니다. 요약은 그럴듯하지만 질문이 묻는 바로 그 값이 없습니다.

거시 수준에서는 검색 실패를 없애고 봅니다. 정답 근거에 대응하는 메모리 단위만 골라 준 뒤에도 남는 세금은 구축에서 생긴 손실로 해석됩니다. 그림 3(LongMemEval-s, Qwen3.6-27B, 그림에서 읽은 값)에서 PlugMem의 세금은 14.4%에서 14.0%로, Memory-R2는 12.8%에서 12.4%로 거의 줄지 않았습니다.

### 4. 세금의 두 번째 출처: 남아 있어도 꺼내기 어려워진다 (그림 3, 그림 4)

표 2에서 MemoryOS와 MAGMA는 정보를 90% 넘게 보존했습니다. 그런데도 표 1에서 RAG보다 낮습니다. 그림 3에서 MAGMA는 정답 메모리 단위를 직접 주면 세금이 15.0%에서 6.4%로 줄고 점수가 84.4까지 올라 원본 근거를 준 경우(84.6)와 비슷해집니다. **정보는 있는데 검색이 못 찾았다**는 뜻입니다.

그림 4는 이를 라운드 수로 보여 줍니다. LongMemEval-s, Qwen3.6-27B에서 첫 라운드에 근거를 전부 회수한 질문의 비율은 RAG 82.7%, Memory-R2 74.9%, MAGMA 68.3%, LightMem 61.6%, PlugMem 60.1%, OpenViking 53.7%입니다.

저자들은 사례 검토(부록 D.3)에서 세 가지 패턴을 정리합니다.

- **쪼개짐(fragmenting):** 자전거 정비 발화 하나가 LightMem에서 세 단위로 나뉘었고, 합계 계산에 필요한 "체인 교체 25달러"는 4라운드에야 나왔습니다.
- **희석(diluting):** "통근이 편도 45분"이 OpenViking에서는 59줄짜리 프로필의 한 줄이 되어 3라운드에 나왔습니다.
- **바꿔 쓰기(rephrasing):** "편두통이 있다는 걸 잊어 달라"는 요청이 LightMem에서 "사용자는 편두통이 없다"는 부정 사실로 바뀌어 13라운드에 나왔습니다.

### 5. 모델을 바꾸면 메모리가 RAG보다 더 흔들린다 (4.4절, 그림 6)

오래 쓰는 에이전트는 메모리를 한 모델로 만들고 나중에 다른 모델로 읽을 수 있습니다. 저자들은 세 모델로 메모리를 각각 구축하고 답변 모델을 교차해 평가했습니다. 구축 모델을 바꾸면 점수가 달라지는 것은 예상된 결과이고, 저자들이 더 주목한 것은 구축을 고정하고 답변 모델만 바꿨을 때 많은 시스템의 점수 변동이 RAG보다 컸다는 점입니다. 이 결과는 그림으로만 제시되어 있어 이 글에서는 수치를 옮기지 않습니다.

### 6. 비용은 구축 단계에 몰려 있다 (PDF 표 19)

LongMemEval-s, GPT-5.6 Luna(low), 100개 코퍼스 기준입니다. 시간은 단일 동시성으로 환산한 값입니다.

| 방법 | 정답률 | 구축+유지 토큰 | 추론 토큰 | 오프라인 구축 | LLM 호출 |
|---|---|---|---|---|---|
| RAG (1rd) | 82.0 | 없음 | 0.27M | 0.11시간 | 0.10K |
| RAG (2rd) | 90.0 | 없음 | 0.65M | 0.11시간 | 0.20K |
| A-Mem | 84.0 | 29.3M + 145.0M | 0.44M | 117.0시간 | 98.4K |
| LightMem | 77.0 | 5.22M | 0.09M | 15.2시간 | 2.67K |
| MemOS | 78.0 | 58.8M | 0.12M | 63.8시간 | 25.2K |
| HippoRAG2 | 81.0 | 79.5M | 0.46M | 11.6시간 | 118.5K |
| Mem-T | 78.0 | 51.7M + 180.4M | 4.90M | 76.0시간 | 114.2K |

RAG는 색인을 만들 때 LLM을 부르지 않습니다. 메모리 시스템은 구축에 적게는 5.22M, 많게는 79.9M(MAGMA) 토큰을 쓰고, 유지 단계가 있는 A-Mem과 Mem-T는 거기에 100M 토큰 넘게 더 씁니다. 다만 LightMem, MemOS처럼 **추론 시점의 토큰은 RAG보다 적은 시스템도 있다**는 점은 함께 봐야 합니다. LongMemEval-s는 코퍼스 하나에 질문이 하나뿐이라 구축 비용을 나눠 낼 질문이 없는 구조이기도 합니다.

### 7. 널리 쓰는 벤치마크 상당수가 검색만으로 잘 풀린다 (4.5절, PDF 표 16)

저자들은 장기 메모리 벤치마크 15종에 검색만 하는 기준선을 돌렸습니다(Qwen3.6-27B). 질문에서 가장 희귀한 단어 두 개가 든 청크를 고르는 IDF-keyword 방식만으로 LoCoMo 58.8, EverMemBench-MCQ 68.2, PersonaMem-v1 57.9 등 6종에서 50점을 넘었습니다. 하이브리드 RAG는 EverMemBench-MCQ 82.7, HaluMem-Medium 79.9, LongMemEval-s 77.6, LoCoMo 75.3이었고, 반대로 RealMem 32.9, MINT-Eval 28.6처럼 낮은 벤치마크도 있습니다.

검색만으로 이미 높은 점수가 나오는 벤치마크에서는 메모리가 더 얻을 것이 적고, 작은 손실이 그대로 드러납니다. 저자들은 이것이 벤치마크의 결함이라고만 보지는 않습니다. 실제 질문도 상당수가 정확한 회상을 요구하기 때문입니다. 대신 메모리 논문이 RAG 점수를 함께 보고해 남은 개선 여지를 드러내라고 제안합니다.

### 8. 다른 종류의 메모리에서도 같은 양상 (5장, 표 3, PDF 표 17)

과거 작업 궤적에서 경험을 쌓는 경험 메모리(Qwen3.5-4B)에서 "단순 RAG"는 설명이 비슷한 과거 작업 2개의 원본 궤적을 프롬프트에 넣는 방식입니다.

| 방법 | ALFWorld | WebShop | Mind2Web | BigCodeBench | AppWorld | τ2-Bench |
|---|---|---|---|---|---|---|
| 메모리 없음 | 52.2 | 45.9 | 48.5 | 16.9 | 12.5 | 61.0 |
| 단순 RAG | 73.1 | 38.4 | 45.3 | 21.6 | 22.6 | 69.0 |
| ReasoningBank | 62.7 | 34.3 | 49.9 | 14.9 | 14.3 | 51.0 |
| Memp | 76.1 | 44.5 | 47.9 | 20.3 | 14.3 | 62.0 |
| G-Memory | 73.9 | 39.5 | 47.0 | 20.3 | 22.6 | 78.0 |
| SkillPro | 47.0 | 42.5 | 43.6 | 11.5 | 10.7 | 55.0 |

지표는 벤치마크별 공식 지표(성공률, 점수, 단계 성공률, pass@1, 과제 목표 달성률, pass^1)입니다. 저자들의 해석은 "웹 과제에서는 긴 궤적을 워크플로로 증류한 메모리가 RAG를 앞서고, 도구 사용 과제에서는 여러 메모리가 RAG보다 낮다"입니다. 표를 직접 보면 WebShop에서는 메모리 없음(45.9)이 RAG와 모든 메모리 방법보다 높다는 점도 눈에 띕니다(필자 관찰).

영상 월드 모델에서도 과거 프레임을 그대로 검색해 다시 넣는 I3DM이 4개 지표 중 3개에서 가장 높았고(Context-as-Memory SSIM .560, 1−LPIPS .704, MemoBench 1−LPIPS .476), KV 캐시나 잠재 벡터 기반 메모리는 이를 일관되게 넘지 못했습니다(표 3). MemoBench SSIM만 MagicWorld(.433)가 I3DM(.430)보다 조금 높습니다.

### 9. 처방: 원본으로 돌아가는 길을 남겨라 (6장, PDF 표 4)

저자들은 새 구조 없이 기존 시스템에 붙일 수 있는 처방을 시험했습니다(Qwen3.6-27B).

| 시스템 | LongMemEval-s 정답률 (세금) | PersonaMem-v2 정답률 (세금) |
|---|---|---|
| SimpleMem | 73.6 (12.0) | 46.7 (11.2) |
| + 원본 병행 | 82.8 (5.2) | 49.6 (7.2) |
| + 재귀 | 해당 없음 | 46.8 (12.1) |
| MemoryOS | 73.4 (11.4) | 48.2 (17.1) |
| + 원본 병행 | 76.4 (7.8) | 53.0 (8.5) |
| + 재귀 | 해당 없음 | 49.1 (16.4) |
| Mem-T | 75.0 (10.8) | 42.1 (15.2) |
| + 원본 병행 | 80.0 (5.2) | 49.0 (8.7) |
| + 재귀 | 해당 없음 | 45.7 (13.6) |

- **원본 병행(src-aug):** 메모리 검색과 함께 원본 기록에서도 검색하고, 둘을 합쳐 재순위화한 뒤 답합니다. 세 시스템 모두 정답률이 오르고 세금이 줄었습니다.
- **재귀(recursive):** 과거 질문과 그때 찾은 근거를 메모리 저장소에 다시 넣어 다음 검색에 쓰게 합니다. LongMemEval-s는 코퍼스당 질문이 하나라 적용할 수 없고, PersonaMem-v2에서의 효과는 +0.1~+3.6점으로 원본 병행보다 작습니다. SimpleMem에서는 세금이 11.2에서 12.1로 오히려 늘었습니다.

세 번째 제안은 실험 없는 방향 제시입니다. 미리 메모리를 만드는 방식(AoT)은 미래 질문을 모른 채 변형을 가하고, 질문이 온 뒤 만드는 방식(JiT)은 지연 시간이 늘어납니다. 저자들은 사용자의 과거 관심사와 접근 패턴으로 미래 수요를 예측해 구축 노력을 선택적으로 배분하는 중간 지점을 제안하며, 메모리를 "과거 정보의 미래 관련성을 추정하는 추천 시스템"으로 볼 수 있다고 말합니다.

## 한계

**저자가 밝힌 것** (Limitations 절)

- 기준선 선택은 대표적일 뿐 전부가 아닙니다. 공식 설정을 최대한 따랐지만 시스템별로 더 튜닝하면 성능이 오를 수 있습니다.
- 벤치마크가 정적이고 오프라인이며 영어입니다. 질문이 구축 중간에 끼어드는 장기 배포나 다국어 상호작용은 다루지 않았습니다.
- 비용 때문에 GPT-5.6 Luna(low)보다 강한 모델은 쓰지 않았고, 일부 벤치마크는 부분집합입니다(PersonaMem-v2 20%, MINT-Eval 10%, GPT-5.6 Luna의 LongMemEval-s 20%).
- 멀티모달, 잠재 벡터, 파라미터형 메모리로의 확장은 후속 과제입니다.

**읽으면서 발견한 것 (필자 판단)**

- **"단순 RAG"가 그리 단순하지 않습니다.** 기준선은 BM25와 임베딩을 합치고 재순위화 모델을 거치는 하이브리드 파이프라인이며, 표 1의 기준인 2회 검색은 LLM이 충분성을 판단해 한 번 더 검색합니다. 부록 B.1의 절제 실험에서 LongMemEval-s 점수(Qwen3.5-4B / Qwen3.6-27B)는 기본 70.2 / 77.6, 임베딩 단독 67.2 / 72.6, BM25 단독 63.4 / 68.2입니다. 임베딩만 붙인 RAG와 비교했다면 표 1의 그림은 덜 일방적이었을 것입니다. 여기서 "단순"은 "메모리 구축이 없다"는 뜻으로 읽어야 합니다.
- **반복 실행과 신뢰구간이 없습니다.** GPT-5.6 Luna의 LongMemEval-s는 100문항이라 1문항이 1점입니다. 표 1의 +0.1, −0.3 같은 차이는 우열로 읽기 어렵습니다.
- **널리 쓰이는 상용 메모리 제품이 평가 대상에 없습니다.** Mem0, Zep, MemGPT는 부록 B.2의 문헌 검토에만 등장하고 11개 평가 대상에는 포함되지 않았습니다. 이 논문의 결과를 그 제품들의 성능으로 옮겨 말할 수는 없습니다.
- **정답률만 봅니다.** 메모리를 쓰는 이유에는 추론 시점 토큰 절감, 개인정보 삭제 요청 반영, 사용자 프로필 관리도 있습니다. 논문도 "명시적 잊기"를 메모리 이득 사례로 들지만, 이런 가치는 순가치 계산에 QA 정답으로만 반영됩니다.
- **세금의 정의가 기준선에 묶여 있습니다.** 저자들도 밝히듯 이득과 세금은 RAG 대비 값입니다. 표 1은 2회 검색을, 질문별 세금 분석은 1회 검색을 기준으로 삼으므로 두 수치를 섞어 읽으면 안 됩니다.
- **판정 모델이 평가 대상 모델 중 하나입니다.** 채점은 Qwen3.6-27B가 하고, 같은 모델이 답변 모델로도 쓰입니다. 사람 판정과의 일치율(95.1~100.0%)이 보고되어 있지만 표본 크기는 본문에서 확인하지 못했습니다.
- **재현 코드가 아직 없습니다.** 2026-11-20 기준 저장소로는 표 1을 다시 만들 수 없습니다. 처방 실험(원본 병행)에서 검색 예산이 얼마나 늘었는지도 본문에 나와 있지 않습니다.

## 인사이트

**왜 지금 중요한가.** 에이전트 메모리는 제품 기능 목록의 한 줄이 되었고, 논문도 빠르게 늘고 있습니다. 이 논문이 지적하는 것은 그 경쟁이 "메모리끼리의 순위표" 안에서 벌어졌다는 점입니다. 필자가 보기에 가장 쓸모 있는 기여는 순위가 아니라 계산 방식입니다. "RAG보다 1.8점 낮다"와 "63문항을 얻고 72문항을 잃었다"는 같은 사실이지만, 뒤의 표현은 무엇을 고쳐야 하는지를 알려 줍니다. 잃은 72문항을 열어 보면 금액이 빠진 요약, 59줄 프로필에 묻힌 한 줄, 틀린 추론 노트가 나옵니다.

**실무에 주는 의미: 메모리를 붙이기 전에 RAG 기준선부터 잽니다.** 구체적으로는 다음 순서를 권합니다(필자 의견).

1. 원본 대화 기록을 턴 단위로 잘라 날짜 머리말을 붙이고, BM25와 임베딩 검색을 합쳐 재순위화하는 기준선을 먼저 만듭니다. 논문의 기준선 구성(부록 A.2)이 그대로 설계서 역할을 합니다.
2. 메모리 시스템을 도입할 때 총점이 아니라 **질문별 정오표**를 기준선과 비교합니다. "기준선은 맞히는데 메모리가 틀린 질문" 목록이 곧 세금 목록입니다.
3. 메모리를 쓰더라도 원본 기록을 지우지 않고, 메모리 검색과 원본 검색을 함께 돌려 합칩니다. 표 4에서 이 방법 하나로 세 시스템의 세금이 약 32~57% 줄었습니다(필자 계산).
4. 금액, 날짜, 수량처럼 정확한 값을 묻는 질문이 많은 서비스라면 요약형 메모리의 손실 사례(60달러가 "비용 효율 선호"로 바뀐 경우)를 자기 데이터로 재현해 봅니다.

비용 쪽에서는 구축 비용을 몇 번의 질문으로 나눠 내는지가 관건입니다. PDF 표 20(PersonaMem-v2, Qwen3.6-27B, 934문항)에서 MemOS는 정답률이 RAG 1회 검색보다 높고(50.2 대 46.8) 추론 토큰도 적지만(1.31M 대 2.77M), 구축에 44.8M 토큰을 썼습니다. 단순 계산으로는 같은 양의 질문을 약 31번 반복해야 구축 토큰이 추론 절감분으로 상쇄됩니다(44.8 ÷ 1.46, 필자 계산이며 입력·출력 단가 차이와 캐시는 반영하지 않았습니다). 사용자당 질문이 수백 건 쌓이는 서비스와 몇 건으로 끝나는 서비스는 결론이 다를 수 있습니다.

**블로그의 기존 글과의 연결.** [컨텍스트 엔지니어링 소개](/tech/2026/10/24/context-engineering.html)에서는 노트와 메모리를 "컨텍스트 밖에 적어 두는" 장기 기법으로 정리했습니다. 이 논문은 그 "적어 두기"가 공짜가 아니라는 것을 수치로 보여 줍니다. [Remory](/papers/2026/10/24/remory-context-compaction.html)는 컴팩션 요약이 놓친 부분을 학습된 소프트 토큰으로 메우려 했고, [Pack Light, CarryOn](/papers/2026/10/24/pack-light-carryon.html)은 기록을 접되 원본 로그는 지우지 않는 규칙을 뒀습니다. 세 논문은 출발점이 다르지만 "가공된 표현은 원본에서 벗어나며, 되돌아갈 길이 필요하다"는 같은 결론에 닿습니다. 이 논문의 표현으로는 "변형을 복구 가능하게 만들라"입니다. 한편 [RAG 조합 실험(LASAGNA)](/papers/2026/10/24/rag-compositionality-lasagna.html)은 RAG 구성 요소의 이득이 조합하면 그대로 더해지지 않는다고 보고했습니다. 이 논문의 부록 B.1에서 기본 하이브리드 구성이 대부분의 변형과 몇 점 이내였다는 결과와 함께 읽으면, 기준선 RAG도 "가장 좋은 구성"을 찾기보다 표준 구성을 고정해 두고 비교 대상으로 쓰는 편이 현실적입니다. 채점을 LLM 판정에 맡길 때의 주의점은 [LLM 평가 실무](/tech/2026/10/24/llm-evals.html) 글에서 다뤘습니다.

**한계와 반론.** 메모리 시스템 쪽에서 할 수 있는 반론은 세 가지로 보입니다. 첫째, 기준선이 재순위화까지 갖춘 강한 RAG라는 점입니다. 둘째, 벤치마크가 회상 위주라 메모리가 유리한 과제(여러 세션에 걸친 집계, 취향 추론)의 비중이 낮다는 점입니다. 저자들도 4.5절에서 이를 인정하고, PersonaMem-v2와 MINT-Eval에서 메모리가 RAG를 넘는 칸이 나온 것도 이 설명과 맞습니다. 셋째, 통일된 임베딩과 답변 프롬프트가 각 시스템의 원래 설계와 맞지 않을 수 있다는 점입니다. 저자들은 부록 B.3에서 설정 변경이 대부분 메모리 쪽에 유리했음을 보이지만(예: MemOS의 LongMemEval-s 점수는 재순위화를 켜서 45.6에서 76.6으로 올랐습니다), 시스템 개발자가 직접 튜닝한 결과와는 다를 수 있습니다. 그래서 이 논문을 "메모리는 쓸모없다"로 읽는 것은 과합니다. 필자의 판단으로는 "메모리의 성능 주장은 같은 원본에 대한 RAG 점수와 함께 제시되지 않으면 해석할 수 없다"가 적절한 독법입니다.

**앞으로 지켜볼 점.** (1) 재현 코드가 공개되어 다른 팀이 표 1을 다시 만들 수 있는지, 특히 각 메모리 시스템의 개발자가 자기 설정으로 반박 결과를 내는지. (2) Mem0, Zep 같은 상용 제품을 같은 틀로 잰 결과. (3) 메모리 논문들이 RAG 기준선과 질문별 이득·세금을 함께 보고하기 시작하는지. (4) 블로그에서 다룬 [Cortex](/papers/2026/10/24/cortex-parametric-memory.html) 같은 파라미터형 메모리에도 같은 세금이 측정되는지. 저자들은 이를 후속 과제로 남겼습니다.
