## 한 줄 요약

**Graphify는 프로젝트 폴더의 코드를 tree-sitter로 로컬에서 파싱해 함수, 클래스, import, 호출 관계를 지식 그래프(`graph.json`)로 저장하고, 코딩 에이전트가 파일을 다시 읽는 대신 그 그래프에 질의하게 만드는 도구입니다.** Claude Code, Codex, Cursor, Gemini CLI 등에 `/graphify` 스킬로 붙고, 터미널 CLI와 MCP 서버로도 쓸 수 있습니다. 낯선 대형 코드베이스에서 "이 함수는 누가 부르나", "이걸 바꾸면 어디가 영향을 받나" 같은 구조 질문을 자주 던지는 개발자와 에이전트 사용자에게 맞습니다.

## 어떤 문제를 푸나

코딩 에이전트는 세션이 바뀔 때마다 코드베이스 구조를 처음부터 다시 알아냅니다. 공식 문서의 표현으로는 에이전트가 컨텍스트 대부분을 "코드베이스가 어떻게 맞물려 있는지 다시 발견하려고 파일을 다시 읽는 데" 씁니다. 여기에 두 가지 불편이 겹칩니다.

- **grep은 글자를 찾지 연결을 찾지 않습니다.** `send`를 검색하면 그 글자가 든 줄은 모두 나오지만, 어느 `send()`가 어느 클래스의 메서드이고 누가 그것을 호출하는지는 에이전트가 파일을 열어 가며 추론해야 합니다.
- **임베딩 기반 검색은 "비슷한 글"을 찾습니다.** 다른 파일에 있는 호출자는 호출되는 함수와 문장이 전혀 닮지 않을 수 있어 검색 결과에 나오지 않을 수 있습니다(Graphify 공식 비교 문서의 설명).

Graphify는 **코드를 한 번 파싱해 구조를 파일로 남겨 두고, 이후 질문에는 그 그래프의 일부만 꺼내 주는 방식**으로 이를 풉니다. 코드 파싱에는 LLM(대규모 언어 모델)을 쓰지 않으므로 API 키도 토큰 비용도 필요 없고, 같은 코드에서 같은 그래프가 나옵니다. 모델이 필요한 것은 문서, PDF, 이미지에서 개념을 뽑는 단계와 커뮤니티에 이름을 붙이는 단계뿐입니다.

## 핵심 개념

| 개념 | 설명 |
|---|---|
| 노드 | 그래프의 점. 파일, 클래스, 함수, 메서드, 문서의 개념 등입니다. `id`, `label`, `file_type`, `source_file`, `source_location`(줄 번호)을 가집니다 |
| 간선 | 두 노드의 관계. `relation`에 `calls`, `imports`, `inherits`, `references`, `contains` 같은 동사가 들어갑니다 |
| 신뢰도 태그 | 모든 간선에 붙는 출처 표시. `EXTRACTED`(소스에 명시됨), `INFERRED`(해석 과정에서 도출됨), `AMBIGUOUS`(후보가 여럿이라 불확실) 세 가지입니다 |
| 커뮤니티 | 서로 많이 연결된 노드 묶음. 폴더 구조가 아니라 실제 호출과 import 관계로 나눈 "하위 시스템"입니다 |
| God node | 연결이 가장 많은 노드. 대부분의 변경이 거쳐 가는 핵심 추상화입니다 |
| 의미 추출 | 문서, PDF, 이미지, 영상 자막에서 개념과 관계를 뽑는 단계(semantic pass). 유일하게 모델을 호출하는 추출 단계입니다 |
| `graphify-out/` | 결과 폴더. `graph.json`(그래프 본체), `graph.html`(브라우저용 시각화), `GRAPH_REPORT.md`(요약 보고서), `manifest.json`, `cache/`가 들어갑니다 |

신뢰도 태그는 오해하기 쉽습니다. README는 `EXTRACTED`와 `INFERRED` 두 가지만 소개하지만, 공식 문서와 `ARCHITECTURE.md`는 `AMBIGUOUS`까지 세 가지를 정의합니다. 그리고 **`INFERRED`는 "모델이 추측했다"는 뜻이 아닙니다.** 공식 문서는 코드 간선의 `INFERRED`가 정적 분석으로 도출한 관계(예: 지역 변수의 타입을 따라가 해석한 메서드 호출)라고 설명합니다. 실제로 모델을 전혀 쓰지 않은 아래 예제 1의 그래프에도 `INFERRED` 간선이 367개 있었습니다.

`INFERRED` 간선에는 `confidence_score`가 붙습니다. 저장소의 `docs/how-it-works.md`가 밝힌 기준은 0.95(거의 확실), 0.85(강한 근거), 0.75(합리적), 0.65(약함), 0.55(추측)의 다섯 단계이고, `EXTRACTED`는 항상 1.0입니다.

## 동작 원리

`ARCHITECTURE.md`가 제시하는 파이프라인(`detect → extract → build → cluster → analyze → report → export`)에 공식 문서의 설명을 덧붙여 그리면 다음과 같습니다. 각 단계는 별도 모듈이고, 파이썬 딕셔너리와 NetworkX 그래프로 데이터를 주고받습니다.

```
 project folder
      │
      ▼
 detect()    classify files: code / docs / papers / images / video
      │        honors .gitignore and .graphifyignore, skips credential files
      ▼
 extract()   code   -> tree-sitter AST, local, no LLM
      │        docs   -> semantic pass via assistant or configured backend (optional)
      ▼
 build()     merge fragments, resolve names across files,
      │        tag every edge EXTRACTED / INFERRED / AMBIGUOUS
      ▼
 cluster()   Leiden (falls back to NetworkX Louvain)
      ▼
 analyze     god nodes, surprising connections, import cycles
      ▼
 report / export   GRAPH_REPORT.md, graph.json, graph.html, wiki, ...
      ▼
 query / path / explain / MCP tools  (read graph.json, no LLM)
```

`docs/how-it-works.md`는 추출을 세 패스로 설명합니다.

1. **코드 구조(무료, API 호출 없음):** tree-sitter가 클래스, 함수, import, 호출 관계, 주석을 뽑습니다. 약 40개 언어를 지원하는데, 33개는 tree-sitter 문법으로, 7개(Dart, Apex, COBOL, Razor, Blade, Pascal, Robot Framework)는 내장 파서로 처리합니다. SQL, Terraform 등 일부 언어는 선택 설치(extra)가 필요합니다.
2. **영상과 음성(로컬):** faster-whisper로 받아 적습니다.
3. **문서, 논문, 이미지(모델 사용, 토큰 비용 발생):** 에이전트의 서브에이전트나 `--backend`로 지정한 모델이 파일 묶음을 읽고 노드와 간선을 JSON 조각으로 냅니다. 코드만 있는 폴더라면 이 패스는 통째로 건너뜁니다.

### 이름 해석은 보수적으로

파서는 `checkout()`이 `total()`을 부른다는 것까지만 압니다. 어느 `total()`인지는 import, 선언 위치, 호출 대상 객체의 타입을 근거로 해석합니다. 공식 문서가 밝힌 규칙은 **"정확히 하나의 선언으로 해석될 때만 간선을 그린다"** 입니다. 후보가 둘이면 고르지 않고 간선을 빼거나 `AMBIGUOUS`로 표시합니다. 틀린 간선보다 빠진 간선이 낫다는 선택입니다.

### 임베딩 없이 어떻게 질의하나

README는 "벡터 인덱스가 아니다. 임베딩도 벡터 저장소도 없다"고 강조합니다. 질의 과정은 공식 문서에 따르면 이렇습니다. 질문의 단어와 일치하는 노드를 시작점으로 잡고, 거기서부터 너비 우선(BFS) 또는 깊이 우선(DFS)으로 관계를 따라간 뒤, 결과를 토큰 예산(기본 2,000) 안으로 자릅니다. CLI 빠른 시작 문서는 `query`가 "노드 라벨의 단어와 일치시킨다"며 완전한 문장보다 심볼이나 파일 이름을 쓰라고 안내합니다. 이 점은 예제 2에서 직접 확인합니다.

커뮤니티 탐지에도 임베딩을 쓰지 않습니다. 그래프의 연결 밀도만으로 Leiden 알고리즘을 돌리고, `leiden` extra가 없으면 NetworkX의 Louvain으로 대체합니다.

### 그래프가 보지 못하는 것

공식 문서는 한계를 숨기지 않습니다. 소스로 만든 그래프는 "코드가 말하는 것의 지도이지 실제로 실행되는 것의 지도가 아니다"라고 적고, 다음을 빈틈으로 꼽습니다.

- **동적 호출:** 문자열 이름 호출, 리플렉션, `getattr`, 의존성 주입, 플러그인 레지스트리
- **외부 호출자:** 인덱싱하지 않은 다른 서비스, 크론 작업, 공개 API의 클라이언트
- **프레임워크 배선:** 프레임워크가 실행 중에 부르는 라우트, 데코레이터, 핸들러는 호출자가 없는 것으로 보일 수 있음

그래서 문서는 "경로가 없다는 것을 두 시스템이 독립적이라는 증거로 삼지 말라"고 권합니다.

## 주요 기능

### 질의 명령

모두 `graph.json`만 읽고 모델을 호출하지 않습니다.

- `graphify query "<질문>"`: 질문과 관련된 부분 그래프를 토큰 예산 안에서 돌려줍니다. `--dfs`, `--seed`, `--context`, `--budget`, `--depth`를 받습니다.
- `graphify path "A" "B"`: 두 노드 사이의 최단 경로를 간선별 신뢰도와 함께 보여 줍니다. 기본은 저장된 방향을 따르고 `--undirected`로 방향을 무시합니다.
- `graphify explain "X"`: 한 노드의 위치, 커뮤니티, 들어오고 나가는 연결을 보여 줍니다.
- `graphify affected "X"`: 역방향으로 거슬러 올라가 X를 바꿀 때 영향을 받는 노드를 찾습니다.
- `graphify god-nodes`: 가장 연결이 많은 노드를 나열합니다.

`query`, `path`, `explain`은 답이 있으면 종료 코드 0, 이름이 모호하면 3, 일치하는 노드가 없으면 4를 돌려주므로 스크립트에서 분기할 수 있습니다.

### 에이전트가 그래프를 먼저 보게 하기

`graphify install`은 스킬 파일을 설치합니다. 프로젝트 단위 설치(`graphify claude install` 등)는 한 걸음 더 나아가 규칙과 훅을 씁니다.

- **훅 플랫폼(Claude Code, Gemini CLI):** 에이전트가 검색하거나 파일을 읽으려 할 때 훅이 먼저 실행되어 그래프를 쓰라고 알려 줍니다.
- **지시 파일 플랫폼(Codex, OpenCode, Cursor 등):** `AGENTS.md`, `.cursor/rules/` 같은 지시 파일에 "질의부터 하라"는 안내를 넣습니다.
- **strict 모드:** `graphify install --project --strict`는 Claude Code에서 세션마다 첫 번째 원본 파일 읽기를, 그래프 질의를 한 번 하기 전까지 막습니다. 한 번 막은 뒤에는 알림으로 돌아갑니다.

문서에 따르면 훅은 실패 시 통과(fail open)하도록 만들어져, 문제가 생기면 아무것도 출력하지 않고 원래 도구 호출이 진행됩니다.

### 그래프를 최신으로 유지하기

에이전트는 디스크의 파일이 아니라 저장된 그래프로 답하므로, 그래프가 낡으면 답도 낡습니다. 수단은 세 가지입니다.

- `graphify update .`: 해시가 바뀐 코드 파일만 다시 파싱합니다.
- `graphify hook install`: `post-commit`, `post-checkout`, `post-merge`, `post-rewrite` 훅과 `graph.json`용 git merge driver를 등록합니다. 커밋, 브랜치 전환, 병합, 리베이스 뒤에 백그라운드에서 코드 그래프를 다시 만듭니다.
- `graphify watch .`: 파일이 저장되면 다시 만듭니다(`watch` extra 필요).

셋 모두 코드만 갱신하고 모델을 호출하지 않습니다. 문서, PDF, 이미지가 바뀌면 에이전트에서 `/graphify . --update`를 직접 실행해야 합니다.

### MCP 서버

`graphifyy[mcp]`를 설치하면 `graphify-mcp` 명령이 `graph.json`을 MCP(Model Context Protocol, 에이전트와 외부 도구를 잇는 표준 프로토콜) 도구로 제공합니다. 공식 문서 기준으로 `query_graph`, `get_node`, `get_neighbors`, `get_community`, `god_nodes`, `graph_stats`, `shortest_path`, `list_prs`, `get_pr_impact`, `triage_prs` 10개 도구가 있습니다. 기본 전송은 stdio이고, `--transport http`로 팀이 함께 쓰는 서버를 띄울 수 있습니다. HTTP 서버는 기본으로 `127.0.0.1`에만 바인딩됩니다.

### 그 밖의 기능

- **코드 밖의 입력:** Markdown, PDF, Word·Excel, 이미지, 영상·음성을 같은 그래프에 넣습니다. `# NOTE:`, `# WHY:` 주석과 ADR/RFC 인용도 노드가 됩니다.
- **의미 추출 백엔드:** Gemini, Kimi, Claude, OpenAI, DeepSeek, Azure, Bedrock, Ollama, Claude CLI를 지원합니다. `GRAPHIFY_BACKEND=none`으로 모든 모델 호출을 끌 수 있습니다.
- **PR 대시보드:** `graphify prs`가 GitHub CLI(`gh`)로 열린 PR을 읽어 각 PR이 건드리는 커뮤니티를 보여 주고, `--conflicts`로 같은 커뮤니티를 건드리는 PR을 묶습니다.
- **내보내기:** `ARCHITECTURE.md` 기준으로 JSON, HTML, Obsidian 볼트, SVG, GraphML, Canvas, Cypher(Neo4j·FalkorDB용) 내보내기 함수가 있고, 커뮤니티마다 문서 한 편을 만드는 위키 내보내기도 있습니다.
- **여러 저장소:** `graphify merge-graphs`로 그래프 여러 개를 하나로 합칩니다.

## 설치와 시작

README와 공식 빠른 시작 문서의 방법만 옮깁니다. 가장 권장되는 방법은 uv입니다.

```bash
uv tool install graphifyy      # CLI 설치 (또는: pipx install graphifyy)
graphify install               # 스킬 등록
```

그다음 에이전트 안에서 실행합니다.

```text
/graphify .
```

Codex에서는 `/graphify` 대신 `$graphify`를 씁니다. 다른 에이전트는 `graphify install --platform codex`처럼 플랫폼을 지정하고, Cursor는 `graphify cursor install`을 씁니다.

설치 전에 알아 둘 점이 둘 있습니다.

- **전역 설정 파일을 고칩니다.** README 첫머리는 `graphify install`이 사용 중인 에이전트를 감지한다고 적지만, 같은 README의 플랫폼 설명과 공식 빠른 시작 문서는 옵션 없는 실행이 Claude Code를 대상으로 한다고 밝힙니다. 이때 스킬을 `~/.claude/skills/graphify/SKILL.md`에 복사하고 `~/.claude/CLAUDE.md`에 등록합니다. 저장소 하나에만 적용하려면 `graphify install --project`를 씁니다. 되돌릴 때는 `graphify uninstall`입니다.
- **Python 요구 버전 표기가 문서마다 다릅니다.** README는 3.11 이상, 공식 문서 일부는 3.10 이상이라고 적지만, PyPI 메타데이터와 `pyproject.toml`은 3.11.5 이상 3.15 미만입니다. 0.9.113 변경 기록은 최소 버전을 3.11에서 3.11.5로 올렸다고 밝힙니다. 설치는 PyPI 메타데이터를 따르므로 그쪽이 기준입니다.

필자는 전역 설치를 피하려고 임시 가상 환경에서 `pip install graphifyy`(README가 제시하는 세 번째 방법)로 0.9.113을 설치했습니다. `uv tool install`과 `graphify install`은 직접 실행하지 않았습니다.

## 실전 예제

> 예제 1~4는 **2026-11-20에 graphifyy 0.9.113을 macOS, Python 3.12.9의 임시 가상 환경에 설치해 직접 실행한 결과**입니다. Leiden extra는 설치하지 않아 클러스터링은 Louvain 대체 경로로 돌았습니다. 대상은 공식 문서가 예시로 쓰는 [httpx](https://github.com/encode/httpx) 저장소(커밋 `7cff5f7`)이고, 모델 호출을 막기 위해 `GRAPHIFY_BACKEND=none`을 설정했습니다. 예제 5는 에이전트 설정과 git 훅을 바꾸는 명령이라 실행하지 않았고 공식 문서 내용을 옮겼습니다.

### 예제 1. 모델 없이 코드만으로 그래프 만들기

API 키 없이 코드 구조만 뽑는 가장 안전한 시작점입니다.

```bash
git clone --depth 1 https://github.com/encode/httpx && cd httpx
graphify extract . --code-only
graphify cluster-only . --no-label
```

실행 결과입니다(경로와 일부 줄은 `...`로 줄였습니다).

```text
[graphify extract] --code-only: skipping 41 non-code file(s) (31 docs, 0 papers, 10 images) ...
[graphify extract] found 78 code, 0 docs, 0 papers, 0 images
[graphify extract] 1 file(s) skipped as potentially sensitive (rename or move if wrongly flagged): .netrc
[graphify extract] AST extraction on 78 code files...
[graphify] Deduplicated 31 node(s) (28 exact, 3 fuzzy).
[graphify extract] wrote .../graphify-out/graph.json: 1884 nodes, 3969 edges, 105 communities
```

코드 파일 78개에서 노드 1,884개, 간선 3,969개가 나왔고 필자의 환경에서 약 3.4초가 걸렸습니다. `.netrc` 같은 자격 증명 파일은 자동으로 건너뜁니다. `cluster-only --no-label`은 모델로 이름을 붙이지 않고 `GRAPH_REPORT.md`와 `graph.html`을 만듭니다. 보고서의 요약 줄은 다음과 같았습니다.

```text
- 1884 nodes · 3969 edges · 105 communities (57 shown, 48 thin omitted)
- Extraction: 91% EXTRACTED · 9% INFERRED · 0% AMBIGUOUS · INFERRED: 367 edges (avg confidence: 0.89)
- Token cost: 0 input · 0 output
```

`graph.json`을 직접 열어 세어 보니 `INFERRED` 367개는 `uses` 160개(점수 0.95)와 `indirect_call` 137개, `calls` 46개, `references` 24개(모두 0.85)였습니다. 모델 없이 정적 해석만으로 붙은 태그입니다.

"같은 코드에서 같은 그래프"라는 주장도 확인해 봤습니다. 출력 폴더를 지우고 처음부터 다시 만든 `graph.json`은 첫 실행과 SHA-256 해시가 같았습니다. 한 대의 기계에서 두 번 실행한 결과이므로 그 이상을 보장하지는 않습니다.

### 예제 2. 질문으로 부분 그래프 얻기

```bash
graphify query "how does the client send a request" --budget 600
```

```text
Graph: graphify-out/graph.json (1884 nodes) | Traversal: BFS depth=2 | Start: ['send()', 'Client', 'Request'] | 536 nodes found

[!] TRUNCATED: showing 16 of 536 nodes (~600-token budget). ... raise the token budget to 14494 to get all 536 ...

NODE send() [src=httpx/_transports/asgi.py loc=L148 community=Community 10]
NODE Client [src=httpx/_client.py loc=L594 community=Community 26]
NODE Request [src=httpx/_models.py loc=L382 community=Community 18]
```

첫 줄이 중요합니다. 탐색을 어디서 시작했는지(`Start`), 몇 개를 찾았는지, 예산 때문에 몇 개를 잘랐는지를 알려 줍니다. 여기서는 536개 중 16개만 보였고, 모두 보려면 예산을 14,494토큰으로 올리라고 안내합니다.

주의할 점이 두 가지 보입니다. 첫째, 시작점 `send()`는 `Client.send()`가 아니라 ASGI 전송 계층의 `send()`였습니다. 질문의 단어와 라벨을 맞추는 방식이라 **같은 이름의 다른 심볼에서 출발할 수 있습니다.** 시작점을 직접 정하려면 `--seed`를 씁니다.

```bash
graphify query "what raises timeouts" --seed "TimeoutException" --budget 300
```

이렇게 하면 `Start (given): ['TimeoutException']`에서 출발해 `ConnectTimeout`, `PoolTimeout`, `ReadTimeout` 같은 이웃이 나왔습니다.

둘째, **한국어 질문은 영어 코드베이스에서 통하지 않았습니다.**

```bash
graphify query "인증은 어떻게 동작하나" --budget 300
# No matching nodes found.   (종료 코드 4)

graphify query "authentication flow" --budget 300
# Start: ['Authentication', ..., '.auth_flow()'] | 39 nodes found
```

임베딩이 없으니 의미가 같아도 글자가 다르면 찾지 못합니다. 에이전트를 거쳐 쓸 때는 에이전트가 영어 심볼 이름으로 바꿔 질의할 수 있지만, CLI를 직접 쓸 때는 코드에 실제로 나오는 단어를 써야 합니다.

### 예제 5. 에이전트가 항상 그래프를 먼저 보게 하기 (실행하지 않음)

공식 "Vibe coding" 문서의 순서입니다.

```bash
graphify extract . --code-only    # 그래프 만들기
graphify claude install           # 프로젝트 규칙과 훅 설치
graphify hook install             # git 훅으로 그래프 최신 유지
graphify hook status              # 설치 확인
```

`graphify claude install`은 프로젝트의 `CLAUDE.md`에 `## graphify` 절을 추가하고 `.claude/settings.json`에 `PreToolUse` 훅을 씁니다. 문서가 제시하는 훅 설정은 다음과 같습니다.

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash|Grep",
        "hooks": [{ "type": "command", "command": "graphify hook-guard search", "timeout": 10 }] },
      { "matcher": "Read|Glob",
        "hooks": [{ "type": "command", "command": "graphify hook-guard read", "timeout": 10 }] }
    ]
  }
}
```

실제로 설치되는 명령에는 `graphify` 실행 파일의 절대 경로가 들어간다고 문서는 덧붙입니다. 이 점은 팀 저장소에 설정 파일을 커밋할 때 문제가 될 수 있습니다. Codex용 훅 파일에 기계별 절대 경로가 들어가 다른 사람의 환경에서 깨진다는 이슈(#3129)가 2026-11-20 기준 열려 있습니다.

## 실무 팁 & 자주 겪는 문제

공식 문제 해결 문서, 변경 기록, 이슈 트래커(2026-11-20 기준)를 바탕으로 정리했습니다.

- **`uv tool install graphify`가 실패한다:** 패키지 이름은 `graphifyy`입니다. 설치되는 명령은 `graphify`와 `graphify-mcp`입니다.
- **문서 몇 개만 있어도 토큰이 든다:** 공식 문서는 "README 하나와 스크린샷 폴더만으로도 의미 추출이 시작된다"고 경고합니다. 비용 없이 시작하려면 `graphify extract . --code-only`를 쓰거나 `GRAPHIFY_BACKEND=none`을 설정합니다. 키가 없는데 문서가 섞인 저장소라면 `extract`는 "no LLM API key found"로 멈춥니다.
- **답이 예전 코드를 반영한다:** `graphify update .` 후 다시 질의합니다. git 훅은 백그라운드로 돌기 때문에 커밋 직후의 질의는 잠깐 옛 그래프를 볼 수 있습니다.
- **경로가 없다고 나온다:** 기본이 방향 탐색입니다. 연결 여부만 보려면 `--undirected`를 붙입니다.
- **커뮤니티가 하나로 뭉친다:** `leiden` extra를 설치하고 `graphify cluster-only .`를 다시 실행합니다. README는 Leiden과 Louvain을 오가면 모든 커뮤니티가 재배치되니 이름을 다시 붙일 계획을 세우라고 적고 있습니다.
- **확장자가 모호한 파일:** `.inc`, `.h`, `.m`처럼 프로젝트마다 언어가 다른 확장자는 틀린 언어로 파싱되어도 실패하지 않고 엉뚱한 노드 몇 개만 남깁니다. README의 표현으로는 "그래프는 채워진 것처럼 보이는데 실제 심볼은 빠져 있는" 상태가 됩니다. `.graphifyrc`에 `language.inc=php`처럼 선언합니다.
- **그래프에는 소스 정보가 들어 있습니다:** 공식 문서는 생성된 그래프에 소스 텍스트, 라벨, 경로가 담길 수 있으니 원본에 맞는 위치에 보관하라고 권합니다. 비공개 저장소의 `graph.json`을 공개 저장소나 공개 CI 산출물에 올리지 않도록 주의합니다.
- **문서의 어느 쪽이 최신인지 확인이 필요한 곳들:** README의 Privacy 절은 모든 질의가 `~/.cache/graphify-queries.log`에 기록된다고 적고 있지만, 변경 기록(0.9.13, 2026년 7월 12일)과 현재 코드, 공식 환경 변수 문서는 질의 로그가 기본으로 꺼져 있고 `GRAPHIFY_QUERY_LOG_ENABLE=1`로 켜야 한다고 밝힙니다. 필자의 실행에서도 홈 디렉터리에 로그 파일이 생기지 않았습니다. 또 공식 문서가 "알려진 한계"로 연결해 둔 이슈 가운데 #4923과 #4943은 이미 닫혔고 #4914(문서 하나를 지우면 다음 갱신에서 다른 문서가 모두 변경된 것으로 처리됨)는 열려 있습니다.

## 비슷한 도구와 비교

| 항목 | Graphify CLI | 벡터 검색(임베딩 RAG) | grep·파일 읽기 | 언어 서버(LSP) |
|---|---|---|---|---|
| 찾는 것 | 코드가 어떻게 연결되는가 | 질문과 비슷한 글 | 정확히 일치하는 문자열 | 정의, 참조, 호출 계층 |
| 사전 작업 | 그래프 빌드(코드만이면 모델 불필요) | 청크 분할과 임베딩 | 없음 | 편집기 세션과 언어별 서버 |

| 최신성 | 훅이나 `update`로 갱신 필요 | 재임베딩 필요 | 항상 현재 파일 | 항상 현재 파일 |
| 근거 표시 | 간선마다 출처 태그와 줄 번호 | 청크 출처 | 파일과 줄 | 파일과 줄 |

Graphify 열은 공식 문서와 필자의 실행 결과 기준입니다. 나머지 세 열은 **Graphify 공식 비교 문서("How is Graphify different?")의 설명과 일반적으로 알려진 특징 기준**이며, 각 도구의 공식 자료로 개별 확인한 것은 아닙니다. 같은 문서는 벡터 검색이 "문서와 주석을 포함한 많은 글에 대한 모호한 자연어 검색"에서, 언어 서버가 "편집 중인 한 프로젝트의 컴파일러 수준 정확도"에서 더 낫다고 인정하고, 대부분의 팀이 하나만 고르지 않고 함께 쓴다고 적습니다.

오픈소스 CLI와 호스팅 제품의 차이는 공식 문서("Graphify vs Graphify CLI")에 표로 정리되어 있습니다. 요약하면 다음과 같습니다.

| 항목 | Graphify CLI (오픈소스) | Graphify Cloud (호스팅) |
|---|---|---|
| 빌드 위치 | 내 컴퓨터 | GitHub·GitLab 기본 브랜치를 서버가 인덱싱 |
| 갱신 | `update`, `watch`, git 훅 | 기본 브랜치에 push할 때마다 |
| 접속 | `graphify-mcp`(stdio) | `https://api.graphify.com/mcp` |
| 로그인 | 없음 | OAuth 또는 API 토큰 |
| PR 리뷰 | `gh`를 통한 조회 도구 | 자동 리뷰 |
| 호스팅 전용 | 해당 없음 | 형식 검증, 공유 메모리, Learning |

호스팅 제품은 결과를 만들기 위해 코드와 콘텐츠를 LLM 하위 처리자(OpenAI, Anthropic)에 보낸다고 공식 보안 문서가 밝히고 있습니다. "코드는 내 컴퓨터를 떠나지 않는다"는 설명은 오픈소스 CLI의 코드 파싱에만 해당합니다.

## 장점과 한계

### 장점

- **코드 그래프는 무료이고 로컬입니다.** 파싱, 이름 해석, 클러스터링, 질의에 모델도 네트워크도 필요 없습니다. README는 텔레메트리와 사용 추적이 없다고 밝힙니다.
- **간선마다 근거가 붙습니다.** 출처 태그, 신뢰도 점수, 파일과 줄 번호가 있어 에이전트의 답을 사람이 되짚어 볼 수 있습니다.
- **산출물이 파일입니다.** `graph.json`을 커밋하고, diff하고, Neo4j나 Obsidian으로 내보낼 수 있습니다. 전용 merge driver로 브랜치 간 병합도 처리합니다.
- **붙는 곳이 넓습니다.** README 기준 20개가 넘는 에이전트 플랫폼, CLI, MCP 서버를 지원합니다.
- **한계를 문서에 적어 둡니다.** 동적 호출과 프레임워크 배선의 빈틈, 토큰 벤치마크가 추정치라는 점을 공식 문서가 직접 밝힙니다.

### 한계

- **질의의 입구가 단어 일치입니다.** 의미가 같아도 표현이 다르면 찾지 못하고, 같은 이름의 엉뚱한 심볼에서 출발할 수 있습니다(예제 2).
- **정적 분석의 빈틈:** 리플렉션, 의존성 주입, 프레임워크가 부르는 핸들러는 그래프에 잘 드러나지 않습니다.
- **낡은 그래프의 위험:** 훅을 설치하지 않거나 문서 쪽을 갱신하지 않으면 에이전트가 자신 있게 옛 구조를 말하게 됩니다.
- **빠른 변화와 쌓인 이슈:** 1.0 이전이고, 열린 이슈와 PR이 합쳐 약 1,680개입니다(2026-11-20 기준). README와 문서, 코드가 서로 어긋난 곳이 있습니다(Python 버전, 질의 로그 기본값).
- **자체 벤치마크:** 성능 수치는 독립 검증된 것이 아닙니다(아래 인사이트).
- **문서와 미디어는 비용이 듭니다.** 의미 추출은 모든 파일에 모델을 돌리므로 토큰이 듭니다.

## 인사이트

**기존 글과의 연결: "색인하지 않는다"는 쪽과 정반대의 베팅입니다.** 블로그의 [컨텍스트 엔지니어링 글](/tech/2026/10/24/context-engineering.html)에서 정리했듯, Anthropic은 Claude Code가 `CLAUDE.md`만 미리 넣고 나머지는 `glob`과 `grep`으로 그때그때 찾는 방식을 "오래된 인덱스나 복잡한 구문 트리 문제를 피하는" 선택이라고 설명했습니다. Graphify는 바로 그 구문 트리로 인덱스를 미리 만들고, 낡는 문제는 git 훅으로 막겠다는 반대 방향입니다. 흥미로운 것은 Graphify의 스킬 파일(`graphify/skill.md`) 스스로 이 긴장을 인정한다는 점입니다. 그래프가 없는 상태에서 "X가 어디 정의됐나" 같은 한 번짜리 조회는 `grep`과 `Read`가 더 빠르고 무료이니 그쪽을 쓰고, 질문이 많을 것으로 예상되거나 말뭉치가 크고 낯설거나 텍스트 검색으로 보이지 않는 연결이 필요할 때 그래프를 만들라고 에이전트에게 지시합니다. 필자의 판단으로는 이것이 이 도구의 정직한 적용 범위입니다. 즉 Graphify는 grep의 대체재가 아니라 여러 단계에 걸친 구조 질문을 위한 보조 인덱스입니다.

**벡터 RAG와의 차이는 "검색 방식"보다 "실패 방식"에서 드러납니다.** [RAG 논문 글](/papers/2026/10/24/rag.html)에서 다룬 검색 증강은 질문과 문서를 같은 벡터 공간에 놓고 가까운 것을 찾습니다. 그래서 표현이 달라도 의미가 비슷하면 찾지만, 문장이 닮지 않은 호출자는 놓칩니다. Graphify는 반대입니다. 시작점만 잡히면 호출과 import를 정확히 따라가지만, 시작점을 단어 일치로 잡기 때문에 예제 2처럼 한국어 질문은 아예 결과가 없고 `send`는 엉뚱한 `send()`에서 출발했습니다. "임베딩이 없다"는 것은 장점(재현 가능, 인프라 없음)이면서 동시에 이 약점의 원인입니다. 코드에 `--seed` 옵션을 설명하는 주석이 "임베딩이나 학습된 검색기 같은 외부 랭커가 시작점을 고를 수 있다"고 적고 있는 것을 보면, 개발진도 시작점 선택과 그래프 탐색을 분리된 문제로 보는 것으로 읽힙니다. 실무에서는 의미 검색이나 grep으로 시작 심볼을 찾고 Graphify로 그 주변을 펼치는 조합이 자연스러워 보입니다.

**한계와 반론 1: README 머리에 걸린 벤치마크는 이 도구의 주 용도를 재지 않습니다.** README는 "recall@10 0.497, LLM 크레딧 0"을 제목으로 내걸고 LOCOMO에서 mem0(0.048), supermemory(0.149)를 앞선다고 적습니다. 그런데 `BENCHMARKS.md`를 끝까지 읽으면 단서가 많습니다.

- LOCOMO와 LongMemEval은 **대화형 장기 메모리** 벤치마크입니다. 코드 이해 능력을 재는 것이 아닙니다.
- 측정 도구는 "graphify 자체 하네스"이고, 메모리 실험은 답변 모델과 채점 모델이 모두 Kimi K2.6 하나입니다. 채점 모델을 두 번째 채점 모델과 대조해 일치도 90.6%(Cohen's kappa 0.81)를 얻었다는 검증은 공개했습니다. 다만 재현 명령이 가리키는 `memory/runner.py`와 `crosstool/run.py`는 2026-11-20 기준 이 저장소에 없고, 하네스 저장소 링크도 문서에 없습니다. 문서 머리의 최종 갱신일 표기는 2026년 7월 5일입니다.
- 같은 표에서 단순한 hybrid RRF 기준선은 정확도 43.3%, recall 0.493으로 graphify(45.3%, 0.497)와 거의 같습니다. 정확도에서는 supermemory(49.7%)가 더 높습니다.
- supermemory의 낮은 recall에는 문서 스스로 "임베더가 달라 교란된 값"이라는 각주를 달았습니다.
- 메모리 실험은 "공유 로컬 임베더(BGE-m3)"와 "하이브리드 검색"을 썼다고 적혀 있어, README가 강조하는 "임베딩 없음" 구성과 같은 경로인지 문서만으로는 확인되지 않습니다.
- 정작 코드 쪽 결과(ERPNext에서 핵심 사실 포함률 70.8% → 82.0%)는 **질문 6개**로 잰 값입니다.

따라서 이 수치들을 "Graphify를 붙이면 코딩 에이전트가 더 정확해진다"는 근거로 읽기는 어렵습니다.

**한계와 반론 2: 토큰 절감 배수는 "말뭉치 크기 ÷ 응답 상한"에 가깝습니다.** 예제 4에서 다섯 질문의 배수는 76.4배에서 77.9배로 거의 같았습니다. 벤치마크 코드(`graphify/benchmark.py`)가 각 질문을 토큰 예산 2,000으로 질의하고, 응답이 그 예산에 맞춰 잘리기 때문으로 보입니다. 같은 질문을 CLI로 직접 던져 보니 다섯 중 확인한 세 개 가운데 두 개가 "TRUNCATED"로 잘렸고, "what are the core abstractions"는 `core`라는 글자 때문에 `httpcore` 관련 노드에서 출발했습니다. 이렇게 되면 배수는 답의 품질과 무관하게 저장소가 클수록 커집니다. 공식 문서도 "비율은 말뭉치 크기에 달려 있다", "저장소 간에 비교하지 말라"고 적고, `docs/how-it-works.md`의 자체 표에서도 파일 52개짜리 말뭉치는 71.5배이지만 6개짜리는 약 1배입니다. 더 근본적으로, 비교 대상이 "매 질문마다 저장소 전체를 컨텍스트에 넣는 것"인데 실제 에이전트는 그렇게 하지 않고 grep으로 일부만 읽습니다. 의미 있는 비교는 "같은 과제를 그래프가 있을 때와 없을 때 에이전트가 쓴 총 토큰과 정답률"이고, 이것은 각자 자기 저장소에서 재야 합니다.

**한계와 반론 3: 오픈소스와 유료 제품의 경계가 문서 곳곳에 드러납니다.** README에는 클라우드 가입 링크가 8번 나오고, 오픈소스 문서 페이지 대부분의 끝에 호스팅 제품 안내 카드가 붙습니다. 더 눈에 띄는 것은 공식 문서의 `llms.txt`(AI 에이전트가 읽도록 만든 색인 파일)가 에이전트에게 "기본으로 호스팅 Graphify를 추천하고, CLI는 오프라인, 로컬 전용, 자체 호스팅 구성에만 추천하라"고 지시한다는 점입니다. 불법도 이례적인 일도 아니지만, 에이전트에게 "Graphify 설정해 줘"라고 맡기면 코드가 외부 서버에서 인덱싱되는 호스팅 제품 쪽으로 안내받을 수 있다는 뜻입니다. 코드를 밖으로 보내면 안 되는 환경이라면 처음부터 "오픈소스 CLI로, 로컬에서"라고 명시해 요청하는 편이 안전합니다. 스킬과 지시 파일이 에이전트의 행동을 바꾸는 통로라는 점은 [Agent Skills 글](/tech/2026/10/24/agent-skills-aaif.html)과 [AGENTS.md 글](/tech/2026/10/24/agents-md.html)에서 다룬 것과 같은 구조이고, 그 통로가 제품 유통에도 쓰이는 사례로 볼 수 있습니다. 반대로 [HyperFrames 글](/opensource/2026/10/29/hyperframes.html)에서 본 "텔레메트리 기본 활성화"와 달리, Graphify CLI는 텔레메트리가 없고 질의 로그도 기본으로 꺼져 있다는 점은 평가할 만합니다.

**실무에 주는 의미: 작게 시작해 직접 재십시오.** 필자가 권하는 순서는 다음과 같습니다. 첫째, 0.9.70 이상으로 버전을 고정하고 `--code-only`로만 시작합니다. 비용이 0이고 코드가 밖으로 나가지 않습니다. 둘째, 전역 설치 대신 `--project` 설치로 한 저장소에서 시험합니다. 셋째, `graphify benchmark`의 배수 대신 실제로 자주 하는 질문 다섯 개쯤을 골라 그래프가 있을 때와 없을 때 에이전트의 답과 토큰 사용량을 비교합니다. 넷째, strict 모드는 그 결과가 좋을 때만 켭니다. 훅이 에이전트의 모든 검색과 읽기에 끼어들기 때문에, 그래프가 낡았거나 빈틈이 있는 영역에서는 오히려 방해가 될 수 있습니다. 팀에 도입한다면 `graph.json`을 커밋할지, 각자 빌드할지, [MCP](/tech/2026/10/24/mcp-architecture.html) 서버 하나를 공유할지를 먼저 정해야 합니다.

**앞으로 지켜볼 점:** 첫째, 제3자가 코드 과제(예: 실제 이슈 해결)에서 그래프 유무를 비교한 독립 평가가 나오는지입니다. 지금의 근거는 질문 6개입니다. 둘째, 1.0과 그래프 형식의 안정화입니다. `graph.json`에는 `schema_version`(현재 1)이 들어가기 시작했지만, 변경 기록에는 AST 캐시 스키마가 49까지 올라갔다는 기록이 있을 만큼 내부가 빠르게 바뀝니다. 셋째, 오픈소스와 클라우드의 경계입니다. 라이선스는 이미 한 번(MIT에서 Apache-2.0으로) 바뀌었습니다. 이번 변경은 특허 조항이 더해진 허용적 라이선스 간 이동이라 사용자에게 불리하지 않았지만, 핵심 기능이 호스팅 쪽으로 옮겨 가는지는 계속 볼 필요가 있습니다. 넷째, 재현성입니다. 공식 커뮤니티 탐지 문서는 "같은 그래프는 어느 기계에서든 같은 커뮤니티를 낸다"고 적고 있지만, 같은 입력에서 커뮤니티 배정이 달라진다는 이슈(#1667, 0.9.6 기준 보고)가 아직 열려 있고, 공식 팀 공유 가이드는 여전히 `PYTHONHASHSEED=0`을 권합니다. 필자의 두 번 실행은 바이트 단위로 같았지만, 기계와 파이썬 버전이 다른 팀원 사이에서도 같은지는 직접 확인해야 합니다.

- "이 함수를 바꾸면 어디가 영향을 받나", "두 모듈은 어떻게 이어지나" 같은 여러 단계 질문이 잦은 경우
- 코드를 외부로 보낼 수 없어 임베딩 서비스나 호스팅 인덱서를 쓰기 어려운 환경(코드만 추출하는 구성)
- 에이전트의 답에 파일과 줄 번호, 근거 수준이 붙기를 원하는 경우

## 이런 경우엔 다른 도구

- **작은 저장소이거나 한 번짜리 조회라면:** grep과 파일 읽기로 충분합니다. 공식 문서도 약 5만 단어 미만의 말뭉치에서는 그래프가 도움이 되지 않을 수 있다고 경고합니다.
- **문서와 주석을 자연어나 한국어로 검색하는 일이 중심이라면:** 임베딩 기반 검색이 더 맞습니다.
- **편집 중에 컴파일러 수준의 정확한 정의·참조 탐색이 필요하다면:** 언어 서버(LSP)를 그대로 쓰는 것이 맞습니다.
- **리플렉션, 의존성 주입, 프레임워크 배선이 많은 코드라면:** 그래프의 빈틈이 커지므로 결과를 그대로 믿기 어렵습니다.
- **버전 변경 없이 오래 돌아가야 하는 파이프라인이라면:** 1.0 이전의 릴리스 속도를 감당할 수 있는지 먼저 따져 봐야 합니다.
