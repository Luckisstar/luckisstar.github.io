# [오픈소스 소개] Appsmith: 관리자 페이지와 사내 도구를 빠르게 만드는 로우코드 플랫폼

- **저장소:** [appsmithorg/appsmith](https://github.com/appsmithorg/appsmith) · [appsmith.com](https://www.appsmith.com) · [문서](https://docs.appsmith.com)
- **라이선스:** Apache 2.0
- **언어:** TypeScript
- **현황 (2026-10-20 기준):** GitHub 스타 약 4.1만 개, 최신 릴리스 v2.5.0 (10월 9일)

## 한 줄 요약

**위젯을 끌어다 놓고, DB 쿼리나 API 결과를 연결하고, 필요한 로직만 JavaScript로 채워 사내 도구를 만드는 오픈소스 로우코드 플랫폼**입니다. 관리자 패널, 데이터 대시보드, 승인 앱, 고객 지원 도구 같은 내부용 앱을 직접 서버에 설치해 운영할 수 있습니다.

## 어떤 문제를 푸나

회사에는 "DB 테이블을 보고 고치는 화면 하나만 있으면 되는" 일이 많습니다. 주문 상태 변경, 회원 정보 수정, 환불 승인, 재고 확인 같은 작업입니다. 이런 화면을 매번 React와 백엔드 API로 만들면 다음 문제가 생깁니다.

- 비즈니스 가치에 비해 개발 비용이 큽니다. 폼, 테이블, 페이지네이션, 권한 처리를 매번 새로 짭니다.
- 담당 개발자가 바뀌면 유지보수가 끊깁니다.
- 결국 운영팀이 DB 클라이언트로 직접 쿼리를 날리는 위험한 상황이 생깁니다.

Appsmith는 UI 컴포넌트와 데이터 연결을 미리 만들어 두고, 개발자는 **SQL과 JavaScript로 핵심 로직만** 작성하게 합니다. 공식 FAQ는 다른 로우코드 도구와의 차이로 **오픈소스라 벤더 종속이 없고, 셀프 호스팅으로 데이터를 직접 통제할 수 있다**는 점을 꼽습니다.

## 핵심 개념: 위젯, 쿼리, JS 객체, 바인딩

Appsmith 앱은 네 가지 요소로 이뤄집니다.

| 요소 | 역할 |
|---|---|
| **위젯(Widget)** | Table, Form, Input, Button, Select, Chart 같은 UI 컴포넌트. 그리드 캔버스에 끌어다 놓습니다. |
| **데이터소스(Datasource)** | PostgreSQL, MySQL, REST API 같은 외부 데이터 연결 정보. 워크스페이스 단위로 공유됩니다. |
| **쿼리(Query)** | 데이터소스에 보내는 SQL이나 API 요청. 이름을 붙여 `getUsers`처럼 부릅니다. |
| **JS 객체(JS Object)** | 함수와 변수를 모아둔 재사용 가능한 JavaScript 모듈. 복잡한 로직을 담습니다. |

이 요소들을 이어주는 것이 **바인딩(binding)** 입니다. 위젯 속성, 쿼리 본문, 이벤트 핸들러 어디서든 **머스태시 문법** 안에 JavaScript를 쓸 수 있고, 다른 요소를 변수처럼 참조합니다.

{% raw %}
```
 +-----------+  {{ getUsers.data }}   +-----------+
 |  Widget   | <--------------------- |   Query   | --> DB/API
 |  (Table)  | ---------------------> |  (SQL)    |
 +-----------+  {{ nameInput.text }}  +-----------+
       |                                    ^
       | onClick                            | run()
       v                                    |
 +-------------------------------------------+
 |  JS Object: JSObject1.saveUser()          |
 +-------------------------------------------+
```

- **위젯 ← 쿼리:** Table의 데이터 속성에 `{{ getUsers.data }}`를 넣으면 쿼리 결과가 표에 표시됩니다.
- **쿼리 ← 위젯:** SQL 안에 `{{ nameInput.text }}`, `{{ usersTable.selectedRow.id }}`를 넣으면 사용자가 입력하거나 선택한 값이 쿼리에 들어갑니다.
- **위젯 → 액션:** 버튼의 `onClick`에서 쿼리를 실행하거나(`updateUsers.run()`) JS 객체 함수를 호출합니다.
- **반응형 평가:** 참조하는 값이 바뀌면 바인딩이 다시 계산됩니다. 표에서 다른 행을 고르면 폼 값이 자동으로 바뀌는 식입니다.

바인딩 안의 코드는 두 가지 형태로 씁니다.

```javascript
// 한 줄 표현식: 결과가 속성 값이 됩니다
{{ getUsers.data.filter((row) => row.id > 5) }}
{{ statusSelect.selectedOptionValue === "1" ? "활성" : "비활성" }}

// 여러 줄에서 값을 반환하려면 즉시 실행 함수(IIFE)로 감쌉니다
{{
  (function () {
    const rows = getUsers.data;
    return rows.filter((row) => row.id > 5);
  })()
}}
```
{% endraw %}

바인딩이 한 줄로 감당하기 어려워지면 **JS 객체로 옮기는 것**이 공식 권장 방식입니다. JS 객체는 `export default { ... }` 하나만 내보내는 모듈이고, 안에 정의한 함수와 변수를 앱 어디서든 `JSObject1.함수명()`으로 부릅니다. 주의할 점은 JS 객체의 변수는 **값으로 할당**되어, 원본이 바뀌어도 자동 갱신되지 않는다는 것입니다. 바꾸려면 명시적으로 다시 대입해야 합니다.

앱에는 **편집 모드**와 **보기(View) 모드**가 있습니다. 편집 후 오른쪽 위 **Deploy**를 눌러야 사용자가 보는 버전에 반영됩니다.

## 주요 기능

### 1. UI 빌더

- 그리드 캔버스에 위젯을 끌어다 놓고 오른쪽 속성 패널(Property Pane)에서 설정합니다.
- 테마(App theming)와 레이아웃 설정으로 앱 전체의 색상, 글꼴, 모서리 모양을 통일합니다.
- 위젯 표시 여부를 바인딩으로 제어하는 동적 UI를 만들 수 있습니다.
- 기본 위젯으로 부족하면 iframe이나 순수 JavaScript로 **커스텀 위젯**을 만들 수 있습니다.

### 2. 데이터 연결

공식 레퍼런스에 나온 지원 대상은 다음과 같습니다.

| 분류 | 대상 |
|---|---|
| API | REST API, Authenticated API, GraphQL |
| 데이터베이스 | PostgreSQL, MySQL, MongoDB, Microsoft SQL Server, Oracle, Redis, Elasticsearch, Firestore, DynamoDB, Redshift, Snowflake, Databricks, ArangoDB, S3, SMTP |
| SaaS | Google Sheets, Airtable, Salesforce, HubSpot, Jira, Linear, Notion, Slack, Stripe, Twilio, Zendesk, GitHub, Gmail 등 |
| AI | OpenAI, Anthropic, Google AI |

목록에 없는 서비스도 REST API로 연결할 수 있습니다. SQL 쿼리에는 **Prepared Statement(매개변수화된 쿼리)** 가 기본으로 켜져 있어 SQL 인젝션을 막아줍니다. 이 설정은 Postgres, MySQL, MSSQL, Oracle에서 쓸 수 있습니다.

### 3. JavaScript

- 위젯 속성, 이벤트, 쿼리 어디서나 JavaScript를 씁니다.
- JS 객체로 재사용 가능한 로직을 모읍니다.
- 외부 JavaScript 라이브러리를 설치해 쓸 수 있습니다.
- `showAlert`, `navigateTo`, `storeValue` 같은 전역 함수와 현재 로그인 사용자 정보를 담은 `appsmith` 전역 객체를 제공합니다.

### 4. Git 버전 관리

- 앱을 Git 저장소에 연결해 브랜치, 커밋, pull, 병합을 합니다. GitHub, GitLab, Bitbucket, Azure 등 SSH와 배포 키(deploy key)를 지원하는 서비스면 됩니다.
- 기본 브랜치 지정, 브랜치 보호, CI/CD 연동은 Enterprise 기능으로 표시되어 있습니다.
- 브랜치별로 작업하면 여러 사람이 같은 앱을 나눠 편집할 수 있습니다.

### 5. 접근 제어(Granular Access Control)

- 앱, 페이지, 쿼리, 데이터소스, 워크스페이스, 워크플로 같은 리소스마다 생성, 조회, 수정, 삭제 권한을 따로 지정합니다.
- 권한을 묶은 **역할(Role)** 을 사용자나 **사용자 그룹**에 부여합니다.
- 조직 관리자, 워크스페이스 관리자 같은 기본 역할이 있고, 사용자 정의 역할은 Business 플랜 기능입니다.

### 6. 재사용과 자동화 (Business 이상)

- **Packages:** 위젯과 로직을 묶은 UI 모듈, 쿼리 모듈, JS 모듈을 워크스페이스 안의 여러 앱에서 재사용합니다.
- **Workflows:** 웹훅, 앱 내 데이터소스, 크론 스케줄로 트리거되는 서버 측 자동화입니다. v2.5.0부터는 Appsmith 자체 워크플로 엔진으로 바뀌었습니다.
- **Datasource Environments:** 같은 쿼리를 Staging과 Production 데이터소스에 번갈아 연결합니다. 환경 설정은 워크스페이스 단위입니다.

### 7. AI 기능

- **Ask AI:** 편집기에서 자연어로 JavaScript와 SQL을 생성하는 어시스턴트입니다. 조직 관리자가 Claude(Anthropic), OpenAI, Azure OpenAI, 로컬 Ollama 중 하나를 골라 API 키를 등록합니다. v2.0 이상에서 쓸 수 있고, 무료 클라우드(app.appsmith.com)에서는 제공되지 않습니다.
- **AI 데이터소스:** OpenAI, Anthropic, Google AI를 데이터소스로 연결해 앱에서 호출합니다.
- 기존 **Appsmith AI 데이터소스는 2026년 9월 30일 지원이 종료**되어 더 이상 동작하지 않습니다. 쓰고 있었다면 위 데이터소스로 옮겨야 합니다.
- GitHub README는 업무 데이터에 AI 모델을 연결하는 **Appsmith Agents**를 소개하고 있습니다. 다만 개발자 문서에서 구체적인 설정 방법은 찾지 못했으니, 관심이 있다면 [appsmith.com/ai](https://www.appsmith.com/ai)에서 확인하세요.

### 8. 운영

- `appsmithctl`로 인스턴스 백업과 복원, 내부 DB 내보내기를 합니다.
- Google, GitHub, OIDC, SAML 같은 SSO와 이메일, 사용자 도메인, SSL을 설정할 수 있습니다(일부는 플랜에 따라 다름).
- 앱을 기존 웹 서비스에 임베드할 수 있습니다.

## 설치와 시작

### 방법 고르기

| 방법 | 언제 쓰나 |
|---|---|
| [Appsmith Cloud](https://login.appsmith.com/) | 가입만 하고 바로 써보고 싶을 때 |
| Docker (Docker Compose) | 셀프 호스팅의 기본 방법 |
| Kubernetes (Helm) | 고가용성 구성이 필요할 때 |
| AWS AMI, ECS, Azure ACI, Google Cloud Run, DigitalOcean 등 | 각 클라우드에 맞춰 설치할 때 |

### Docker Compose로 설치하기

**사전 준비**

- Docker 20.10.7 이상, Docker Compose 1.29.2 이상
- 방화벽 아웃바운드에서 `cs.appsmith.com` 허용
- 호스트 메모리 **8GB 이상** 권장. 기본 구성은 MongoDB, Redis, PostgreSQL을 Appsmith 컨테이너 안에서 함께 돌리기 때문입니다.

**설치 순서**

1. 작업 폴더를 만들고 이동합니다.

   ```bash
   mkdir appsmith && cd appsmith
   ```

2. `docker-compose.yml`을 만듭니다. `<version>`에는 [GitHub 릴리스](https://github.com/appsmithorg/appsmith/releases)의 태그를 넣습니다.

   ```yaml
   version: "3"
   services:
     appsmith:
       image: index.docker.io/appsmith/appsmith-ee:<version>
       container_name: appsmith
       ports:
         - "80:80"
         - "443:443"
       volumes:
         - ./stacks:/appsmith-stacks
       restart: unless-stopped
   ```

   Community Edition을 쓰려면 `appsmith-ee`를 `appsmith-ce`로 바꿉니다. 태그를 생략하면 `latest`가 쓰이는데, 공식 문서는 운영 환경에서는 **태그를 고정**하라고 권합니다.

3. 컨테이너를 띄웁니다. 권한이 없으면 `sudo`를 붙입니다.

   ```bash
   docker-compose up -d
   ```

4. 브라우저에서 `http://localhost`를 엽니다. 서버가 뜨는 데 최대 5분 정도 걸릴 수 있습니다.
5. 관리자 계정을 만들고, 무료 플랜으로 시작하거나 라이선스 키로 활성화합니다.

모든 데이터는 `./stacks` 폴더에 쌓이므로 이 폴더가 곧 인스턴스입니다. 운영용이라면 SSO, 이메일, 사용자 도메인과 SSL, 백업을 이어서 설정하세요.

## 실전 예제

이후 예제는 공식 튜토리얼과 PostgreSQL 레퍼런스의 흐름을 따릅니다. 튜토리얼은 공용 샘플 DB(`mockdb.internal.appsmith.com`)를 제공하지만, 모든 사용자가 공유하고 매일 초기화되므로 민감한 정보는 넣지 마세요.

{% raw %}
### 예제 1: PostgreSQL 사용자 테이블 CRUD 관리자 화면

**1단계: 데이터소스 연결**

1. 왼쪽 사이드바의 **Data** > **+** > **PostgreSQL**을 고릅니다.
2. 이름을 `usersDB`로 바꾸고 Host, Port(기본 5432), Database, Username, Password를 입력합니다.
3. Connection Mode를 고릅니다. 조회만 할 화면이면 **Read Only**가 안전합니다.
4. **Test Configuration**으로 확인한 뒤 **Save** 합니다.

Appsmith Cloud에서 쓴다면 DB의 `pg_hba.conf`와 방화벽에 Appsmith 클라우드 IP(`18.223.74.85`, `3.131.104.27`)를 허용해야 합니다.

**2단계: 조회 쿼리 (Read)**

**New Query/API**로 `getUsers` 쿼리를 만듭니다. 표 위젯의 페이지 크기와 오프셋을 바인딩하면 서버 측 페이지네이션이 됩니다.

```sql
SELECT * FROM users
ORDER BY id
LIMIT {{ usersTable.pageSize }}
OFFSET {{ usersTable.pageOffset }};
```

쿼리의 **Settings** 탭에서 **Run query on page load**를 켭니다.

**3단계: 표 위젯 연결**

1. **UI** 탭 > **+ New UI element**에서 Table 위젯을 놓고 이름을 `usersTable`로 바꿉니다.
2. 데이터 속성을 `getUsers` 쿼리에 연결합니다. JS 모드로 `{{ getUsers.data }}`를 직접 써도 됩니다.
3. 서버 측 페이지네이션을 켜고, 표의 **onPageChange** 이벤트에서 `getUsers`를 실행하도록 설정합니다. 전체 건수를 보여주려면 **Total records** 속성에 별도 COUNT 쿼리 결과를 연결합니다.

**4단계: 수정 폼 (Update)**

표 오른쪽에 Form 위젯을 놓고 Input 위젯 `nameInput`, `emailInput`을 넣습니다. 각 Input의 Default Value를 선택한 행에 바인딩합니다.

```javascript
{{ usersTable.selectedRow.name }}
{{ usersTable.selectedRow.email }}
```

`updateUser` 쿼리를 만듭니다.

```sql
UPDATE users
SET name = {{ nameInput.text }},
    email = {{ emailInput.text }}
WHERE id = {{ usersTable.selectedRow.id }};
```

폼의 버튼 `onClick`에서 `updateUser`를 실행하고, **onSuccess** 콜백에서 `getUsers`를 다시 실행해 표를 갱신합니다.

**5단계: 추가 (Create)와 삭제 (Delete)**

```sql
-- insertUser
INSERT INTO users (name, email)
VALUES ({{ newNameInput.text }}, {{ newEmailInput.text }});

-- deleteUser
DELETE FROM users WHERE id = {{ usersTable.selectedRow.id }};
```

추가는 Modal 위젯 안에 별도 입력 폼을 두는 방식이 깔끔합니다. 삭제는 실수 방지를 위해 확인 단계를 두는 편이 좋습니다. 쿼리 Settings 탭의 **Request confirmation before running query/API** 옵션을 켜면 실행 전에 확인 창이 뜨고, 표 위젯의 인라인 편집 기능으로 행 삭제를 구성할 수도 있습니다.

**6단계: 배포**

오른쪽 위 **Deploy**를 누르면 보기 모드 URL이 생깁니다. 이 링크를 운영팀에 공유하고, 필요하면 권한으로 접근을 제한합니다.

### 예제 2: REST API 연동

외부 검색 API에 표의 검색어와 페이지 정보를 넘기는 예입니다.

1. **New Query/API** > **REST API**를 고르고 이름을 `searchUsers`로 정합니다.
2. Method는 `POST`, URL에는 엔드포인트를 넣습니다.
3. Headers에 `Content-Type: application/json`과 인증 헤더를 넣습니다.
4. Body를 **JSON**으로 고르고 다음처럼 바인딩합니다.

```json
{
  "q": {{ usersTable.searchText }},
  "limit": {{ usersTable.pageSize }},
  "offset": {{ usersTable.pageOffset }}
}
```

5. 응답 구조에 맞춰 표 데이터를 `{{ searchUsers.data.items }}`처럼 연결합니다.

같은 API에 쿼리를 여러 개 만들 계획이라면 **Authenticated API** 데이터소스를 쓰는 편이 낫습니다. 인증 정보와 기본 URL을 한 곳에서 관리하고 쿼리마다 이어받기 때문입니다. 파일 업로드는 Body를 `MULTIPART_FORM_DATA`로 바꾸고 `{{ Filepicker.files[0] }}`를 넘깁니다.

보안 측면에서 하나 주의할 점이 있습니다. `{{ appsmith.user.email }}`은 **브라우저에서 평가**되므로 사용자가 바꿀 수 있습니다. 서버가 보증하는 현재 사용자 이메일이 필요하면 저장된 쿼리에 `<<APPSMITH_USER_EMAIL>>`을 쓰라고 공식 문서는 안내합니다.

### 예제 3: JS 객체로 저장 로직 정리하기

버튼 `onClick`에 쿼리 실행, 알림, 새로고침을 줄줄이 쓰면 금방 읽기 어려워집니다. JS 객체로 옮기면 깔끔합니다.

**JS** 탭 > **+ New JS object**로 `UserActions`를 만듭니다.

```javascript
export default {
  // 상태 값에 따라 셀 배경색을 돌려줍니다
  statusColor(status) {
    if (status === "active") return "#d1fae5";
    if (status === "blocked") return "#fee2e2";
    return "#f3f4f6";
  },

  // 수정 쿼리를 실행하고 결과에 따라 알림을 띄웁니다
  async saveUser() {
    try {
      await updateUser.run();
      showAlert("저장했습니다", "success");
      await getUsers.run();
    } catch (e) {
      showAlert("저장 실패: " + e.message, "error");
    }
  },
};
```

이제 위젯에서는 호출만 합니다.

- 버튼 `onClick`: `{{ UserActions.saveUser() }}`
- 표의 status 열 > Style > Cell Background: `{{ UserActions.statusColor(currentRow.status) }}`

`currentRow`는 표 열 속성 안에서 현재 행을 가리키는 값입니다. 로그인 사용자 이름을 화면에 띄우려면 Text 위젯에 `Hello {{ appsmith.user.name || appsmith.user.email }}`처럼 씁니다.

### 예제 4: Git으로 버전 관리하기

1. GitHub에 **빈 저장소**를 만듭니다. 비어 있지 않으면 연결이 실패할 수 있습니다.
2. 앱 편집기 아래쪽 바의 **Connect Git**을 누르고 GitHub를 고릅니다.
3. 저장소의 **SSH URL**을 붙여 넣습니다. HTTPS 연결은 지원하지 않습니다.
4. **Generate SSH Keys**로 ECDSA 256 또는 RSA 4096 키를 만들고 복사합니다.
5. GitHub 저장소 Settings > **Deploy keys**에 키를 추가하고 **Allow write access**를 켭니다.
6. Appsmith에서 **Connect Git**을 눌러 마무리합니다.

이후 작업은 일반 Git 흐름과 같습니다. 기능마다 브랜치를 만들어 편집하고 커밋, push 한 뒤 GitHub에서 PR로 병합합니다. 병합 충돌은 Appsmith 안이 아니라 Git 서비스나 로컬에서 해결하고, 앱에서 **Pull** 하거나 **Discard and Pull**로 반영합니다.

알아둘 점:

- Git 연결과 해제에는 워크스페이스의 앱 **Create 권한**이 필요합니다.
- Appsmith 버전이 올라가면 위젯 구조(DSL) 변경분을 자동 커밋하는 **Auto-Commit**이 있습니다. 끄면 시스템 변경이 커밋되지 않은 채 남을 수 있습니다.
- **Disconnect Git**은 되돌릴 수 없고, 같은 저장소에 다시 연결할 수 없습니다. 다시 연결하려면 새 빈 저장소가 필요합니다.
- 같은 페이지를 같은 브랜치에서 여러 명이 동시에 고치면 작업이 사라질 수 있습니다. 공식 FAQ는 브랜치를 나눠 작업하라고 권합니다.

## 실무 팁 & 자주 겪는 문제

**SQL 바인딩에 따옴표를 직접 붙이지 마세요**

Prepared Statement가 켜져 있으면 바인딩 값은 매개변수로 넘어가고 필요한 따옴표 처리를 Appsmith가 합니다. 반대로 **테이블 이름을 동적으로 바꾸거나, 쿼리 전체나 WHERE 절 일부를 조건부로 조립**하면 Prepared Statement로 처리할 수 없어 쿼리 설정에서 꺼야 합니다. 이때는 SQL 인젝션 위험을 직접 관리해야 하니, 가능하면 쿼리 구조를 고정하는 쪽으로 설계하세요.

**로컬 DB에 연결이 안 될 때**

셀프 호스팅 Appsmith는 Docker 컨테이너 안에서 돌기 때문에 `localhost`가 호스트 PC를 가리키지 않습니다. 공식 문서는 두 방법을 안내합니다.

- `host.docker.internal`: 셀프 호스팅 개발용. Docker Desktop 밖의 운영 환경에서는 동작하지 않습니다.
- ngrok: 로컬 DB를 외부 주소로 노출해 연결합니다. 클라우드 버전에서도 쓸 수 있고 공식 권장 방법입니다.

**업그레이드 후 서버가 안 뜰 때 (체크포인트)**

일부 릴리스는 반드시 거쳐야 하는 **체크포인트**입니다. 건너뛰고 올리면 백엔드 로그에 `APPSMITH BACKEND START ABORTED`로 시작하는 체크포인트 누락(CHECKPOINT MISSED) 메시지가 찍히고 서버가 멈춥니다. 로그에 적힌 버전으로 이미지 태그를 되돌려 띄운 뒤, **Admin Settings > Instance > Admin central**에서 체크포인트를 완료하고 다시 올리면 됩니다.

지금 시점에 특히 중요한 것은 **v2.5.0 워크플로 엔진 전환**입니다. v2.6에서 기존 엔진(Temporal)이 제거되므로, Workflows를 쓰는 셀프 호스팅 인스턴스는 v2.5.x에서 진행 중인 실행이 끝나기를 기다려 체크포인트를 처리한 뒤 v2.6으로 올려야 합니다.

**v2.5.0 업그레이드 시 확인할 것**

릴리스 노트에 따르면 Git에 연결된 앱은 다음에 열 때 서버 스키마 13으로 바뀌며 시스템 커밋이 한 번 생길 수 있고, 이 버전에서 내보낸 앱은 구버전 서버로 가져올 수 없습니다. 또 데이터소스 연결 설정을 바꾸면 인증 정보를 다시 입력해야 합니다.

**백업은 자동화하세요**

```bash
docker-compose exec -it appsmith appsmithctl backup
```

백업은 컨테이너의 `/appsmith-stacks/data/backup/`, 호스트의 `./stacks/data/backup/`에 저장됩니다. 대화형으로 실행하면 비밀번호로 암호화하는데, **이 비밀번호를 잃으면 복원할 수 없습니다.** `--non-interactive`로 돌리면 암호화되지 않은 파일이 만들어지므로 보관에 주의하고, 이 경우 복원에 원본 인스턴스의 `APPSMITH_ENCRYPTION_PASSWORD`, `APPSMITH_ENCRYPTION_SALT` 값이 필요하니 따로 저장해 두세요. 외부 PostgreSQL(Keycloak, Temporal용)은 백업에 포함되지 않습니다. S3 자동 업로드는 유료 플랜 기능입니다.

**환경 분리**

개발용 DB와 운영 DB를 같은 앱에서 바꿔 쓰고 싶다면 Business 플랜의 Datasource Environments를 쓰거나, Git 브랜치와 별도 인스턴스로 환경을 나누는 방법을 씁니다.

**클라우드 데이터 위치**

공식 FAQ에 따르면 Appsmith Cloud의 데이터는 미국 서버에서 저장, 처리됩니다. 데이터 위치 규정이 있다면 셀프 호스팅을 고려하세요.

## 비슷한 도구와 비교

| 항목 | Appsmith | Retool | Budibase | ToolJet |
|---|---|---|---|---|
| 소스 공개 | 오픈소스 (Apache 2.0) | 상용 | 오픈소스 (라이선스 구성은 저장소 확인) | 오픈소스 (AGPL-3.0) |
| 셀프 호스팅 | 지원 | 유료 플랜에서 지원하는 것으로 알려짐 | 지원 | 지원 |
| 로직 작성 | JavaScript 중심 | JavaScript 중심 | 로우코드 자동화 + JS | JavaScript, Python |
| 내장 DB | 없음 (외부 연결 중심) | 제공하는 것으로 알려짐 | 제공 | 제공 |
| Git 연동 | 지원 (무료 플랜은 저장소 3개) | 상위 플랜 | 확인 필요 | 확인 필요 |
| GitHub 스타 | 약 4.1만 | 해당 없음 | 약 2.8만 | 약 4.1만 |

Appsmith 외 도구의 기능과 플랜은 이 글에서 공식 문서로 검증하지 않았으므로 도입 전에 직접 확인하세요. 대체로 Retool은 완성도와 생태계가 강한 상용 제품, Budibase는 내장 DB와 폼 중심의 간단한 앱에 강한 편, ToolJet은 Appsmith와 가장 비슷한 위치의 오픈소스 대안으로 이야기됩니다. Appsmith는 **오픈소스 + JavaScript 중심 + Git 워크플로**의 조합이 강점입니다.

## 장점과 한계

**장점**

- Apache 2.0 오픈소스이고, Docker 한 개로 셀프 호스팅할 수 있습니다.
- 데이터베이스, API, SaaS, AI 서비스까지 연결 대상이 넓습니다.
- 바인딩과 JS 객체로 "로우코드지만 코드를 막지 않는" 구조입니다. 개발자가 답답함을 덜 느낍니다.
- Prepared Statement가 기본이라 안전한 쿼리를 쓰기 쉽습니다.
- Git 연동으로 코드 리뷰, 브랜치 작업, 롤백이 가능합니다.
- 튜토리얼, 템플릿, 공식 문서가 잘 정리되어 있습니다.

**한계**

- 사용자 정의 역할, 감사 로그, Workflows, Packages, 환경 분리 등 팀 운영에 중요한 기능이 **Business 이상 유료 플랜**에 있습니다.
- 브랜치 보호, 기본 브랜치 지정, CI/CD, SAML/OIDC SSO는 **Enterprise** 기능입니다.
- 기본 Docker 구성은 MongoDB, Redis, PostgreSQL을 한 컨테이너에 넣어 메모리를 8GB 이상 권장합니다.
- 체크포인트 버전이 있어 업그레이드를 계획적으로 해야 합니다.
- Git 연결은 SSH만 지원하고, 병합 충돌은 Appsmith 밖에서 해결해야 합니다.
- 고객용 서비스처럼 디자인 자유도와 성능이 중요한 앱에는 맞지 않습니다. 어디까지나 **내부 도구**용입니다.

## 이런 분께 추천

- 운영팀이 쓸 관리자 화면을 빨리 만들어야 하는 백엔드 개발자
- SQL과 JavaScript에 익숙하고, 프런트엔드 작업에 시간을 덜 쓰고 싶은 분
- 사내 데이터를 외부 SaaS에 맡기기 어려운 팀
- Retool 같은 상용 도구의 대안으로 오픈소스를 검토하는 팀
- 내부 도구도 Git으로 리뷰하고 버전 관리하고 싶은 조직

**이런 경우엔 다른 도구를 고려하세요**

- 고객에게 직접 노출되는 서비스 화면이 목적이라면 일반 웹 프레임워크가 낫습니다.
- 코드를 전혀 쓰지 않는 비개발자만으로 만들어야 한다면, 폼과 내장 DB 중심의 노코드 도구가 더 쉬울 수 있습니다.
- 서버 운영 인력이 없고 데이터 위치 제약도 없다면, 셀프 호스팅보다 클라우드나 상용 SaaS가 총비용이 낮을 수 있습니다.
- 세밀한 권한과 SSO가 필수인데 유료 플랜 도입이 어렵다면, 각 도구의 무료 범위를 먼저 비교해 보세요.
