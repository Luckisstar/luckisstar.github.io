# [오픈소스 소개] Orca: 여러 코딩 에이전트를 워크트리별로 나란히 돌리는 작업 공간

- **저장소:** [stablyai/orca](https://github.com/stablyai/orca) · [공식 사이트](https://www.onorca.dev) · [문서](https://www.onorca.dev/docs)
- **라이선스:** MIT (LICENSE 저작권 표기: Lovecast Inc.)
- **언어:** TypeScript (Electron 데스크톱 앱, 모바일 앱과 릴레이 서버 포함)
- **현황 (2026-10-27 기준):** GitHub 스타 약 10.7만 개, 포크 약 6,700개, 커밋 약 1만 6,700개, 최신 안정 릴리스 v1.4.241 (2026년 10월 26일). 릴리스가 거의 매일 나오는 활발한 프로젝트입니다.
- **도입 전 확인할 점:** **기본 설정에서 Orca는 Claude Code에 `--dangerously-skip-permissions`, Codex에 `--dangerously-bypass-approvals-and-sandbox`처럼 각 에이전트의 권한 확인 우회 플래그를 붙여 실행합니다.** 공식 문서 스스로 “워크트리는 격리된 체크아웃일 뿐 보안 샌드박스가 아니다”라고 경고하므로, 신뢰하지 않는 작업이라면 Settings → Agents → Agent Permissions에서 **Manual**로 바꾸고 쓰는 것이 안전합니다. 익명 사용 통계(텔레메트리)도 기본으로 켜져 있으며 끌 수 있습니다. 모바일 앱과 원격 서버는 베타, 오케스트레이션은 실험 기능입니다.

## 한 줄 요약

**Orca는 코딩 에이전트 자체가 아니라, 여러 CLI 에이전트를 git 워크트리 하나에 하나씩 배치해 나란히 돌리고 결과를 비교·리뷰·커밋하는 데스크톱 작업 공간입니다.** 이미 Claude Code나 Codex 구독을 쓰고 있고, 한 번에 에이전트 하나만 기다리는 흐름이 답답한 개발자를 위한 도구입니다.

## 어떤 문제를 푸나

코딩 에이전트를 하나만 쓸 때는 터미널 하나로 충분합니다. 둘 이상을 동시에 돌리기 시작하면 문제가 생깁니다.

- **같은 디렉터리에서 두 에이전트가 파일을 고치면 서로의 변경을 덮어씁니다.** 브랜치를 바꾸거나 stash를 하면 다른 에이전트의 작업 상태가 흔들립니다.
- 에이전트마다 터미널 창이 흩어져 **누가 끝났고 누가 내 승인을 기다리는지** 일일이 들어가 봐야 합니다.
- 결과 diff를 비교하고 피드백을 주려면 줄 번호를 복사해 프롬프트에 붙여 넣는 수작업이 반복됩니다.

Orca는 이를 **“작업 하나 = git 워크트리 하나 = 에이전트 터미널 하나”** 라는 규칙으로 풉니다. 공식 문서의 표현을 빌리면 Orca는 “worktree-native”이며, 작업마다 `git worktree`로 디스크에 별도 복사본을 만들기 때문에 병렬 에이전트가 서로의 파일을 밟지 않습니다. 문서가 제시하는 대표 시나리오는 “같은 버그를 세 에이전트에게 동시에 맡기고 가장 나은 결과를 고른다”입니다.

## 핵심 개념

| 개념 | 설명 |
|---|---|
| 워크트리(worktree) | `git worktree`로 만든 독립 작업 디렉터리. 브랜치, 파일, 에이전트 터미널을 각각 가집니다 |
| 기준 ref(base ref) | 저장소의 기본 기준점. 보통 `origin/main`입니다 |
| 시작 ref(start-from ref) | 새 워크트리가 갈라져 나오는 지점. 기준 ref, 다른 브랜치, 커밋 SHA, 원격 브랜치 중 고릅니다 |
| 에이전트 세션 | 워크트리 안의 터미널 하나에서 도는 CLI 에이전트 하나. 작업 중, 입력 대기, 완료, 실패 상태를 추적합니다 |
| `orca.yaml` | 저장소 루트에 두는 프로젝트 설정. 설치 스크립트, 기본 탭, 공유 디렉터리 등을 정합니다 |
| `.worktreeinclude` | 새 워크트리로 **복사**할 gitignore 대상 파일 목록(예: `.env`) |
| 실행 위치(Run on) | 워크트리가 실제로 도는 곳. 로컬, SSH 호스트, 원격 Orca 서버, 작업 공간별 클라우드 VM 중 선택 |

공식 문서가 “Orca가 아닌 것”으로 꼽는 세 가지도 위치를 이해하는 데 도움이 됩니다. **모델이 아니고**(각자의 Claude, Codex, OpenCode 구독을 씀), **git 대체품이 아니며**(모든 워크트리는 진짜 git 워크트리라 `cd`해서 평범한 git을 써도 됨), **호스팅 VPS 상품이 아닙니다**(원격 실행도 사용자가 가진 머신과 클라우드 계정을 씀).

## 동작 원리

저장소를 얕게 받아 확인한 구조는 Electron 데스크톱 앱(`src/main`, `src/renderer`, `src/preload`), CLI(`src/cli`), 모바일 앱(`mobile/`), 모바일과 데스크톱을 잇는 릴레이 서버(`cloud/`), 운영체제별 네이티브 모듈(`native/`), 에이전트용 스킬(`skills/`)로 나뉩니다. `package.json` 기준으로 Electron, React, `node-pty`(가상 터미널), `@xterm/xterm`(터미널 렌더링), `monaco-editor`(VS Code의 편집기 컴포넌트)를 씁니다.

```
 저장소(주 체크아웃)
   │  Create Worktree: git fetch → git worktree add (백그라운드)
   ▼
 ┌─────────────────────────────────────────────┐
 │ 워크트리 A        워크트리 B       워크트리 C │
 │ ├ orca.yaml setup  ├ setup         ├ setup    │
 │ ├ 에이전트 터미널   ├ Codex         ├ Cursor   │
 │ │ (Claude Code)    │               │          │
 │ └ 브라우저 탭       └ ...           └ ...      │
 └──────────┬──────────────────────────────────┘
            │ OSC 터미널 제목 + 에이전트 훅으로 상태 감지
            ▼
 사이드바 상태 표시 · 알림 · Agent Dashboard · 모바일 앱
            │
            ▼
 diff 보기 → Annotate AI Diff → 커밋/푸시/PR → 나머지 워크트리 삭제
```

1. **워크트리 생성:** 생성 대화상자를 제출하면 창은 바로 닫히고 `git fetch`와 `git worktree add`가 백그라운드에서 진행됩니다. 실패하면 오류와 재시도 버튼을 보여 줍니다.
2. **환경 준비:** 새 워크트리는 깨끗한 체크아웃이라 `node_modules`나 `.env` 같은 gitignore 대상이 없습니다. Orca는 설정의 공유 경로, `orca.yaml`의 `worktree.sharedDirectories`(링크로 공유), `.worktreeinclude`(복사) 세 가지로 이를 채웁니다.
3. **에이전트 실행:** 에이전트 콤보박스에서 고르면 해당 CLI를 워크트리 디렉터리에서 실행합니다. 문서는 Orca가 “에이전트 콤보박스는 터미널에서 프로세스를 띄울 뿐”이라고 설명합니다. 즉 에이전트 내부에 끼어드는 방식이 아니라 **터미널 수준에서 감싸는 방식**입니다.
4. **상태 감지:** 상태는 터미널의 OSC 제목 시퀀스(터미널 창 제목을 바꾸는 제어 문자열)와 에이전트 훅으로 판단합니다. Claude Code, Codex 등 이를 내보내는 에이전트는 작업 중, 입력 대기, 완료 상태가 사이드바에 표시되고, 작업 중에서 대기로 바뀌는 순간 알림이 갑니다. 콤보박스를 거치지 않고 터미널에 직접 실행 파일을 치면 인식하지 못할 수 있다고 문서는 안내합니다.

## 주요 기능

### 병렬 워크트리와 상태 추적

워크트리마다 탭과 분할 레이아웃이 따로 저장되어, 워크트리를 바꾸면 화면 전체가 바뀝니다. 사이드바의 상태 아이콘은 다음과 같습니다(공식 문서 기준).

| 표시 | 의미 |
|---|---|
| 회전 아이콘 | 작업 중 |
| 주황 물음표 | 권한이나 입력을 기다림 |
| 초록 점/체크 | 완료 |
| 빨간 점 | 막힘, 중단, 실패 |
| 회색 점 | 유휴 |

실험 기능인 **Agent Dashboard**를 켜면 모든 워크트리의 에이전트를 Needs You, Working, Done, Idle 칸반으로 볼 수 있습니다.

### 지원 에이전트

README에는 34개 에이전트 배지와 “+ any CLI agent”가 있고, 공식 문서의 지원 표에는 40개 항목이 있습니다. Claude Code와 Codex는 사용량 추적과 계정 전환(hot-swap)까지 깊게 연동되고, 나머지 상당수는 “Auto-setup”(실행 설정 자동화) 수준입니다. 표에 없는 에이전트도 터미널에서 돌아가면 쓸 수 있다는 것이 README의 설명입니다.

### Annotate AI Diff

diff의 아무 줄에나 코멘트를 달고, 리뷰가 끝나면 **Send to agent**로 모든 코멘트를 줄 위치와 함께 한 번에 묶어 보냅니다. 문서는 코멘트를 하나씩 보내면 에이전트가 이리저리 흔들리기 때문에 한 번의 수정 패스로 묶는 편이 낫다고 설명합니다. 코멘트는 에이전트가 고친 뒤에도 해당 줄에 남아 수정 여부를 확인하는 데 쓸 수 있습니다.

### 원격 실행 네 가지

| 모드 | 파일과 에이전트 위치 | 적합한 경우 |
|---|---|---|
| 로컬 | 내 데스크톱 | 일상 작업 |
| SSH 대상 | SSH로 붙는 원격 호스트 | 이미 있는 개발 서버, GPU 머신 |
| 원격 Orca 서버(베타) | Orca 데스크톱 또는 `orca serve`가 도는 머신 | 노트북을 덮어도 계속 돌아야 할 때, 모바일 연결 |
| 클라우드 VM(실험) | 작업 공간마다 만드는 일회용 VM/샌드박스 | 작업별 깨끗한 격리 환경 |

SSH 워크트리는 첫 연결 때 Orca가 원격 호스트에 자신을 설치하고, 노트북 앱을 닫아도 원격 터미널 세션이 유지됩니다. 클라우드 VM은 Orca가 VM을 파는 것이 아니라, 저장소의 레시피 스크립트로 사용자의 클라우드 계정(Vercel Sandbox, Fly, Modal, Docker 등)에서 환경을 만들고 지우는 얇은 래퍼라고 문서가 명시합니다.

### 모바일 앱(베타)

iOS와 Android 앱을 데스크톱과 페어링하면 워크트리별 에이전트 상태를 보고, 입력을 기다리는 에이전트에 “continue” 같은 짧은 답을 보내고, 완료 푸시 알림을 받을 수 있습니다. 문서는 모바일 앱을 “편집기가 아니라 이미 돌고 있는 데스크톱의 리모컨”이라고 규정합니다.

### Orca CLI와 스킬

`orca` 명령으로 실행 중인 Orca를 스크립트에서 조종합니다. 워크트리 생성, 터미널에 텍스트 보내기, 내장 브라우저 조작(`snapshot`, `click`, `fill`) 등이 가능합니다. 에이전트가 이 CLI를 쓰도록 `orca-cli`, `orchestration`, `computer-use` 같은 스킬을 `npx skills add`로 설치할 수 있습니다. 공개 스킬은 얇은 SKILL.md 스텁이고, 실제 명령 안내는 실행 중인 CLI가 버전에 맞춰 내려 주는 구조라서 앱 버전과 스킬 내용이 어긋나지 않게 했다고 설명합니다.

### 그 밖의 기능

WebGL 렌더링 터미널과 분할, Chromium 창의 UI 요소를 클릭해 HTML·CSS·스크린샷을 에이전트 프롬프트로 보내는 Design Mode, GitHub·Linear·Jira·GitLab 작업 항목에서 바로 워크트리 만들기, Claude·Codex 사용량과 한도 초기화 시각 표시 등이 있습니다.

## 설치와 시작

README와 공식 설치 문서에 있는 방법만 옮깁니다.

- **직접 다운로드:** [onOrca.dev 다운로드 페이지](https://onorca.dev/download) 또는 [GitHub 최신 릴리스](https://github.com/stablyai/orca/releases/latest)에서 macOS(Apple Silicon, Intel), Windows 설치 파일, Linux AppImage를 받습니다. Linux는 `.deb`, `.rpm`도 있습니다.
- **Homebrew(macOS):**

```bash
# 반드시 전체 이름을 씁니다. 그냥 `orca`는 관련 없는 Plotly cask입니다.
brew install --cask stablyai/orca/orca
brew upgrade --cask stablyai/orca/orca
```

- **Arch Linux(AUR):**

```bash
yay -S stably-orca-bin
```

Linux에서는 CLI 이름이 `orca`가 아니라 **`orca-ide`** 입니다. GNOME 데스크톱의 화면 낭독기 Orca가 이미 `/usr/bin/orca`를 쓰고 있기 때문입니다. 공식 문서는 `command -v orca`로 설치를 확인하지 말라고 경고합니다. GNOME에서는 화면 낭독기가 잡히기 때문입니다. Orca 안의 터미널에서는 그냥 `orca`가 동작합니다.

Linux AppImage만 자동 업데이트되고, `.deb`·`.rpm`은 Orca가 설치 명령을 복사해 주면 사용자가 직접 실행하는 방식입니다. 첫 실행 시 Orca는 홈 디렉터리 접근 권한을 묻고, `~/.claude`, `~/.codex`, Ghostty 터미널 설정이 있으면 가져올지 묻습니다.

## 실전 예제

아래 예제는 모두 공식 문서의 절차와 명령을 바탕으로 정리했습니다. **Orca는 GUI 데스크톱 앱이라 이 글을 쓰는 환경에서 직접 실행해 보지는 못했습니다.** 명령의 정확한 옵션은 설치한 버전의 `orca` 도움말과 [CLI 레퍼런스](https://www.onorca.dev/docs/cli/reference)로 확인하세요.

### 예제 1. 같은 버그를 세 에이전트에게 맡기고 이긴 쪽을 고르기

공식 문서가 “가장 중요한 페이지”라고 부르는 첫 세션 흐름입니다.

1. 사이드바의 **Add Repo**로 로컬 체크아웃을 등록합니다. 기본 브랜치가 기준 ref가 됩니다.
2. 저장소 이름 옆 **+** 를 눌러 `fix-login-race` 워크트리를 만들고, 에이전트로 Claude Code를 고릅니다.
3. 같은 과정을 두 번 더 해 `fix-login-race-2`(Codex), `fix-login-race-3`(Cursor CLI)을 만듭니다.
4. 세 터미널에 같은 프롬프트를 넣습니다.
5. 사이드바 상태 아이콘을 보다가 `Cmd-J`(macOS) / `Ctrl-Shift-J`(Windows, Linux)로 워크트리를 오갑니다.
6. 각 워크트리의 diff를 열어 비교하고, 가장 나은 쪽에 Annotate AI Diff로 코멘트를 보내 다듬은 뒤 커밋·푸시합니다. 나머지 두 워크트리는 클릭 한 번으로 브랜치와 함께 지웁니다.

**주의:** 세 에이전트가 같은 저장소를 고치므로 구독 사용량도 세 배로 듭니다. 간단한 버그에는 하나만 돌리는 편이 낫고, 접근법이 갈릴 만한 문제에서 이 방식이 의미가 있습니다.

### 예제 2. `orca.yaml`과 `.worktreeinclude`로 새 워크트리 준비 자동화

새 워크트리마다 `pnpm install`을 직접 치고 `.env`를 복사하는 일을 없애는 설정입니다. 공식 문서 예제를 그대로 옮겼습니다.

```yaml
# orca.yaml (저장소 루트)
scripts:
  setup: |
    pnpm install
  archive: |
    echo Workspace archived
setupAgentStartupPolicy: wait-for-setup
defaultTabs:
  - title: Agent
  - title: Git status
    command: git status --short
worktree:
  sharedDirectories:
    - .cache
```

```text
# .worktreeinclude (저장소 루트)
.env
.env.local
.vscode/settings.json
```

- `setupAgentStartupPolicy: wait-for-setup`은 설치가 끝난 뒤에 에이전트를 시작하게 합니다. 기본값은 `start-immediately`입니다.
- 첫 번째 탭에 명령을 두지 않은 것은 의도입니다. 데스크톱에서 에이전트와 함께 만들면 **첫 탭의 명령은 실행되지 않고 에이전트가 그 자리를 차지**합니다.
- `sharedDirectories`는 주 체크아웃의 디렉터리에 **링크**를 걸어 공유하고(편집이 원본에 반영됨), `.worktreeinclude`는 워크트리마다 **복사본**을 만듭니다. 두 경우 모두 대상이 이미 존재하고 gitignore되어 있어야 하며, 추적 중인 파일은 건너뜁니다.
- `.worktreeinclude`는 한 줄에 경로 하나만 받고 글롭(`*`)과 부정(`!`)은 무시합니다. 복사 한도는 워크트리당 2 GiB, 항목 5만 개입니다.
- **YAML에 중복 키가 하나라도 있으면 파일 전체가 거부**되어 설치, 탭, 공유 설정이 한꺼번에 사라집니다. 설정이 먹지 않으면 이것부터 확인하라고 문서가 안내합니다.

설치 스크립트에는 `ORCA_ROOT_PATH`(주 체크아웃 경로), `ORCA_WORKTREE_PATH`(새 워크트리 경로), `ORCA_WORKSPACE_NAME` 환경 변수가 주어집니다.

### 예제 3. CLI로 워크트리와 에이전트 터미널 스크립팅

Orca 안의 터미널이나 등록된 CLI에서 실행 중인 Orca를 조종합니다. 공식 CLI 개요 문서의 명령입니다.

```bash
orca status --json

# 이슈 123에 연결된 워크트리 만들기
orca worktree create --repo id:<repoId> --name my-task --issue 123 --json
orca worktree ps --json

# 에이전트 터미널에 입력 보내고, 화면이 조용해질 때까지 기다리기
orca terminal send --text "continue" --enter --json
orca terminal wait --for tui-idle --timeout-ms 30000 --json

# 테스트 전용 터미널 만들기
orca terminal create --worktree path:/projects/app --command "npm test" --json
```

`--json` 출력 덕분에 셸 스크립트나 다른 에이전트가 결과를 파싱해 다음 단계를 정할 수 있습니다. Linux 셸에서는 `orca` 대신 `orca-ide`를 씁니다.

### 예제 4. 오케스트레이션: 조정자 에이전트가 작업자 에이전트를 감독하기

여러 작업을 나눠 맡기고 완료 여부를 추적해야 할 때 쓰는 구조화된 다중 에이전트 계층입니다. **실험 기능이라 Settings → Experimental에서 켜야 합니다.** 개념은 Run(작업 묶음과 받은편지함), Task(작업 항목과 의존성), Dispatch(작업을 터미널 하나에 배정한 한 번의 시도), Message, Decision gate(결정이 날 때까지 작업을 막는 질문)입니다.

```bash
orca orchestration run-create --objective "Split checkout QA and summarize blockers" --json
orca orchestration task-create --spec "Audit billing settings for mobile layout" --task-title "Billing audit" --json

# 새 자식 워크트리에서 Codex 작업자 시작
orca orchestration worker-start --task <taskId> --worktree new-child \
  --name billing-audit --agent codex --setup run --json

# 작업자의 완료, 질문, 에스컬레이션 기다리기
orca orchestration check --wait --types worker_done,escalation,question \
  --timeout-ms 900000 --json
```

작업자는 끝나면 `worker_done` 메시지를 `--task-id`, `--dispatch-id`와 함께 정확히 한 번 보내야 하고, 막히면 `orca orchestration ask`로 조정자에게 질문합니다. 공식 문서는 단발성 프롬프트에는 `orca terminal send`로 충분하고, 소유권과 완료 추적이 필요할 때만 이 계층을 쓰라고 권합니다.

### 예제 5. 노트북을 덮어도 에이전트가 계속 돌게 하기

원격 Orca 서버(베타)는 다른 머신이 프로젝트, 워크트리, 터미널, 에이전트 세션을 갖고 노트북은 화면만 맡는 구성입니다. 공식 문서가 권하는 가장 쉬운 방법은 두 컴퓨터에 Orca와 Tailscale을 설치하고, 서버 쪽 **Settings → Remote Orca Servers → Advertise this app as a server → New Link**로 접속 링크를 만들어 클라이언트에 붙여 넣는 것입니다. 화면 없는 Linux 서버라면 다음처럼 시작합니다.

```bash
orca-ide serve --pairing-address <reachable-tailscale-ip-or-hostname>

# 서버 셸에서 에이전트 계정 등록
orca account add --agent claude
orca account add --agent codex
```

노트북에서 로그인한 에이전트 계정은 서버로 넘어가지 않으므로 **에이전트 CLI 설치와 인증은 서버에서 따로** 해야 합니다. 문서는 서버와 클라이언트를 같은 Tailscale 망이나 LAN 같은 사설 경로에만 두라고 권합니다.

## 실무 팁 & 자주 겪는 문제

공식 Troubleshooting 문서와 설정 문서를 바탕으로 정리했습니다.

- **권한 모드부터 정합니다.** 기본값은 각 에이전트의 확인 우회 플래그(Gemini, Cursor 등은 `--yolo`)를 붙인 “Yolo” 실행입니다. Settings → Agents → Agent Permissions에서 **Manual**로 전체 전환할 수 있고, 특정 에이전트의 실행 인수를 직접 고쳐 둔 경우에는 전체 전환이 그 설정을 덮지 않습니다.
- **에이전트가 시작되지 않으면** Orca 밖 터미널에서 해당 CLI를 직접 실행해 봅니다. 거기서도 실패하면 Orca가 아니라 CLI 설치나 인증 문제입니다. Orca가 보는 `PATH`도 Settings → Agents에서 확인합니다.
- **워크트리 생성이 실패하면** 시작 ref가 아직 fetch되지 않았거나, 같은 브랜치의 워크트리가 이미 있는 경우가 많습니다. `git fetch origin` 후 다시 시도합니다.
- **상태 아이콘이 안 뜨면** 에이전트를 콤보박스로 띄웠는지 확인합니다. 셸에서 실행 파일을 직접 치면 인식하지 못할 수 있습니다.
- **메모리가 부족하면** 쓰지 않는 워크트리를 닫습니다. 워크트리마다 파일 감시가 살아 있고, 브라우저 탭이 많은 분할 레이아웃이 RAM을 가장 많이 씁니다.
- **텔레메트리를 끄려면** Settings → Privacy에서 “Share anonymous usage data”를 끄거나, `DO_NOT_TRACK=1` 또는 `ORCA_TELEMETRY_DISABLED=1`을 설정합니다. 문서에 따르면 파일 내용, 프롬프트, 에이전트 출력, 저장소·브랜치 이름, 경로는 보내지 않고, 사용한 에이전트 종류와 토큰 수 등은 수집합니다. 저장 위치는 PostHog Cloud 미국 리전입니다.
- **Homebrew로 설치할 때 `brew install --cask orca`라고 치면 다른 앱(Plotly의 orca)이 설치됩니다.** 반드시 `stablyai/orca/orca`를 씁니다.
- **SSH 원격 터미널이 안 뜨면** 원격에 Node와 네트워크 접근이 있는지, Linux라면 C/C++ 빌드 도구(make, g++ 또는 clang++, python3)가 있는지 확인한 뒤 다시 연결합니다.

## 장점과 한계

### 장점

- **이미 쓰는 에이전트와 구독을 그대로 씁니다.** 새 에이전트나 모델을 배울 필요가 없고, 에이전트를 바꿔도 작업 공간은 그대로입니다.
- **워크트리라는 git 기본 기능 위에 지어져** 빠져나가기 쉽습니다. Orca를 지워도 브랜치와 워크트리는 평범한 git 상태로 남습니다.
- `orca.yaml`의 설치 스크립트, 공유 디렉터리, 복사 목록으로 “새 워크트리는 환경이 비어 있다”는 워크트리 방식의 고질적인 불편을 정면으로 다룹니다.
- 상태 감지, 알림, 모바일 앱, 원격 서버로 **에이전트를 기다리는 시간을 사람이 다른 일에 쓸 수 있게** 해 줍니다.
- 문서가 매우 구체적입니다. `orca.yaml`의 한도, 거부 조건, 어느 체크아웃에서 설정을 읽는지까지 표로 정리되어 있습니다.

### 한계

- **기본 권한 설정이 공격적입니다.** 확인 우회 플래그가 기본이고, 워크트리는 파일 충돌을 막을 뿐 에이전트가 홈 디렉터리나 네트워크에 접근하는 것을 막지 않습니다.
- **비용이 에이전트 수만큼 늘어납니다.** 병렬 실행은 구독 한도와 API 비용을 그만큼 빨리 씁니다.
- **변화 속도가 매우 빠릅니다.** 릴리스가 거의 매일 나오고 README도 “기능 목록은 항상 뒤처져 있으니 변경 기록이 진짜 기능 목록”이라고 적습니다. 문서와 실제 동작이 어긋날 여지가 있습니다.
- **주요 원격 기능이 아직 베타나 실험 단계입니다.** 모바일 앱, 원격 Orca 서버는 베타, 오케스트레이션, 클라우드 VM, Agent Dashboard는 실험 기능입니다.
- **Electron 앱이라 리소스를 씁니다.** 문서도 워크트리와 브라우저 탭이 많아지면 메모리 부담이 크다고 인정합니다.
- 상태 감지는 에이전트가 OSC 제목이나 훅을 내보내는지에 달려 있어, 지원 수준이 에이전트마다 다릅니다.

## 인사이트

**왜 지금 중요한가: 병목이 “에이전트의 실력”에서 “사람의 주의력”으로 옮겨 가고 있습니다.** 코딩 에이전트가 한 작업을 수십 분씩 혼자 진행할 수 있게 되면서, 개발자의 하루는 에이전트를 기다리는 시간과 결과를 검토하는 시간으로 채워지기 시작했습니다. Orca의 기능 대부분(상태 아이콘, 완료 알림, 입력 대기 칸반, 모바일 푸시, 묶음 diff 리뷰)은 모델 성능이 아니라 **사람이 여러 에이전트에게 주의를 배분하는 문제**를 겨냥합니다. 스타가 10만 개를 넘었다는 사실(2026-10-27 기준)은 이 문제가 많은 개발자에게 이미 현실이라는 신호로 읽힙니다.

**기존 글과의 연결: OpenHands와 Orca는 같은 문제를 반대 방향에서 풉니다.** [OpenHands 소개 글](/opensource/2026/10/20/openhands.html)에서 본 OpenHands는 실행 환경을 서버로 옮기고 그 위에 에이전트를 올리는 “플랫폼” 쪽입니다. Orca는 개발자 데스크톱에서 출발해 이미 쓰는 CLI 에이전트를 감싸고, 필요할 때만 SSH나 원격 서버로 실행 위치를 넓힙니다. 필자의 판단으로는 팀 공용 자동화(매일 PR 요약, 의존성 업데이트)가 목적이면 OpenHands 쪽이, 개인 개발자가 여러 에이전트를 손에 쥐고 빠르게 비교하는 것이 목적이면 Orca 쪽이 더 잘 맞습니다. 또한 Orca의 스킬 배포 방식(얇은 SKILL.md 스텁 + 실행 중인 CLI가 버전에 맞는 안내를 제공)은 [Agent Skills 표준 글](/tech/2026/10/24/agent-skills-aaif.html)에서 다룬 스킬 생태계가 실제 제품에서 어떻게 쓰이는지 보여 주는 사례이고, 워크트리마다 다른 에이전트를 띄우는 환경에서는 [AGENTS.md](/tech/2026/10/24/agents-md.html)처럼 에이전트에 상관없이 읽히는 저장소 안내 파일의 가치가 더 커집니다.

**한계와 반론: “워크트리가 곧 샌드박스”라는 설계 의도와 보안 경고가 같은 문서 사이트 안에서 충돌합니다.** Agents & sessions 문서는 기본 권한 우회를 “워크트리 자체가 샌드박스라는 의도”로 설명하지만, 지원 에이전트 문서는 “워크트리는 보안 샌드박스가 아니다”라고 경고합니다. 사실관계는 후자가 맞습니다. git 워크트리는 같은 사용자 권한으로 도는 디렉터리일 뿐이라, 프롬프트 주입이 섞인 이슈나 README를 읽은 에이전트가 `~/.ssh`나 클라우드 자격 증명에 접근하는 것을 막지 못합니다. 에이전트를 여러 개 동시에, 확인 없이 돌리는 구조는 이 위험을 곱절로 키웁니다. 신뢰하지 않는 저장소나 외부 이슈를 다룬다면 Manual 모드로 바꾸거나, 실행 위치를 SSH 호스트나 일회용 VM으로 옮기는 편이 안전해 보입니다.

**실무에 주는 의미: “여러 에이전트에게 같은 일을 시켜 고르기”는 생각보다 비쌉니다.** 같은 프롬프트를 세 에이전트에 보내면 비용은 세 배지만 리뷰할 diff도 세 개가 됩니다. 결국 사람이 세 결과를 읽고 비교해야 하므로, 이 방식은 정답이 하나로 수렴하지 않는 문제(설계 선택이 갈리는 리팩터링, 원인이 불분명한 버그)에서만 값을 합니다. 오히려 일상에서 더 큰 효용은 **서로 다른 작업 여러 개를 동시에 굴리는 것**과, `orca.yaml`로 새 워크트리의 준비 시간을 0에 가깝게 만드는 것으로 보입니다.

**앞으로 지켜볼 점:** 오케스트레이션이 실험 딱지를 떼고 조정자 에이전트가 작업자 에이전트를 안정적으로 감독할 수 있게 되면, Orca는 “사람이 여러 에이전트를 보는 화면”에서 “에이전트가 에이전트를 관리하는 런타임”으로 성격이 바뀝니다. 또 하나는 권한 기본값입니다. 사용자 수가 늘어날수록 Yolo 기본값이 유지될지, 에이전트별 샌드박스(컨테이너 실행 등)가 기본 경로로 들어올지가 도입 판단에 중요한 변수가 될 것입니다.

## 이런 분께 추천

- Claude Code, Codex 등 CLI 에이전트를 이미 매일 쓰고, 여러 작업을 동시에 맡기고 싶은 개발자
- 에이전트 결과를 diff로 꼼꼼히 리뷰하고 커밋 단위로 관리하는 습관이 있는 분
- 개발 서버나 GPU 머신에 에이전트를 돌려 두고 노트북이나 휴대폰으로 상태만 확인하고 싶은 분
- 새 브랜치마다 의존성 설치와 `.env` 복사를 반복하느라 지친 분

## 이런 경우엔 다른 도구

- 에이전트를 하나만, 가끔 쓴다면 에이전트 CLI를 터미널에서 직접 쓰는 것으로 충분합니다.
- 팀 공용 서버에서 스케줄·웹훅 기반 자동화를 돌리는 것이 주목적이라면 OpenHands 같은 셀프 호스팅 플랫폼이 더 맞습니다.
- 강한 격리(컨테이너, VM)가 기본으로 보장되어야 하는 보안 환경이라면, Orca의 클라우드 VM 레시피를 직접 구성하거나 실행 환경을 벤더가 관리하는 서비스를 검토합니다.
- 코드를 직접 읽지 않고 결과만 받고 싶다면 맞지 않습니다. 공식 문서도 Orca는 diff를 읽고 커밋을 신경 쓰는 사람을 위한 도구이며 노코드 도구가 아니라고 밝힙니다.
