# [오픈소스 소개] HTTPie: 사람이 읽기 쉬운 커맨드라인 HTTP 클라이언트

- **저장소:** [httpie/cli](https://github.com/httpie/cli) · [httpie.io](https://httpie.io) · [문서](https://httpie.io/docs)
- **라이선스:** BSD 3-Clause
- **언어:** Python
- **현황 (2026-10-20 기준):** GitHub 스타 약 3.9만 개, 최신 릴리스 3.2.4 (2024년 11월)

## 한 줄 요약

**HTTP 요청을 "HTTP 메시지를 받아 적듯이" 쓰게 해 주는 터미널용 HTTP 클라이언트**입니다. `name=John`처럼 쓰면 JSON 본문이 되고, `X-API-Token:123`처럼 쓰면 헤더가 됩니다. 응답은 색과 들여쓰기가 적용된 형태로 보여 줍니다.

## 어떤 문제를 푸나

REST API를 개발하거나 디버깅할 때 가장 흔한 도구는 curl입니다. curl은 강력하지만 사람이 매번 손으로 치기에는 불편한 점이 있습니다.

- JSON을 보내려면 `-H 'Content-Type: application/json'`과 `-d '{"name":"John"}'`을 직접 써야 하고, 셸 따옴표 처리도 신경 써야 합니다.
- 응답 JSON이 한 줄로 붙어서 나오기 때문에 보통 `jq`를 따로 연결합니다.
- 요청 헤더와 응답 헤더를 같이 보려면 `-v` 출력에서 필요한 부분을 골라 읽어야 합니다.

HTTPie는 "사람이 대화하듯 API를 다루는 경험"에 초점을 맞춥니다. 공식 문서는 명령어 인자의 순서와 문법이 실제로 전송되는 HTTP 요청과 거의 그대로 대응하도록 설계했다고 설명합니다. 예를 들어 아래 HTTP 요청과

```http
POST /post HTTP/1.1
Host: pie.dev
X-API-Key: 123
User-Agent: Bacon/1.0
Content-Type: application/x-www-form-urlencoded

name=value&name2=value2
```

아래 명령은 거의 같은 순서로 읽힙니다. HTTP 메시지와 대응하지 않는 부분은 폼 전송을 뜻하는 `-f` 하나뿐입니다.

```bash
http -f POST pie.dev/post \
    X-API-Key:123 \
    User-Agent:Bacon/1.0 \
    name=value \
    name2=value2
```

참고로 HTTPie라는 이름 아래에는 웹/데스크톱 앱(HTTPie for Web & Desktop)도 있지만, 이 글에서 다루는 것은 오픈소스 **CLI**(`httpie/cli` 저장소)입니다. 둘은 별개의 제품입니다.

## 핵심 개념 / 동작 원리

### 기본 형태

```bash
http [flags] [METHOD] URL [ITEM [ITEM]]
```

- **`http` / `https`:** 설치하면 두 실행 파일이 생깁니다. 스킴(`http://`, `https://`)을 생략하면 `http`는 `http://`, `https`는 `https://`를 붙입니다.
- **METHOD 생략 규칙:** 본문 데이터가 없으면 `GET`, 있으면 `POST`가 기본입니다. `AHOY` 같은 임의의 메서드 이름도 쓸 수 있습니다.
- **localhost 단축:** `http :3000/bar`는 `http://localhost:3000/bar`로, `http :/foo`는 포트 80의 `localhost/foo`로 해석됩니다.
- **내부 구성:** HTTP 통신은 Python의 [Requests](https://requests.readthedocs.io/) 라이브러리가, 구문 강조는 [Pygments](https://pygments.org/)가 담당합니다.

### Request item 문법 (가장 중요한 부분)

HTTPie의 핵심은 **request item**입니다. URL 뒤에 오는 `키<구분자>값` 쌍인데, 구분자 종류에 따라 헤더가 되기도 하고 JSON 필드나 쿼리 파라미터가 되기도 합니다.

| 구분자 | 의미 | 예시 | 결과 |
|---|---|---|---|
| `:` | HTTP 헤더 | `X-API-Token:123` | `X-API-Token: 123` 헤더 |
| `==` | URL 쿼리 파라미터 | `q==httpie per_page==1` | `?q=httpie&per_page=1` (자동 URL 인코딩) |
| `=` | 데이터 필드 (문자열) | `name=John` | JSON `{"name": "John"}` (기본), `-f`면 폼 필드 |
| `:=` | 원시(raw) JSON 필드 | `age:=29`, `married:=false`, `tags:='["a","b"]'` | 숫자, 불리언, 배열, 객체를 타입 그대로 넣음 |
| `@` | 파일 업로드 필드 | `cv@~/files/cv.pdf` | `--form`/`--multipart`에서만 사용, multipart 파일 필드 |
| `=@` | 파일 내용을 문자열 필드로 | `description=@about.txt` | 파일 텍스트가 JSON 문자열 값으로 들어감 |
| `:=@` | 파일 내용을 JSON으로 | `bookmarks:=@data.json` | 파일의 JSON이 그대로 객체/배열 값으로 들어감 |
| `:@` | 헤더 값을 파일에서 | `X-Data:@token.txt` | 파일 내용이 헤더 값 (끝 개행 제거) |
| `==@` | 쿼리 값을 파일에서 | `text==@q.txt` | 파일 내용이 쿼리 값 |

몇 가지 세부 규칙도 알아 두면 좋습니다.

- `Header:`처럼 값을 비우면 그 헤더를 **제거**합니다. 예를 들어 `Accept: User-Agent:`는 기본 헤더 두 개를 지웁니다. 빈 값을 실제로 보내려면 `'Header;'`처럼 세미콜론을 씁니다.
- 구분자 문자를 그대로 쓰고 싶으면 `\`로 이스케이프합니다. `foo\==bar`는 쿼리가 아니라 키 `foo=`, 값 `bar`인 데이터 필드가 됩니다.
- 이름이 `-`로 시작하는 필드나 헤더는 `--` 뒤에 둬야 옵션으로 오해받지 않습니다.
- 데이터 필드가 있으면 HTTPie가 `Content-Type: application/json`과 `Accept: application/json, */*;q=0.5`를 자동으로 붙입니다. 둘 다 직접 덮어쓸 수 있습니다.

### 중첩 JSON 문법

3.x부터는 대괄호 경로로 중첩 JSON을 바로 만들 수 있습니다.

| 문법 | 의미 |
|---|---|
| `a[b]=x` | 객체 `a` 안에 키 `b` |
| `a[]=x` | 배열 `a`에 값 추가(append) |
| `a[2]=x` | 배열 `a`의 2번 인덱스에 값 (빈 인덱스는 `null`로 채움) |
| `[]:=1` | 최상위를 배열로 |
| `a[\1]=x` | 숫자 `1`을 인덱스가 아닌 문자열 키로 |

경로는 처음 쓰일 때 타입(객체/배열)이 정해지고, 이후 다른 타입으로 접근하면 `HTTPie Type Error`를 냅니다. 괄호를 빠뜨리는 등 문법 오류가 나면 `HTTPie Syntax Error: Expecting ']'`처럼 어느 위치가 틀렸는지 표시해 줍니다.

### 출력 방식이 두 가지

HTTPie는 출력 대상에 따라 기본값이 다릅니다.

- **터미널로 출력할 때:** 최종 응답의 헤더와 본문을 모두 보여 주고, 색과 포맷(`--pretty=all`)을 적용합니다. 바이너리 본문은 숨깁니다.
- **파이프나 파일로 리다이렉트할 때:** 응답 **본문만**, 포맷 없이(`--pretty=none`) 내보냅니다. 그래서 `http URL > file.png`나 `http URL | jq`가 별도 옵션 없이 동작합니다.

## 주요 기능

### 요청 만들기

- **JSON 기본:** 데이터 필드는 기본적으로 JSON 객체로 직렬화됩니다. `--json, -j`는 데이터가 없어도 `Accept`를 JSON으로 맞춥니다.
- **폼:** `--form, -f`는 `application/x-www-form-urlencoded`로 보냅니다. 파일 필드(`@`)가 하나라도 있으면 자동으로 `multipart/form-data`가 됩니다. 파일 없이 multipart가 필요하면 `--multipart`를 씁니다. `--boundary`로 경계 문자열을 지정할 수도 있습니다.
- **원시 본문(raw body):** 표준 입력 파이프(`< data.json`, `echo ... |`), `--raw='...'`, `@/path/file` 세 가지 방법이 있습니다. 단, 원시 본문과 request item 데이터 필드는 함께 쓸 수 없습니다.
- **전송 방식:** `--chunked`(청크 전송 인코딩), `--compress, -x`(요청 본문 압축)를 지원합니다.
- **경로 정규화 끄기:** `--path-as-is`는 `/./../` 같은 경로를 정리하지 않고 그대로 보냅니다.

### 인증

- `--auth, -a`에 `username:password` 또는 토큰을 넘깁니다. 비밀번호를 빼고 `-a username`만 주면 프롬프트로 안전하게 입력받습니다. 빈 비밀번호는 `-a username:`입니다.
- `--auth-type, -A`로 방식을 고릅니다. 기본은 `basic`이고 `digest`, `bearer`, 그리고 설치한 인증 플러그인 이름을 쓸 수 있습니다.
- `~/.netrc`의 인증 정보를 기본으로 사용합니다. 끄려면 `--ignore-netrc`를 씁니다.
- 공식 문서에 소개된 인증 플러그인으로 AWS(`httpie-aws-auth`), JWT(`httpie-jwt-auth`), NTLM(`httpie-ntlm`), OAuth 1.0a(`httpie-oauth1`), HMAC 등이 있습니다.

### 세션

- `--session=NAME`은 같은 호스트에 대한 요청 사이에 **커스텀 헤더, 인증 정보, 쿠키**를 유지합니다. `Content-`나 `If-`로 시작하는 헤더는 저장하지 않습니다.
- 이름 세션은 `~/.config/httpie/sessions/<host>/<name>.json`(Windows는 `%APPDATA%\httpie\sessions\<host>\<name>.json`)에 저장됩니다.
- `--session=./session.json`처럼 경로에 `/`를 넣으면 파일 경로 기반 "익명 세션"이 되어 여러 호스트에서 재사용할 수 있습니다.
- `--session-read-only=`는 세션을 읽기만 하고 응답으로 갱신하지 않습니다.
- 쿠키는 `domain` 필드로 호스트에 묶입니다. 예전 형식 세션은 `httpie cli sessions upgrade-all`로 변환할 수 있습니다.

### 출력 제어

| 옵션 | 출력 내용 |
|---|---|
| `--headers, -h` | 응답 헤더만 |
| `--body, -b` | 응답 본문만 |
| `--meta, -m` | 응답 메타데이터(경과 시간)만 |
| `--verbose, -v` | 요청과 응답 전체 (`--all`도 함께 켜짐) |
| `-vv` | `-v` + 응답 메타데이터 |
| `--print, -p` | 문자 조합으로 선택: `H` 요청 헤더, `B` 요청 본문, `h` 응답 헤더, `b` 응답 본문, `m` 메타 |
| `--quiet, -q` | 표준 출력/에러 출력 없음 (`-qq`는 경고까지 숨김) |

- `--pretty=all|colors|format|none`으로 색과 포맷을 제어하고, `--style=monokai`처럼 색 테마를 고릅니다. 기본값 `auto`는 터미널의 ANSI 색을 따릅니다.
- `--format-options=json.indent:2,json.sort_keys:false`처럼 포맷 세부값을 조정합니다. `--unsorted`/`--sorted`는 헤더와 JSON 키 정렬을 끄고 켜는 단축 옵션입니다.
- 응답 `Content-Type`이 틀렸을 때 `--response-mime`, 인코딩이 틀렸을 때 `--response-charset`으로 바로잡을 수 있습니다.
- 출력에 본문이 포함되지 않으면 본문을 아예 내려받지 않습니다. 예를 들어 `--headers`로 PATCH를 보내면 헤더 수신 직후 연결을 닫습니다.

### 리다이렉트, 다운로드, 스트리밍

- 리다이렉트는 **기본적으로 따라가지 않습니다.** `--follow, -F`로 따라가고, `--all`로 중간 응답까지 보며, 최대 횟수(기본 30)는 `--max-redirects`로 바꿉니다.
- `--download, -d`는 wget처럼 진행률 표시와 함께 파일로 저장합니다. `--output, -o`로 파일명을 정하고, `--continue, -c`로 중단된 다운로드를 이어받습니다(서버가 `Range` 요청을 지원할 때). `--download`는 `--follow`와 `--check-status`를 자동으로 포함합니다.
- `--stream, -S`는 버퍼링 없이 줄 단위로 바로 출력합니다. 응답이 `text/event-stream`이면 자동으로 켜집니다.

### HTTPS와 프록시

- `--verify=no`로 서버 인증서 검증을 끄고, `--verify=/path/ca_bundle`로 사설 CA 번들을 지정합니다.
- 클라이언트 인증서는 `--cert`, 개인키는 `--cert-key`, 키 비밀번호는 `--cert-key-pass`로 넘깁니다.
- `--ssl=tls1.2`처럼 프로토콜 버전을, `--ciphers`로 암호 스위트를 지정할 수 있습니다.
- `--proxy=http:http://host:port`로 프로토콜별 프록시를 지정하며, `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` 환경 변수도 인식합니다. SOCKS(`socks5://`)도 지원합니다.

### 오프라인 모드

`--offline`은 요청을 만들어서 출력만 하고 **네트워크에 전혀 연결하지 않습니다.** 자동으로 `--print=HB`(요청 헤더와 본문)가 켜집니다. API 문서 예제 작성, 요청 형태 검증, "드라이 런"에 유용합니다.

### 설정 파일과 플러그인

- 설정 파일은 기본적으로 `~/.config/httpie/config.json`(정확히는 `$XDG_CONFIG_HOME/httpie/config.json`), Windows는 `%APPDATA%\httpie\config.json`입니다. 기본으로 존재하지 않으니 직접 만들면 됩니다. `http --debug` 출력의 `config_dir`에서 실제 위치를 확인할 수 있고, `HTTPIE_CONFIG_DIR` 환경 변수로 바꿀 수 있습니다.
- 주요 항목은 `default_options`(모든 호출에 붙일 옵션 배열)와 `plugins_dir`입니다. 설정한 기본 옵션은 `--no-style`, `--no-session`처럼 `--no-옵션`으로 일시 해제합니다.
- 3.0부터 `httpie cli plugins install|list|upgrade|uninstall` 플러그인 관리자가 있습니다(문서상 베타). pip로 설치한 환경이 아니어도(예: Homebrew) 플러그인을 넣을 수 있게 하려고 만든 기능입니다. 플러그인은 대부분 커뮤니티가 만든 것이며 공식적으로 검토하지 않는다는 점이 문서에 명시돼 있습니다.

## 설치와 시작

공식 문서에 있는 설치 명령입니다.

```bash
# PyPI (모든 플랫폼)
python -m pip install --upgrade pip wheel
python -m pip install httpie

# macOS / Linuxbrew
brew update
brew install httpie

# macOS MacPorts
port selfupdate
port install httpie

# Windows (Chocolatey)
choco install httpie

# Fedora
dnf install httpie

# CentOS / RHEL
yum install epel-release
yum install httpie

# Arch Linux
pacman -Syu httpie

# Snap
snap install httpie

# FreeBSD
pkg install www/py-httpie
```

Debian/Ubuntu는 HTTPie 공식 APT 저장소를 등록한 뒤 설치합니다.

```bash
curl -SsL https://packages.httpie.io/deb/KEY.gpg | sudo gpg --dearmor -o /usr/share/keyrings/httpie.gpg
echo "deb [arch=amd64 signed-by=/usr/share/keyrings/httpie.gpg] https://packages.httpie.io/deb ./" | sudo tee /etc/apt/sources.list.d/httpie.list > /dev/null
sudo apt update
sudo apt install httpie
```

PyPI 패키지는 Python 3.7 이상을 요구합니다(`setup.cfg`의 `python_requires`). 설치 후 첫 요청은 이렇게 해 볼 수 있습니다.

```bash
https httpie.io/hello
http --help        # 전체 옵션
```

이 글의 예제에 나오는 `pie.dev`는 공식 문서 예제가 사용하는 테스트용 엔드포인트입니다(`/get`, `/post`, `/headers`처럼 받은 요청을 그대로 돌려줍니다).

## 실전 예제

### 1. curl과 HTTPie 대응표

| 하고 싶은 일 | curl | HTTPie |
|---|---|---|
| JSON POST | `curl -X POST -H 'Content-Type: application/json' -d '{"name":"John","age":29}' https://pie.dev/post` | `https pie.dev/post name=John age:=29` |
| 헤더 추가 | `curl -H 'X-API-Token: 123' https://pie.dev/get` | `https pie.dev/get X-API-Token:123` |
| 쿼리 파라미터 | `curl 'https://api.github.com/search/repositories?q=httpie&per_page=1'` | `https api.github.com/search/repositories q==httpie per_page==1` |
| 폼 전송 | `curl -d 'name=John' https://pie.dev/post` | `https -f pie.dev/post name=John` |
| 파일 업로드 | `curl -F 'cv=@cv.pdf' https://pie.dev/post` | `https -f pie.dev/post cv@cv.pdf` |
| Bearer 토큰 | `curl -H 'Authorization: Bearer TOKEN' https://pie.dev/bearer` | `https -A bearer -a TOKEN pie.dev/bearer` |
| 요청/응답 모두 보기 | `curl -v https://pie.dev/get` | `https -v pie.dev/get` |
| 리다이렉트 따라가기 | `curl -L https://pie.dev/redirect/3` | `https --follow pie.dev/redirect/3` |
| 파일 다운로드 | `curl -L -O https://example.org/file.zip` | `https --download example.org/file.zip` |

curl은 기본적으로 리다이렉트를 따라가지 않고 HTTPie도 마찬가지라는 점, 그리고 HTTPie의 JSON 숫자/불리언은 `:=`로 넣어야 한다는 점이 자주 헷갈리는 부분입니다. `age=29`라고 쓰면 문자열 `"29"`가 됩니다.

### 2. 토큰 인증과 세션으로 로그인 상태 유지

API 토큰을 매번 붙이기 번거롭다면 이름 세션에 한 번만 저장합니다.

```bash
# 첫 요청: 인증 정보와 커스텀 헤더를 세션 'dev'에 저장
https --session=dev -A bearer -a "$API_TOKEN" pie.dev/bearer X-Client:cli

# 이후 요청: 같은 호스트라면 Authorization, X-Client 헤더가 자동으로 붙음
https --session=dev pie.dev/headers

# 서버가 Set-Cookie로 내려준 쿠키도 세션에 저장되고 다음 요청에 재사용됨
https --session=dev pie.dev/cookies/set foo==bar
https --session=dev pie.dev/cookies
```

세션 파일은 평범한 JSON이라 직접 열어 수정할 수 있습니다. 다만 **토큰, 비밀번호, 쿠키가 평문으로 저장**된다는 점을 기억해야 합니다(프롬프트로 입력한 비밀번호도 포함). 로그인 플로우를 테스트할 때는 `--session-read-only`를 쓰면 기준 세션이 오염되지 않습니다.

### 3. 파일 업로드와 다운로드

```bash
# multipart 업로드: 일반 필드 + 파일 필드
http -f POST pie.dev/post name='John Smith' cv@~/files/data.xml

# 업로드 파일의 MIME 타입 직접 지정
http -f POST pie.dev/post cv@'~/files/data.bin;type=application/pdf'

# 파일 전체를 요청 본문으로 (JSON 파일을 그대로 PUT)
http PUT pie.dev/put X-API-Token:123 < files/data.json

# wget 스타일 다운로드 (진행률 표시)
http --download https://github.com/httpie/cli/archive/master.tar.gz

# 파일명 지정 + 이어받기
http -dco file.zip example.org/file

# 다운로드하면서 바로 압축 해제
http -d https://github.com/httpie/cli/archive/master.tar.gz | tar zxf -
```

`@`는 multipart 파일 필드이고 `=@`는 파일 내용을 일반 텍스트 값으로 넣는 것이라 결과가 완전히 다릅니다. 업로드 파일은 메모리를 아끼기 위해 항상 스트리밍으로 전송됩니다.

### 4. 중첩 JSON을 만들고 --offline으로 확인

복잡한 본문을 실제 서버에 보내기 전에 `--offline`으로 모양부터 확인하는 습관이 좋습니다. `--print=B`는 요청 본문만 출력합니다.

```bash
http --offline --print=B pie.dev/post \
  category=tools \
  search[type]=keyword \
  search[keywords][]=APIs \
  search[keywords][]=CLI \
  search[limit]:=10 \
  search[exact]:=false
```

```json
{
    "category": "tools",
    "search": {
        "exact": false,
        "keywords": [
            "APIs",
            "CLI"
        ],
        "limit": 10,
        "type": "keyword"
    }
}
```

출력은 키가 정렬되어 보이지만 이것은 화면 포맷일 뿐입니다. 결과가 맞으면 `--offline --print=B`만 지우고 실제로 보냅니다. `--offline`의 결과를 파일로 저장하면 다른 도구로도 그대로 보낼 수 있는 원시 HTTP 요청이 됩니다.

```bash
http --offline POST pie.dev/post hello=world > request.http
nc pie.dev 80 < request.http
```

## 실무 팁 & 자주 겪는 문제

- **스크립트나 cron에서 멈춘 것처럼 보일 때:** HTTPie는 표준 입력이 터미널이 아니면 그것을 요청 본문으로 읽으려고 기다립니다. 비대화형 환경에서는 `--ignore-stdin`을 꼭 붙이라고 공식 문서가 권장합니다. 응답 없는 서버 대비로 `--timeout`도 함께 쓰세요.
- **에러 상태 코드를 종료 코드로 받기:** `--check-status`를 쓰면 3xx/4xx/5xx 응답일 때 종료 코드 3/4/5를 돌려줍니다. 타임아웃은 2, `--max-redirects` 초과는 6입니다.

  ```bash
  if http --check-status --ignore-stdin --timeout=2.5 HEAD pie.dev/get &> /dev/null; then
      echo 'OK!'
  fi
  ```

- **숫자나 불리언이 문자열로 들어갈 때:** `count=1`은 `"1"`입니다. `count:=1`, `active:=true`로 써야 합니다.
- **`--form`에서 `:=` 배열/객체가 안 될 때:** `:=`는 JSON 전용입니다. 폼/multipart에서는 문자열과 숫자만 문자열 값으로 바뀌어 들어가고, 배열이나 객체는 허용되지 않습니다.
- **리다이렉트 응답만 보일 때:** 기본값이 "따라가지 않음"입니다. `--follow`를 붙이세요. `307`/`308`은 원래 메서드와 본문을 유지하고, 그 외에는 본문 없는 `GET`으로 따라갑니다.
- **응답을 jq로 넘길 때 색이 섞일까 걱정된다면:** 리다이렉트 출력은 자동으로 `--pretty=none`이고 본문만 나갑니다. 반대로 `less`에서 색을 보고 싶으면 `http --pretty=all --verbose pie.dev/get | less -R`처럼 명시합니다.
- **같은 이름 헤더 여러 개:** `Cookie:one Cookie:two`는 헤더 두 줄로, `Numbers:one,two`는 한 줄로 보냅니다. 세션에 저장된 헤더는 명령줄 헤더에 의해 덮어써집니다(합쳐지지 않음).
- **기본 옵션 고정:** 매번 같은 스타일을 쓴다면 `config.json`에 `{"default_options": ["--style=fruity"]}`처럼 넣어 둡니다. 다만 공식 문서는 다른 사람과의 호환성을 깨는 수준으로 기본 동작을 바꾸지 말라고 조언합니다.
- **사내 CA 인증서 오류:** `--verify=no`로 끄기보다 `--verify=/path/to/ca_bundle`로 사내 CA를 지정하는 편이 안전합니다.
- **업데이트 경고 끄기:** 새 버전이 있으면 주 1회 경고합니다. `config.json`에서 `disable_update_warnings`를 `true`로 두면 꺼집니다.

## 비슷한 도구와 비교

| 항목 | HTTPie (CLI) | curl | xh | Postman / Hoppscotch |
|---|---|---|---|---|
| 형태 | 터미널 CLI | 터미널 CLI + 라이브러리(libcurl) | 터미널 CLI | GUI 앱 / 웹 앱 |
| 구현 언어 | Python | C | Rust | (앱) |
| 문법 | `key=value`, `Header:value` request item | 옵션 플래그 중심(`-H`, `-d`, `-F`) | HTTPie와 매우 유사한 문법 | 폼 UI |
| JSON 기본 | 예 | 아니요 (직접 헤더/본문 작성) | 예 | 예 |
| 출력 포맷/색 | 기본 적용 | 없음 (jq 등과 조합) | 기본 적용 | UI에서 표시 |
| 시작 속도 | Python 인터프리터 기동 비용이 있음 | 매우 빠름 | 단일 네이티브 바이너리라 빠른 편 | 앱 기동 필요 |
| 지원 프로토콜 범위 | HTTP/HTTPS 중심 | HTTP 외 FTP, SMTP 등 매우 넓음 | HTTP/HTTPS 중심 | HTTP 외 일부(앱별 상이) |
| 설치 보편성 | 별도 설치 필요 | 대부분 OS에 기본 탑재 | 별도 설치 필요 | 별도 설치/계정 |
| 협업, 컬렉션 관리 | 세션 파일 정도 | 없음 | 없음 | 강점 (컬렉션, 환경 변수, 공유) |

- **curl**은 어디에나 설치돼 있고 프로토콜 지원 범위가 압도적으로 넓어서, 서버 스크립트나 Dockerfile처럼 의존성을 최소화해야 하는 곳에서는 여전히 기본 선택입니다.
- **xh**는 "HTTPie의 설계를 최대한 재구현한" Rust 도구로 소개됩니다. 문법이 거의 같아 HTTPie에 익숙하면 바로 쓸 수 있지만, 모든 옵션과 플러그인이 동일하게 지원되는지는 xh 문서에서 확인해야 합니다.
- **Postman/Hoppscotch** 같은 GUI 도구는 요청 컬렉션을 팀과 공유하거나 환경별 변수를 관리할 때 유리합니다. 반대로 셸 스크립트, 파이프 연결, 터미널 작업 흐름과의 결합은 CLI가 훨씬 자연스럽습니다.

## 장점과 한계

**장점**

- request item 문법 덕분에 JSON API 호출이 짧고 읽기 쉽습니다. 문서나 이슈에 붙여 넣어도 사람이 바로 이해합니다.
- 중첩 JSON, 세션, 오프라인 모드, wget식 다운로드, 스트리밍까지 API 디버깅에 필요한 기능이 한 도구에 모여 있습니다.
- 터미널용과 파이프용 기본값이 분리돼 있어 대화형 사용과 스크립트 사용이 모두 편합니다.
- 공식 매뉴얼이 매우 상세하고 예제가 풍부합니다.

**한계**

- **릴리스 주기가 느려졌습니다.** 2026-10-20 기준 최신 릴리스는 3.2.4(2024년 11월)이고, 그 직전은 3.2.3(2024년 7월), 3.2.2(2023년 5월)입니다. 저장소의 마지막 커밋도 2024년 12월입니다. 기능은 성숙했지만 새 기능이나 빠른 버그 수정을 기대하기는 어렵습니다.
- **Python 기반이라 시작 비용이 있습니다.** 한 번 호출할 때마다 인터프리터와 모듈 로딩이 필요하므로, 반복문 안에서 수천 번 호출하는 용도에는 curl이나 네이티브 바이너리 도구가 더 적합합니다.
- 컬러/포맷 출력이 켜지면 응답 전체를 버퍼링한 뒤 처리합니다. 큰 응답을 실시간으로 보려면 `--stream`을 써야 합니다.
- HTTP/HTTPS 중심이라 curl처럼 다양한 프로토콜을 다루지는 못합니다.
- 세션 파일에 자격 증명이 평문으로 저장됩니다.
- 플러그인 관리자는 문서상 아직 베타이고, 플러그인 대부분은 커뮤니티 제작물입니다.

## 이런 분께 추천 / 이런 경우엔 다른 도구

**추천**

- 터미널에서 JSON REST API를 자주 호출하고 디버깅하는 백엔드 개발자
- curl의 `-H`, `-d`, 따옴표 처리가 매번 번거로운 분
- API 문서나 사내 위키에 사람이 읽기 쉬운 호출 예제를 남기고 싶은 분 (`--offline`으로 예제 생성)
- 토큰/쿠키 기반 인증이 필요한 API를 반복 테스트하는 분 (세션)

**다른 도구가 나은 경우**

- 최소한의 의존성으로 컨테이너나 CI 스크립트에서 HTTP를 호출해야 한다면: **curl**
- HTTPie 문법은 좋은데 더 빠른 시작 속도와 단일 바이너리가 필요하다면: **xh**
- 요청 컬렉션을 팀과 공유하고 환경별로 관리해야 한다면: **Postman, Hoppscotch** 같은 GUI 도구
- 활발한 신규 기능 개발과 빠른 릴리스가 중요하다면: 대안 도구의 활동성을 함께 비교해 보세요.
