# [오픈소스 소개] Tabby: 사내 서버에 직접 띄우는 셀프 호스팅 AI 코딩 어시스턴트

- **저장소:** [TabbyML/tabby](https://github.com/TabbyML/tabby) · [tabbyml.com](https://tabbyml.com) · [문서](https://tabby.tabbyml.com/docs/welcome/)
- **라이선스:** Apache 2.0 (`ee/` 디렉터리는 별도의 Tabby Enterprise 라이선스)
- **언어:** Rust (웹 UI와 IDE 확장은 TypeScript)
- **현황 (2026-10-20 기준):** GitHub 스타 약 3.4만 개, 최신 릴리스 v0.32.0 (2026년 1월 25일), main 브랜치 마지막 커밋 2026년 6월 30일

## 한 줄 요약

**GitHub Copilot 같은 코드 자동완성과 코딩 Q&A를 내 GPU 서버 한 대에서 돌릴 수 있게 해 주는 셀프 호스팅 AI 코딩 어시스턴트**입니다. README는 스스로를 "GitHub Copilot의 오픈소스·온프레미스 대안"이라고 소개합니다. 별도 DBMS나 클라우드 서비스 없이 바이너리(또는 Docker 컨테이너) 하나로 서버가 뜨고, VS Code, JetBrains, Vim/Neovim 확장이 이 서버에 붙습니다.

다만 2026년 들어 개발 속도가 눈에 띄게 줄었습니다. 이 부분은 아래 "유지보수 현황"에서 따로 정리했으니, 도입을 검토한다면 꼭 먼저 읽어 보시길 권합니다.

## 어떤 문제를 푸나

AI 코드 자동완성은 이미 많은 팀에 익숙하지만, 클라우드 서비스를 그대로 쓰기 어려운 조직도 많습니다.

- 보안 규정상 **소스 코드를 외부 SaaS로 보낼 수 없는** 금융·공공·제조 조직
- 인터넷이 막힌 폐쇄망 개발 환경
- 사용자 수만큼 구독료를 내기보다 **보유한 GPU로 직접 서빙**하고 싶은 팀
- 사내 저장소와 문서를 맥락으로 쓰는 코딩 어시스턴트를 원하지만, 데이터는 내부에 두고 싶은 경우

Tabby는 모델 서빙, 프롬프트 구성, 저장소 인덱싱, 사용자 관리, IDE 확장까지 **전체 스택을 하나로 묶어** 제공해서 이 문제를 풉니다. 문서의 원칙에 따르면 IDE 확장 쪽에서도 스트리밍, 요청 취소, 적응형 캐시를 최적화해 1초 안쪽의 빠른 완성을 노리고, 서버 쪽에서는 Tree-sitter로 코드를 파싱해 프롬프트에 넣을 맥락을 만듭니다.

## 핵심 개념 / 동작 원리

### 구조

```
 IDE (VS Code / JetBrains / Vim)
   │  tabby-agent (LSP-like client)
   │  HTTP + Bearer token
   ▼
 Tabby server (Rust, port 8080)
   ├─ /v1/completions ──▶ Completion model (FIM)
   ├─ /v1/chat/completions ─▶ Chat model
   ├─ Index (repos, docs) ◀─ Embedding model
   ├─ Web UI: admin, users, Answer Engine
   └─ SQLite (~/.tabby)
          │
          ▼
 Models: local llama.cpp subprocess
         or HTTP API (Ollama, vLLM, OpenAI...)
```

- **서버:** Rust로 작성된 단일 서버입니다. 데이터는 `~/.tabby`(Docker에서는 `/data`)에 저장되며, 내부 DB로 SQLite를 씁니다.
- **tabby-agent:** IDE 확장의 핵심 컴포넌트입니다. 각 편집기 확장은 이 에이전트를 통해 서버와 통신합니다.
- **모델 연결:** 로컬 모델이면 Tabby가 [llama.cpp](https://github.com/ggml-org/llama.cpp) 서버를 하위 프로세스로 띄워 연결하고, 원격 모델이면 HTTP로 공급자 API에 붙습니다.

### 세 종류의 모델

[모델 설정 문서](https://tabby.tabbyml.com/docs/administration/model/)에 따르면 Tabby는 모델을 세 역할로 나눠 각각 설정합니다.

| 역할 | 용도 | 특징 |
| --- | --- | --- |
| **Completion** | 편집기 인라인 자동완성 | FIM(Fill-in-the-Middle, 커서 앞뒤 코드를 함께 주고 가운데를 채우게 하는 방식) 프롬프트 중심. 빠른 응답이 중요해서 작은 모델이 유리합니다. |
| **Chat** | 사이드 패널 채팅, 인라인 편집, Answer Engine | OpenAI 채팅 API 규격과 호환됩니다. 품질이 중요해서 1B 이상을 권장합니다. |
| **Embedding** | 저장소·문서 인덱싱과 검색 | 텍스트를 벡터로 바꿔 RAG(검색 증강 생성)에 씁니다. 기본값은 `Nomic-Embed-Text`입니다. |

### 저장소 맥락(RAG)

[Context Providers 문서](https://tabby.tabbyml.com/docs/administration/context/) 기준으로, Tabby는 연결된 Git/GitHub/GitLab 저장소에서 **코드, PR/MR, 이슈, 커밋**을 가져와 AST(추상 구문 트리)로 파싱하고 인덱스에 저장합니다. 이 인덱스는 코드 완성, 채팅, 검색 모두에 쓰입니다. 개발자 문서 사이트도 맥락으로 넣을 수 있는데, 기본적으로 [Katana](https://github.com/projectdiscovery/katana) 크롤러를 쓰고, 사이트가 [llms.txt](https://llmstxt.org/)를 제공하면 크롤링 대신 그 목록을 바로 인덱싱합니다.

코드 완성 요청 API(`/v1/completions`)의 스키마를 보면, 클라이언트가 커서 앞뒤 코드(`prefix`, `suffix`) 외에도 LSP가 찾아 준 선언(`declarations`), 최근 수정한 파일의 관련 조각(`relevant_snippets_from_changed_files`), 저장소 URL(`git_url`)을 함께 보낼 수 있습니다. 서버는 이 정보와 인덱스를 섞어 프롬프트를 만듭니다.

### 라이선스 구조

GitHub가 라이선스를 "Other"로 표시하는 이유는 루트 `LICENSE` 파일이 이중 구조이기 때문입니다.

- `ee/` 디렉터리 밖의 코드는 **Apache 2.0**입니다.
- `ee/` 디렉터리(웹 UI `tabby-ui`, `tabby-webserver`, `tabby-db`, `tabby-schema`, `tabby-email` 등)는 **Tabby Enterprise License**입니다. 개발·테스트 목적의 복사와 수정은 구독 없이 가능하지만, 프로덕션 사용은 Tabby 구독 약관과 유효한 라이선스(좌석 수 포함)를 전제로 합니다.

실제 운영에서는 관리자 UI 안에서 **Community(무료), Team, Enterprise** 라이선스 등급을 고르는 방식입니다. 2026-10-20에 확인한 가격 페이지 기준으로 Community는 최대 5명, Team은 좌석당 월 19달러에 최대 50명, Enterprise는 별도 문의이며, SSO는 Enterprise 기능으로 표시돼 있습니다. 가격과 좌석 정책은 바뀔 수 있으니 [가격 페이지](https://www.tabbyml.com/pricing)를 직접 확인하시기 바랍니다. **5명이 넘는 팀이 무료로 쓸 수 있다고 가정하면 안 된다**는 점이 실무에서 가장 중요합니다.

## 주요 기능

- **코드 자동완성:** 인라인 제안, 여러 후보 보기, 스트리밍과 취소 처리.
- **채팅 사이드 패널과 인라인 편집:** `@`로 파일·문서를 맥락에 추가하고, 우클릭 메뉴로 선택 코드를 채팅으로 편집합니다(v0.27, VS Code 1.20 기준 기능).
- **Answer Engine:** 웹 UI 홈 화면의 사내용 Q&A 엔진입니다. 연결된 저장소와 개발 문서를 검색해 답합니다. 스레드는 기본적으로 임시이며 1주 뒤 삭제되고, 공유 링크를 만들면 팀 전체에 보이는 영구 스레드가 됩니다. `SERPER_API_KEY` 환경 변수를 주면 `@Web` 웹 검색(베타)도 쓸 수 있습니다.
- **Code Browser:** 인덱싱된 저장소를 웹에서 둘러봅니다.
- **사용자와 그룹:** 이메일 초대, 허용 도메인 기반 자가 가입, 그룹별 맥락 접근 제어. 그룹이 지정되지 않은 맥락은 모든 멤버에게 열립니다.
- **인증:** OAuth(GitHub, Google, GitLab 등, v0.32.0에서 일반 OAuth 추가), LDAP(v0.24.0부터).
- **사용량 리포트:** 팀 단위 완성 수락률 등 분석 화면(v0.10.0부터).
- **커스텀 문서 수집 API:** `POST /v1beta/ingestion`으로 사내 데이터를 인덱스에 직접 넣습니다(v0.29.0부터).
- **다중 브랜치 인덱싱:** v0.32.0에서 추가됐습니다.

## 유지보수 현황 (2026-10-20 기준)

GitHub 저장소와 커밋 기록에서 직접 확인한 사실만 정리합니다.

- **마지막 정식 릴리스는 v0.32.0(2026-01-25)입니다.** 이후 9개월 가까이 새 정식 릴리스가 없습니다.
- v0.32.0 이후 main 브랜치에는 커밋 8개뿐이고, 마지막 커밋(2026-06-30)은 모델 공급자 추가를 되돌린 revert입니다.
- 릴리스 이후 main에 들어간 변경 중에 **"sunset knowledge and chat features"(#4425)**가 있습니다. 웹 UI의 채팅 기능 플래그를 끄고, Pages/Search 화면을 홈으로 리다이렉트하며, 홈의 스레드 피드를 제거하는 변경입니다.
- 같은 시기의 #4429는 임베딩 서비스를 `TABBY_EMBEDDING_ENABLED=yes` 환경 변수가 있을 때만 켜도록 바꿨습니다. 즉 **main 브랜치 기준으로는 임베딩과 인덱싱이 기본 비활성**입니다.
- 이 두 변경은 **v0.32.0 릴리스에는 포함되지 않았습니다**(GitHub compare 기준, main이 v0.32.0보다 8커밋 앞섬). 이 글의 설명과 예제는 v0.32.0과 현재 공식 문서를 기준으로 합니다.
- 이슈와 외부 PR은 2026년 10월에도 계속 올라오고 있지만, 메인테이너의 반응은 확인하기 어렵습니다.
- README의 최근 소식은 TabbyML의 코딩 에이전트 제품인 **Pochi** 쪽으로 옮겨 가 있습니다.

종합하면, 회사의 개발 역량이 Pochi로 옮겨 갔고 Tabby는 **사실상 유지보수 모드에 가깝다**고 보는 것이 합리적입니다. 이는 커밋 기록을 근거로 한 해석이며 공식 발표는 확인하지 못했습니다. 지금 새로 도입한다면 v0.32.0을 고정해 쓰되, 보안 패치나 새 모델 지원이 늦거나 없을 수 있다는 전제를 두어야 합니다.

## 설치와 시작

### 하드웨어 기준

[모델 레지스트리](https://tabby.tabbyml.com/docs/models/)와 [FAQ](https://tabby.tabbyml.com/docs/faq)에 나온 기준입니다.

| 항목 | 내용 |
| --- | --- |
| 1B~3B 완성 모델 | NVIDIA T4, 10·20 시리즈, 또는 Apple Silicon(M1 등) 이상 |
| 7B~13B 완성 모델 | NVIDIA V100, A100, 30·40 시리즈 권장 |
| VRAM 예시 | CUDA 기본 int8 모드에서 CodeLlama-7B가 약 8GB |
| int8 추론 | Compute Capability 7.0 이상 또는 6.1 |
| GPU 개수 | **GPU 1장만 사용**. 여러 장이면 인스턴스를 여러 개 띄우고 `CUDA_VISIBLE_DEVICES`로 나눔 |
| 지원 장치 | `--device` 값: `cpu`, `cuda`, `rocm`, `metal`, `vulkan` |

Apple Silicon은 개인용으로는 충분하지만 팀 공유 서버로는 CUDA나 ROCm 기반 Docker를 권한다고 문서에 적혀 있습니다.

### Docker로 실행 (CUDA)

[NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/install-guide.html)을 설치한 뒤, 공식 문서의 명령으로 띄웁니다.

```bash
docker run -d \
  --name tabby \
  --gpus all \
  -p 8080:8080 \
  -v $HOME/.tabby:/data \
  registry.tabbyml.com/tabbyml/tabby \
    serve \
    --model StarCoder-1B \
    --chat-model Qwen2-1.5B-Instruct \
    --device cuda

docker logs -f tabby
```

- 처음 실행하면 모델을 내려받으므로 시간이 걸립니다. 모델은 `/data`(호스트의 `~/.tabby`)에 저장됩니다.
- SELinux가 켜진 시스템이면 볼륨 뒤에 `:Z`를 붙입니다(`-v $HOME/.tabby:/data:Z`).
- README에는 `tabbyml/tabby`(Docker Hub) 이미지로 같은 명령이 나옵니다.
- 문서 소스를 보면 CPU용 Docker 탭은 현재 숨겨져 있습니다. CPU 전용 환경이라면 Linux용 독립 실행 파일 쪽 안내를 따르는 편이 안전합니다.

### `tabby serve` 주요 옵션

v0.32.0 소스(`crates/tabby/src/serve.rs`)에서 확인한 옵션입니다.

| 옵션 | 기본값 | 의미 |
| --- | --- | --- |
| `--model` | 없음 | 완성(`/completions`)용 모델 ID |
| `--chat-model` | 없음 | 채팅용 모델 ID |
| `--device` | `cpu` | 추론 장치 |
| `--chat-device` | `--device`와 같음 | 채팅 모델만 다른 장치로 |
| `--host` / `--port` | `0.0.0.0` / `8080` | 바인딩 주소 |
| `--parallelism` | `1` | 동시 서빙 수. 올리면 VRAM 사용량이 크게 늘어남 |

### macOS (Homebrew)와 Linux 바이너리

```bash
# Apple Silicon
brew install tabbyml/tabby/tabby
tabby serve --device metal --model StarCoder-1B --chat-model Qwen2-1.5B-Instruct
```

Linux는 GitHub 릴리스의 `tabby_x86_64-manylinux2014.zip`(CPU), `-cuda117.zip`(CUDA), `-vulkan.zip`(비 NVIDIA GPU)을 받아 `chmod +x tabby llama-server` 후 `./tabby serve ...`로 실행합니다. 개발 문서 크롤링에는 Katana 1.1.2 이상을 따로 설치해야 하며, Docker 이미지에는 미리 들어 있습니다.

### 계정 등록과 IDE 연결

1. `http://localhost:8080`에 접속합니다. **처음 가입한 계정이 owner 권한의 관리자**가 됩니다. 서버를 띄웠으면 바로 가입해 두는 게 안전합니다.
2. 홈 화면에서 **Endpoint**와 개인 **토큰**을 확인합니다.
3. IDE에 확장을 설치합니다. VS Code, IntelliJ 플랫폼(IDEA, PyCharm, GoLand, Android Studio 등), Vim/Neovim을 공식 지원합니다(저장소의 `clients/`에는 Eclipse 클라이언트도 있습니다).
4. 확장 설정에 Endpoint를 넣고, 알림이 뜨면 **Set Credentials**로 토큰을 입력합니다. 상태 표시줄에 연결 아이콘이 보이면 끝입니다.

## 실전 예제

### 1. GPU 서버 한 대로 팀 서버 만들기 (Docker Compose + config.toml)

Qwen2.5-Coder 계열(Apache 2.0)로 완성·채팅 모델을 고르고, 설정 파일로 고정하는 구성입니다. 모델 ID는 공식 레지스트리에 있는 이름입니다.

```yaml
# docker-compose.yml
services:
  tabby:
    restart: always
    image: registry.tabbyml.com/tabbyml/tabby:0.32.0
    command: serve --device cuda
    environment:
      - TABBY_DISABLE_USAGE_COLLECTION=1
    volumes:
      - "./tabby-data:/data"
    ports:
      - 8080:8080
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

```toml
# ./tabby-data/config.toml  (컨테이너 안에서는 /data/config.toml)
[model.completion.local]
model_id = "Qwen2.5-Coder-1.5B"

[model.chat.local]
model_id = "Qwen2.5-Coder-7B-Instruct"

[model.embedding.local]
model_id = "Nomic-Embed-Text"

[answer]
system_prompt = """
You are a helpful coding assistant for our team. \
Answer in Korean when the user writes in Korean."""
```

- `config.toml`은 **Tabby가 자동으로 만들지 않습니다.** 데이터 디렉터리에 직접 만들어야 합니다.
- 이미지 태그는 `latest` 대신 버전으로 고정했습니다. 유지보수 현황을 고려하면 재현 가능한 배포가 특히 중요합니다. Docker Hub(`tabbyml/tabby`)에는 `v` 없는 `0.32.0` 태그가 있으며, `registry.tabbyml.com` 쪽 태그도 같은지 한 번 확인해 주세요.
- `TABBY_DISABLE_USAGE_COLLECTION=1`은 서버가 Tabby 팀으로 보내는 사용 통계(실행 명령의 모델, 장치, CPU 정보 등)를 끕니다. 폐쇄망이라면 꼭 넣어 둡니다.
- 모델 연결이 잘 됐는지는 웹 UI의 **Information > System** 화면에서 모델 카드로 확인합니다.
- GPU 하나에 완성·채팅·임베딩 모델을 함께 올리므로 VRAM 여유를 확인해야 합니다. 부족하면 채팅 모델을 작게 하거나 `--chat-device`로 분리를 검토합니다.

### 2. 이미 돌고 있는 Ollama를 모델 백엔드로 쓰기

GPU 서빙은 Ollama에 맡기고, Tabby는 IDE 연동·인덱싱·사용자 관리만 하게 하는 구성입니다. [Ollama 연결 문서](https://tabby.tabbyml.com/docs/references/models-http-api/ollama/)의 설정입니다.

```toml
# ~/.tabby/config.toml
[model.completion.http]
kind = "ollama/completion"
model_name = "codellama:7b"
api_endpoint = "http://localhost:11434"
prompt_template = "<PRE> {prefix} <SUF>{suffix} <MID>"

[model.chat.http]
kind = "openai/chat"
model_name = "mistral:7b"
api_endpoint = "http://localhost:11434/v1"

[model.embedding.http]
kind = "ollama/embedding"
model_name = "nomic-embed-text"
api_endpoint = "http://localhost:11434"
```

```bash
ollama pull codellama:7b
ollama pull mistral:7b
ollama pull nomic-embed-text
tabby serve
```

주의할 점이 세 가지 있습니다.

- **완성 모델은 `prompt_template`이 모델마다 다릅니다.** 위 값은 CodeLlama용입니다. Qwen2.5-Coder 계열이라면 문서 예시처럼 `<|fim_prefix|>{prefix}<|fim_suffix|>{suffix}<|fim_middle|>`를 씁니다. 템플릿이 틀리면 엉뚱한 제안이 나옵니다.
- 채팅은 Ollama의 OpenAI 호환 API라서 `api_endpoint`에 `/v1`을 붙이고, 완성과 임베딩은 붙이지 않습니다.
- 모델을 HTTP로만 연결할 때 `tabby serve`에 `--model`을 생략하는 구성은 공식 문서에 명시돼 있지 않습니다. 저는 설정 파일 우선으로 동작한다고 이해했지만, 실제 배포 전에 System 화면에서 세 모델이 모두 잡히는지 꼭 확인하세요.

vLLM이나 OpenAI도 같은 방식입니다. OpenAI는 FIM 완성 모델을 제공하지 않으므로 채팅과 임베딩에만 쓸 수 있고, 채팅 엔드포인트에 `/chat/completions`를 붙이면 안 됩니다. 채팅 모델 여러 개를 UI에서 고르게 하려면 `supported_models = ["gpt-4o", "gpt-4o-mini"]`를 추가합니다.

```toml
# 사내 vLLM 서버에 완성 모델 연결
[model.completion.http]
kind = "vllm/completion"
model_name = "your_model"          # vLLM 실행 시 이름과 정확히 같아야 함
api_endpoint = "http://gpu-01:8000/v1"
api_key = "your-api-key"
prompt_template = "<|fim_prefix|>{prefix}<|fim_suffix|>{suffix}<|fim_middle|>"
```

### 3. 사내 저장소를 맥락으로 인덱싱하기

관리자 UI의 **Integrations > Context Providers**에서 추가해도 되고, 설정 파일로 선언해도 됩니다. 문서는 설정 파일 방식이 "Tabby OSS에서 저장소를 추가하는 유일한 방법"이라고 설명합니다.

```toml
# ~/.tabby/config.toml
[[repositories]]
name = "backend"
git_url = "git@gitlab.internal:platform/backend.git"

[[repositories]]
name = "frontend"
git_url = "https://github.com/your-org/frontend.git"

# 로컬 디렉터리도 가능
[[repositories]]
name = "monorepo"
git_url = "file:///repos/monorepo"
```

- Docker로 돌린다면 `file://` 경로는 **컨테이너 안의 경로**여야 합니다. 예: `-v /srv/repos:/repos`로 마운트한 뒤 `file:///repos/monorepo`.
- 비공개 GitHub/GitLab 저장소를 UI로 추가할 때는 개인 액세스 토큰이 필요합니다.
- 추가하면 인덱싱 잡이 자동으로 시작되고, 진행 상황과 로그는 **Information > Jobs**에서 봅니다. 결과는 Code Browser에서 확인할 수 있습니다.
- 그룹을 지정하면 해당 그룹 멤버만 그 저장소 맥락을 쓸 수 있습니다.

인덱싱이 끝나면 IDE 채팅이나 Answer Engine에서 저장소를 선택하고 "결제 모듈의 재시도 로직이 어디 있나요?" 같은 질문을 할 수 있습니다.

### 4. HTTP API로 완성 호출하고, 사내 문서 밀어 넣기

Tabby 서버는 OpenAPI 규격의 HTTP API를 제공합니다. 사내 웹 IDE나 스크립트에서 직접 부를 수 있습니다. 토큰은 웹 UI 홈 화면에서 확인합니다.

```bash
export TABBY=http://localhost:8080
export TOKEN=your-token

# 서버 상태 (모델, 장치 정보)
curl -s -H "Authorization: Bearer $TOKEN" $TABBY/v1/health

# 코드 완성
curl -s -X POST $TABBY/v1/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "language": "python",
    "segments": {
      "prefix": "def fib(n):\n    ",
      "suffix": "\n        return fib(n - 1) + fib(n - 2)"
    }
  }'
```

채팅은 OpenAI 호환 경로인 `/v1/chat/completions`로 부를 수 있습니다.

Confluence나 위키처럼 Tabby가 직접 크롤링하기 어려운 자료는 [Data Ingestion API](https://tabby.tabbyml.com/docs/administration/index-custom-document/)로 넣습니다. 처리는 비동기라서 `202 Accepted`가 오면 다음 인덱스 갱신 때 반영됩니다.

```bash
# 문서 추가 (90일 뒤 자동 삭제)
curl -s -X POST $TABBY/v1beta/ingestion \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "source": "wiki",
    "id": "deploy-guide",
    "title": "배포 가이드",
    "body": "운영 배포는 매주 화요일 ...",
    "link": "https://wiki.internal/deploy",
    "ttl": "90d"
  }'

# source 단위 전체 삭제 / 문서 하나 삭제
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" $TABBY/v1beta/ingestion/wiki
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" $TABBY/v1beta/ingestion/wiki/deploy-guide
```

문서상 이 API의 인증에는 Registration API 토큰을 쓴다고 되어 있습니다. 어떤 토큰이 필요한지는 설치한 버전의 UI에서 확인하시기 바랍니다.

### 5. IDE 쪽 설정 파일로 일괄 배포하기

여러 개발자 PC에 같은 설정을 깔아야 한다면 IDE 설정 화면 대신 tabby-agent 설정 파일을 씁니다. 첫 실행 때 `~/.tabby-client/agent/config.toml`이 자동 생성되고, 수정하면 확장이 다시 읽습니다.

```toml
# ~/.tabby-client/agent/config.toml
[server]
endpoint = "https://tabby.internal.example.com"
token = "your-token-here"   # Authorization: Bearer 헤더로 자동 추가

[server.requestHeaders]
X-Team = "platform"

[logs]
level = "error"             # "silent" | "error" | "debug"

[anonymousUsageTracking]
disable = true
```

- **IDE 설정 화면 값이 이 파일보다 우선합니다.** 파일 값을 쓰려면 IDE 설정을 비워 둬야 합니다.
- 주석을 풀 때는 값 줄만이 아니라 `[server]` 같은 섹션 줄까지 함께 풀어야 합니다.
- 브라우저에서 돌리는 VS Code(웹)에서는 이 파일을 쓸 수 없습니다.
- 로그는 `~/.tabby-client/agent/logs/`에 쌓입니다.

## 실무 팁 & 자주 겪는 문제

| 증상 | 원인과 해결 |
| --- | --- |
| 완성이 느리거나 시간 초과 | 완성 모델이 너무 큽니다. 완성은 1B~3B, 채팅은 7B 이상처럼 역할별로 크기를 나눕니다. `--parallelism`을 올리면 동시 처리량은 늘지만 VRAM이 크게 늘어납니다. |
| GPU가 여러 장인데 하나만 씀 | 설계상 단일 GPU만 지원합니다. 인스턴스를 나누고 `CUDA_VISIBLE_DEVICES`(ROCm은 `HIP_VISIBLE_DEVICES`)로 할당합니다. |
| AMD GPU가 ROCm 미지원 | 비슷한 지원 GPU 버전으로 `HSA_OVERRIDE_GFX_VERSION`을 지정합니다(RDNA2는 10.3.0, RDNA3는 11.0.0). |
| 데이터 디렉터리가 깨짐 | `~/.tabby`를 NFS에 두지 마세요. SQLite가 파일 잠금에 의존하는데 NFS는 잠금 구현이 불완전한 경우가 많아 DB가 손상될 수 있습니다. |
| 리버스 프록시 뒤에서 Answer Engine 응답이 안 옴 | 스트리밍에 WebSocket을 씁니다. Nginx라면 `proxy_http_version 1.1`, `Upgrade`, `Connection "upgrade"` 헤더를 설정합니다. |
| 초대 메일 링크가 엉뚱한 주소 | 가입 링크는 설정한 External URL로 만들어집니다. 사용자가 접근 가능한 주소로 설정하고, 메일 발송에는 SMTP 설정이 필요합니다. |
| 문서 크롤링이 안 됨 | Docker가 아닌 설치는 Katana를 직접 설치해야 합니다. 대상 사이트에 llms.txt가 있으면 크롤링 없이 처리됩니다. |
| 원인을 모르겠음 | 서버는 `RUST_LOG=debug tabby serve`(Docker는 `-e RUST_LOG=debug`), IDE는 agent 설정의 `[logs] level = "debug"`로 로그를 켭니다. |
| 사용자 6명부터 막힘 | Community 라이선스 좌석 제한(가격 페이지 기준 5명)입니다. 팀 규모를 먼저 확인합니다. |

추가로 몇 가지를 권합니다.

- **외부 모델 API를 쓰면 "셀프 호스팅"의 의미가 바뀝니다.** 채팅 모델을 OpenAI 등에 연결하면, 질문과 함께 검색된 코드 조각이 그 API로 나갑니다. 보안 요건이 엄격하다면 로컬 모델이나 사내 vLLM/Ollama만 쓰세요.
- 완성 품질은 모델보다 **맥락 구성**에 좌우되는 경우가 많습니다. `[completion]`의 `max_input_length`(기본 1536자)와 `max_decoding_tokens`(기본 64)는 모델 서빙 설정과 맞물려 있으니, 문서 권고대로 모델 서빙 쪽 컨텍스트 길이를 확인한 뒤에만 바꿉니다.
- 공식 지원 언어에 없는 언어는 `[[additional_languages]]`로 확장자, 주석 문자, 최상위 키워드를 정의해 추가할 수 있습니다(문서에 Swift 예시가 있음).
- 버전 업그레이드 전에는 데이터 디렉터리를 백업합니다. 관리 문서에 백업·업그레이드 페이지가 따로 있습니다.

## 비슷한 도구와 비교

아래 표의 Tabby 항목은 문서 기준이고, 다른 도구는 일반적으로 알려진 내용을 바탕으로 한 대략적인 비교입니다. 각 제품의 기능과 가격은 자주 바뀌니 도입 전에 공식 자료를 확인하세요.

| 항목 | Tabby | GitHub Copilot | Continue | Sourcegraph Cody | Ollama + Continue |
| --- | --- | --- | --- | --- | --- |
| 형태 | 셀프 호스팅 서버 + IDE 확장 | 클라우드 SaaS | IDE 확장(오픈소스) | 코드 검색 플랫폼 기반 어시스턴트 | 로컬 모델 런타임 + IDE 확장 |
| 코드 위치 | 내 서버 | 외부 클라우드 | 연결한 모델에 따라 다름 | 배포 방식에 따라 다름 | 내 PC/서버 |
| 서버 필요 | 필요(팀 공유) | 불필요 | 불필요 | 플랫폼 필요 | Ollama만 |
| 팀 기능 | 사용자·그룹, SSO/LDAP, 사용량 리포트 | 조직 관리, 정책 | 거의 없음(개인 중심) | 엔터프라이즈 기능 풍부 | 없음 |
| 저장소 RAG | 서버 측 인덱싱, Answer Engine | 제품 기능으로 제공 | 로컬 인덱싱 중심 | 강력한 코드 검색 기반 | Continue 기능에 의존 |
| 모델 선택 | 로컬 레지스트리 + HTTP 공급자 다수 | 제공 모델 중 선택 | 자유롭게 연결 | 제공 모델 중심 | Ollama 모델 |
| 비용 구조 | 무료(5명) / 유료 좌석 + 내 GPU | 좌석 구독 | 무료 + 모델 비용 | 상용 | 무료 + 하드웨어 |
| 유지보수 | 2026년 들어 둔화 | 활발 | 대체로 활발 | 제품 방향 변화가 잦았음 | 각각 활발 |

정리하면, "팀 공용 서버 + 사용자 관리 + 사내 저장소 RAG"를 한 덩어리로 원한다면 Tabby가 설계상 가장 잘 맞습니다. 반면 개인 또는 소규모 팀이 로컬 모델만 쓰고 싶다면 Ollama와 Continue 조합이 더 가볍고, 활발히 개발되는 도구를 원한다면 Copilot이나 Continue 쪽이 덜 위험합니다.

## 장점과 한계

**장점**

- 코드와 질문이 내 인프라 밖으로 나가지 않는 구성이 가능합니다(로컬 모델 사용 시).
- 바이너리나 컨테이너 하나에 모델 서빙, 웹 UI, 사용자 관리, 인덱싱이 모두 들어 있어 운영 구성 요소가 적습니다.
- 완성·채팅·임베딩 모델을 역할별로 따로 고르고, 로컬과 HTTP 공급자(Ollama, vLLM, llama.cpp, OpenAI, Anthropic Claude, Azure OpenAI, Bedrock 등)를 섞어 쓸 수 있습니다.
- 소비자용 GPU로도 작은 완성 모델을 충분히 돌릴 수 있습니다.
- OpenAPI 규격의 HTTP API가 있어 사내 도구와 통합하기 쉽습니다.
- 서버 측 저장소·문서 인덱싱과 그룹별 접근 제어가 있습니다.

**한계**

- **개발이 사실상 멈춘 것으로 보입니다.** 마지막 릴리스가 2026년 1월이고, main에는 채팅·지식 기능을 정리하는 변경이 들어가 있습니다. 장기 운영에는 위험 요소입니다.
- 웹 UI와 팀 기능이 있는 `ee/` 코드는 Apache 2.0이 아니며, 6명 이상 팀은 유료 라이선스가 필요합니다(가격 페이지 기준).
- GPU 1장만 쓰는 구조라 대규모 팀은 인스턴스를 나누는 운영 부담이 생깁니다.
- 레지스트리의 기본 모델들(StarCoder, CodeLlama, Qwen2.5-Coder 등)은 최신 대형 모델에 비해 품질이 떨어질 수 있습니다. 좋은 품질을 원하면 결국 큰 GPU나 외부 API가 필요합니다.
- 모델마다 FIM `prompt_template`을 맞춰야 하는 등 튜닝 지식이 필요합니다.
- 에이전트형 코딩(여러 파일을 스스로 고치고 테스트하는 방식)은 Tabby의 범위 밖이며, TabbyML은 이 영역을 Pochi로 분리했습니다.

## 이런 분께 추천 / 이런 경우엔 다른 도구

**추천**

- 폐쇄망이나 보안 규정 때문에 클라우드 코딩 어시스턴트를 쓸 수 없는 5명 이하 팀
- 유료 라이선스를 감수하더라도 온프레미스 완성 서버와 사용자 관리를 한 번에 갖추고 싶은 조직
- 이미 GPU 서버나 Ollama/vLLM 같은 사내 모델 서빙이 있고, IDE 연동 계층만 필요한 팀
- 셀프 호스팅 코딩 어시스턴트의 구조(FIM, RAG, IDE 에이전트)를 직접 공부해 보고 싶은 분

**다른 도구가 나은 경우**

- 장기간 활발한 업데이트와 지원이 중요하다면 GitHub Copilot 같은 상용 서비스나 활발히 개발되는 오픈소스를 고려하세요.
- 개인 개발자가 로컬 모델로 자동완성만 원한다면 서버 없이 Ollama와 Continue 같은 IDE 확장 조합이 더 간단합니다.
- 저장소를 스스로 수정하고 테스트까지 돌리는 코딩 에이전트가 필요하다면 OpenHands, Claude Code 같은 에이전트 도구가 맞습니다.
- 대규모 코드베이스 검색과 탐색이 핵심이라면 코드 검색 플랫폼 기반 도구가 더 적합할 수 있습니다.
