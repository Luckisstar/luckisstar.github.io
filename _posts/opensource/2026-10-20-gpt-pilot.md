## 한 줄 요약

**앱 설명을 입력하면 명세 작성, 아키텍처 결정, 작업 분해, 코드 작성, 리뷰, 디버깅을 각각 맡은 LLM 에이전트들이 순서대로 일하며 앱을 한 단계씩 만들어 가는 오픈소스 AI 개발 도구**입니다. 사람이 중간중간 질문에 답하고, 실행 결과를 확인하고, 막힌 부분을 고쳐 주는 "감독자" 역할을 합니다.

## 어떤 문제를 푸나

2023년 무렵의 코드 생성 도구(GPT Engineer, Smol Developer 등)는 설명을 받으면 **코드베이스 전체를 한 번에** 생성하는 방식이 많았습니다. 결과물이 그럴듯해 보여도 실행하면 버그가 여러 곳에서 동시에 터지고, AI도 사람도 어디서부터 고쳐야 할지 알기 어려웠습니다.

GPT Pilot은 README에서 이렇게 문제를 정의합니다.

- AI가 앱 코드의 대부분(README 표현으로 "아마 95%")을 쓸 수 있지만, 나머지 5%는 AGI가 오기 전까지 개발자가 필요하다.
- 그러니 AI가 **실제 개발자처럼 작업을 잘게 나눠 한 단계씩** 코딩하고, 단계마다 실행해 보고, 문제가 생기면 그 자리에서 디버깅해야 한다.
- 각 LLM 호출에는 코드베이스 전체가 아니라 **현재 작업과 관련된 코드만** 보여 줘야 앱이 커져도 동작한다.

즉 "한 방에 생성"이 아니라 "사람이 감독하는 단계적 개발"을 자동화하려는 연구 성격의 프로젝트였습니다. 팀은 이 과정에서 배운 점을 [블로그 글](https://blog.pythagora.ai/2024/02/19/gpt-pilot-what-did-we-learn-in-6-months-of-working-on-a-codegen-pair-programmer/)로 정리하기도 했습니다.

## 핵심 개념

### 에이전트(Agent)

여기서 **에이전트**는 특정 역할의 프롬프트와 로직을 가진 LLM 호출 단위입니다. README가 설명하는 역할은 다음과 같습니다.

| 에이전트 | README가 설명하는 역할 |
| --- | --- |
| Product Owner | "실제 회사에서처럼 아무것도 안 한다"(README의 농담) |
| Specification Writer | 설명이 부족하면 질문을 던져 요구 사항을 구체화 |
| Architect | 사용할 기술을 정하고, 머신에 설치되어 있는지 확인하고 없으면 설치 |
| Tech Lead | Developer가 구현할 개발 작업(task) 목록 작성 |
| Developer | 각 작업을 사람이 읽을 수 있는 구현 설명으로 풀어 씀 |
| Code Monkey | Developer의 설명과 기존 파일을 보고 실제로 코드 변경 |
| Reviewer | 작업의 각 단계를 검토하고 잘못되면 Code Monkey에게 되돌림 |
| Troubleshooter | 문제가 있을 때 사용자가 좋은 피드백을 주도록 도움 |
| Debugger | 일이 꼬였을 때 등장하는 디버깅 담당 |
| Technical Writer | 프로젝트 문서 작성 |

마지막 코드(`core/agents/`)를 보면 README 목록보다 세분화되어 있습니다. `SpecWriter`, `Architect`, `TechLead`, `Developer`, `CodeMonkey`, `Executor`(명령 실행), `BugHunter`(로그로 버그 추적), `Troubleshooter`, `ProblemSolver`(같은 문제를 반복할 때), `TechnicalWriter`, `Frontend`, `Importer`, `HumanInput`, `Wizard`(새 프로젝트 시작 마법사), `ErrorHandler` 같은 클래스가 있습니다. README의 Reviewer와 Debugger 역할은 코드에서 `CodeMonkey`의 코드 리뷰 단계와 `BugHunter`·`Troubleshooter` 흐름으로 나뉘어 들어가 있습니다.

### 에픽, 작업, 스텝, 이터레이션

GPT Pilot은 개발 과정을 상태(state)로 저장합니다. 코드에 등장하는 단위는 다음과 같습니다.

| 단위 | 의미 |
| --- | --- |
| Epic | 큰 기능 묶음. 처음 앱 전체도 하나의 에픽으로 시작 |
| Task | Tech Lead가 나눈 개발 작업 하나 |
| Step | 작업을 실행하는 단계. 파일 저장, 명령 실행, 사람 개입 요청 등 |
| Iteration | 사용자가 문제를 보고했을 때 버그를 찾고 고치는 반복 |

모든 상태는 데이터베이스(기본 SQLite)에 쌓이므로, 중간에 끊겨도 마지막 단계부터 이어 가거나 특정 단계로 되돌릴 수 있습니다.

### 템플릿

Architect는 명세를 보고 미리 준비된 **프로젝트 템플릿**을 고를 수 있습니다. 최신 코드에서 활성화된 템플릿은 Vite + React 계열(`vite_react`, `vite_react_swagger`)이고, Node/Express/Mongoose 등 다른 템플릿은 주석 처리되어 있습니다. 즉 마지막 버전은 사실상 **JavaScript 웹앱 중심**으로 좁혀져 있었습니다.

## 동작 원리

### 전체 흐름

```
 User: app name + description
           |
           v
   [SpecWriter] ask questions
           |
           v
   [Architect] pick stack, check deps
           |
           v
   [TechLead] split into tasks
           |
   +-------v--------------------+
   | for each task:             |
   |  [Developer] describe how  |
   |  [CodeMonkey] edit files   |
   |  [CodeMonkey] review       |
   |  [Executor] run commands   |
   |  User tests the app        |
   |   ok -> [TechWriter] docs  |
   |   bug -> [BugHunter]       |
   |          [Troubleshooter]  |
   +----------------------------+
           |
           v
   workspace/<app>/ (source code)
```

이 흐름을 조율하는 것이 `Orchestrator`입니다. 오케스트레이터는 현재 상태를 보고 다음에 실행할 에이전트를 고릅니다. 예를 들어 코드상 규칙은 다음과 같습니다.

- 에픽이 없으면 `Wizard`, 명세가 없으면 `SpecWriter`
- 아키텍처가 정해지지 않았으면 `Architect`
- 남은 작업이 없으면 `TechLead`가 다음 작업을 계획
- 작업에 스텝이 없으면 `Developer`가 스텝을 만들고, 스텝 종류에 따라 `CodeMonkey`(파일 저장), `Executor`(명령), `HumanInput`(사람 확인)으로 넘김
- 사용자가 버그를 보고하면 이터레이션 상태에 따라 `BugHunter`, `Developer`, `Troubleshooter`가 번갈아 동작
- 사용자가 "같은 곳에서 맴돈다"고 하면 `ProblemSolver` 호출

### 컨텍스트를 줄이는 방법

앱이 커지면 모든 파일을 프롬프트에 넣을 수 없습니다. GPT Pilot은 다음 방식으로 컨텍스트를 관리합니다.

1. 파일마다 짧은 설명을 LLM으로 만들어 저장합니다(`CodeMonkey.describe_files`).
2. 작업을 처리할 때 그 설명을 보고 관련 파일만 고릅니다(`get_relevant_files`).
3. `fs.ignore_paths`에 있는 경로와 50KB가 넘는 파일, 바이너리 파일은 아예 추적하지 않습니다.

### 사람의 역할

GPT Pilot은 완전 자동이 아닙니다. 사람은 다음 시점에 개입합니다.

- 명세 단계의 질문에 답하기
- 작업이 끝날 때마다 앱을 실행해 보고 "잘 된다" 또는 "이런 문제가 있다"고 알려 주기
- API 키 입력, 외부 서비스 설정처럼 AI가 할 수 없는 일 처리
- AI가 같은 버그에서 빠져나오지 못할 때 직접 코드를 고치기

## 주요 기능

- **멀티 에이전트 파이프라인:** 명세부터 문서화까지 역할을 나눈 에이전트들이 순서대로 동작합니다.
- **에이전트별 모델 지정:** `config.json`의 `agent` 항목에서 에이전트마다 다른 공급자, 모델, temperature를 줄 수 있습니다.
- **여러 LLM 공급자:** 설정 스키마상 `openai`, `anthropic`, `groq`, `azure`, `lm-studio`, `relace`를 지원합니다. README는 OpenRouter와 로컬 LLM(LM Studio 등)도 `openai` 설정으로 연결할 수 있다고 안내합니다.
- **상태 저장과 되감기:** 모든 단계가 DB에 저장되어 `--project`, `--step`으로 이어 가거나 되돌릴 수 있습니다.
- **명령 실행:** 의존성 설치, 서버 실행 같은 명령을 직접 실행하고 결과를 다음 판단에 사용합니다.
- **기존 프로젝트 가져오기:** `Importer` 에이전트가 기존 코드를 읽어 상태로 만드는 흐름이 있습니다.
- **VS Code 확장 연동:** 기본 UI는 터미널(`ui.type: "plain"`)이지만, IPC(프로세스 간 통신) 서버로 VS Code 확장과 연결하는 옵션이 있습니다. 실제로 마지막 버전의 많은 CLI 옵션(`--extension-version`, `--access-token`, `--local-api-server-port` 등)은 확장을 위한 것입니다.
- **텔레메트리:** 실행 시간, LLM 요청 수, 앱 설명, 아키텍처 등을 수집합니다. `docs/TELEMETRY.md`는 `~/.gpt-pilot/config.json`에서 `telemetry.enabled`를 `false`로 두면 끈다고 안내합니다.

## 설치와 시작

> 아래 절차는 README 기준입니다. **반드시 2026-06-11 이후 커밋(악성 코드 제거 이후)을 받고, 격리된 환경(VM이나 개발용 컨테이너)에서 실행하세요.** 자세한 이유는 실전 예제 5와 실무 팁에 정리했습니다.

준비물은 Python 3.9 이상이고, PostgreSQL은 선택입니다(기본은 SQLite).

```bash
git clone https://github.com/Pythagora-io/gpt-pilot.git
cd gpt-pilot
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp example-config.json config.json
# config.json에 LLM 공급자와 API 키를 넣은 뒤
python main.py
```

실행하면 앱 이름과 설명을 묻고, 생성된 코드는 `workspace/<앱 이름>/` 폴더에 저장됩니다.

PostgreSQL을 쓰려면 드라이버를 추가 설치하고 `db.url`을 바꿉니다.

```bash
pip install asyncpg psycopg2
```

```json
"db": { "url": "postgresql+asyncpg://user:pass@localhost/gptpilot" }
```

Docker는 사실상 쓰기 어렵습니다. 저장소의 `Dockerfile`은 마지막에 Pythagora 클라우드 환경용으로 바뀌어 `pythagora-vs-code.vsix` 파일을 복사하는 단계가 있고, README 목차의 Docker 항목 링크도 깨져 있습니다(관련 이슈가 열려 있습니다).

## 실전 예제

### 1. Anthropic 키로 최소 설정하기

`example-config.json`을 복사한 뒤 필요한 부분만 남긴 예시입니다. 이 설정 파일은 `//`로 시작하는 줄을 주석으로 허용합니다.

```json
{
  // 공급자 접속 정보
  "llm": {
    "anthropic": {
      "base_url": "https://api.anthropic.com",
      "api_key": "sk-ant-...",
      "connect_timeout": 60.0,
      "read_timeout": 20.0
    }
  },
  // 모든 에이전트가 쓰는 기본 모델
  "agent": {
    "default": {
      "provider": "anthropic",
      "model": "claude-sonnet-4-20250514",
      "temperature": 0.5
    }
  },
  "db": {
    "url": "sqlite+aiosqlite:///data/database/pythagora.db",
    "debug_sql": false
  },
  "ui": { "type": "plain" },
  "fs": {
    "type": "local",
    "workspace_root": "workspace",
    "ignore_paths": [".git", "node_modules", "venv", "dist", "build"],
    "ignore_size_threshold": 50000
  }
}
```

`api_key`를 `null`로 두면 각 공급자 SDK의 기본 환경 변수(예: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`)에서 읽습니다. 키를 파일에 쓰기 싫다면 이 방식이 낫습니다.

알아 둘 점이 하나 있습니다. 코드에 들어 있는 기본 설정은 에이전트마다 서로 다른 모델(Claude Sonnet 4, GPT-4o mini, Relace의 코드 병합 모델 등)을 지정해 둡니다. 그런데 `config.json`에 `agent` 항목을 직접 쓰면 이 기본 목록이 **통째로 교체**되고, 목록에 없는 에이전트는 모두 `default` 설정을 씁니다. 위 예시처럼 쓰면 모든 에이전트가 같은 모델을 쓰게 되어 동작이 예측 가능해집니다.

### 2. 에이전트별로 모델 나누기

비용을 줄이려면 단순한 일(파일 설명 생성)은 싼 모델에, 코드를 직접 고치는 일은 강한 모델에 맡길 수 있습니다. 에이전트 이름은 코드의 상수와 정확히 같아야 하며, 클래스 이름 또는 `클래스.메서드` 형식입니다.

```json
{
  "llm": {
    "openai": { "base_url": null, "api_key": null },
    "anthropic": { "base_url": "https://api.anthropic.com", "api_key": null }
  },
  "agent": {
    "default": {
      "provider": "openai",
      "model": "gpt-4o-2024-05-13",
      "temperature": 0.5
    },
    "CodeMonkey": {
      "provider": "anthropic",
      "model": "claude-sonnet-4-20250514",
      "temperature": 0.0
    },
    "CodeMonkey.describe_files": {
      "provider": "openai",
      "model": "gpt-4o-mini-2024-07-18",
      "temperature": 0.0
    },
    "TechLead.plan_epic": {
      "provider": "anthropic",
      "model": "claude-sonnet-4-20250514",
      "temperature": 0.5
    }
  }
}
```

코드에 정의된 이름 중 자주 쓸 만한 것은 `SpecWriter`, `TechLead.plan_epic`, `TechLead.epic_breakdown`, `Developer.parse_task`, `Developer.breakdown_current_task`, `CodeMonkey`, `CodeMonkey.code_review`, `CodeMonkey.implement_changes`, `CodeMonkey.describe_files`, `BugHunter.check_logs`, `Troubleshooter.generate_bug_report`, `Frontend`, `get_relevant_files`입니다. 모델 ID는 2024~2025년 기준이라 지금은 공급자에서 지원이 끝났을 수 있으니 실제로 쓸 수 있는 모델로 바꿔야 합니다.

### 3. OpenAI 호환 엔드포인트(OpenRouter, LM Studio) 쓰기

README와 예시 설정은 OpenRouter나 로컬 LLM을 `openai` 공급자로 연결하라고 안내합니다. `base_url`에는 `chat/completions` 앞부분까지만 씁니다.

```json
{
  "llm": {
    "openai": {
      "base_url": "http://localhost:1234/v1",
      "api_key": "lm-studio",
      "connect_timeout": 60.0,
      "read_timeout": 120.0
    }
  },
  "agent": {
    "default": {
      "provider": "openai",
      "model": "your-local-model-id",
      "temperature": 0.3
    }
  }
}
```

설정 파일을 고치지 않고 실행할 때만 바꾸고 싶다면 CLI 옵션을 씁니다. 형식은 `공급자:값`입니다.

```bash
python main.py \
  --llm-endpoint openai:https://openrouter.ai/api/v1 \
  --llm-key openai:$OPENROUTER_API_KEY
```

로컬 모델은 응답이 느리므로 `read_timeout`을 넉넉히 두는 편이 좋습니다. 다만 GPT Pilot의 프롬프트는 큰 상용 모델을 전제로 다듬어졌기 때문에, 작은 로컬 모델에서는 JSON 응답 형식을 지키지 못해 단계가 자주 실패할 수 있습니다(일반적인 경향이며 공식 수치는 없습니다).

### 4. 프로젝트 목록 보기, 이어 하기, 되돌리기

모든 진행 상황이 DB에 저장되므로 중간에 터미널을 닫아도 됩니다.

```bash
# 만든 프로젝트(앱)와 브랜치 목록
python main.py --list

# 마지막 단계부터 이어 하기
python main.py --project <app_id>

# 특정 단계로 되돌려 다시 진행 (이후 진행 내용은 삭제됨)
python main.py --project <app_id> --step 42

# 프로젝트 삭제 (되돌릴 수 없음)
python main.py --delete <app_id>

# 그 밖의 옵션
python main.py --help
```

`--step`은 그 단계 이후의 기록을 **지운다**는 점에 주의합니다. 되돌리기 전에 `data/database/pythagora.db`와 `workspace/<앱>` 폴더를 복사해 두면 안전합니다. 기본으로 Git을 쓰지 않으므로, 생성된 앱 폴더에서 직접 `git init` 후 단계마다 커밋해 두는 습관도 도움이 됩니다(`--use-git` 옵션도 있습니다).

### 5. 예전에 받은 저장소가 감염 버전인지 확인하기

README가 안내하는 침해 지표(IoC, Indicators of Compromise)를 기준으로 점검하는 스크립트입니다. 2025년 8월부터 2026년 6월 11일 사이에 받은 저장소가 있다면 한 번 돌려 보세요.

```bash
cd gpt-pilot

# 1) 악성 커밋이 현재 이력에 포함되어 있는지
if git merge-base --is-ancestor 065ee8eb HEAD 2>/dev/null; then
  echo "[!] 악성 커밋 065ee8eb 이 이력에 있음"
fi

# 2) 제거 커밋(PR #1183 병합) 이후인지 확인
git log --oneline -5

# 3) README가 밝힌 파일 흔적
ls -la core/telemetry/_runtime.bin \
       core/telemetry/_hooks.py \
       core/telemetry/.loader.lock 2>/dev/null

# 4) 예상치 못한 bun 실행 파일, rt-* 임시 폴더
command -v bun
find "${TMPDIR:-/tmp}" -maxdepth 1 -name 'rt-*' 2>/dev/null
```

README 기준으로 **코드를 받아만 두고 실행하지 않았다면 영향이 없습니다.** 실행했다면 그 머신에 있던 GitHub/npm 토큰, AWS 등 클라우드 키, SSH 키, LLM API 키를 모두 교체하고, 깨끗하다고 확인할 때까지 그 머신을 침해된 것으로 취급하라고 안내합니다. 최신 `main`을 받아도 **악성 파일은 Git 이력에는 남아 있습니다**(PR 본문에 명시). 오래된 커밋으로 체크아웃하지 않도록 주의합니다.

## 실무 팁 & 자주 겪는 문제

| 증상 | 원인과 해결 |
| --- | --- |
| 설정 파일을 읽다가 검증 오류 | 설정은 엄격 모드로 검증되어 모르는 키가 있으면 실패합니다. 키 이름 오타를 확인합니다. |
| 주석을 넣었더니 JSON 파싱 오류 | `//`로 **시작하는 줄**만 주석으로 지웁니다. 값 뒤에 붙인 줄 끝 주석은 지원하지 않습니다. |
| 일부 에이전트가 이상한 모델/공급자로 호출 | `agent` 항목을 쓰지 않으면 코드의 기본 목록(여러 모델 혼합)이 쓰입니다. `agent`를 직접 정의해 통제합니다. |
| `relace` 관련 오류 | 기본 설정의 `CodeMonkey.implement_changes`가 Relace 모델을 씁니다. `agent`를 직접 정의하면 `default`로 대체됩니다. |
| 같은 버그를 계속 못 고침 | 작업 크기가 너무 크거나 작을 때 품질이 떨어진다고 README가 직접 언급합니다. 직접 코드를 고치고 진행하거나, `--step`으로 앞 단계로 돌아가 설명을 바꿔 봅니다. |
| 비용이 예상보다 큼 | 단계마다 여러 에이전트가 호출되고, 리뷰·디버깅 루프가 돌면 호출 수가 빠르게 늘어납니다. 공급자 콘솔에 사용 한도를 걸어 두세요. |
| 생성된 앱이 특정 스택으로만 나옴 | 마지막 버전은 Vite + React 템플릿만 활성화되어 있습니다. |

보안 관련 추가 주의점입니다.

- **격리된 환경에서 실행하세요.** GPT Pilot은 LLM이 정한 명령을 실제로 실행하고 파일을 씁니다. 2026-10-17에는 LLM이 정한 파일 경로로 작업 폴더 밖에 파일을 쓸 수 있다는 경로 탈출(path traversal) 이슈가 올라왔고, 작성 시점에 열려 있습니다. 개인 자격 증명이 있는 메인 PC가 아니라 VM이나 일회용 컨테이너를 권합니다.
- `requests` 패키지가 알려진 취약점(CVE-2024-47081)이 있는 버전으로 고정되어 있다는 이슈와 수정 PR도 열린 상태입니다. 유지보수가 끝났으므로 이런 문제가 병합될 가능성은 낮습니다.
- 텔레메트리에는 앱 설명과 아키텍처가 포함됩니다. 민감한 사내 아이디어라면 꺼 두는 편이 안전합니다.

## 비슷한 도구와 비교

아래 표에서 GPT Pilot 열은 저장소 코드와 README 기준이고, 다른 도구 열은 일반적으로 알려진 내용을 정리한 것입니다. 이 분야는 변화가 매우 빨라 세부 기능과 가격은 현재와 다를 수 있습니다.

| 오픈소스 | 소스 공개(FSL) | 아니오 | 예(MIT 계열로 알려짐) | 아니오 | 아니오 |
| 유지보수 | 종료 | 활발 | 활발 | 활발 | 활발 |
| 주 용도 | 새 앱을 처음부터 생성 | 이슈 단위 작업 위임 | 이슈 해결, 자동화 | 기존 코드베이스 작업 | 편집 중 코드 작성·수정 |

## 장점과 한계

**장점**

- 명세, 아키텍처, 작업 분해, 구현, 리뷰, 디버깅을 역할별로 나눈 구조가 코드로 남아 있어 멀티 에이전트 설계를 공부하기 좋은 자료입니다.
- 오케스트레이터가 상태를 보고 다음 에이전트를 고르는 방식, 파일 설명으로 관련 파일만 고르는 방식 등 실전 기법을 읽을 수 있습니다.
- 에이전트마다 모델을 따로 지정할 수 있어 비용·품질 균형을 실험하기 쉽습니다.
- 모든 진행 상태가 DB에 남아 이어 하기와 되감기가 가능합니다.

**한계**

- **유지보수가 끝났습니다.** 버그, 취약점, 새 모델 대응이 이뤄지지 않습니다.
- 2025-08~2026-06 동안 저장소에 자격 증명 탈취 웜이 들어 있었고, 악성 파일은 Git 이력에 여전히 남아 있습니다.
- 라이선스가 MIT가 아니라 FSL-1.1-MIT입니다. 내부 사용, 비상업적 교육·연구는 허용하지만, 이 소프트웨어를 대체하거나 같은 기능을 제공하는 **경쟁 상업 제품·서비스**로 쓰는 것은 금지됩니다. LICENSE의 "Grant of Future License" 조항에 따라 각 버전은 공개된 날로부터 2년이 지나면 MIT 라이선스로도 쓸 수 있습니다. 따라서 2024년 공개분 코드는 이미 MIT로 쓸 수 있는 부분이 생겼지만, 어떤 파일이 언제 공개되었는지는 직접 따져 봐야 합니다.
- 마지막 버전은 Vite + React 템플릿 중심이라 다른 스택의 앱 생성은 기대하기 어렵습니다.
- 코드 기본값의 모델 ID가 2024~2025년 것이라 그대로는 동작하지 않을 수 있습니다.
- 많은 CLI 옵션과 기능이 VS Code 확장과 Pythagora 클라우드 API를 전제로 만들어져 있어, 순수 CLI 사용 경험은 거칠 수 있습니다.

## 이런 분께 추천

- 멀티 에이전트 코딩 시스템을 직접 설계하려고 참고 구현을 찾는 분
- "에이전트 역할 분리 + 상태 기반 오케스트레이션" 패턴을 코드 수준에서 공부하고 싶은 분
- LLM 코드 생성의 역사(2023~2025년 흐름)를 정리하는 분

실제로 실행해 보고 싶다면 최신 커밋을 받아 격리된 VM에서, 사용 한도를 건 API 키로 실험하는 정도를 권합니다.

## 이런 경우엔 다른 도구

- **지금 실무에서 AI 코딩 에이전트가 필요하다면** 활발히 유지보수되는 도구를 고르세요. 오픈소스를 원하면 OpenHands, 터미널 중심이면 Claude Code, 에디터 통합이면 Cursor 같은 선택지가 일반적입니다.
- **기존 대규모 코드베이스를 다룬다면** GPT Pilot은 새 앱 생성에 초점이 있어 맞지 않습니다.
- **상업 서비스에 엔진으로 넣으려 한다면** FSL의 경쟁 사용 금지 조항 때문에 법무 검토가 필요하며, 유지보수 종료와 보안 이력까지 고려하면 권하지 않습니다.
