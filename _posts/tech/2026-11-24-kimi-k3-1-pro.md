# [기술 소개] Kimi K3.1 Pro: 2.8T MoE 오픈웨이트, 그러나 매출·사용자 조건이 붙은 MIT 기반 자체 라이선스

- **발표:** Moonshot AI. 기술 블로그와 API 문서에 발표 날짜 표기는 없고, Hugging Face 저장소는 2026-11-02 생성, 2026-11-05 마지막 수정입니다(Hugging Face API 기준). 발표문은 "전체 가중치를 11월 4일까지 공개"한다고 적었습니다.
- **원문:** [기술 블로그](https://www.kimi.ai/blog/kimi-k3-1-pro) · [Hugging Face 모델 카드](https://huggingface.co/moonshotai/Kimi-K3.1-Pro) · [LICENSE 원문](https://huggingface.co/moonshotai/Kimi-K3.1-Pro/blob/main/LICENSE) · [API 퀵스타트](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart) · [API 가격](https://platform.kimi.ai/docs/pricing/chat) · [vLLM 레시피](https://recipes.vllm.ai/moonshotai/Kimi-K3.1-Pro)
- **한눈에 (2026-11-24 기준):** 총 2.8T, 토큰당 활성 104B 파라미터의 MoE(전문가 혼합, Mixture of Experts) 모델로, 전문가 896개 중 16개를 고릅니다. 컨텍스트 1,048,576토큰, 입력은 텍스트·이미지입니다. 가중치는 safetensors 96개 파일, 합계 약 1.56TB이며 Hugging Face 좋아요 2,437개, 최근 다운로드 73,560회입니다(Hugging Face API 수치).
- **도입 전 확인할 사항:**
  - **OSI 승인 오픈소스 라이선스가 아닙니다.** MIT 문구로 시작하지만 이름은 "Kimi K3.1-Pro License"이고, ① 연 매출 2,000만 달러를 넘는 MaaS(Model as a Service, 모델을 API 등으로 제공하는 사업) 사업자는 상업적 사용 전에 Moonshot AI와 별도 계약을 맺어야 하며, ② 월 활성 사용자 1억 명 또는 월 매출 2,000만 달러를 넘는 상업 제품은 UI에 "Kimi K3.1-Pro"를 눈에 띄게 표시해야 합니다(아래 "라이선스" 절에서 원문 인용).
  - **벤치마크는 모두 제조사 자체 보고입니다.** 경쟁 모델 수치는 여러 출처에서 가져왔고, Kimi 쪽은 주로 Claude Code 하네스로 측정했습니다.
  - **직접 운영하려면 데이터센터급 장비가 필요합니다.** vLLM 레시피의 기본 구성은 GB300 트레이 2개 또는 B300 노드 1개(GPU 8장)의 텐서 병렬입니다.

## 한 줄 요약

**Moonshot AI가 2.8T 모델 Kimi K3를 대규모 강화학습으로 후학습하고 긴 컨텍스트용 희소 어텐션을 넣은 Kimi K3.1 Pro를 가중치와 함께 내놓았습니다.** 코딩·에이전트 벤치마크 일부에서 상위 상용 모델에 근접한 자체 수치를 보고했지만, 라이선스는 K2 시절보다 조건이 늘어난 자체 라이선스라 "MIT 오픈소스"로 읽으면 안 됩니다.

## 배경

Kimi K3의 Hugging Face 저장소는 2026-06-13에 만들어졌고(Hugging Face API 기준), 모델 카드는 K3를 "세계 최초의 오픈 3T급 모델"로 소개하며 KDA(Kimi Delta Attention)와 AttnRes(Attention Residuals), 896개 전문가 중 16개를 쓰는 LatentMoE 구조를 내세웠습니다. 블로그의 [Reflection AI Beam 글](/tech/2026/10/20/reflection-beam.html)에서 Reflection 스스로 "Kimi K3가 더 강하다"고 인정했고, [Meta Muse Spark Open 글](/tech/2026/10/24/meta-muse-spark-open.html)의 Meta 비교표에서도 Kimi K3가 여러 항목에서 앞섰습니다. 지금 K3 모델 카드에는 `new_version: moonshotai/Kimi-K3.1-Pro`가 표시되어 있습니다.

K3.1 Pro는 이름처럼 K3의 후속 버전입니다. 기술 블로그는 "K3의 사후 학습판으로, 사후 학습 연산량을 크게 늘렸다"고 설명하고, 수백 개 도메인에 걸친 대규모 공동 강화학습을 위해 RL 프레임워크, 긴 컨텍스트 추론, 샌드박스 인프라, 롤아웃 스케줄링까지 스택 전체를 손봤다고 밝힙니다. K3.1 Pro보다 2~3배 빠르다는 Kimi K3.1 Pro Highspeed(API 모델 ID `kimi-k3.1-pro-highspeed`)도 함께 Kimi 제품군과 API에 나왔습니다.

## 핵심 내용

### 1. 구조: K3의 뼈대에 희소 어텐션을 얹다

모델 카드의 주요 사양은 다음과 같습니다.

| 항목 | 값 (모델 카드 기준) |
|---|---|
| 파라미터 | 총 2.8T / 활성 104B |
| 레이어 | 93개 (dense 1개) |
| 어텐션 구성 | KDA 69개 + Gated DSA 24개 |
| 어텐션 은닉 차원·헤드 | 7168, 96개 |
| DSA 인덱서 | 헤드 32개, 헤드 차원 128, Top-K 2048 |
| 전문가 | 896개 중 토큰당 16개, 공유 전문가 2개, 전문가당 은닉 3072, Latent MoE 차원 3584 |
| 어휘 / 컨텍스트 | 160K / 1,048,576토큰 |
| 비전 인코더 | MoonViT-V2, 401M |
| 양자화 | MXFP4 가중치 / MXFP8 활성값 (양자화 인식 학습) |

모델 카드 각주는 K3 대비 변화를 한 문장으로 설명합니다. **"K3의 전체 어텐션(Gated MLA) 레이어를 더 효율적인 긴 컨텍스트 모델링을 위해 Gated DSA(DeepSeek Sparse Attention) 레이어로 바꿨다"**는 것입니다. 실제로 K3 모델 카드의 어텐션 구성은 "69 KDA + 24 Gated MLA"이고, K3.1 Pro는 "69 KDA + 24 Gated DSA"입니다.

공개된 `config.json`을 보면 배치가 더 구체적으로 보입니다. `linear_attn_config`의 `kda_layers`에 69개 레이어가, `full_attn_layers`와 `dsa_config.dsa_layers`에 같은 24개 레이어(4, 8, 12, …, 92와 마지막 93)가 들어 있습니다. 즉 **네 레이어마다 한 번(와 마지막 레이어)만 전체 토큰을 볼 수 있는 어텐션을 두고, 나머지는 선형 어텐션 계열인 KDA로 처리하는 하이브리드 구조**입니다(`model_type`도 `kimi_linear`입니다). K3.1에서는 그 24개 레이어마저 인덱서가 고른 상위 2,048개 토큰만 보는 희소 어텐션으로 바뀌었습니다. vLLM 레시피도 "K3.1은 K3의 레이아웃을 유지하면서 24개 MLA 레이어에 희소 어텐션(DSA, top-2048 인덱서)을 추가했다"고 같은 내용을 적고 있습니다.

활성 비율은 104B/2.8T로 약 3.7%입니다. [MoE 개념 글](/tech/2026/10/24/mixture-of-experts.html)에서 다룬 것처럼 연산량은 활성 파라미터 규모를 따르지만 메모리에는 전체 가중치를 올려야 합니다. 가중치 파일 합계가 약 1.56TB인 것도 그래서입니다. 체크포인트는 라우팅 전문가 가중치만 MXFP4이고 나머지는 BF16입니다(vLLM 레시피 설명).

### 2. 후학습: 코딩, 3D, 금융, 사실성

기술 블로그가 꼽은 개선 영역은 네 가지입니다.

- **코딩:** Unity, Unreal Engine, Godot 같은 게임 엔진 작업과 Three.js 장면, 장기 과제를 강조합니다. 내부 사례로, 뼈 296개·근육 402개로 된 오픈소스 인체 모델 human-atlas 위에서 보행 시뮬레이터를 만들며 167개 임무와 420번의 독립 리뷰를 거쳐 "몇 초 만에 쓰러지던" 인체를 11.2초 동안 걷게 했고, 그 과정에서 어깨 근육 모멘트 암 계산 오류 36개를 찾아 고쳤다고 합니다.
- **3D 모델링:** 다시점 렌더링에서 CAD 코드로 3D를 복원하는 BenchCAD(도구 사용)에서 92.7%를 보고하며, MCP 커넥터 없이 Blender나 CAD 스크립트를 직접 작성·실행할 수 있다고 설명합니다.
- **금융:** 실제 재무 문서 분석인 OfficeQA Pro v2에서 64.4로 "최고 수준"이라고 하고, 내부 금융 모델링은 K3 대비 7.2점, 금융 리서치는 11.6점 올랐으며, 내부 Business Operation 벤치마크는 K3의 약 4.2배라고 밝힙니다.
- **사실성:** 내부 Kimi Hallu Bench Hard에서 주장 단위 환각률이 K3의 23.4%에서 8.3%로 떨어졌다고 합니다. 블로그 스스로 "오류가 나기 쉬운 상황을 일부러 만든 스트레스 테스트이며, 일상 사용의 전체 오류율을 뜻하지 않는다"고 단서를 답니다.

### 3. 사이버 능력: "데이터를 빼서" 낮췄다

이번 발표에서 가장 눈에 띄는 대목입니다. 기술 블로그에 따르면 사후 학습 규모를 키울수록 취약점 연구 능력이 꾸준히 올라갔고, 원인을 추적해 보니 일반 중간 학습(mid-training) 코퍼스와 RL 환경에 사이버 관련 내용이 섞여 있었습니다. 그래서 **오픈웨이트 공개판에서는 두 단계 모두에서 사이버 관련 데이터를 찾아 제거**하고, 일반 코딩 과제는 유지했다고 합니다.

결과는 내부 벤치마크 xdev-bench-hard(Linux 커널, Node.js, JavaScriptCore, Exim, VirGL 등 최근 공개 취약점을 재현한 익스플로잇 과제, pass@3)로 보고합니다. 제거 조치를 하지 않은 체크포인트는 90.5%, 최종 K3.1 Pro는 81.0%였습니다. 블로그는 동시에 "K3.1 Pro가 이전 모델보다는 크게 나아졌다"고 인정하며, 공개 원칙으로 "사이버 능력의 절대 최전선을 넓히는 가중치는 공개하지 않는다"와 "공개 가중치의 사이버 능력은 점진적으로 높여 간다"는 두 가지를 제시합니다. 또 K3.1 Pro의 사이버 능력은 "공개된 지 최소 3개월 된 최전선 상용 모델보다 뒤처진다"고 설명합니다. 모델 카드 표에서도 ExploitBench 74.7, ExploitGym 20.7로 비교한 상용 모델(각각 83.0~100, 30.4~42.4)보다 낮습니다.

### 4. API 사용법에서 달라진 점

API 문서 기준 주요 사항입니다.

- **추론은 항상 켜져 있습니다.** 강도는 최상위 `reasoning_effort` 필드로 `low`, `high`, `max` 중 고르며 기본값은 `max`입니다. K2.x에서 옮겨 올 때는 기존 `thinking` 설정을 지우라고 안내합니다.
- **멀티턴과 도구 호출에서는 API가 돌려준 어시스턴트 메시지를 그대로 다시 넣어야 합니다.** `content`만이 아니라 `reasoning_content`와 `tool_calls`까지 포함해야 하며, 모델 카드 예제는 이전 추론 내용에만 있던 숫자를 다음 턴에서 기억하는지로 이를 보여 줍니다.
- **샘플링 값이 고정입니다.** `temperature=1.0`, `top_p=0.95`, `n=1`, `presence_penalty=0`, `frequency_penalty=0`이 고정이므로 요청에서 빼라고 합니다. `max_completion_tokens` 기본값은 131,072, 최대 1,048,576입니다.
- **컨텍스트 캐싱은 자동입니다.** TTL은 `5m`(기본)과 `1h` 두 가지이고 `prompt_cache_options.ttl`로 고릅니다. 블록 단위로 저장되어 블록을 다 채우지 못한 끝부분은 캐시 미스로 과금됩니다.
- **제약:** 이미지는 공개 URL을 받지 않고 base64나 `ms://<file-id>`만 받으며, 공식 웹 검색 도구는 "업데이트 중이라 당분간 프로덕션 사용을 권하지 않는다"고 적혀 있습니다. K3.1 Pro는 최소 1달러를 충전해야 열리는 플래그십 모델입니다.

아래는 API 문서의 예제를 그대로 옮긴 것입니다. 필자는 Moonshot API 키가 없어 실행해 보지 않았습니다.

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["MOONSHOT_API_KEY"],
    base_url="https://api.moonshot.ai/v1",
)

completion = client.chat.completions.create(
    model="kimi-k3.1-pro",
    reasoning_effort="max",
    messages=[{"role": "user", "content": "Prove that the square root of 2 is irrational."}],
)

print(completion.choices[0].message.content)
```

**측정 방식이 항목마다 다릅니다.** 모델 카드와 기술 블로그 각주에 따르면 다음과 같습니다.

- Terminal-Bench 4.0, SWE-Marathon, DeepSWE, ProgramBench, PostTrainBench, BenchCAD(도구 사용)에서 **K3.1 Pro는 Claude Code 하네스로 측정**했습니다. 반면 BioMysteryBench, Agents' Last Exam, ExploitGym, xdev-bench-hard에서는 자사 Kimi Code 하네스를 썼고, OSWorld V2.1은 Kimi Agent 하네스입니다.
- 경쟁 모델 수치는 공식 리더보드, 각 회사 시스템 카드·기술 보고서, Artificial Analysis, Vals AI 등에서 가져왔습니다. Terminal-Bench 4.0은 "블로그 게시물이나 공식 리더보드 중 최댓값"을 썼고, Terminal-Bench-Science의 DeepSeek 수치는 자체 측정 9.3 대신 이전 버전의 리더보드 값 15.7을 실었다고 밝힙니다.
- ProgramBench는 원래 점수가 아니라 "95% 이상이면 1, 아니면 0"으로 바꾼 이진 점수입니다. PostTrainBench는 H100 대신 H20 GPU에서, 심사 모델을 DeepSeek-V4.1-Flash-1017로 바꿔 측정했습니다.
- OfficeQA Pro에서는 "일부 외부 모델 궤적에서 정답을 온라인으로 찾아온 사례를 발견해 그 과제를 0점 처리"했다고 적습니다. 공정성을 위한 조치이지만 경쟁 모델 점수를 Moonshot 판단으로 조정한 것이기도 합니다.
- Kimi Code Bench, Business Operation, DECK-Arena, Design Bench, PerceptionBench, Kimi Hallu Bench, xdev-bench-hard는 **내부 벤치마크**입니다.

표에서 읽을 수 있는 경향은 분명합니다. **도구를 쓰는 장기 에이전트 과제(Terminal-Bench, SWE Marathon, BrowseComp, OfficeQA)에서는 상위 상용 모델과 비슷하거나 앞서지만, 도구 없는 고난도 추론(HLE-Diamond 39.4 대 55.1~65.8)과 ProgramBench(31.5 대 50.0~65.0)에서는 차이가 큽니다.** 같은 표에서 [DeepSeek-V4.1-Flash-1017](/tech/2026/10/24/deepseek-v4-1-flash-1017.html)이 DeepSWE 최고점(77.0)을 기록한 것까지 보면, 필자의 판단으로는 오픈 모델이 에이전트 하네스 위의 코딩 과제에서 먼저 상용 모델을 따라잡는 흐름으로 보입니다.

K3.1 Pro가 이전 모델 K3보다 입출력 모두 3분의 1 싸고, 캐시 적중 입력은 일반 입력의 10분의 1입니다. 실시간 응답이 필요 없는 작업은 Batch API로 표준 가격의 60%에 쓸 수 있습니다. 1시간 TTL 캐시 쓰기는 5분 TTL의 두 배이므로, 요청 간격이 5분을 자주 넘는 에이전트 세션에서만 이득입니다. API 고객에게는 데이터 무보존(ZDR, Zero Data Retention) 옵션이 있다고 발표문은 밝힙니다. 가격 페이지는 또 K2 시리즈를 2026-10-31부터 신규 가입자에게 제공하지 않고 12월 말까지 모두 종료할 계획이라고 공지하고 있어, K2를 쓰는 팀은 이전이 필요합니다.

**직접 배포.** 모델 카드는 vLLM, SGLang, TokenSpeed를 권장 추론 엔진으로 듭니다. vLLM 레시피(2026-11-24 확인)의 요점은 다음과 같습니다.

- 기본 구성은 MXFP4 체크포인트를 GPU 8장 텐서 병렬(TP8)로 띄우는 것으로, GB300 트레이 2개, B300 노드 1개, 또는 MI355X 노드 1개입니다. TPU는 v7x 슬라이스(호스트 4개)에서 TP32로, 이 경우 비전 타워는 올리지 않는 텍스트 전용입니다. vLLM 0.35.0 이후 nightly가 필요하다고 표시되어 있습니다.
- 레시피는 이 기본 구성이 "처리량을 튜닝하지 않은 가장 단순한 구성"이라고 하며, B300에서는 KV 캐시가 기본값 1,024개 시퀀스를 담지 못해 `--max-num-seqs 128`을 쓰고, FlashInfer 자동 튜닝을 끈다고(켜면 기동에 약 2시간이 더 걸림) 설명합니다.
- 긴 컨텍스트용 DCP(디코드 컨텍스트 병렬)는 KV 캐시를 8장에 나눠 담아, B300 8장 FP8 KV 기준 담을 수 있는 토큰이 약 260만에서 약 1,850만 개로 약 7배 늘지만, 디코드 단계는 같은 배치에서 7~25% 느려집니다. 텐서+전문가 병렬 구성에서는 34만 토큰 프롬프트 하나의 프리필이 약 10초(일반 TP8은 약 15초)였는데, 이는 출시 전 체크포인트 기준입니다.

아래는 vLLM 레시피의 기본 명령 중 노드 0(첫 번째 트레이) 부분을 옮긴 것입니다. 필자는 해당 장비가 없어 실행해 보지 않았습니다.

```bash

export NCCL_SOCKET_IFNAME=$IFACE_NAME
export VLLM_ENGINE_READY_TIMEOUT_S=3600
vllm serve moonshotai/Kimi-K3.1-Pro \
  --trust-remote-code \

```

## 한계와 논란

- **모든 수치가 자체 보고입니다.** 경쟁 모델 수치를 여러 출처에서 모으고 일부는 자체 판단으로 0점 처리하거나 다른 버전 값으로 대체했습니다. 같은 조건에서 다시 잰 제3자 비교는 2026-11-24 기준 확인하지 못했습니다.
- **하네스가 섞여 있습니다.** K3.1 Pro는 과제에 따라 Claude Code, Kimi Code, Kimi Agent 하네스를 썼고, 경쟁 모델은 각자의 보고치나 다른 하네스 결과입니다. [Harness² 논문](/papers/2026/10/24/harness-squared.html)이 보여 줬듯 하네스만 바꿔도 점수가 크게 달라질 수 있습니다.
- **K3.1의 기술 보고서는 없습니다.** K3는 모델 카드에 전체 보고서 링크가 있지만, K3.1 Pro 모델 카드와 기술 블로그에는 별도 보고서가 없습니다. 후학습 규모("상당히 큰 연산량")와 사이버 데이터 제거 방법은 정량적으로 공개되지 않았습니다.
- **사이버 데이터 제거의 효과는 내부 벤치마크 하나로만 보고됐습니다.** 90.5%에서 81.0%로의 변화는 xdev-bench-hard 결과이고, 미세조정으로 능력이 얼마나 쉽게 회복되는지는 다루지 않았습니다.
- **모달리티 표기가 자료마다 다릅니다.** 모델 카드 표의 모달리티는 "Text, Image"인데, API 퀵스타트에는 영상 파일 업로드 예제 탭이 있습니다. 가중치로 직접 띄울 때 영상 입력이 되는지는 확인하지 못했습니다.

## 인사이트

**왜 지금 중요한가: 오픈웨이트 진영의 "능력 제한" 방식이 갈리고 있습니다.** 한 달 전 Meta는 Muse Spark Open을 내며 "가드레일 없이 단독으로 배포된다고 가정하고 거절을 더 강하게 학습시키는" 방식을 택했고, 그 대가로 무해한 요청 거절률(FORTRESS ORS)이 비교 모델 중 가장 높았습니다. Moonshot은 반대 방향을 택했습니다. 거절을 학습시키는 대신 학습 데이터에서 사이버 관련 내용을 빼서 능력 자체를 낮췄고, 그 수준을 "공개된 지 3개월 이상 된 상용 모델보다 낮게"라는 상대 기준으로 잡았습니다. 필자의 판단으로는 Moonshot 방식이 미세조정에 더 강할 가능성이 있습니다. 거절 성향은 미세조정 몇 번으로 걷어 낼 수 있지만, 학습되지 않은 능력은 다시 가르쳐야 하기 때문입니다. 다만 이것은 추론이고, Moonshot은 이 점을 검증한 수치를 내놓지 않았습니다. 두 회사의 접근이 공개 후 파생 모델에서 어떻게 달라지는지가 오픈웨이트 안전성 논의의 좋은 비교 사례가 될 것으로 보입니다.

**실무에 주는 의미: 라이선스가 "누가 쓰느냐"에 따라 다르게 작동합니다.** 대부분의 스타트업과 기업 내부 도입에는 조건 2, 3이 걸리지 않습니다. 사내 코딩 에이전트나 내부 문서 분석처럼 출력을 제3자에게 제공하지 않으면 조건 4(a)의 내부 사용 예외에 해당하고, 제품 기능에 넣더라도 월 활성 1억 명이나 월 매출 2,000만 달러를 넘지 않으면 표시 의무도 없습니다. 반대로 추론 API를 파는 회사, 특히 연 매출 2,000만 달러를 넘는 클라우드·호스팅 사업자는 사실상 Moonshot과 계약하거나 "인증 파트너"가 되어야 합니다. 이 구조는 K2 시절에 비해 Moonshot이 자사 모델의 상업 유통 경로를 직접 관리하겠다는 신호로 읽힙니다. 비용 면에서는, 1.56TB 가중치를 GPU 8장 이상에 올려야 하는 모델을 직접 운영하기보다 100만 토큰당 입력 2달러, 캐시 적중 0.2달러인 API를 쓰는 편이 대부분의 팀에 현실적입니다. [프롬프트 캐싱 글](/tech/2026/10/24/prompt-caching.html)에서 정리한 원칙(바뀌지 않는 접두사를 앞에 두기)이 여기서도 그대로 통하며, 에이전트 세션처럼 요청 간격이 긴 경우 1시간 TTL을 쓸지 계산해 볼 만합니다.

**블로그의 기존 글과의 연결: 기본값이 `max`라는 점.** K3.1 Pro API는 추론을 끌 수 없고 기본 강도가 `max`입니다. [추론 effort의 경제학 논문 글](/papers/2026/11/20/reasoning-effort-economics.html)은 Kimi K3를 포함한 여러 모델에서 높은 effort가 낮은 effort의 성공을 보장하지 않으며, 실패한 과제에서만 effort를 올리는 사다리 전략이 비용을 줄였다고 보고했습니다. 그 글의 Terminal-Bench 2.1 표에서 Kimi K3는 사다리 전략으로 API 비용이 30.5% 줄고 성공률은 73.0%에서 84.3%로 올랐습니다. 같은 계열인 K3.1 Pro에도 그대로 적용된다고 단정할 수는 없지만, 기본값을 그대로 두고 쓰기보다 `low`나 `high`에서 시작해 실패 시 올리는 설계를 먼저 시험해 볼 만하다고 봅니다.

**한계와 반론: "상용 모델에 근접"의 범위.** 기술 블로그는 "코딩, 에이전트, 지식 벤치마크 전반에서 가장 강한 상용 모델과 같거나 근접한다"고 말합니다. 그러나 같은 모델 카드 표에서 도구 없는 HLE-Diamond는 39.4로 GPT-6 Astra(65.8), Claude Opus 5.5(60.9)와 20점 이상 차이가 나고, ProgramBench도 절반 수준입니다. 필자의 해석으로는 K3.1 Pro의 강점은 "하네스 위에서 오래 도구를 다루는 일"에 집중되어 있고, 하네스 없이 모델 혼자 푸는 고난도 추론에서는 아직 격차가 큽니다. 에이전트 하네스가 있는 코딩·문서 업무에 쓰려는 팀에게는 좋은 후보이지만, 단발성 고난도 추론이 중요한 용도라면 자체 평가를 먼저 해 보는 편이 안전합니다.

**앞으로 지켜볼 점.** (1) Artificial Analysis나 공식 리더보드처럼 같은 조건에서 다시 잰 제3자 수치가 모델 카드 수치와 얼마나 맞는지. (2) "인증 추론 파트너" 목록과 기준이 공개되는지, 그리고 대형 클라우드가 이 모델을 실제로 올리는지. (3) 사이버 데이터를 제거한 공개판에 미세조정으로 능력을 되돌리는 파생 모델이 나오는지, 나온다면 Moonshot의 "점진적 공개" 원칙이 다음 버전에서 어떻게 바뀌는지.
