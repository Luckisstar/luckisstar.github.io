# [기술 소개] 프롬프트 캐싱: 긴 프롬프트의 비용과 지연을 줄이는 법

- **주요 출처:** [Anthropic 프롬프트 캐싱 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) · [OpenAI 프롬프트 캐싱 문서](https://platform.openai.com/docs/guides/prompt-caching) · [Gemini 컨텍스트 캐싱 문서(generateContent)](https://ai.google.dev/gemini-api/docs/generate-content/caching) · [Gemini 가격 페이지](https://ai.google.dev/gemini-api/docs/pricing)
- **한눈에 (2026-10-24 기준):** 세 공급자 모두 "프롬프트 앞부분(접두사)이 완전히 같을 때만" 캐시를 재사용합니다. 캐시 읽기 단가는 대부분 모델에서 일반 입력의 10%이고, 일부 최신 모델은 5% 이하입니다. 대신 Anthropic과 OpenAI(GPT-5.6 이후)는 캐시 쓰기에 1.25배 이상을 받고, Gemini 명시적 캐시는 보관 시간에 비례하는 저장 비용을 받습니다.
- **주의:** 가격, 최소 토큰, 지원 모델은 자주 바뀝니다. 이 글의 수치는 모두 2026-10-24에 각 공식 문서에서 확인한 값입니다(Gemini 캐싱 문서 최종 수정 2026-10-23, 가격 페이지 2026-10-22). 코드 예제는 공식 문서 예제를 옮긴 것이며 필자가 직접 실행하지는 않았습니다.

## 한 줄 요약

**프롬프트 캐싱은 요청마다 반복되는 긴 앞부분(시스템 지시, 도구 정의, 문서, 대화 기록)의 계산 결과를 서버가 잠시 저장해 두었다가 재사용하는 기능으로, 핵심은 "바뀌지 않는 것을 앞에, 바뀌는 것을 뒤에" 두는 프롬프트 배치입니다.**

## 배경

LLM API 비용의 상당 부분은 입력 토큰에서 나옵니다. 특히 에이전트처럼 한 작업 안에서 모델을 여러 번 부르는 경우, 매 요청에 같은 시스템 프롬프트와 도구 정의, 점점 길어지는 대화 기록이 다시 실립니다. 10턴짜리 대화라면 첫 턴의 내용은 10번 처리됩니다.

OpenAI 문서는 이 반복을 줄이는 원리를 KV 캐시로 설명합니다. 모델은 입력 토큰을 처리하면서 키-값(KV, key-value) 상태라는 중간 계산 결과를 만들고, 이 상태로 앞 토큰을 참조하며 다음 토큰을 생성합니다. 프롬프트 캐싱은 재사용 가능한 접두사(prefix)의 KV 상태를 보존해 두었다가, 다음 요청의 접두사가 같으면 그 부분의 계산을 건너뜁니다. 문서는 **캐시가 토큰 자체가 아니라 KV 텐서를 저장한다**고 명시합니다.

## 핵심 내용

### 1. 원리: 접두사가 100% 같아야 한다

세 공급자의 설명은 같은 원리로 모입니다.

- Anthropic: 캐시 적중에는 캐시 지정 블록까지의 텍스트와 이미지가 **100% 동일**해야 합니다. 캐시 접두사는 `tools` → `system` → `messages` 순서로 만들어지고, 앞 단계가 바뀌면 그 뒤가 모두 무효가 됩니다.
- OpenAI: 캐시 재사용에는 **렌더링된 접두사 전체**가 일치해야 하며, OpenAI가 넣는 숨은 지시, 개발자 메시지, 도구 정의, 대화 기록이 모두 포함됩니다.
- Gemini: 캐시된 콘텐츠는 프롬프트의 접두사이며, 모델은 캐시된 토큰과 일반 입력 토큰을 구분하지 않습니다.

그래서 **중간의 한 글자만 바뀌어도 그 뒤는 전부 다시 계산**됩니다. 시스템 프롬프트 첫 줄에 현재 시각을 넣으면 캐시는 사실상 동작하지 않습니다. 또 캐싱은 출력에 영향을 주지 않습니다. Anthropic은 캐싱 여부와 관계없이 응답이 같다고, OpenAI는 캐싱이 출력 생성 방식을 바꾸지 않는다고 설명합니다.

### 2. 자동인가, 명시적인가: 캐시 지점(breakpoint)을 누가 정하나

| 공급자 | 자동(암묵적) | 명시적 |
|---|---|---|
| Anthropic | 요청 최상위에 `cache_control` 하나를 두면 마지막 캐시 가능 블록에 지점을 자동 배치하고, 대화가 길어지면 지점도 따라 이동 | 개별 블록에 `cache_control`을 붙여 최대 4개 지점 지정 |
| OpenAI | 지원 모델에서 기본 활성화. GPT-5.6 이후는 마지막 적격 메시지 끝에 자동 지점 | GPT-5.6 이후만. `prompt_cache_options.mode: "explicit"`과 블록별 `prompt_cache_breakpoint`. 요청당 캐시 쓰기 최대 4개 |
| Gemini | 2.5 이후 모든 모델에서 기본 활성화. 설정 불필요하지만 **절감 보장 없음** | `cachedContents` API로 캐시 객체를 직접 만들고 이름으로 참조(v1beta, 베타). Gemini 3·2.5만 지원, Gemini 4 Argon 이후와 Interactions API는 미지원 |

명시적 방식의 Anthropic 공식 예제는 이렇습니다. 긴 계약서를 시스템 프롬프트에 넣고 그 블록 끝에 캐시 지점을 둡니다.

```python
client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": "You are an AI assistant tasked with analyzing legal documents.",
        },
        {
            "type": "text",
            "text": "Here is the full text of a complex legal agreement: [Insert full text of a 50-page legal agreement here]",
            "cache_control": {"type": "ephemeral"},
        },
    ],
    messages=[
        {
            "role": "user",
            "content": "What are the key terms and conditions in this agreement?",
        }
    ],
)
print(response.usage.model_dump_json())
```

OpenAI의 GPT-5.6 이후 명시적 모드 예제는 고정 지시 뒤에 지점을 두고, 바뀌는 질문은 지점 뒤에 둡니다(Responses API 요청 본문, 공식 문서에서 발췌).

```json
{
  "model": "gpt-6.1-sol",
  "prompt_cache_options": { "mode": "explicit" },
  "input": [
    {
      "role": "developer",
      "content": [
        {
          "type": "input_text",
          "text": "Stable instructions and shared reference material...",
          "prompt_cache_breakpoint": { "mode": "explicit" }
        }
      ]
    },
    { "role": "user", "content": "The user's current question..." }
  ]
}
```

Gemini의 명시적 캐시는 성격이 다릅니다. 요청 안에 표시를 하는 대신, 캐시 객체를 먼저 만들고 TTL을 정한 뒤 이름으로 참조합니다(공식 Python 예제에서 발췌).

```python
cache = client.caches.create(
    model=model_name,
    config=types.CreateCachedContentConfig(
      system_instruction=system_instruction,
      contents=[document],
    )
)

response = client.models.generate_content(
  model=model_name,
  contents="Please summarize this transcript",
  config=types.GenerateContentConfig(
    cached_content=cache.name
  ))
```

### 3. 지점이 어떻게 찾아지나: "뒤로 훑기"는 과거에 쓴 것만 찾는다

명시적 지점을 쓸 때 가장 많이 오해하는 부분입니다. Anthropic 문서는 세 원칙으로 설명합니다.

1. **캐시 쓰기는 지점에서만 일어납니다.** 지점까지의 접두사 해시 하나가 저장되고, 그 앞 위치에는 아무것도 저장되지 않습니다.
2. **캐시 읽기는 이전 요청이 써 둔 항목을 뒤로 훑으며 찾습니다.** 지점에서 일치하는 항목이 없으면 한 블록씩 뒤로 가며 확인합니다. 찾는 것은 "안정적인 내용"이 아니라 "과거의 쓰기"입니다.
3. **뒤로 훑는 범위는 20블록입니다.** 한 턴에 20블록 이상이 추가되면 이전 항목을 놓치므로, 그 위치에 지점을 하나 더 두라고 권합니다.

OpenAI도 GPT-5.6 이후 모델에서 비슷하게 동작합니다. 문서의 "주의할 점"에 따르면 정적 개발자 메시지 뒤에 동적 사용자 메시지가 오는 요청을 암묵적 모드로만 보내면, 캐시는 동적 내용 끝까지 쓰이고 정적 부분만의 지점은 생기지 않아 다음 요청에서 재사용되지 않습니다. 해법은 양쪽 문서 모두 같습니다. **바뀌지 않는 마지막 블록 끝에 명시적 지점을 두는 것**입니다.

### 4. TTL과 비용: 쓰기에 돈을 내고 읽기로 돌려받는다

| 항목 | Anthropic | OpenAI (GPT-5.6 이후) | OpenAI (이전 모델) | Gemini |
|---|---|---|---|---|
| 기본 수명 | 5분, 사용할 때마다 무료 갱신 | 최소 30분 | `in_memory`: 비활성 5~10분(최대 1시간), `24h`: 최대 24시간 | 암묵적: 명시 없음. 명시적: 기본 1시간, 상한·하한 없음 |
| 긴 수명 옵션 | 1시간 | 12시간(Responses API) | 24시간 | 명시적 캐시의 TTL을 원하는 만큼 |
| 캐시 쓰기 | 5분: 1.25배, 1시간: 2배 | 30분: 1.25배, 12시간: 2.5배 | 추가 요금 없음 | 암묵적: 추가 요금 명시 없음. 명시적: 시간당 저장 요금 |
| 캐시 읽기 | 기본 0.1배. Opus 5.5·Sonnet 5.5는 0.05배, Fable 5.1·Mythos 5.1은 0.025배 | 0.1배, GPT-6.1 Sol은 0.05배 | 모델별 캐시 입력 단가 | 모델별 단가 (예: 아래) |
| 최소 길이 | 512~4,096토큰(모델별, 최신 모델은 512) | 보이는 입력 1,024토큰 | 요청 설정에 따라 다름 | 2,048(2.5 Flash·Pro) 또는 4,096(3.x, 4 Argon) |
| 격리 범위 | 조직, 그리고 Claude API에서는 워크스페이스 | 조직, 처리 지역 | 조직, 처리 지역 | (문서에 명시 없음) |

배수는 일반 입력 단가 대비입니다. Gemini는 가격 페이지 기준으로 Gemini 3.8 Flash가 입력 100만 토큰당 $0.75, 캐시 $0.075(10%), 저장 100만 토큰·시간당 $0.50이고(2026-12-31까지 가격), Gemini 4 Argon이 입력 $2.00, 캐시 $0.10(5%)이며 암묵적 캐싱만 지원합니다(2026-11-30까지 가격). 두 모델 모두 이후 날짜부터 가격이 오른다고 공지돼 있습니다.

쓰기 할증이 있으니 **몇 번 재사용해야 이득인지** 계산해 둘 만합니다. 같은 접두사를 n번 보낼 때, 캐시 없이는 n, 캐시를 쓰면 "쓰기 배수 + 0.1 × (n − 1)"입니다.

| 쓰기 배수 (읽기 0.1배 가정) | 2번 보낼 때 | 이득이 나는 최소 횟수 |
|---|---|---|
| 1.25배 (Anthropic 5분, OpenAI 30분) | 1.35 대 2 | 2번 |
| 2배 (Anthropic 1시간) | 2.1 대 2 | 3번 |
| 2.5배 (OpenAI 12시간) | 2.6 대 2 | 3번 |

1.25배 기준 수치는 OpenAI 문서의 예시(한 번 쓰고 한 번 읽으면 1.35배, 쓰기 1번과 읽기 9번이면 10배 대신 2.15배)와도 일치합니다. 긴 수명은 "한 번 더 맞히면 본전" 정도의 차이라, **요청 간격이 짧은 서비스라면 짧은 수명이 대개 유리**합니다. Anthropic 문서도 5분보다 자주 쓰는 프롬프트는 무료 갱신되는 5분 캐시를 계속 쓰라고 권합니다.

### 5. 적중률을 높이는 프롬프트 배치

세 문서가 공통으로 권하는 순서를 하나로 합치면 다음과 같습니다.

```text
[가장 안 바뀌는 것]  도구 정의  →  시스템 지시  →  고정 참고 자료·예시
                    →  (지점)  →  대화 기록(뒤에 덧붙이기만)  →  (지점)
[가장 자주 바뀌는 것] 현재 시각·사용자별 정보·이번 질문
```

- **고정 부분을 앞에.** OpenAI는 타임스탬프나 사용자별 내용을 앞이 아니라 끝에, 혹은 이후 대화 메시지로 옮기라고 권합니다. Gemini도 "크고 공통적인 내용을 프롬프트 앞에" 두라고 합니다.
- **대화는 덧붙이기만.** 이전 턴을 고쳐 쓰거나 요약하면 접두사가 바뀌어 캐시가 리셋됩니다(OpenAI). 컨텍스트 압축(compaction)은 첫 요청의 재사용을 줄일 수 있지만, 입력 자체가 줄어 총비용은 오히려 낮아질 수 있으니 비교해 보라고 문서는 덧붙입니다.
- **도구 목록은 고정하고, 쓸 수 있는 도구만 바꾸기.** OpenAI는 도구를 빼는 대신 `tool_choice: "none"`이나 `allowed_tools`로 호출 가능한 도구만 제한하라고 권합니다. Anthropic에서는 도구 정의를 바꾸면 전체 캐시가 무효가 됩니다.
- **최소 길이 함정 피하기.** 공유 접두사가 최소 길이에 조금 못 미치면, 유용한 고정 지시나 예시를 더해 기준을 넘기는 편이 쌀 수 있습니다. OpenAI 문서의 계산으로는 최소 1,024토큰, 읽기 0.1배, 쓰기 1.25배에서 요청 10번이면 원래 접두사가 221토큰 이상일 때 1,024토큰으로 늘리는 쪽이 이득입니다.
- **미리 데워 두기(pre-warming).** 첫 사용자 요청의 지연을 줄이려면 앱 시작 시 캐시를 먼저 씁니다. Anthropic은 `max_tokens: 0` 요청으로 출력 없이 캐시만 쓰고, OpenAI는 GPT-5.6 이후 `prompt_cache_options.prewarm: true`를 씁니다. 둘 다 쓰기 요금은 냅니다.

### 6. 적중했는지 확인하기

| 공급자 | 응답의 사용량 필드 |
|---|---|
| Anthropic | `cache_creation_input_tokens`(이번에 쓴 토큰), `cache_read_input_tokens`(읽은 토큰), `input_tokens`(마지막 지점 이후 토큰) |
| OpenAI | `usage.input_tokens_details.cached_tokens`, `cache_write_tokens`, 수명별 `ttl_30m_tokens`·`ttl_12h_tokens` |
| Gemini | `usage_metadata`의 캐시 토큰 수 (Interactions API는 `usage.total_cached_tokens`) |

Anthropic의 `input_tokens`는 **전체 입력이 아니라 마지막 지점 뒤의 토큰만** 셉니다. 전체는 세 필드의 합입니다. OpenAI는 "캐시된 토큰 합 ÷ 전체 입력 토큰 합"을 사용자, 워크스페이스, 날짜별로 집계해 적중률을 추적하라고 권하고, 2026년 8월부터는 대시보드도 제공합니다.

## 실무에서 흔한 실수

1. **변하는 블록에 지점을 둔다.** Anthropic 문서가 "흔한 실수"로 직접 드는 사례입니다. 정적 블록 1~5 뒤에 타임스탬프와 사용자 메시지가 든 블록 6이 있을 때 블록 6에 `cache_control`을 두면, 매 요청 쓰기 요금만 내고 읽기는 한 번도 일어나지 않습니다. 지점을 블록 5로 옮겨야 합니다. 자동 캐싱도 마지막 블록에 지점을 두므로 같은 문제가 생깁니다.
2. **최소 길이 미달을 모른다.** Anthropic은 최소 길이보다 짧으면 `cache_control`이 있어도 **오류 없이 캐싱하지 않습니다.** 쓰기와 읽기 필드가 모두 0이면 이 경우를 의심하라고 문서는 안내합니다. 모델을 바꾸면 최소 길이도 바뀝니다(OpenAI 문서도 같은 경고).
3. **동시에 몰아서 보낸다.** Anthropic에서 캐시 항목은 첫 응답이 시작된 뒤에야 쓸 수 있습니다. 같은 접두사로 병렬 요청 100개를 동시에 보내면 대부분 캐시를 못 씁니다. 첫 응답을 기다린 뒤 나머지를 보내라고 문서는 권합니다.
4. **설정값을 요청마다 바꾼다.** Anthropic은 `tool_choice`, 이미지 유무, 사고(thinking) 설정, `output_config.effort` 변경이 메시지 캐시를 무효화한다고 표로 정리합니다. OpenAI도 `tools`, `parallel_tool_calls`, 구조화 출력 형식, `reasoning.effort`가 캐시 접두사에 영향을 준다고 적습니다.
5. **JSON 키 순서가 흔들린다.** Anthropic 문제 해결 항목에 따르면 Swift, Go 등 일부 언어는 JSON 변환 시 키 순서를 무작위로 바꿔 캐시를 깹니다. 도구 정의나 `tool_use` 블록을 직렬화할 때 키 순서를 고정해야 합니다.
6. **암묵적 캐싱을 보장으로 착각한다.** Gemini 문서는 암묵적 캐싱에 "절감 보장이 없다"고 명시하고, OpenAI도 "공유 접두사가 항상 캐시된 접두사는 아니다"를 별도 주의 사항으로 둡니다. OpenAI는 캐시가 개별 머신에 있어 분당 약 15건을 넘는 트래픽은 다른 머신으로 넘칠 수 있다고 설명합니다.
7. **캐시가 속도 제한도 풀어 준다고 가정한다.** 공급자마다 다릅니다. OpenAI는 캐시된 입력 토큰도 분당 토큰 한도에 포함된다고 하고, Gemini도 토큰 한도에 캐시 토큰이 포함된다고 합니다. 반면 Anthropic 문서는 1시간 캐시를 쓰는 이유 중 하나로 "캐시 적중은 속도 제한에서 차감되지 않는다"를 듭니다.

## 한계와 논란

- **가격 구조가 공급자마다, 모델마다 다릅니다.** 같은 "캐시 할인"이라도 쓰기 할증이 있는 곳(Anthropic, OpenAI GPT-5.6 이후), 없는 곳(OpenAI 이전 모델), 저장 시간 요금이 있는 곳(Gemini 명시적)으로 나뉩니다. 그리고 2026년 10월 기준으로도 OpenAI는 GPT-5.6을 기점으로, Gemini는 Gemini 4 Argon을 기점으로 캐싱 방식 자체가 바뀌었습니다. 한 공급자에서 최적화한 프롬프트 구조가 다른 공급자나 다음 모델에서 같은 효과를 낸다는 보장이 없습니다.
- **"최대 90%", "최대 95%" 같은 문구는 상한입니다.** 실제 절감은 적중률에 달려 있고, OpenAI 문서가 예로 든 배포 사례의 적중률도 단일 턴 판정기 약 70%, 다중 턴 에이전트 90% 이상으로, "가능한 결과의 예시"라고 단서를 달았습니다.
- **암묵적 캐싱은 관찰하기 어렵습니다.** 언제 적중할지 공급자가 정하고, 라우팅이나 부하에 따라 결과가 달라집니다. 비용 예측이 중요한 서비스라면 명시적 방식이나 적중률 모니터링이 사실상 필수입니다.
- **캐시도 데이터입니다.** Anthropic은 KV 캐시 표현과 해시를 메모리에만 두고 원문은 저장하지 않으며 조직·워크스페이스 단위로 격리한다고 밝힙니다. OpenAI는 확장 보관 시 암호화된 KV 텐서를 GPU 로컬 저장소에 둘 수 있다고 설명합니다. 또 OpenAI 문서는 한 애플리케이션 안의 사용자끼리 "후보 프롬프트를 보내 캐시 적중 여부로 다른 사용자가 같은 내용을 보냈는지 알아내는" 캐시 적중 탐지(cache-hit probing)를 언급하며, 사용자별로 `prompt_cache_key`를 나누라고 권합니다. 여러 고객의 데이터를 한 계정으로 처리하는 서비스라면 따져 볼 지점입니다.

## 인사이트

**왜 지금 중요한가: 에이전트 시대의 기본 비용 구조.** 프롬프트 캐싱은 2024년에 "긴 문서 질의응답 비용을 줄이는 옵션"으로 시작했지만, 2026년 문서들은 에이전트 루프를 중심에 두고 다시 쓰여 있습니다. OpenAI 문서의 예시는 "도구 결과마다 지점을 두는 다중 턴 에이전트"이고, Gemini 문서는 Gemini 4의 에이전트 루프에서 새 요청이 2,050토큰 이상 늘어날 때만 이전 요청 전체를 캐시한다는 별도 규칙을 둡니다. 에이전트는 매 턴 같은 접두사에 도구 결과를 덧붙이는 구조라, 캐시를 잘 쓰면 대화가 길어져도 매 턴 새로 처리하는 양은 "새로 붙은 부분"으로 줄어듭니다. 필자의 판단으로는, 이제 캐싱은 선택적 최적화가 아니라 **프롬프트와 하네스를 설계할 때 처음부터 고려해야 하는 제약 조건**에 가깝습니다. 프롬프트의 "어느 부분이 얼마나 자주 바뀌는가"가 비용을 결정하기 때문입니다.

**실무에 주는 의미: 세 가지 습관.** 첫째, **프롬프트를 바뀌는 빈도 순으로 층을 나눠** 관리합니다. 도구 정의와 시스템 지시를 템플릿으로 고정하고, 날짜나 사용자 이름처럼 매번 바뀌는 값은 맨 끝 메시지로 보냅니다. "오늘 날짜는 …"을 시스템 프롬프트 첫 줄에 넣는 습관 하나가 캐시 전체를 무력화할 수 있습니다. 둘째, **캐시 지표를 비용 지표와 함께 봅니다.** 적중률만 높아도 쓰기가 과하면 손해일 수 있으므로, 쓰기 토큰과 읽기 토큰을 따로 기록해야 합니다. 셋째, **모델을 바꿀 때 캐시 설정도 다시 확인합니다.** 최소 길이(Anthropic 모델별 512~4,096토큰), 기본 동작(OpenAI GPT-5.6 이전과 이후), 명시적 캐시 지원 여부(Gemini 4 Argon 이후 미지원)가 모두 모델 단위로 달라집니다.

**블로그의 기존 글과의 연결.** [Agent Skills 소개](/tech/2026/10/24/agent-skills-aaif.html)에서 본 점진적 공개(progressive disclosure)는 컨텍스트에 넣는 양을 줄이는 접근이고, 프롬프트 캐싱은 넣은 것을 다시 계산하지 않는 접근입니다. 두 방식은 서로 보완적입니다. 스킬 카탈로그처럼 세션 시작 때 들어가는 고정 부분은 캐시의 앞쪽에 두기 좋은 대상이고, 필요할 때 불러오는 스킬 본문은 대화 뒤쪽에 덧붙는 형태라 기존 접두사를 깨지 않습니다. 도구 정의가 캐시 접두사의 맨 앞이라는 점은 [함수 호출과 구조화된 출력](/tech/2026/10/24/function-calling.html)에서 다룬 도구 설계와도 이어집니다. 도구 목록을 자주 바꾸는 설계는 기능 면에서는 유연하지만 캐시 면에서는 가장 비쌉니다. OpenAI와 Anthropic이 모두 도구를 나중에 불러오는 도구 검색(tool search) 기능을 두고, 불러온 도구를 맥락의 끝에 덧붙여 앞부분을 보존한다고 설명하는 것도 같은 이유로 보입니다.

**한계와 반론.** 캐싱이 강력할수록 "일단 다 넣고 캐시하자"는 유혹이 생깁니다. Anthropic 문서는 캐싱 덕분에 예시를 20개 이상 넣을 수 있다고까지 권하지만, 캐시 읽기도 공짜는 아니고(0.025~0.1배), 맥락이 길어질수록 모델이 중요한 정보를 놓칠 위험은 캐싱과 무관하게 남습니다. 또 캐시를 위해 프롬프트 구조를 고정하면, 사용자별 맞춤이나 동적인 지시를 앞에 두기 어려워지는 설계상의 비용도 생깁니다. 비용 절감과 품질 사이의 선택이라는 점을 잊지 않는 편이 좋겠습니다.

**앞으로 지켜볼 점.** (1) 공급자들이 명시적 제어 쪽으로 수렴하는지. OpenAI는 GPT-5.6에서 명시적 지점을 도입했고, Gemini는 반대로 Gemini 4부터 명시적 캐시를 지원하지 않습니다. 방향이 갈리는 이 상태가 어떻게 정리되는지가 멀티 공급자 하네스 설계에 영향을 줍니다. (2) 캐시 진단 도구의 발전. Anthropic은 연속된 두 요청을 비교해 접두사가 어디서(모델, 시스템 프롬프트, 도구, 대화 기록) 갈라졌는지 알려 주는 진단 기능을, OpenAI는 캐시 미스를 진단하는 도구와 대시보드를 문서에 소개하고 있습니다. 이것이 표준적인 관측 지표(예: 공통 형식의 캐시 사용량 필드)로 이어지는지. (3) 긴 수명 캐시의 가격. 12시간·24시간 캐시가 흔해지면 "사내 문서 전체를 캐시해 두고 하루 종일 쓰는" 패턴이 RAG(검색 증강 생성)의 일부를 대체할 수 있는지 지켜볼 만합니다.
