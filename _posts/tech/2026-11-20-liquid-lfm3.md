# [기술 소개] Liquid AI LFM3: 1.7B 뼈대 하나에서 갈라낸 텍스트·비전·음성·옴니 온디바이스 모델

- **발표:** Liquid AI, 2026년 10월 27일
- **원문:** [공식 발표](https://www.liquid.ai/blog/lfm3) · [Hugging Face 블로그](https://huggingface.co/blog/LiquidAI/lfm3) · [LFM3-1.7B 모델 카드](https://huggingface.co/LiquidAI/LFM3-1.7B) · [LICENSE 원문](https://huggingface.co/LiquidAI/LFM3-1.7B/blob/main/LICENSE) · [라이선스 안내 페이지](https://www.liquid.ai/lfm-license)
- **한눈에 (2026-11-20 기준):** 1.73B 파라미터 베이스 모델 하나(LFM3-1.7B-Base)에서 텍스트, 비전, 오디오, 옴니 모델과 판단(decision) 모델 2개까지 모두 6개가 갈라져 나온 2B급 제품군입니다. 텍스트 모델은 24개 층 중 13개가 합성곱이고 컨텍스트는 256K 토큰이며, 4비트 GGUF(llama.cpp용 모델 파일 형식) 파일은 약 1.05~1.10GB입니다. Hugging Face API 기준 LFM3-1.7B는 좋아요 2,028개, 다운로드 약 12만 회입니다.
- **도입 전 확인할 사항:**
  - **오픈소스 라이선스가 아닙니다.** 모든 LFM3 모델은 LFM Open License v1.0(Hugging Face 메타데이터로는 `license: other`, `lfm1.0`)으로 배포됩니다. Apache 2.0 문구를 바탕으로 하지만 연 매출 1,000만 달러 이상인 법인의 상업적 사용은 허용 범위 밖이며, 그 경우 Liquid AI와 별도 상용 계약이 필요합니다(아래 "라이선스" 절에서 원문 인용).
  - **벤치마크는 모두 Liquid AI 자체 발표입니다.** 경쟁 모델 수치도 Liquid AI가 같은 설정으로 직접 돌린 값이고, 제3자 재현 결과는 이 글을 쓰는 시점에 확인하지 못했습니다.
  - **실행 환경 조건이 있습니다.** Transformers에서는 저장소의 사용자 정의 코드를 실행하는 `trust_remote_code=True`가 필요하고, llama.cpp는 b11960(v0.8.0) 이상이어야 합니다.
  - **작은 모델의 한계를 모델 카드가 직접 밝힙니다.** LFM3-1.7B는 에이전트형 코딩과 복잡한 다단계 추론에는 권장되지 않으며, 지식이 필요한 작업에는 검색을 붙이라고 안내합니다.

## 한 줄 요약

**Liquid AI가 합성곱, 슬라이딩 윈도 어텐션, 전역 어텐션을 섞은 1.7B 베이스 하나에서 텍스트·비전·오디오·옴니·판단 모델을 갈라낸 온디바이스 제품군 LFM3를 오픈웨이트로 공개했습니다.** 자체 측정으로는 9B급 모델과 비슷한 에이전트 성능을 내면서 휴대폰에서 돌아간다고 주장하지만, 라이선스에 매출 기준 상업 사용 제한이 있고 수치는 아직 회사 발표뿐이라는 점을 함께 봐야 합니다.

## 배경

Liquid AI는 온디바이스 실행을 목표로 한 LFM(Liquid Foundation Model) 계열을 내 온 회사입니다. 이전 세대 LFM2는 짧은 합성곱과 어텐션을 섞은 하이브리드 구조였고, 이 구조는 실제 기기에서 속도를 재면서 구조를 탐색하는 "하드웨어 인 더 루프(hardware-in-the-loop) 아키텍처 탐색"으로 설계됐다고 발표문은 설명합니다(관련 자료: [LFM2 Technical Report, arXiv:2511.23404](https://arxiv.org/abs/2511.23404)).

발표문에 따르면 LFM3는 같은 탐색 방법을 "에이전트 용도"에 맞춰 다시 돌린 결과입니다. 에이전트는 도구 정의와 실행 결과가 계속 쌓여 컨텍스트가 길어지므로, 파라미터당 성능과 함께 긴 컨텍스트에서의 추론 속도가 중요하다는 것이 Liquid AI의 문제 설정입니다. 탐색에 넣은 하드웨어도 LFM2 때의 휴대폰 1종, 노트북 1종의 CPU에서 14가지 기기·백엔드 조합으로 늘렸다고 합니다. 발표문이 든 예는 Samsung Galaxy S26 Ultra, OnePlus 15, Raspberry Pi 5, Apple M4 Max, AMD Ryzen AI, Arm·x86 클라우드 CPU, GPU, Qualcomm Hexagon NPU입니다.

비교 기준이 되는 직전 모델은 LFM2.5-2.6B(텍스트), LFM2.5-VL-3B(비전), LFM2.5-Audio-1.5B(오디오), d1-3B(판단)입니다. Liquid AI는 LFM3-1.7B가 LFM2.5-2.6B보다 파라미터가 35% 적으면서 성능은 더 높다고 발표했습니다.

## 핵심 내용

### 1. 구조: 합성곱 13층, 슬라이딩 윈도 5층, 전역 어텐션 6층

LFM3-1.7B의 구조는 모델 카드와 저장소의 [config.json](https://huggingface.co/LiquidAI/LFM3-1.7B/blob/main/config.json)에 공개돼 있습니다.

| 항목 | 값 |
|---|---|
| 파라미터 | 1.73B (Hugging Face API 기준 1,728,801,536개, BF16) |
| 층 구성 | 24층: 게이트 단기 합성곱 13, 슬라이딩 윈도 어텐션 5, 전역 어텐션 6 |
| 합성곱 | 커널 크기 7 (LFM2는 3) |
| 윈도 | 슬라이딩 윈도 256 토큰 |
| 차원 | 은닉 2048, 어텐션 헤드 16개, KV 헤드 4개, 헤드 차원 128 |
| 컨텍스트 | 256K 토큰 (입력과 출력 합계, config 기준 262,144) |
| 어휘 | 128,000 토큰 |
| 언어 | 영어, 한국어, 일본어, 중국어 등 16개 |

발표문이 "삼중 하이브리드(tri-hybrid)"라고 부르는 구조입니다. 세 가지 연산은 역할이 다릅니다. 게이트 단기 합성곱(gated short convolution)은 바로 앞 몇 토큰만 보는 값싼 연산이고, SWA(슬라이딩 윈도 어텐션, Sliding-Window Attention)는 최근 256 토큰 안에서만 어텐션을 하며, 전역 어텐션은 일반 트랜스포머처럼 컨텍스트 전체를 봅니다. config의 `layer_types`를 보면 합성곱 층 사이사이에 전역 어텐션과 슬라이딩 어텐션이 번갈아 끼어 있습니다. 발표문은 합성곱 일부를 다른 블록으로 바꿔 보는 실험에서 SWA가 품질과 속도의 균형이 가장 좋았다고 설명합니다.

그 밖에 발표문이 밝힌 변경은 세 가지입니다.

- **헤드별 게이트 어텐션:** 시그모이드 게이트가 각 어텐션 헤드의 출력을 조절해, 보탤 것이 없는 헤드는 스스로 꺼질 수 있습니다. 발표문은 이것이 양자화를 어렵게 하는 활성값 이상치를 억제하는 데 도움이 될 수 있다고 적습니다.
- **부분 RoPE:** RoPE(회전 위치 임베딩, Rotary Position Embedding)를 전역 어텐션 층에서는 각 헤드의 고주파 절반에만 적용합니다. 나머지 절반은 거리와 무관하게 내용만으로 매칭됩니다. SWA 층은 전체 RoPE를 유지합니다.
- **샌드위치 정규화:** 각 블록의 입력과 출력을 모두 정규화합니다.

### 2. 긴 컨텍스트가 싼 이유: 전체 길이 KV 캐시를 갖는 층이 6개뿐

이 구조의 실질적인 이득은 KV 캐시(이전 토큰의 키·값 벡터를 저장해 두는 메모리)에서 나옵니다. 발표문은 128K 토큰 컨텍스트를 가득 채웠을 때 LFM3-1.7B의 KV 캐시가 1.6GB이고, Qwen3.5-4B는 4.3GB, MiniCPM5-2B는 5.6GB라고 밝혔습니다(자체 발표).

이 숫자는 공개된 config로 검산할 수 있습니다. 블로그의 [양자화 해설](/tech/2026/10/24/llm-quantization.html)에서 쓴 식 `2 × 층 수 × KV 헤드 수 × 헤드 차원 × 바이트 수`에, 컨텍스트 길이에 비례해 KV 캐시가 커지는 층을 전역 어텐션 6개로만 잡아 넣으면 다음과 같습니다(필자의 계산이며 FP16 캐시를 가정했습니다).

```text
토큰당: 2 × 6층 × KV 헤드 4 × 헤드 차원 128 × 2바이트 = 12,288바이트 (12KiB)
128K(131,072 토큰): 12,288 × 131,072 ≈ 1.61GB
256K(262,144 토큰): 12,288 × 262,144 ≈ 3.22GB
```

128K에서 1.61GB로 발표문의 1.6GB와 맞습니다. SWA 5개 층은 최근 256 토큰만 저장하면 되므로 같은 식으로 약 2.6MB에 그치고, 합성곱 층은 어텐션용 KV 캐시가 없습니다. 같은 헤드 구성으로 24층이 모두 전역 어텐션이었다면 128K에서 약 6.4GB가 됐을 것입니다(필자의 가정 계산). **즉 LFM3는 층의 4분의 3을 "길이에 비례하는 메모리가 필요 없는 연산"으로 채워서 긴 컨텍스트 비용을 줄인 설계입니다.**

속도에 대해서 발표문은 파라미터당으로 보면 LFM3-1.7B가 짧은 프롬프트에서는 LFM2-1.2B와 같고, 컨텍스트에 8K 토큰이 있을 때는 약 25% 빠르다고 설명합니다.

### 3. 학습: 22T 토큰 사전학습과 4단계 후학습

모델 카드에 따르면 LFM3-1.7B-Base는 총 22T(22조) 토큰으로 사전학습됐습니다. 카드의 도식 설명 기준으로 웹·합성 데이터 약 15T, 코드·수학·과학 3T(4K 컨텍스트), 선별한 에이전트 데이터 3T(32K 컨텍스트), 128K 확장 500B, 256K 확장 50B 순서입니다. 마지막 3.5T 토큰은 "중간 학습(mid-training)" 단계로, 에이전트 실행 기록과 도구 호출 비중을 높인 고품질 데이터를 쓰면서 컨텍스트를 256K까지 늘렸습니다.

후학습(post-training)은 네 단계입니다.

1. **SFT(지도 미세조정, Supervised Fine-Tuning):** 대화, 추론, 도구 호출, 에이전트 실행 기록 등 1.75T 토큰
2. **혼합 강화학습:** 수학, 코드, SQL, 구조화 출력 등 여러 영역을 한꺼번에 학습하고, 보상에 길이 벌점을 넣어 답을 간결하게 유지
3. **MOPD(다영역 온폴리시 증류, Multi-domain On-Policy Distillation):** 코드, 수학, 도구 사용, 긴 컨텍스트, 에이전트 작업, 기업 업무 흐름을 각각 강화학습한 전문 교사 모델 6개를 하나의 모델로 증류
4. **에이전트 강화학습:** 웹 탐색부터 사무 작업까지를 실제 에이전트 하네스(Hermes Agent, Pi, OpenClaw 등 에이전트 실행 프로그램) 안에서 수행

### 4. 하나의 베이스에서 여섯 모델

Hugging Face 블로그는 "모든 LFM3 모델이 LFM3-1.7B-Base에서 갈라진다"고 설명합니다. 아래 표는 각 모델 카드의 사양을 모은 것입니다.

| 모델 | 파라미터 | 입력 | 출력 | 컨텍스트 |
|---|---|---|---|---|
| [LFM3-1.7B](https://huggingface.co/LiquidAI/LFM3-1.7B) | 1.73B | 텍스트 | 텍스트 | 256K |
| [LFM3-VL-2B](https://huggingface.co/LiquidAI/LFM3-VL-2B) | 1.92B | 텍스트, 이미지, 영상 | 텍스트 | 128K |
| [LFM3-Audio-2B](https://huggingface.co/LiquidAI/LFM3-Audio-2B) | 2B | 텍스트, 오디오(16kHz) | 텍스트, 음성(24kHz) | 32K |
| [LFM3-Omni-2B](https://huggingface.co/LiquidAI/LFM3-Omni-2B) | 2.17B | 텍스트, 이미지, 영상, 오디오 | 텍스트, 음성 | 32K |
| [d1-2B](https://huggingface.co/LiquidAI/d1-2B) | 1.92B | 상태(텍스트·JSON), 이미지·영상, 질문 목록 | 확률이 붙은 답 | 128K |
| [d1-Omni-2B](https://huggingface.co/LiquidAI/d1-Omni-2B) | 2.17B | 위에 오디오 추가 | 확률이 붙은 답 | 128K |

여기에 직접 후학습을 하려는 사용자를 위한 사전학습 체크포인트 [LFM3-1.7B-Base](https://huggingface.co/LiquidAI/LFM3-1.7B-Base)가 따로 공개됐습니다. 모델별로 짚어 둘 점은 다음과 같습니다.

- **LFM3-VL-2B**는 LFM 비전 모델 중 처음으로 영상을 입력받고, 답하기 전에 단계별로 추론합니다. 모델 카드는 코딩, 여러 턴 대화, 복잡한 추론에는 권장하지 않는다고 적습니다.
- **LFM3-Audio-2B**는 음성 인식, 음성 합성, 번역, 음성 대화를 한 모델로 처리합니다. 음성 언어 목록에 한국어가 들어 있지만, 모델 카드는 음성 대화(voice chat) 기능이 현재 영어만 지원한다고 밝힙니다.
- **LFM3-Omni-2B**는 Liquid AI의 첫 옴니 모델로, 모델 카드는 음성 인식 모델, 비전 언어 모델, LLM, 음성 합성 모델을 따로 두는 구성을 한 모델로 대체한다고 설명합니다. 추론(thinking)을 지원하지 않는 모델입니다.
- **d1-2B, d1-Omni-2B**는 글을 생성하지 않는 판단 모델입니다. 상황 하나와 질문 여러 개를 주면 한 번의 순전파(forward pass)로 예/아니오, 선택, 점수, 위치 지정, 값 추출 같은 타입별 답과 확률을 돌려줍니다. d1-2B 카드는 상태가 약 64K 토큰을 넘으면 답의 신뢰도가 떨어진다고 적습니다.

### 5. 자체 개발한 비전 인코더, 오디오 인코더, 코덱

비전과 오디오 모델에는 베이스 외에 새 부품이 붙습니다. 수치는 모두 Liquid AI 발표 기준입니다.

- **비전 인코더(164M):** 합성곱과 어텐션을 섞은 14층 구조(게이트 depthwise 2D 합성곱 8, 양방향 어텐션 6)입니다. 이전 LFM 비전 모델이 쓰던 SigLIP2 인코더보다 연산량이 3배 적고, Qwen3.5-2B의 비전 인코더와 13개 벤치마크 평균 정확도(55.9%)가 같으면서 FLOPs는 2.2배 적다고 합니다(두 인코더 모두 같은 LFM2.5-230M 언어 모델에 붙여 측정). 영상은 표본 프레임을 두 장씩 묶어 한 조각으로 임베딩해 시간축 길이를 절반으로 줄입니다.
- **오디오 인코더:** SWA와 단기 합성곱을 섞었고 완전히 인과적(causal)이어서, 사용자가 말하는 동안 프리필(prefill, 입력을 미리 처리하는 단계)을 진행할 수 있습니다. 첫 토큰까지 걸리는 시간이 최소 50ms라고 밝힙니다.
- **LiquidCodec:** 음성 80ms를 이산 토큰 12개로 표현하는 오디오 토크나이저입니다. Apple M4 Max의 CPU 스레드 하나에서 실시간의 약 87배 속도로 토큰을 음성으로 바꾸며 스트리밍 디코딩을 지원합니다.

### 6. "특화용 모델"이라는 포지셔닝

발표문 제목부터 "Specialized Intelligence"이고, Liquid AI는 모든 모델을 GPU 한 장으로 미세조정할 수 있다고 강조합니다. 모델 카드와 Hugging Face 블로그에는 TRL 기반 Colab 노트북이 연결돼 있습니다. 텍스트 모델용은 네 가지입니다. SFT로 지저분한 문서에서 JSON을 추출하기, 선호 데이터로 학습하는 DPO로 검색 문서에 근거해 답하거나 거절하기, 강화학습 방식인 GRPO로 도구 108개짜리 휴대폰 앱에서 맞는 도구 호출하기, CPT(계속 사전학습, Continued Pre-Training)로 원문 텍스트만으로 터키어 익히기입니다.

발표문이 든 특화 사례 두 가지는 이렇습니다.

- **풍력 터빈 블레이드 결함 검사:** 공개 사진 약 3,000장(WTBs2025)으로 LFM3-VL-2B를 A100 한 장에서 몇 시간 SFT와 GRPO로 학습했습니다. 따로 떼어 둔 약 1,400장에서 결함 분류 정확도가 67%로, 검출 F1이 0.003에서 0.11로 올랐다고 합니다. 미세조정 전에는 결함 종류를 맞힌 이미지가 10% 미만이었습니다.
- **로봇:** LFM3-VL-2B를 도구 기반 로봇 팔 제어(랭크 32 LoRA 어댑터, 약 4만 샘플, AMD Instinct MI325X 한 장에서 약 6 GPU 시간), 시각·언어 내비게이션(R2R 53%, RxR 43%), VLA(시각·언어·행동 모델, LIBERO 4개 과제군 평균 96.2%, RoboCasa-GR1 45.7%)로 확장했습니다. 모두 Liquid AI 연구팀의 자체 실험 결과입니다.

발표문에는 파트너사 MacPaw의 인용도 실려 있습니다. 실제 macOS 환경의 일상 에이전트 과제 65개에서 LFM3-1.7B가 Qwen3.5-2B보다 과제 성공률이 높았고(64% 대 48%) 과제당 토큰을 58% 덜 썼다는 내용입니다. 출시 파트너의 평가이므로 독립적인 제3자 검증으로 보기는 어렵습니다.

### 온디바이스 속도 (LFM3-1.7B 모델 카드의 차트)

조건은 llama.cpp, Q4_0 GGUF, 컨텍스트 32,768 토큰, 배치 1, 출력 100 토큰, GPU 오프로드입니다. 괄호 안은 비교 모델(MiniCPM5-2B, Qwen3.5-4B, Qwen3.5-9B, Gemma 4 E4B) 중 그 항목에서 가장 좋은 값입니다. 수치는 필자가 카드의 차트 이미지에서 읽어 옮겼습니다.

| 기기 | 프리필 (tok/s) | 디코드 (tok/s) | 메모리 (GB) |
|---|---|---|---|
| AMD Ryzen AI Max+ 395 | 3,771 (1,355) | 129.6 (70.1) | 2.75 (3.84) |

카드는 세 기기 모두에서 프리필이 최소 2.5배, 디코드(토큰을 하나씩 생성하는 단계)가 최소 1.8배 빠르고 메모리를 가장 적게 쓴다고 요약합니다. 다만 LFM3-1.7B는 "LFM3 지원이 들어간 llama.cpp 빌드"로, 나머지 모델은 릴리스 b11744로 측정했다고 적혀 있어 빌드가 서로 다릅니다.

### 비전, 오디오, 옴니 (공식 발표문의 표)

- **LFM3-VL-2B:** 62개 비전 벤치마크 평균 71.4로, LFM2.5-VL-3B(57.6), Qwen 3.5 2B(64.0), Gemma 4 E2B(53.6)보다 높고 Gemma 4 12B(71.7)와 비슷합니다. 범주별로는 GUI 이해(83.1), 시각적 위치 지정(77.3)이 강하고, 에이전트(42.5)와 영상(61.2) 범주는 표의 상용 모델들보다 낮습니다.
- **LFM3-Audio-2B:** 다국어 음성 인식 평균 오류율은 6.0%로 표에서 가장 낮지만(한국어 포함 9개 언어), 영어만 보면 6.2%로 Voxtral Mini 3B(5.5%)나 Kimi-Audio-7B-Instruct(5.3%)보다 높습니다. 영어 음성 합성은 UTMOSv2(합성 음성 품질 점수, 1~5) 3.8, 오류율 1.4%입니다. VoiceBench(73.1)와 오디오 이해 MMAR(50.6)에서는 MiMo-Audio-7B-Instruct(77.3, 62.3)가 앞서고, 도구 호출 항목(58.5)은 Liquid AI 내부 평가이며 Gemma 4 E4B(72.4)가 더 높습니다.
- **LFM3-Omni-2B:** 영상과 소리를 함께 이해하는 Daily-Omni(70.1), WorldSense(47.1), AV-SpeakerBench(46.8)에서 10.7B인 Qwen2.5-Omni-7B(61.3, 45.4, 43.2)를 앞섭니다. 이미지와 오디오를 함께 보는 OmniBench 전체 점수는 46.3으로 Qwen2.5-Omni-7B(49.7)보다 낮습니다.

## 써 볼 수 있나

아래 명령과 코드는 모두 공식 모델 카드와 문서의 예제이며, **필자는 가중치를 내려받지 않았고 직접 실행해 보지 않았습니다.**

### 배포 형식

LFM3-1.7B 모델 카드가 안내하는 형식은 다음과 같습니다.

| 형식 | 엔진 | 용도 |
|---|---|---|
| BF16 | vLLM, SGLang, Transformers | GPU 추론 |
| FP8, NVFP4 | SGLang | GPU용 양자화 |
| GGUF | llama.cpp, Ollama, LM Studio | CPU·GPU 로컬 추론 |
| MLX | MLX | Apple Silicon |
| ONNX | ONNX Runtime | 여러 플랫폼 |
| OpenVINO | OpenVINO | Intel 하드웨어(4비트) |

[GGUF 저장소](https://huggingface.co/LiquidAI/LFM3-1.7B-GGUF)의 파일 크기는 Hugging Face API 기준 Q4_0(QAD) 1.05GB, Q4_K_M 1.10GB, Q6_K 1.43GB, Q8_0 1.85GB, BF16 3.47GB입니다. 발표문의 "4비트에서 약 1GB"는 이 가중치 파일 크기에 해당합니다. Q4_0 파일은 일반 변환본이 아니라 QAD(양자화 인지 증류, Quantization-Aware Distillation) 체크포인트로, GGUF 카드는 Q4_0 양자화로 잃은 정확도를 되찾도록 학습한 것이라고 설명합니다.

### llama.cpp로 실행

GGUF 카드의 대화형 실행 명령입니다. llama.cpp b11960(v0.8.0) 이상이 필요합니다.

```bash
llama-cli -hf LiquidAI/LFM3-1.7B-GGUF:Q4_K_M \
  --temp 0.1 --top-k 50 --repeat-penalty 1.1
```

에이전트 하네스에 연결할 때는 OpenAI 호환 서버로 띄웁니다. 아래는 [Agent Harnesses 가이드](https://docs.liquid.ai/examples/agent-harnesses)의 명령입니다.

```bash
llama-server -hf LiquidAI/LFM3-1.7B-GGUF:Q4_K_M \
  --jinja \
  --port 8080 \
  -c 262144 \
  -fa on \
  -ngl 99 \
  --temp 0.1 \
  --top-k 50 \
  --repeat-penalty 1.1
```

`--jinja`는 모델의 채팅 템플릿으로 도구 호출을 켜는 옵션이고, `-c 262144`는 256K 컨텍스트 전체를 엽니다. 같은 가이드는 메모리가 부족하면 32K 정도로 줄여 띄우라고 권하며, 에이전트 과제 하나에는 대체로 충분하다고 설명합니다. 주의할 점이 하나 더 있습니다. 저장소의 NVFP4 GGUF 파일은 b12088 이상에서만 지원되고, 카드에 따르면 그보다 오래된 빌드는 파일을 불러오기는 하지만 잘못된 출력을 냅니다.

### Transformers로 실행

모델 카드의 빠른 시작 예제입니다.

```python
from transformers import pipeline

generator = pipeline(
    "text-generation",
    model="LiquidAI/LFM3-1.7B",
    trust_remote_code=True,
)

messages = [{"role": "user", "content": "What is C. elegans?"}]
output = generator(
    messages,
    do_sample=True,
    temperature=0.1,
    top_k=50,
    repetition_penalty=1.1,
    max_new_tokens=2048,
)
print(output[0]["generated_text"][-1]["content"])
```

`trust_remote_code=True`는 저장소에 들어 있는 모델 코드(`modeling_lfm3.py` 등)를 내려받아 실행한다는 뜻이므로, 사내 환경에서는 보안 검토 대상이 됩니다. 카드가 권하는 샘플링 값은 일반 용도(대화, 도구 사용, 에이전트, 코딩)에 `temperature=0.1, top_k=50, repetition_penalty=1.1`, 수학·과학에 `temperature=1.0, top_p=0.95, top_k=20`입니다.

### 추론과 도구 호출

카드에 따르면 추론(thinking)은 기본으로 켜져 있습니다. `enable_thinking=False`로 끌 수 있지만 "특히 추론이 많이 필요한 과제에서 동작이 일관되지 않을 수 있다"고 적혀 있습니다. 도구 스키마는 `apply_chat_template()`의 `tools` 인자로 넘기고, 모델은 아래와 같은 XML 형식으로 호출을 생성합니다.

```text
<tool_call>
<function=get_weather>
<parameter=city>
Paris
</parameter>
</function>
</tool_call>
```

도구 정의를 프롬프트에 미리 넣지 않고, 하네스의 검색 도구가 이름을 돌려준 뒤에야 정의를 끼워 넣는 지연 로딩(`defer_loading`)도 지원합니다. 검색 자체는 하네스가 구현해야 합니다.

### API 가격과 하드웨어

Liquid AI [가격 페이지](https://www.liquid.ai/pricing) 기준(2026-11-20 확인) 호스팅 API 요금은 다음과 같습니다. 단위는 100만 토큰당 달러입니다.

로컬 하드웨어는 위 온디바이스 표가 기준이 됩니다. Liquid AI 측정으로 32K 컨텍스트에서 실행 중 메모리는 iPhone 17 Pro 1.90GB, Apple M5 Max 2.25GB, AMD Ryzen AI Max+ 395 2.75GB였습니다. 가중치 파일 1GB에 KV 캐시와 런타임 메모리가 더해진 값이므로, 실제 기기 예산은 "약 1GB"가 아니라 이 숫자로 잡아야 합니다.

필자가 확인한 8개 저장소(LFM3-1.7B, LFM3-1.7B-Base, LFM3-VL-2B, LFM3-Audio-2B, LFM3-Omni-2B, d1-2B, d1-Omni-2B, LFM3-1.7B-GGUF)의 LICENSE 파일은 줄 끝 공백을 빼면 모두 같은 LFM Open License v1.0입니다. 아래 인용은 [LICENSE 원문](https://huggingface.co/LiquidAI/LFM3-1.7B/blob/main/LICENSE)이며(2026-11-20 확인), 해석은 필자의 독해일 뿐 법률 자문이 아닙니다.

Liquid AI의 [라이선스 안내 페이지](https://www.liquid.ai/lfm-license)는 이 라이선스가 Apache 2.0 문구를 바탕으로 하고, 달라진 부분은 저작권·특허 허락에 붙은 조건(2·3항), 상업적 사용 제한(5항), 라이선서 명시, 자동 종료 조항(11항)이라고 설명합니다. 핵심 조항은 다음과 같습니다.

**정의.**

> "Commercial Use" shall mean any use of the Work for direct or indirect commercial advantage or monetary compensation.

> "Threshold" shall mean annual revenue of 10 million United States dollars ($10,000,000) or more.

**5항, 상업적 사용 제한.**

> (a) The rights granted under this License for Commercial Use are conditioned upon You or Your Legal Entity not exceeding the Threshold.
>
> (b) Any Commercial Use of the Work or a Derivative Work by a Legal Entity that exceeds the Threshold is not licensed under this Agreement.
>
> (c) The Threshold shall not apply to a Qualified Non-Profit Organization's use of the Work or a Derivative Work for Non-Commercial or Research Purposes.

**11항, 종료.**

> This License will terminate automatically and immediately if You fail to comply with any of its terms and conditions. Upon termination, You must cease all use of the Work and any Derivative Works and delete all copies in Your possession.

실무에서 확인할 점은 네 가지입니다.

- **연 매출 1,000만 달러 미만이면 상업적 사용도 무료입니다.** 가격 페이지도 "연 매출 1,000만 달러 미만 기업은 운영 환경에서 무료"라고 적습니다. 그 이상이면 유료 엔터프라이즈 라이선스 견적을 받아야 합니다.
- **파생 모델에도 같은 조건이 붙습니다.** 5항은 "Work or a Derivative Work"를 함께 적고 있어, 직접 미세조정한 모델도 매출 기준을 넘는 법인이 상업적으로 쓰면 허용 범위 밖입니다. 대신 카피레프트 조건은 없어서 미세조정 모델을 공개할 의무는 없습니다.
- **"법인"의 범위가 넓습니다.** 라이선스의 Legal Entity 정의는 Apache 2.0과 같이 지배하거나 지배받거나 공통 지배 아래 있는 모든 법인을 합친 것입니다. 필자의 독해로는 자회사 단독 매출이 작아도 모회사와 계열사를 합쳐 기준을 넘으면 해당할 가능성이 있습니다. 또 "연 매출"을 어느 기간, 어떤 기준으로 계산하는지는 원문에 정의돼 있지 않습니다.
- **비영리와 연구는 예외입니다.** 미국 세법 501(c)(3) 단체 또는 다른 나라의 동등한 비영리·자선 단체가 비상업적 또는 연구 목적으로 쓰는 경우에는 매출 기준이 적용되지 않습니다.

OSI의 [오픈소스 정의(OSD)](https://opensource.org/osd) 5항은 특정 개인이나 집단에 대한 차별을, 6항은 사업 목적 사용을 포함한 특정 분야에서의 사용 제한을 금지합니다. 매출 규모에 따라 상업적 사용 권리가 사라지는 조항은 이 정의와 맞지 않는 것으로 읽힙니다. 따라서 LFM3는 가중치를 내려받아 수정하고 재배포할 수 있다는 의미의 **오픈웨이트**이지, 오픈소스 라이선스로 배포된 모델은 아닙니다. Liquid AI의 발표문과 모델 카드도 "open-weight"라는 표현을 씁니다.

## 한계와 논란

- **제3자 검증이 아직 없습니다.** 텍스트, 비전, 오디오, 옴니 표 모두 Liquid AI 자체 실행입니다. 경쟁 모델에 공통 샘플링 값(temperature 0.6, top_p 0.95)을 쓴 항목이 많아, 각 모델에 최적화된 설정의 성능과 다를 수 있습니다. 오디오 도구 호출 항목은 내부 평가이고, MacPaw 수치는 출시 파트너의 인용입니다.
- **평균 행의 구성.** 위에서 계산했듯 텍스트 모델의 "평균 49.37 대 47.24"는 AA-Omniscience 세 행을 빼면 51.20 대 51.24가 됩니다.
- **모델 카드의 권장 범위와 벤치마크 표 사이의 간극.** 카드는 LFM3-1.7B를 에이전트형 코딩에 권장하지 않는다고 적으면서, 표에는 OpenCode 하네스로 최대 250턴을 돌린 SWE-bench Verified 43.40을 싣고 있습니다. 점수가 있다고 해서 그 용도에 쓸 만하다는 뜻은 아니라는 점을 카드 스스로 밝힌 셈입니다.
- **지식과 긴 컨텍스트 검색은 약합니다.** GPQA Diamond, HLE, AA-Omniscience 정확도에서 4B·9B 모델에 뒤지고, RULER 128K도 65.56으로 Qwen3.5-4B(84.63), Qwen3.5-9B(87.11)보다 낮습니다. 256K 컨텍스트를 "열 수 있다"는 것과 그 안의 정보를 "정확히 찾아 쓴다"는 것은 다른 문제입니다.
- **온디바이스 비교의 빌드 차이.** LFM3-1.7B와 비교 모델의 llama.cpp 빌드가 다르고, Q4_0 파일이 QAD 체크포인트인 LFM3와 달리 비교 모델의 Q4_0이 어떤 방식으로 만들어졌는지는 카드에 적혀 있지 않습니다.
- **모델별 기능 제한.** 컨텍스트는 텍스트 256K, 비전 128K, 오디오·옴니 32K로 다릅니다. LFM3-Audio-2B의 음성 대화는 현재 영어만 지원하고, LFM3-Omni-2B는 추론을 지원하지 않으며, `enable_thinking=False`는 동작이 일관되지 않을 수 있습니다.
- **특화 사례의 절대 수치.** 풍력 터빈 예시에서 검출 F1은 미세조정 후에도 0.11입니다. 몇 시간 미세조정으로 크게 올랐다는 것은 맞지만, 그대로 현장 검사에 쓸 수준이라는 근거는 아닙니다.
- **라이선스.** 매출 기준, 법인 범위, 종료 시 삭제 의무 때문에 성장 중인 회사나 대기업 계열사는 도입 전에 법무 검토가 필요합니다.

## 인사이트

**왜 지금 중요한가: KV 캐시를 "관리"하는 대신 "구조로 없애는" 접근.** 블로그의 [KV 캐시와 추측 디코딩 해설](/tech/2026/10/24/kv-cache-speculative-decoding.html)에서 다뤘듯 KV 캐시는 컨텍스트 길이에 정비례하고, 그 글에서 소개한 GQA(KV 헤드를 줄이는 설계)나 PagedAttention(낭비 없이 할당하는 서빙 기법)은 모두 "모든 층이 전체 길이의 KV를 갖는다"는 전제 위에 있습니다. LFM3는 그 전제를 바꿉니다. 24층 중 6층만 전체 길이를 보게 하고 나머지 18층은 고정 크기 상태만 갖게 해서, 필자의 검산으로 토큰당 12KiB까지 내렸습니다. 양자화 해설 글에서 계산한 Qwen2.5-1.5B(28층, KV 헤드 2개)의 토큰당 28KiB와 비교하면 절반 이하입니다. 에이전트가 도구 정의와 실행 기록을 256K까지 쌓는 시대에, 휴대폰급 메모리에서 긴 컨텍스트를 감당하려면 서빙 기법보다 모델 구조 쪽에서 답이 나와야 한다는 주장으로 읽힙니다. 다만 RULER 128K 점수가 보여 주듯, 전역 어텐션 층을 줄인 대가가 긴 컨텍스트 검색 정확도에서 나타나는지는 따로 검증이 필요합니다(필자의 추정이며 발표문은 이 인과를 다루지 않습니다).

**실무에 주는 의미.** 필자의 판단으로는 이 제품군이 맞는 자리는 세 가지입니다. 첫째, 기기 안에서 끝나야 하는 좁은 작업(문서에서 필드 추출, 도구 라우팅, 화면 이해, 음성 명령 해석)에 미세조정해서 쓰는 경우입니다. 모델 카드가 제공하는 SFT·DPO 노트북은 블로그의 [LoRA 논문 글](/papers/2026/10/24/lora.html), [DPO 논문 글](/papers/2026/10/24/dpo.html)에서 다룬 기법을 그대로 쓰므로 진입 장벽이 낮습니다. 둘째, 분류·라우팅·검수처럼 "생성"이 아니라 "판단"만 필요한 파이프라인 단계에는 텍스트 모델보다 d1 모델이 구조적으로 맞습니다. 셋째, 지식이 필요한 질의응답은 모델 카드 권고대로 검색을 붙여야 합니다. 발표문 표에서도 도구를 쓰면 HLE 점수가 7.17에서 13.90으로 오릅니다. 그리고 용량 계획은 "4비트 약 1GB"가 아니라 32K 컨텍스트 기준 1.9~2.75GB(자체 측정)로 잡고, 256K 전체를 열면 KV 캐시만 약 3.2GB(필자 계산)가 더 든다는 점을 감안해야 합니다. 양자화 형식을 고를 때는 [양자화 해설](/tech/2026/10/24/llm-quantization.html)에서 정리한 PTQ와 QAT의 구분이 도움이 됩니다. LFM3의 Q4_0은 사후 변환이 아니라 제작사가 양자화를 전제로 다시 학습한 체크포인트라는 점이 일반 GGUF 변환본과 다릅니다.

**블로그의 기존 글과의 연결.** 같은 "한 모델로 여러 기능"이라는 목표를 두고 접근이 갈립니다. [IBM Granite Switch 4.1](/tech/2026/10/24/ibm-granite-switch-4-1.html)은 기본 모델에 어댑터와 음성인식 인코더를 합쳐 한 엔드포인트에서 기능을 전환하고, LFM3는 반대로 한 베이스에서 모달리티별 모델을 따로 갈라내 필요한 것만 기기에 올립니다. 서버에서는 합치는 쪽이, 메모리가 2~3GB인 기기에서는 갈라내는 쪽이 자연스럽습니다. 음성에서는 [Mistral Voxtral 3](/tech/2026/10/24/mistral-voxtral-3.html)가 전사, LLM, 음성 합성을 스트리밍 파이프라인으로 엮는 API 제품인 반면, LFM3-Omni-2B는 그 단계를 2.17B 모델 하나로 대체하겠다는 구상입니다. 라이선스는 [Meta Muse Spark Open](/tech/2026/10/24/meta-muse-spark-open.html)과 나란히 놓고 볼 만합니다. 그 글에서 정리한 Muse Model License는 모델을 API로 제공하는 사업자에게만 매출 2,000만 달러 조건을 걸고 분야별 사용 금지를 두는데, LFM Open License는 분야 제한이 없는 대신 매출 1,000만 달러 이상 법인의 모든 상업적 사용을 유료로 돌립니다. 둘 다 "오픈웨이트이지만 오픈소스는 아닌" 모델이며, 걸리는 지점이 다르므로 각자 조건을 따로 확인해야 합니다. 후학습에서 보상에 길이 벌점을 넣고 전문 교사 모델을 증류하는 방식은 [Reflection AI Beam 글](/tech/2026/10/20/reflection-beam.html)에서 본 대형 모델의 학습법과 같은 방향이라, 이 기법이 2B급까지 내려왔다는 점도 눈에 띕니다.

**한계와 반론.** "9B가 필요하던 에이전트 애플리케이션을 1.7B로"라는 문구는 Liquid AI가 고른 29개 항목과 자체 실행 조건에서 성립하는 주장입니다. 29개 중 15개가 에이전트, 도구 사용, 지시 따르기 항목이라 이 모델이 강한 영역에 무게가 실려 있습니다. 또 LiveClaw와 BrowseComp-Plus는 OpenClaw 에이전트로 측정됐는데, LFM3-1.7B는 OpenClaw를 포함한 하네스에 맞춰 후학습된 모델입니다. 학습에 쓴 하네스와 평가에 쓴 하네스가 겹치면 다른 하네스나 사내 도구 체계에서는 같은 성능이 나오지 않을 수 있습니다(필자의 추정). 도입 전에 자기 도구 세트로 직접 평가해야 하는 이유입니다.

**앞으로 지켜볼 점.** (1) 독립 기관이나 커뮤니티가 같은 체크포인트로 재현한 에이전트·도구 호출 점수. (2) llama.cpp 정식 릴리스에서 다른 모델과 같은 빌드로 잰 속도와 메모리. (3) 한국어 품질: 텍스트 16개 언어와 음성 언어 목록에 한국어가 있지만, 필자가 읽은 발표문과 모델 카드에서 한국어만 따로 잰 수치는 찾지 못했습니다(음성 인식은 한국어를 포함한 9개 언어 평균만 제시). (4) 매출 기준 라이선스가 실제 기업 도입에서 어떻게 해석되고 집행되는지. 이 네 가지가 확인되기 전까지는 사내 도구와 프로토타입에서 먼저 써 보고, 제품 탑재는 자체 평가와 라이선스 검토 뒤에 결정하는 편이 안전해 보입니다.
