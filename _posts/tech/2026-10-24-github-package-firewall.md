# [기술 소개] GitHub package firewall: 에이전트와 CI의 npm 설치 앞에 놓는 정책 관문

- **발표:** GitHub, 2026년 10월 20일 (changelog, 10월 21일 편집자 주석으로 내용 재작성)
- **원문:** [공식 changelog](https://github.blog/changelog/2026-10-20-github-package-firewall-in-public-preview) · [공식 문서: Protecting endpoints with GitHub package firewall](https://docs.github.com/enterprise-cloud@latest/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/protecting-endpoints-with-package-firewall) · [GitHub Community 토론](https://github.com/orgs/community/discussions/210809)
- **한눈에 (2026-10-24 기준):** 엔드포인트와 공개 레지스트리 사이에서 메타데이터 요청과 패키지 다운로드를 모두 검사하는 설치 시점 정책 관문입니다. 제어 항목은 알려진 악성코드, 취약점 권고, 증명(attestation) 다운그레이드, 새로 추가된 설치 스크립트, 최소 패키지 나이(기본 1일) 다섯 가지입니다.
- **도입 전 확인할 제약 (2026-10-24 기준):**
  - **퍼블릭 프리뷰**이며 공식 문서는 "변경될 수 있다"고 명시합니다.
  - **GitHub Enterprise Cloud 고객만** 쓸 수 있습니다(데이터 레지던시 포함). Free, Pro, Team 플랜에 대한 언급은 없습니다.
  - **npm 패키지만 지원**합니다. PyPI, Maven 등 다른 생태계는 지원하지 않습니다.
  - 프리뷰 기간에는 무료이고, 정식 출시(GA) 후에는 Actions처럼 **사용량 기반 과금**으로 바뀔 예정입니다.
  - Artifactory 연동은 **실험적(experimental)** 기능입니다.

## 한 줄 요약

**GitHub가 사람 없이 의존성을 설치하는 코딩 에이전트와 CI 러너를 겨냥해, npm 설치 요청을 엔터프라이즈 정책으로 걸러 주는 레지스트리 프록시형 방화벽을 프리뷰로 내놓았습니다.** 개별 개발자가 패키지 매니저 설정으로 하던 방어(새 버전 대기, 설치 스크립트 차단, 증명 확인)를 조직 단위의 네트워크 관문으로 옮겼다는 점이 핵심입니다.

## 배경

changelog는 출시 이유를 직접 적고 있습니다. 최근 "설치 시점을 노리는 악성코드 공격이 쏟아졌고", 에이전트와 CI 러너는 "사람이 개입하지 않은 채 작업이나 빌드를 끝내기 위해 의존성을 설치하기 때문에 특히 취약하다"는 것입니다.

이 문장은 지난 1~2년 사이 개발 환경의 변화를 정확히 짚습니다. 과거에는 `npm install`을 사람이 쳤고, 낯선 패키지 이름이 보이면 멈칫할 여지가 있었습니다. 지금은 코딩 에이전트가 오류 메시지를 보고 스스로 패키지를 추가하고 설치합니다. 패키지 매니저의 기본 동작(최신 버전 해석, 설치 스크립트 실행)은 그대로인데, 그 앞에서 판단하던 사람이 빠진 셈입니다.

블로그에서도 비슷한 사례를 다뤘습니다. [GPT Pilot 소개](/opensource/2026/10/20/gpt-pilot.html)에서 정리한 것처럼 그 저장소에는 2025년 8월부터 2026년 6월까지 자격 증명을 훔치는 웜이 숨어 있었고, README는 그 기간에 소스를 받아 **실행한** 사람에게 모든 자격 증명을 교체하라고 안내했습니다. 이 사례는 패키지 레지스트리가 아니라 저장소 자체가 오염된 경우라 package firewall의 대상은 아닙니다. 다만 "받아서 실행하는 순간 자격 증명이 털린다"는 구조는 같고, package firewall은 그중 npm 패키지를 설치하는 경로를 겨냥합니다.

## 핵심 내용

### 1. 구조: 엔드포인트와 레지스트리 사이의 프록시

동작은 두 단계입니다(changelog와 공식 문서 기준).

1. 엔터프라이즈 관리자나 보안 관리자가 정책을 설정합니다.
2. 코딩 에이전트, CI/CD 호스트, 개발자 PC 같은 엔드포인트가 공개 레지스트리 대신 방화벽 URL로 요청합니다.

changelog에 따르면 **패키지 목록을 가져오는 메타데이터 요청과 실제 패키지 다운로드가 모두** 방화벽을 지나고, 각각 정책에 비춰 평가됩니다. 공식 문서의 예시 로그는 "testcontainers: 1 version blocked by package-firewall due to security policies (version cooldown)"처럼 버전 단위로 차단을 알려 줍니다. 필자가 이해하기로는 메타데이터 단계에서 걸러진 버전은 의존성 해석 대상에서 빠지므로, 설치가 무조건 실패하기보다 정책을 통과하는 다른 버전으로 해석될 수 있습니다. 다만 이 해석 동작을 공식 문서가 명시적으로 설명하지는 않으므로 실제 환경에서 확인이 필요합니다.

### 2. 다섯 가지 정책 제어와 기본값

정책은 방화벽을 지나는 모든 요청에 적용됩니다. 공식 문서 기준 제어 항목과 기본값은 다음과 같습니다.

| 제어 | 검사 내용 | 기본값 |
|---|---|---|
| 알려진 악성코드 차단 | GitHub Advisory Database에 활성 악성코드 권고가 있는 패키지 차단 | 켜짐 |
| 취약점 권고 차단 | 요청 버전에 영향을 주는 취약점 권고의 최소 심각도 선택(Critical만 / High 이상 / Medium 이상 / 전체) | Critical만 |
| 증명 다운그레이드 차단 | 이전 버전에는 SLSA 증명이 있었는데 요청 버전에는 없으면 차단 | 켜짐 |
| 새 설치 스크립트 차단 | `preinstall`, `postinstall`처럼 설치 시 실행되는 스크립트가 최근 추가된 경우 차단 | 켜짐 |
| 최소 패키지 나이 | 새로 게시된 버전을 설정 기간 동안 차단(1~365일, 0이면 끔) | 1일 |

각 항목이 겨냥하는 공격이 다릅니다. 증명 다운그레이드 차단은 문서 표현대로 "증명이 사라진 것은 게시 과정이 탈취됐다는 신호일 수 있다"는 가정에 기댑니다. 정상적으로 CI에서 증명을 붙여 배포하던 패키지가 갑자기 증명 없이 올라왔다면, 누군가 유지보수자의 토큰을 훔쳐 로컬에서 게시했을 가능성을 의심하는 것입니다. 새 설치 스크립트 차단은 문서가 "임의 명령을 실행할 수 있고 자격 증명을 훔치는 데 쓰일 수 있다"고 설명하는 설치 스크립트 경로를 막습니다. 최소 패키지 나이는 악성 버전이 발견되어 내려가기 전의 시간 창을 피하는 장치입니다.

### 3. 엔드포인트 설정: npm과 Artifactory

**npm 직접 연결.** 공식 문서의 사용자 수준 `.npmrc` 예시입니다. `ENTERPRISE`는 엔터프라이즈 슬러그로 바꿉니다.

```ini
registry=https://package-firewall.githubapp.com/npm/enterprises/ENTERPRISE
//package-firewall.githubapp.com/npm/enterprises/ENTERPRISE/:_authToken=${GITHUB_TOKEN}
```

명령줄로도 같은 설정을 할 수 있습니다.

```bash
npm config set registry \
  https://package-firewall.githubapp.com/npm/enterprises/ENTERPRISE
npm config set \
  '//package-firewall.githubapp.com/npm/enterprises/ENTERPRISE/:_authToken=${GITHUB_TOKEN}'
```

레지스트리 URL은 엔터프라이즈마다 다르고, 모든 요청에 엔터프라이즈 구성원(사용자 또는 봇 계정)의 토큰이 필요합니다. 문서는 이 토큰에 "공개 저장소 읽기 전용 접근" 이상의 권한이 필요 없다고 하며, CI 비밀값 등에 보관하고 저장소에 커밋하지 말라고 안내합니다. 필자는 엔터프라이즈 계정이 없어 위 설정을 직접 실행해 보지 못했습니다. 모두 공식 문서의 예시를 그대로 옮긴 것입니다.

**Artifactory 경유.** 이미 JFrog Artifactory를 사내 레지스트리로 쓰고 있다면, Artifactory의 원격(Remote) npm 저장소 URL을 방화벽 주소로 두는 방식도 문서에 있습니다. 엔드포인트는 계속 Artifactory를 바라보고, 공개 패키지만 방화벽을 거칩니다. 문서는 이때 가상(virtual) 저장소에서 **공개 npm 레지스트리로 직접 가는 원격 저장소를 빼라**고 강조합니다. 그렇지 않으면 방화벽을 우회하는 경로가 남기 때문입니다. 이 연동은 실험적 기능입니다.

### 4. 예외 요청과 승인 흐름

방화벽이 필요한 패키지를 막을 때를 위한 절차가 있습니다. 문서가 드는 대표 예는 **보안 수정이 들어간 새 버전이 최소 나이 정책에 걸리는** 경우입니다.

1. 차단되면 npm 출력이나 CI 로그에 예외 요청 URL이 찍힙니다.
2. 사용자는 저장소, 생태계(현재 npm만), 패키지 이름, 버전, 사유를 채워 요청합니다.
3. 엔터프라이즈 관리자나 보안 관리자가 Security and quality > Package firewall bypass에서 검토하고 승인합니다. 이때 버전 칸을 `*`로 바꾸면 그 패키지의 모든 버전을 허용할 수 있습니다. 문서는 사내 소유 패키지처럼 매번 예외를 받기 번거로운 경우를 예로 듭니다.
4. 승인된 예외는 정책의 Package overrides에 쌓이고, 관리자가 나중에 제거할 수 있습니다.

정책 수정 권한은 기본적으로 엔터프라이즈 관리자와 보안 관리자에게만 있고, "Edit enterprise-level package firewall policy"라는 세분화 권한을 사용자 지정 역할에 붙여 다른 팀에 넘길 수 있습니다.

## 비교: 패키지 매니저 자체 설정과 무엇이 다른가

방화벽이 하는 검사 중 상당수는 최신 패키지 매니저에도 클라이언트 설정으로 들어와 있습니다. 아래는 각 공식 문서에서 확인한 범위입니다(2026-10-24 기준, npm은 v12 설정 문서, pnpm은 공식 문서의 공급망 보안 페이지).

| 검사 | GitHub package firewall | npm 설정 | pnpm 설정 |
|---|---|---|---|
| 새 버전 대기 | 최소 패키지 나이(일 단위, 기본 1일) | `min-release-age`(일 단위, 기본 없음), `before`(절대 날짜) | `minimumReleaseAge`(분 단위, 기본 1440분 = 1일) |
| 설치 스크립트 | 새로 추가된 설치 스크립트 차단(기본 켜짐) | `ignore-scripts`(기본 꺼짐), `allow-scripts` 허용 목록 | v10부터 의존성 `postinstall` 자동 실행 비활성화, `allowBuilds`로 허용 목록 |
| 증명·신뢰 하락 | SLSA 증명이 사라지면 차단 | (해당 설정 확인 못 함) | `trustPolicy: no-downgrade` |
| 악성코드·취약점 권고 | GitHub Advisory Database 기준 차단 | (설치 차단 설정 확인 못 함) | (설치 차단 설정 확인 못 함) |
| 적용 단위 | 엔터프라이즈 전체(네트워크 관문) | 각 머신·프로젝트의 설정 파일 | 각 프로젝트의 `pnpm-workspace.yaml` 등 |

npm 문서에 따르면 `min-release-age`는 지정한 일수보다 오래된 버전만 설치하도록 트리를 만들고, 이 제한 때문에 `npm audit fix`가 수정 버전을 못 설치하면 경고와 함께 0이 아닌 코드로 종료합니다. pnpm 문서는 악성코드가 보통 빨리 발견되므로 24시간만 늦춰도 나쁜 버전을 대부분 피할 수 있다고 설명합니다.

**차이는 검사 내용보다 "누가 강제하느냐"에 있습니다.** 클라이언트 설정은 그 설정 파일을 읽는 프로세스에만 적용됩니다. 에이전트가 다른 디렉터리에서 `npx`를 실행하거나, 설정이 없는 새 컨테이너에서 작업하거나, 스스로 `.npmrc`를 고치면 방어가 사라집니다. 방화벽은 레지스트리 요청 자체가 지나는 길목에 있으므로, 엔드포인트가 방화벽 URL을 쓰도록 강제되어 있다면 개별 프로세스의 설정과 무관하게 정책이 적용됩니다. 반대로 말하면, **엔드포인트가 공개 레지스트리에 직접 접속할 수 있는 한 방화벽은 우회됩니다.** Artifactory 연동 문서가 직접 연결 원격 저장소를 빼라고 강조한 것도 같은 이유입니다. 이 점에서 방화벽은 네트워크 이그레스(egress, 외부로 나가는 트래픽) 통제와 함께 써야 의미가 있습니다.

일반적인 사설 레지스트리 프록시(Artifactory 등)도 엔드포인트를 한 곳으로 모은다는 점은 같습니다. 이 글에서 확인한 범위는 GitHub 문서가 설명하는 "Artifactory를 방화벽 앞단에 두는" 연동뿐이며, 각 사설 레지스트리 제품의 자체 보안 기능은 이번 조사 범위에서 다루지 않았습니다.

## 한계와 논란

- **npm만 지원합니다.** 에이전트는 Python 작업에서 `pip install`을, 시스템 작업에서 OS 패키지를 설치합니다. 2026-10-24 기준 이 경로는 방화벽 대상이 아닙니다. 공식 문서의 예외 요청 양식도 "현재 npm만 지원"이라고 적고 있습니다.
- **Enterprise Cloud 전용입니다.** 오픈소스 유지보수자, 개인 개발자, 소규모 팀처럼 공격 표적이 되기 쉬운 쪽은 이 기능을 쓸 수 없습니다. 이들에게는 위 표의 클라이언트 설정이 현실적인 대안입니다.
- **알려진 것만 막습니다.** 악성코드·취약점 차단은 GitHub Advisory Database에 권고가 올라온 뒤에야 동작합니다. 그 전의 시간 창은 최소 나이 정책이 막아야 하는데, 기본값 1일보다 오래 탐지되지 않는 공격(예: 정상 버전으로 신뢰를 쌓은 뒤 나중에 악성 코드를 넣는 경우)에는 효과가 제한됩니다.
- **"새로 추가된" 설치 스크립트만 봅니다.** 문서 표현은 "최근 추가된" 스크립트이므로, 원래부터 설치 스크립트가 있던 패키지가 탈취되어 그 스크립트 내용만 바뀌는 경우는 이 제어의 대상이 아닌 것으로 읽힙니다. pnpm 문서도 같은 위험을 지적하며 "postinstall 스크립트가 있는 신뢰 패키지를 갱신할 때 주의하라"고 적고 있습니다.
- **설치된 코드가 실행 시점에 하는 일은 다루지 않습니다.** 방화벽은 설치 관문입니다. 설치 스크립트를 피한 악성 코드가 `require` 시점에 실행되는 경우, 그리고 에이전트가 직접 작성한 코드의 취약점은 별도 문제입니다.
- **과금 방식이 미정입니다.** GA 후 Actions처럼 사용량 기반 과금이라고만 밝혔고 단가는 2026-10-24 기준 공개되지 않았습니다. CI와 에이전트가 하루에 내는 레지스트리 요청 수를 생각하면 비용 예측이 도입 판단의 변수가 될 수 있습니다.

## 인사이트

**왜 지금 중요한가: "누가 설치 버튼을 누르는가"가 바뀌었습니다.** changelog가 에이전트와 CI 러너를 특정해 언급한 것은 상징적입니다. 공급망 공격 방어는 지금까지 상당 부분 "의존성을 추가하는 사람이 이름과 평판을 확인한다"는 인간의 판단에 기대 왔습니다. 에이전트가 스스로 의존성을 고르고 설치하는 순간 이 단계가 사라지고, 방어는 패키지 매니저 설정이나 네트워크로 옮겨 가야 합니다. 필자의 판단으로는 GitHub가 이 기능을 개별 저장소 설정이 아니라 **엔터프라이즈 정책**으로 설계한 것도 그 때문입니다. 에이전트가 고칠 수 있는 파일 안에 있는 방어는 에이전트에 대한 방어가 되기 어렵습니다.

**블로그의 기존 글과의 연결: 에이전트 보안의 두 방향.** 같은 날 소개하는 [LSCBench 논문](/papers/2026/10/24/last-secure-code-benchmark.html)은 에이전트가 **작성하는** 코드가 기능 테스트는 통과해도 보안 테스트에는 실패한다는 문제를 다룹니다. package firewall은 반대 방향, 즉 에이전트가 **가져오는** 코드의 문제를 다룹니다. 둘 다 "에이전트가 사람 검토 없이 코드를 저장소에 들인다"는 같은 뿌리에서 나옵니다. [Agent Skills 표준 기증 글](/tech/2026/10/24/agent-skills-aaif.html)에서 지적했듯 스킬 생태계에는 아직 서명이나 출처 증명 장치가 없는데, npm 생태계에서 증명 다운그레이드를 정책으로 쓸 수 있게 된 것은 그쪽에 참고가 될 만한 선례로 보입니다. 증명이 "있느냐"가 아니라 "있다가 사라졌느냐"를 보는 방식은, 모든 게시자에게 증명을 강제하지 않고도 탈취 신호를 잡을 수 있는 실용적인 타협입니다.

**실무에 주는 의미: 대상 플랜이 아니어도 지금 할 수 있는 것.** Enterprise Cloud 고객이라면 프리뷰가 무료인 동안 CI 한 파이프라인과 에이전트 실행 환경 하나에 먼저 붙여 차단 로그와 예외 요청 빈도를 재 보는 것이 좋겠습니다. 특히 최소 나이 정책이 보안 패치를 늦추는 상황을 예외 승인 흐름이 얼마나 빨리 처리하는지가 운영 부담을 가를 것입니다. 대상이 아니라면 같은 원리를 클라이언트 쪽에서 적용할 수 있습니다. 에이전트가 쓰는 컨테이너 이미지의 전역 `.npmrc`에 `min-release-age`와 `ignore-scripts`를 넣고, pnpm을 쓴다면 `minimumReleaseAge`와 `trustPolicy: no-downgrade`를 설정하며, 에이전트가 그 설정 파일을 수정하지 못하게 권한을 분리하는 것입니다. 어느 쪽이든 핵심은 에이전트의 작업 디렉터리 밖에서 정책을 강제하는 것입니다.

**한계와 반론.** 이 기능을 "에이전트 공급망 보안의 해결책"으로 보기는 이릅니다. 지원 생태계가 npm 하나이고, 알려진 위협과 최근 변경만 신호로 쓰며, 엔드포인트의 직접 접속을 막지 않으면 우회됩니다. 또 중앙 관문은 그 자체로 가용성 의존점이 됩니다. 방화벽이 느려지거나 장애가 나면 모든 CI와 에이전트의 설치가 함께 멈출 수 있는데, 프리뷰 문서에는 가용성 목표나 장애 시 동작에 대한 설명이 없습니다.

**앞으로 지켜볼 점.** (1) PyPI, Maven, NuGet 등 다른 생태계 지원 일정. 에이전트가 가장 많이 쓰는 언어 중 하나인 Python이 빠져 있는 한 적용 범위는 반쪽입니다. (2) GA 시점의 가격과 대상 플랜 확대 여부. (3) GitHub 자체의 코딩 에이전트 실행 환경이 이 방화벽을 기본값으로 쓰게 되는지. 이 세 가지가 정해지면 "에이전트 실행 환경의 표준 구성 요소"가 될지 판단할 수 있을 것입니다.
