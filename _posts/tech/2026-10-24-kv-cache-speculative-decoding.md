# [기술 소개] LLM 추론 최적화 해설: KV 캐시, PagedAttention, 추측 디코딩

- **주요 출처:** [vLLM/PagedAttention 논문 (arXiv:2309.06180, SOSP 2023)](https://arxiv.org/abs/2309.06180) · [Leviathan 외, 추측 디코딩 (arXiv:2211.17192, ICML 2023)](https://arxiv.org/abs/2211.17192) · [Chen 외, 추측 샘플링 (arXiv:2302.01318)](https://arxiv.org/abs/2302.01318) · [FlashAttention (arXiv:2205.14135, NeurIPS 2022)](https://arxiv.org/abs/2205.14135) · [vLLM 공식 문서](https://docs.vllm.ai/en/latest/)
- **한눈에 (2026-10-24 기준):** vLLM 논문은 기존 서빙 시스템이 KV 캐시용으로 잡은 메모리 중 실제 토큰 상태를 담는 비율이 20.4%~38.2%에 그친다고 측정했고, PagedAttention으로 이를 96.3%까지 올렸습니다. 추측 디코딩은 작은 초안 모델이 여러 토큰을 미리 쓰고 큰 모델이 한 번에 검증하는 방식으로, 원 논문들에서 **출력 분포를 바꾸지 않고** 2~3배 안팎의 속도 향상을 보고했습니다. vLLM은 v0.32.0(2026-10-18)이 최신 릴리스이며 Apache-2.0 라이선스입니다.

## 한 줄 요약

**LLM 추론은 계산보다 메모리가 병목이고, 그 중심에 KV 캐시가 있습니다.** PagedAttention은 KV 캐시를 운영체제의 페이지처럼 잘게 나눠 메모리 낭비를 없애 한 번에 더 많은 요청을 묶게 하고, 추측 디코딩은 큰 모델을 한 번 돌릴 때 토큰을 여러 개 확정해 요청 하나의 지연을 줄입니다.

## 배경

### 디코딩은 왜 느린가

LLM은 토큰을 하나씩 생성합니다(자기회귀 생성). 입력 프롬프트 전체를 한 번에 처리하는 **프리필(prefill)** 단계는 행렬 곱셈이 커서 GPU 연산을 잘 활용하지만, 이후 토큰을 하나씩 만드는 **디코드(decode)** 단계는 매 스텝 모델 가중치 전체와 지금까지의 KV 캐시를 메모리에서 읽어 와야 합니다. vLLM 논문은 이 디코드 단계가 GPU 연산을 충분히 쓰지 못하고 메모리 대역폭에 묶인다(memory-bound)고 설명합니다. Leviathan 외 논문도 큰 모델 추론의 병목은 산술 연산이 아니라 메모리 대역폭과 통신인 경우가 많다고 지적합니다.

그래서 추론 최적화는 크게 두 방향으로 나뉩니다. 첫째, **메모리를 아껴 한 번에 더 많은 요청을 묶는 것**(처리량). 둘째, **메모리를 한 번 읽을 때 토큰을 더 많이 만드는 것**(지연). 이 글의 PagedAttention과 추측 디코딩이 각각을 대표합니다.

### 이 글이 다루지 않는 것

같은 날 올라오는 [프롬프트 캐싱 해설](/tech/2026/10/24/prompt-caching.html)과 헷갈리기 쉬운데, 한 줄로 구분하면 이렇습니다. 프롬프트 캐싱은 **API 공급자가 요청 사이에 반복되는 접두어의 계산 결과를 재사용해 요금과 첫 토큰 지연을 줄이는 기능**이고, 이 글은 **서빙 엔진 내부에서 KV 캐시 메모리를 관리하고 디코딩 자체를 빠르게 하는 기법**을 다룹니다. vLLM의 자동 접두어 캐싱(아래 4절)은 두 주제가 만나는 지점입니다.

## 핵심 내용

### 1. KV 캐시란 무엇이고 얼마나 큰가

트랜스포머의 어텐션은 새 토큰을 만들 때마다 앞선 모든 토큰의 키(key)와 값(value) 벡터가 필요합니다. 매번 다시 계산하지 않도록 이 벡터를 GPU 메모리에 저장해 두는 것이 **KV 캐시**입니다. 크기는 다음 식으로 구할 수 있습니다.

```text
토큰당 KV 캐시 바이트 = 2(키, 값) × 레이어 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트
요청당 KV 캐시 = 토큰당 바이트 × (프롬프트 + 생성 토큰 수)
```

vLLM 논문은 OPT-13B의 토큰당 KV 캐시를 2(키, 값) × 5120(은닉 차원) × 40(레이어) × 2바이트(FP16) = 800KB로 계산하고, 최대 2,048토큰이면 요청 하나가 최대 1.6GB를 쓴다고 설명합니다. 같은 논문은 NVIDIA A100 40GB에서 13B 모델을 서빙할 때 메모리의 약 65%가 가중치, 약 30%가 KV 캐시에 쓰인다고 보고합니다(그림 1).

필자가 위 식을 공개된 모델 구성에 적용해 계산한 값입니다(16비트 자료형 가정, 아래 Python 스크립트로 직접 실행해 확인). Llama 3 구성은 Llama 3 논문(arXiv:2407.21783) 표 3의 레이어 수, 모델 차원, 어텐션 헤드 수, KV 헤드 수에서 가져왔습니다.

| 모델 | 구성 | 토큰당 | 8K 토큰 | 128K 토큰 |
|---|---|---|---|---|
| OPT-13B | 40층, 헤드 40개(MHA), 헤드 차원 128 | 800 KiB | 6.25 GiB | 100 GiB (가정값) |
| Llama 3 8B | 32층, KV 헤드 8개(GQA), 헤드 차원 128 | 128 KiB | 1.0 GiB | 16 GiB |
| Llama 3 70B | 80층, KV 헤드 8개(GQA), 헤드 차원 128 | 320 KiB | 2.5 GiB | 40 GiB |

OPT-13B의 128K는 실제 지원 길이가 아니라 비교용 가정입니다. 표에서 두 가지가 보입니다. 첫째, KV 캐시는 **컨텍스트 길이와 동시 요청 수에 정비례**하므로 긴 컨텍스트 요청 몇 개만으로 GPU 메모리가 찹니다. 둘째, 쿼리 헤드 여러 개가 KV 헤드 하나를 공유하는 GQA(Grouped-Query Attention)는 KV 캐시를 직접 줄이는 모델 설계입니다. Llama 3 논문은 추론 속도를 높이고 디코딩 중 KV 캐시 크기를 줄이려고 GQA를 썼다고 밝힙니다. Llama 3 70B는 OPT-13B보다 5배 넘게 크지만 토큰당 KV 캐시는 오히려 작습니다.

```python
# 직접 실행해 위 표를 확인한 스크립트 (Python 3, 외부 의존성 없음)
def kv_bytes_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
    return 2 * layers * kv_heads * head_dim * dtype_bytes

for name, (l, h, d) in {"OPT-13B": (40, 40, 128),
                        "Llama-3-8B": (32, 8, 128),
                        "Llama-3-70B": (80, 8, 128)}.items():
    b = kv_bytes_per_token(l, h, d)
    print(name, b // 1024, "KiB/token", round(b * 131072 / 2**30, 1), "GiB @128K")
# OPT-13B 800 KiB/token 100.0 GiB @128K
# Llama-3-8B 128 KiB/token 16.0 GiB @128K
# Llama-3-70B 320 KiB/token 40.0 GiB @128K
```

### 2. 연속 배칭: 요청 단위가 아니라 스텝 단위로 묶기

디코드 단계는 메모리 대역폭에 묶이므로, 여러 요청을 한 배치로 묶어 가중치를 한 번 읽을 때 여러 토큰을 만들면 처리량이 크게 오릅니다. 문제는 요청마다 도착 시각과 출력 길이가 다르다는 점입니다. 요청 단위로 배치를 묶으면 먼저 끝난 요청이 가장 긴 요청을 기다려야 하고, 새로 온 요청은 배치가 끝날 때까지 대기합니다.

vLLM 논문이 배경으로 소개하는 Orca(OSDI 2022)의 **반복 단위 스케줄링(iteration-level scheduling)**, 흔히 연속 배칭(continuous batching)이라고 부르는 방식은 이를 디코드 스텝 단위로 바꿉니다. 매 스텝마다 끝난 요청은 빼고 대기 중인 요청을 넣습니다. 그런데 이렇게 배치를 키우면 이제 **KV 캐시를 담을 메모리**가 배치 크기를 정하는 한계가 됩니다. PagedAttention은 바로 이 지점을 겨냥합니다.

### 3. PagedAttention: KV 캐시를 페이지처럼 나누기

vLLM 이전 시스템은 요청마다 최대 길이만큼의 KV 캐시를 연속된 메모리로 미리 잡았습니다. 출력이 얼마나 길어질지 모르기 때문입니다. vLLM 논문은 이것이 세 가지 낭비를 만든다고 분석합니다(3절, 그림 3).

- **예약(reserved):** 나중에 쓸 토큰을 위해 미리 잡아 두었지만 아직 비어 있는 공간
- **내부 단편화(internal fragmentation):** 최대 길이만큼 잡았는데 실제 출력이 짧아 끝내 쓰지 않는 공간
- **외부 단편화(external fragmentation):** 요청마다 크기가 다른 연속 공간을 잡다 보니 생기는 틈

그림 2의 측정에서 기존 시스템(Orca, FasterTransformer 계열)은 KV 캐시 메모리 중 실제 토큰 상태를 담는 비율이 20.4%~38.2%에 그쳤습니다.

PagedAttention은 운영체제의 가상 메모리와 페이징에서 아이디어를 가져옵니다. 요청의 KV 캐시를 고정 크기 **블록**(기본 16토큰)으로 나누고, 블록들이 물리 메모리에서 연속일 필요가 없게 했습니다. 요청마다 논리 블록과 물리 블록을 잇는 **블록 테이블**을 두고, 토큰이 생길 때마다 필요한 만큼만 블록을 할당합니다. 그 결과 낭비가 요청당 마지막 블록 하나 안으로 줄어들고, 같은 측정에서 vLLM은 96.3%를 실제 토큰 상태로 채웠습니다.

블록 단위 관리에는 부수 효과도 있습니다. 한 프롬프트에서 답을 여러 개 뽑는 병렬 샘플링이나 빔 서치에서는 같은 프롬프트의 KV 블록을 여러 시퀀스가 공유하고, 내용이 달라질 때만 복사하는 **쓰기 시 복사(copy-on-write)**를 씁니다. 논문의 Alpaca 데이터 실험에서 이 공유로 병렬 샘플링은 6.1%~9.8%, 빔 서치는 37.6%~55.2%의 메모리를 아꼈습니다(6.3절). 메모리가 모자라면 일부 요청을 선점(preemption)해 블록을 CPU로 옮기거나(swap) 버렸다가 다시 계산합니다(recompute).

논문이 보고한 성능은 다음과 같습니다.

| 비교 | 결과 (논문 기준) |
|---|---|
| 처리량 (요약) | 같은 지연 수준에서 FasterTransformer, Orca 대비 2~4배 |
| ShareGPT 데이터, Orca(Oracle) 대비 | 1.7~2.7배 요청 처리율 |
| ShareGPT 데이터, Orca(Max) 대비 | 2.7~8배 |
| FasterTransformer 대비 | 최대 22배 |
| OPT-13B 동시 처리 요청 수 | Orca(Oracle) 대비 2.2배 |
| 어텐션 커널 지연 | FasterTransformer 대비 20~26% 느림 (블록 테이블 조회 비용) |

Orca(Oracle)는 실제 출력 길이를 미리 안다고 가정한 이상적인 Orca라는 점에서, 이 비교는 기존 방식에 유리한 조건에서도 PagedAttention이 앞선다는 의미입니다. 반면 커널 자체는 블록 테이블을 따라가는 간접 참조 때문에 더 느립니다. **메모리 이득으로 배치를 키워 커널 손해를 메우는 구조**입니다.

### 4. 지금의 vLLM: 기본으로 켜진 최적화들

2026-10-24 기준 vLLM 공식 문서(v0.32.0)를 보면, 논문 이후 기능 다수가 기본값이 됐습니다.

- **자동 접두어 캐싱(Automatic Prefix Caching):** 같은 접두어를 가진 요청이 이전 요청의 KV 블록을 재사용합니다. 설정 코드에서 `enable_prefix_caching` 기본값은 켜짐입니다. 문서는 이것이 프리필 시간만 줄이고 디코드 시간은 줄이지 않는다고 명시합니다.
- **청크 프리필(chunked prefill):** V1 엔진에서 기본으로 켜져 있습니다. 긴 프롬프트의 프리필을 조각내 디코드 요청과 같은 배치에 섞고, 스케줄러는 디코드 요청을 먼저 넣습니다. 문서는 `max_num_batched_tokens`를 작게(예: 2048) 잡으면 토큰 간 지연이 좋아지고, 8192보다 크게 잡으면 처리량에 유리하다고 안내합니다.
- **선점:** V1의 기본 선점 방식은 재계산(RECOMPUTE)입니다. 선점이 자주 일어나면 `gpu_memory_utilization`을 올리거나(기본 0.92), `max_num_seqs`나 `max_num_batched_tokens`를 줄이거나, 텐서·파이프라인 병렬도를 높이라고 권합니다.
- **FP8 KV 캐시:** `kv_cache_dtype="fp8"`로 KV 캐시를 8비트로 저장해 같은 메모리에 토큰을 약 두 배 담을 수 있습니다(위 계산식에서 자료형 바이트가 2에서 1로 바뀜). 문서는 정확도를 위해 llm-compressor로 스케일을 보정(calibration)하는 방식을 권장합니다.

### 5. 추측 디코딩: 큰 모델 한 번에 토큰 여러 개

PagedAttention이 처리량을 올린다면, 추측 디코딩(speculative decoding)은 요청 하나의 디코딩 지연을 줄입니다. 2022년 11월 Google의 Leviathan 외와 2023년 2월 DeepMind의 Chen 외가 독립적으로 거의 같은 방법을 제안했습니다. Chen 외 논문은 Leviathan 외를 동시 연구로 언급합니다.

아이디어는 다음과 같습니다. 큰 대상 모델(target)은 메모리 대역폭에 묶여 있어 토큰 1개를 검증하나 여러 개를 동시에 검증하나 시간이 크게 다르지 않습니다. 그러니 작고 빠른 초안 모델(draft)이 토큰 γ개를 먼저 쓰게 하고, 큰 모델은 그 γ개를 **한 번의 병렬 실행으로 검증**합니다.

검증 규칙이 이 방법의 핵심입니다(Leviathan 외 알고리즘 1). 초안 모델이 토큰 x를 확률 q(x)로, 대상 모델이 같은 위치에서 p(x)로 낸다고 할 때,

1. q(x) ≤ p(x)이면 그대로 받아들입니다.
2. q(x) > p(x)이면 확률 1 − p(x)/q(x)로 거부합니다. 즉 min(1, p(x)/q(x))의 확률로 받아들입니다.
3. 거부되면 그 위치에서 정규화된 max(0, p(x) − q(x)) 분포로 토큰을 다시 뽑고, 뒤의 초안 토큰은 버립니다.
4. γ개가 모두 받아들여지면 대상 모델이 이미 계산한 분포에서 한 토큰을 더 뽑습니다.

논문은 이 절차로 나온 토큰이 **대상 모델에서 직접 샘플링한 것과 정확히 같은 분포**를 따른다고 증명합니다. 근사가 아니라는 점이 양자화나 증류와 다른 점입니다. 또 대상 모델을 한 번 돌릴 때마다 최소 1개 토큰은 확정되므로 최악의 경우에도 일반 디코딩보다 실행 횟수가 늘지 않습니다(다만 초안 모델 비용은 듭니다).

얼마나 빨라지는지는 초안 토큰의 평균 수락률 α에 달렸습니다. 대상 모델 1회 실행당 기대 생성 토큰 수는 (1 − α^(γ+1)) / (1 − α)입니다(식 1). 필자가 이 식으로 계산한 값입니다.

| 수락률 α | γ = 3 | γ = 5 | γ = 7 |
|---|---|---|---|
| 0.6 | 2.18 | 2.38 | 2.46 |
| 0.75 | 2.73 | 3.29 | 3.60 |
| 0.9 | 3.44 | 4.69 | 5.70 |

α가 낮으면 γ를 늘려도 이득이 금방 포화됩니다. 실제 속도는 초안 모델 비용 c(대상 모델 대비 실행 시간 비율)까지 반영해 (1 − α^(γ+1)) / ((1 − α)(γc + 1))배가 됩니다(정리 3.8).

원 논문들의 실측 결과입니다.

| 실험 | 설정 | 속도 향상 |
|---|---|---|
| Leviathan 외, 영독 번역 | T5-XXL(11B) 대상, T5-small 초안, γ=7, α=0.75, TPU-v4, 배치 1 | 3.4배 (온도 0), 2.6배 (온도 1) |
| Leviathan 외, CNN/DM 요약 | 같은 대상과 초안 | 3.1배 (온도 0), 2.3배 (온도 1) |
| Chen 외, XSum 요약 | Chinchilla 70B 대상, 4B 초안, K=4 | 1.92배 (뉴클리어스 샘플링), 2.01배 (그리디) |
| Chen 외, HumanEval 코드 | 같은 대상과 초안 | 2.46배 |

Chen 외 실험에서 초안 모델은 토큰당 1.8ms, 대상 모델은 14.1ms였습니다. 코드처럼 예측하기 쉬운 토큰이 많을수록 수락률이 올라 이득이 큽니다. 두 논문 모두 산술 연산량 자체는 늘어나지만 메모리 접근 횟수가 줄어서 빨라진다고 설명합니다. 연산 여유가 있는 상황에서만 이득이라는 뜻입니다.

### 6. vLLM에서 추측 디코딩 쓰기

2026-10-24 기준 vLLM 문서는 별도 초안 모델 외에도 EAGLE, MTP(다중 토큰 예측), PARD, MLP 추측기, n-gram, suffix 방식 등을 지원합니다. n-gram 방식은 초안 모델 없이 프롬프트에서 이미 나온 토큰 열을 찾아 다음 토큰을 추측하므로, 문서 요약이나 코드 수정처럼 입력을 많이 베끼는 작업에 맞습니다. 아래는 공식 문서 예제를 그대로 옮긴 것이며 GPU 환경이 없어 직접 실행하지 않았습니다.

```bash
# 별도 초안 모델 방식 (vLLM 문서 기반, 실행하지 않음)
vllm serve Qwen/Qwen3-8B \
  --speculative-config '{"method": "draft_model", "model": "Qwen/Qwen3-0.6B", "num_speculative_tokens": 5}'
```

```python
# 오프라인 추론 (vLLM 문서 기반, 실행하지 않음)
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen3-8B",
    speculative_config={
        "model": "Qwen/Qwen3-0.6B",
        "num_speculative_tokens": 5,
        "method": "draft_model",
    },
)
outputs = llm.generate(["The future of AI is"], SamplingParams(temperature=0.8, top_p=0.95))
```

vLLM은 기본적으로 초안 모델과 대상 모델이 같은 어휘(vocabulary)를 쓰도록 요구합니다. 위 예시처럼 같은 계열의 작은 모델을 고르는 이유입니다. 문서에는 어휘가 다른 모델을 잇는 `use_heterogeneous_vocab` 옵션도 있지만, 현재는 그리디 초안 샘플링에서만 동작한다는 제약이 있습니다.

## 실무에서 쓰는 법

| 상황 | 먼저 볼 손잡이 |
|---|---|
| 동시 요청이 많아 처리량이 부족 | `gpu_memory_utilization`, FP8 KV 캐시, `max_num_seqs`, 텐서 병렬 |
| 긴 컨텍스트 요청이 짧은 요청의 응답을 막음 | 청크 프리필의 `max_num_batched_tokens`를 낮춰 토큰 간 지연 확보 |
| 같은 시스템 프롬프트나 문서를 반복 사용 | 자동 접두어 캐싱(기본 켜짐) 적중률 확인 |
| 요청이 적고 개별 응답 속도가 중요 | 추측 디코딩 (n-gram부터 시험, 이후 EAGLE이나 초안 모델) |
| 선점 경고가 자주 발생 | KV 캐시 여유 확보 또는 동시 처리 한도 축소 |

vLLM 문서는 추측 디코딩이 **중간에서 낮은 QPS(초당 요청 수)의 메모리 대역폭 제약 워크로드**에 맞는다고 명시합니다. 요청이 많아 배치가 이미 크면 GPU가 연산 쪽으로 포화되어, 초안 토큰을 검증하는 추가 연산이 오히려 손해가 될 수 있습니다. 필자의 판단으로는 "처리량 최적화는 PagedAttention 계열 설정으로, 한산한 시간대의 지연 최적화는 추측 디코딩으로"라는 구분이 출발점으로 무난해 보입니다.

FlashAttention(arXiv:2205.14135)도 같은 그림의 일부입니다. FlashAttention은 어텐션을 GPU의 빠른 온칩 메모리(SRAM)에 맞는 타일로 나눠 계산하고 큰 중간 행렬을 느린 HBM에 쓰지 않는 **IO 인지(IO-aware)** 방식의 정확한(exact) 어텐션입니다. 논문은 학습 기준으로 BERT-large 15%, GPT-2(1K 길이) 3배의 속도 향상을 보고했습니다. PagedAttention이 KV 캐시를 "어디에 둘지"를 다룬다면 FlashAttention은 어텐션을 "어떻게 계산할지"를 다루며, 둘 다 같은 메모리 계층 문제에서 출발합니다.

## 한계와 논란

- **추측 디코딩의 "무손실"은 수학적 보장이지 비트 단위 보장이 아닙니다.** vLLM 문서는 출력이 하드웨어 수치 오차 범위 안에서 같다고 설명하면서도, 배치 크기 변화나 수치 정밀도 때문에 결과가 달라질 수 있고 logprob 값이 일정하게 유지된다는 보장은 없다고 적습니다. Chen 외 논문도 "하드웨어 수치 범위 안에서" 분포를 보존한다고 표현합니다.
- **기능 조합 제약.** vLLM 문서는 "vllm 0.15.0 이하 기준으로" 파이프라인 병렬과 추측 디코딩을 함께 쓸 수 없다고 적고 있습니다. 쓰는 버전에서 다시 확인해야 합니다.
- **초안 모델 관리 비용.** 초안 모델은 GPU 메모리를 추가로 쓰고, 대상 모델을 바꾸면 수락률이 떨어지므로 함께 갱신해야 합니다. 수락률 α는 작업 종류에 따라 크게 달라서 논문의 2~3배를 그대로 기대하기 어렵습니다. Leviathan 외 논문에서 바이그램 수준의 아주 단순한 초안 모델은 α=0.2, 속도 향상 1.25배에 그쳤습니다.
- **PagedAttention의 커널 비용.** 블록 테이블을 따라가는 간접 참조로 어텐션 커널 자체는 20~26% 느려집니다. 배치를 키울 수 없는 상황(아주 큰 단일 요청)에서는 이득이 줄어듭니다.
- **FP8 KV 캐시의 정확도.** 보정 없이 쓰면 긴 생성에서 품질 저하가 생길 수 있어, 문서도 보정과 일부 레이어 제외 옵션(`--kv-cache-dtype-skip-layers`)을 함께 안내합니다. 자체 평가 세트로 확인하는 것이 안전합니다.
- **논문 수치의 시점.** vLLM 논문의 비교 대상(Orca, FasterTransformer)과 하드웨어는 2023년 기준입니다. 이후 경쟁 엔진들도 페이지 방식 KV 관리를 도입했으므로, 오늘 엔진 간 격차를 이 수치로 판단해서는 안 됩니다.

## 인사이트

**왜 지금 중요한가: 추론 비용이 학습 비용을 앞지르는 시대.** [Chinchilla 논문 소개](/papers/2026/10/24/chinchilla.html)에서 정리했듯 최근 모델들은 추론 비용을 줄이려고 작은 모델을 더 오래 학습시키는 쪽으로 움직였습니다. 같은 맥락에서 [추론 모델 해설](/tech/2026/10/24/reasoning-models.html)이 다룬 것처럼 답 하나에 수천에서 수만 개의 사고 토큰을 쓰는 모델이 기본이 되면서, 디코드 단계의 효율은 서비스 비용의 대부분을 결정하는 요소가 됐습니다. 사고 토큰이 길어질수록 KV 캐시가 커지고 디코드 스텝이 늘어나므로, 이 글의 두 기법은 추론 모델 시대에 더 중요해졌다고 볼 수 있습니다.

**두 기법이 공통으로 가르쳐 주는 것.** 두 기법 모두 모델을 바꾸지 않고 **시스템 설계로 출력 품질을 그대로 둔 채 비용을 줄였습니다.** PagedAttention은 운영체제의 40년 된 아이디어를, 추측 디코딩은 CPU의 분기 예측과 비슷한 "먼저 추측하고 나중에 검증" 아이디어를 가져왔습니다. 필자의 판단으로는 LLM 서빙 문제의 상당 부분이 새로운 머신러닝보다 고전적인 시스템 기법을 메모리 대역폭 제약에 맞게 다시 적용하는 문제로 보입니다.

**실무 판단 기준.** (1) **먼저 계산하고 고르기.** 위 KV 캐시 식으로 "우리 모델, 우리 컨텍스트 길이, 목표 동시 요청 수"에 필요한 메모리를 먼저 구하면 GPU 대수와 FP8 KV 캐시 필요 여부가 대부분 정해집니다. (2) **처리량과 지연 중 무엇이 목표인지 정하기.** 배치를 키우는 최적화와 추측 디코딩은 트래픽 수준에 따라 서로 반대 방향으로 작동할 수 있습니다. (3) **수락률을 관측 지표로 두기.** 추측 디코딩을 켰다면 작업 유형별 수락률을 추적해야 효과를 판단할 수 있습니다. (4) **무손실 주장도 회귀 테스트로 확인하기.** 수치 오차 수준의 차이가 결정적 출력을 요구하는 테스트를 깨뜨릴 수 있습니다.

**한계와 반론.** 대부분의 팀은 vLLM 같은 엔진을 직접 운영하지 않고 API를 씁니다. 그 경우 이 글의 손잡이 대부분은 공급자 쪽에 있고, 사용자가 직접 조절할 수 있는 것은 프롬프트 캐싱과 출력 길이 정도입니다. 그래도 원리를 알아 두면 공급자의 가격 구조(입력보다 비싼 출력 토큰 단가, 캐시 적중 할인, 긴 컨텍스트 할증)가 왜 그렇게 생겼는지 이해할 수 있고, 자체 호스팅으로 옮길지를 판단할 때 근거가 됩니다.
