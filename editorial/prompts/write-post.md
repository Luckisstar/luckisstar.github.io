# 글 작성 절차 (매주 화·목요일 자동 실행)

목표: `editorial/backlog.yml`의 승인된 주제 하나를 골라, 1차 자료를 조사하고, `CLAUDE.md` 기준에 맞는 깊이 있는 한국어 글을 써서 PR로 올린다.
운영자가 PR을 검토하고 병합하면 게시된다. **절대 main에 직접 푸시하거나 PR을 병합하지 않는다.**

## 0. 준비

1. `CLAUDE.md` 전체를 읽는다. 문체, 사실성 규칙, 인사이트 기준이 이 작업의 품질 기준이다.
2. 같은 카테고리의 기존 글 하나를 끝까지 읽고 깊이와 형식을 맞춘다. 예: 오픈소스는 `_posts/opensource/*-d2.md`, 논문은 `_posts/papers/*-livemace.md`, 기술은 `_posts/tech/*-reflection-beam.md`
3. 현재 시각(한국 시간): `TZ=Asia/Seoul date '+%Y-%m-%d %H:%M:%S +0900'` → 글의 date와 파일 이름 날짜로 쓴다.

## 1. 주제 고르기

`editorial/backlog.yml`에서 `status: approved` 항목 중 하나를 고른다.

1. 이미 작업 중인 주제는 제외한다: 원격 브랜치 `post/<id>`가 있거나(`git ls-remote --heads origin "post/*"`), 열린 PR이 있는 id
2. `priority: high`를 먼저 고른다.
3. 그다음 최근 14일간 게시된 글이 가장 적은 카테고리의 항목을 고른다(카테고리 균형).
4. 같으면 `proposed_at`이 가장 오래된 항목.

승인된 항목이 없으면 아무것도 바꾸지 않고 종료한다.

## 2. 자료 조사 (1차 출처만)

backlog 항목의 sources에서 시작해 공식 자료를 최대한 깊이 읽는다. 읽은 출처 URL과 확인한 사실을 메모해 둔다(PR 본문에 사용).

- **오픈소스**: README 전체, 공식 문서의 시작하기·개념·설정·FAQ, 최근 릴리스 노트(`gh release list`, `gh api repos/OWNER/REPO/releases/latest`), 저장소 메타데이터(`gh api repos/OWNER/REPO` → 스타 수, 라이선스, 언어, archived 여부, 마지막 push), LICENSE 파일 원문, 최근 커밋 활동, 이슈 트래커의 반복 문제. 가능하면 저장소를 얕게 clone해 디렉터리 구조와 핵심 코드를 확인한다.
- **논문**: arXiv 초록과 본문(HTML 버전 https://arxiv.org/html/<id> 또는 PDF)을 끝까지 읽는다. 표와 그림의 수치를 정확히 옮긴다. 코드 저장소가 있으면 README 확인.
- **기술**: 공식 발표문, 기술 보고서, 모델 카드, 가격/문서 페이지. 성능 수치는 누가 측정했는지 구분한다.

조사 중 다음을 발견하면 반드시 글 앞부분에 표시한다: 유지보수 중단/보관, 비오픈소스 라이선스, 보안 사고, 유료 전환, 큰 호환성 변경.

조사 결과 주제가 부적절하면(1차 자료 부족, 이미 사라진 프로젝트, 과장된 화제 등) 해당 항목을 `status: rejected`와 `note: 이유`로 바꾸고 다음 후보로 넘어간다(같은 PR에 포함).

## 3. 작성

1. `editorial/templates/<category>.md`를 복사해 `_posts/<category>/YYYY-MM-DD-<id>.md`를 만든다.
2. 템플릿의 모든 섹션을 채운다. 안내 문구와 자리표시자는 모두 지운다.
3. 분량 기준: 기존 같은 카테고리 글과 비슷한 깊이. 오픈소스는 실전 예제 3~5개와 비교표, 논문은 주요 결과 3~5개, 기술은 핵심 포인트 4개 이상.
4. **인사이트** 섹션은 요약의 반복이 아니라 독자가 다른 곳에서 얻기 어려운 해석이어야 한다. `CLAUDE.md`의 인사이트 기준 중 2가지 이상을 구체적으로 다룬다. 블로그에 관련 글이 있으면 `{{ "/경로.html" | relative_url }}` 형식이 아닌 일반 상대 경로 링크(예: `[D2 소개](/opensource/2026/10/20/d2.html)`)로 연결한다.
5. 인사이트 섹션 끝에 `<!-- EDITOR_NOTE: ... -->` 주석을 남긴다.
6. 코드 예제는 공식 문서 기반으로 쓰고, 실행 가능한 환경이면 실제로 실행해 본다. 실행하지 못한 예제가 있으면 글 안에 밝힌다.
7. 본문에 `{{`나 `{%`가 들어가면 `{% raw %}`로 감싼다.
8. `editorial/backlog.yml`의 해당 항목을 `status: published`로 바꾸고 `post: _posts/<category>/YYYY-MM-DD-<id>.md`를 추가한다.

## 4. 검증

1. `python3 scripts/validate_posts.py _posts/<category>/YYYY-MM-DD-<id>.md` → 오류 0개가 될 때까지 고친다. WARN도 가능하면 해결한다.
2. 글의 모든 외부 링크를 확인한다: `curl -sIL -o /dev/null -w '%{http_code}' URL` (200이 아니면 고치거나 제거).
3. 사실 대조: 글에 나온 모든 수치, 날짜, 버전, 라이선스, 명령어를 조사 메모와 다시 대조한다. 출처를 찾을 수 없는 문장은 삭제하거나 “확인되지 않음”으로 표시한다.
4. 마지막으로 처음부터 끝까지 다시 읽으며 어색한 번역투, 반복, 과장 표현을 고친다.

## 5. PR 열기

- 브랜치: `post/<id>`
- 커밋 메시지: `Add post: <영문 요약>`
- PR 제목: `[글] <title에서 접두어를 뺀 부분>`
- PR 본문(한국어):
  1. **요약**: 글이 다루는 내용 3줄
  2. **주요 출처**: 실제로 읽은 1차 출처 목록
  3. **검증 결과**: validate_posts.py 결과, 링크 확인 결과, 실행해 본 예제와 실행하지 못한 예제
  4. **검토해 주세요**: 사실 확인이 애매했던 부분, 판단이 들어간 문장, 독자 판단에 중요한 경고(라이선스, 유지보수 등)
  5. **에디터 코멘트**: “직접 써 본 경험이나 의견이 있으면 인사이트 섹션 끝 EDITOR_NOTE 주석 자리에 한두 문단 추가해 주세요. 없으면 그대로 병합해도 됩니다.”
- PR은 병합하지 않는다.
